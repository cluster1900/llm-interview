## TRAIN-001. A batch-mean cross entropy of 2.3 nats is what token perplexity? If the correct logit leads by only 0.1, where does the gradient land?

**Answer:** Language-model cross entropy is −log p_θ(y*), in nats when the log is natural. Perplexity is PPL = exp(mean CE), so 2.3 nats is PPL ≈ e^{2.3} ≈ 10: the model is about as uncertain as guessing among 10 equally likely candidates. The gradient on logits is softmax minus one-hot: g = p − e_{y*}. When the correct class leads the runner-up by only 0.1 the distribution is still flat, p_{y*} is often only ~0.2–0.3, and a visible slice of gradient lands on nearby wrong tokens, pushing them down and the correct class up.

**Deep dive:** Let z be vocab logits, p = softmax(z), L = −log p_{y*}. Then ∂L/∂z_j = p_j − 1[j = y*]. Confident and correct ⇒ small gradient; as p_{y*} → 1, g → 0. Label smoothing replaces the one-hot with (1−ε)e + ε/V, so the gradient is no longer a single spike. Scale check: uniform over a 10⁵ vocab is CE = log(10⁵) ≈ 11.5 nats, PPL = 10⁵. Reaching 2.3 nats means mass has concentrated on about 10 candidates—this is intuition, not a reported number from a released model. Edge cases: mean CE is dragged by hard tokens (code, numbers, rare entities), so bucket it. Falling train CE can be memorization; you still need a validation set and downstream tasks. Sampling temperature changes the generation distribution, not the trained CE. High probability is not factual correctness; do not treat CE as accuracy.

**Follow-ups:** With a one-hot target, why do cross entropy and KL differ by a model-independent constant? Why is a language model rarely trained from scratch with BLEU or RL? What numerical failure does a penalty on logsumexp (z-loss) suppress?

**Extended questions:**
- If loss is computed only on the answer span and prompt positions are masked, how do gradient scale and convergence change?
- Does 2.3 nats mean the same “confidence” at vocab 32K versus 128K?
- If validation CE falls while chat scores fall, do you inspect data duplication or an alignment-target mismatch first?

**Reasoning:** From the CE definition, PPL = exp(CE); 2.3 → about 10 gives scale. Differentiate softmax CE to get g = p − e, and “correct class only 0.1 ahead ⇒ flat p” places gradient on nearby classes. Use a per-token CE histogram to check that a few outliers are not driving the mean.

## TRAIN-002. Under a fixed compute budget, growing parameters 4× without more tokens often worsens validation loss. How should you split N and D? If online QPS is huge, does that split still hold?

**Answer:** Pretraining loss falls roughly as a power law in parameter count N, token count D, and compute C. The 2022 compute-optimal study’s rule of thumb is: at fixed C, grow N and D together rather than only stacking parameters, at about 20 training tokens per parameter, with the budget C≈6ND. Quadrupling N at fixed D is a larger model on thinner data — worse validation loss fits the curve. After launch, if decode steps dwarf training steps, compute-optimal is not deploy-optimal: train a smaller model on far more than 20× tokens to buy lower per-request latency and memory.

**Deep dive:** C≈6ND comes from ~2ND for a forward pass and about 2× that for backward, ~6ND total (order-of-magnitude; ignores log-attention terms and comms). With D≈20N you get C≈120N², so N≈√(C/120) and D≈20N. For example at C on the order of 6×10²³ that is about 70B parameters and 1.4T tokens, which typically buys more loss reduction per FLOP than a much larger model on fewer tokens. The curve assumes nearly independent, even-quality data; duplicates, low-quality crawls, and a bad mix bend the exponents. It forecasts pretraining loss, not a sudden jump in tool use or long-horizon reasoning. When data is short of 20N, extra epochs hit memorization of repeats quickly; synthetic data needs its own check that you are not replaying templates. On the serving side the objective becomes task score at a latency cap, which tilts toward over-trained small models.

**Follow-ups:** How does the 6 in C≈6ND split across forward and backward, and does it still hold for MoE? If you have fewer than 20N tokens, do you try extra epochs, heavier dedup, or synthetic data first? Can you extrapolate LR or step count in finetune or RL with the same power law?

**Extended questions:**
- Given C, estimate N and D at 20 tokens/parameter, and say whether you shrink N or accept repeats if you only have half the tokens.
- When inference QPS is high, how do you rewrite “compute-optimal” as an objective with a latency constraint?
- At one compute budget, fit two small curves — grow N versus grow D — how do you tell which side you are on?

**Reasoning:** First set the goal to lowest pretraining loss at fixed C; N and D compete for the same FLOPs. C≈6ND plus D∝N says split them in proportion, which explains why 4× parameters alone lose. Switch the goal to high-QPS serving and the constraint becomes per-request memory and latency, so you want a small model and more tokens. Accept by whether a small-scale loss–C fit still extrapolates, not by one downstream score killing the whole law.

## TRAIN-003. A 7B fits on one GPU and a 70B does not. For a two-week pretrain, when do you pick data vs model parallelism, and what does each step synchronize?

**Answer:** When a 7B fits with forward, backward, and optimizer state on one GPU, use data parallelism: a full replica per card, different microbatches, AllReduce gradients at step end. When a 70B does not fit, model-parallel first (by layer or by tensor) so a slice lands in memory, then wrap data parallelism around it to scale samples. They synchronize different objects: data parallel syncs the full-model gradient; model parallel syncs per-layer activations or sharded partial sums.

**Deep dive:** Data-parallel cards share one compute graph and differ only in the data slice. Traffic per step is about 2× parameter bytes (both directions of a gradient AllReduce). 7B BF16 gradients are ~14 GB and often overlap the backward on an in-node fast link. Peak memory per card does not drop — if the optimizer keeps two extra state tensors per parameter, a 7B may add tens of GB, still usually fine on 80 GB. Model parallel splits parameters. Pipeline parallel cuts by layer and ships activations and their gradients point-to-point; volume is the microbatch activation, not the whole model. Tensor parallel cuts a matrix dimension and AllReduces / AllGathers inside the layer; the number of collectives grows with depth and wants in-node high-speed links. 70B BF16 weights are 140 GB plus a several-times-larger optimizer, which cannot live on one 80 GB GPU, so model parallel answers “does it fit” and data parallel answers “are samples fast enough.” A common 3D mix is in-node tensor parallel × cross-node pipeline × outer data parallel. Do not confuse parameter-sharded data parallel with tensor parallel that cannot finish a single layer on one card: the former still computes a full layer per card; the latter cannot.

**Follow-ups:** Why a data-parallel AllReduce can overlap the backward while a tensor-parallel AllReduce sits on the in-layer critical path; which hurts step time more, a pipeline bubble or a data-parallel sync wait; if you only add GPUs and do not change the parallel plan, does a 70B OOM first or stall on communication first.

**Extended questions:**
- If you insist on pure data parallel for 70B with activation recomputation and CPU offload, what throughput order of magnitude should you expect?
- You raise the data-parallel degree but hold global batch fixed — what happens to convergence and to communication?
- Do you still want data parallelism at serve time, and how is that different from just running more replicas?

**Reasoning:** The fork is “does one GPU hold the model plus optimizer?” If yes, data-parallel to spread samples; if no, model-parallel to spread parameters. Then compare whether each step syncs gradients or activations to choose in-node versus cross-node cuts.

## TRAIN-004. Fine-tuning 70B, Adam's first and second moments blow GPU memory. Where do FSDP and ZeRO-3 each place parameters, gradients, and optimizer state — and when do you pick one of them instead of switching to layer-wise pipeline split?

**Answer:** Both shard, along the data-parallel ranks, the parameter shard, gradient shard, and Adam m/v shard of every parameter, then briefly gather parameters when a layer or unit runs. ZeRO-3 is DeepSpeed's full shard; FSDP is the PyTorch-native counterpart (gather a wrapped unit, compute, reshard). Optimizer state is usually the bulk: Adam's m and v are commonly fp32, about 8 bytes/parameter, and with parameters and gradients the unsharded footprint is often more than ten bytes/parameter. Choose FSDP versus ZeRO by whether you want DeepSpeed's offload and existing configs or to stay in vanilla PyTorch. Only after a full shard still cannot hold activations or cannot afford the communication do you add a layer-wise pipeline.

**Deep dive:** Illustrative: 70B × about 16 bytes/parameter ≈ 1.1 TB of training state before activations. Full-shard that across 8 cards and each card still holds on the order of a hundred GB of state; activations are extra, so activation checkpointing is common. ZeRO-1 shards only optimizer state; ZeRO-2 also shards gradients. Both communicate less than also sharding parameters, and they fit mid-size models whose parameters still replicate but Adam does not. 70B bf16 training usually goes straight to parameter-sharded ZeRO-3 or FSDP. The communication pattern is similar: gather a full unit's parameters before forward/backward, reduce-scatter gradients, and hide latency by overlapping with compute. FSDP's grain is the module you wrap (often each Transformer block): too coarse raises peak memory, too fine multiplies gathers. DeepSpeed's path to dump state to CPU or NVMe is more mature; if the team already has a stable ZeRO config, do not migrate just to match a name. A layer pipeline cuts depth, ships activations between stages, and trades bubbles for fewer layers per card. It does not replace optimizer sharding and is often stacked with data parallelism. When the fabric is weak and gathering a full layer already exceeds compute time, add pipeline or a matrix-dimension split — not “more FSDP replicas.”

**Follow-ups:** Can ZeRO-1 alone train 70B, and which memory piece is still missing; wrapping the whole model as one FSDP unit versus wrapping every block — how does peak memory differ; after CPU offload, how does the bottleneck move from HBM to host memory bandwidth and PCIe.

**Extended questions:**
- Why are FSDP and ZeRO-3 shards along the data-parallel axis, yet people describe them as “another way to split matrices”?
- On one 80 GB card, what shape is activation peak under 8-way FSDP versus an 8-stage layer pipeline?
- Using per-layer gather time versus compute time, how do you decide to shrink wrap grain versus change the parallel strategy?

**Reasoning:** Use bytes/parameter × 70B / GPUs to see that both optimizer and parameters must be sharded, then pick FSDP or ZeRO-3 from the ecosystem. Add pipeline only when activations or gather traffic become the new wall. Accept the setup on per-card peak memory, communication share of step time, and loss matching a small single-card implementation.

## TRAIN-005. An 8-stage pipeline training 70B loses nearly 40% of step time to bubbles. Should you add microbatches, switch to 1F1B, or admit you have too many stages?

**Answer:** Bubble fraction is about `(P−1)/(M+P−1)`. With P=8 and only 8 microbatches, idle time is 7/15≈47%, which matches “nearly 40%.” Raise microbatches well above the stage count (e.g. M=32 → 7/39≈18%), or switch to 1F1B so forward and backward interleave and in-flight activations are no longer “every microbatch at once.” If global batch is locked and you cannot grow M, eight stages do not pay — drop P, lean on more tensor parallel, or buy more memory per GPU.

**Deep dive:** Pipeline parallel places adjacent layer blocks on different devices: microbatch b finishes stage 1's forward, ships activations to stage 2, and stage 1 takes the next microbatch. A schedule that runs all forwards then all backwards must store M activation sets, so memory pressure is high and bubbles sit at fill and drain. 1F1B alternates one forward and one backward per stage in steady state, so in-flight activations fall to about P copies; step time is still gated by the slowest stage — uneven cuts or a fatter MLP in one block leave the others waiting. Communication is point-to-point activations of volume `[microbatch, seq, hidden] × dtype`. For example seq=4K, hidden 8192, BF16, microbatch=1 is about 4K×8192×2 ≈ 64 MB and often overlaps on the inter-node link; too many stages make the tiny boundary layers communication-heavy. Serving pipelines are worse: decode is often microbatch 1, the pipe never fills, one request walks 8 GPUs serially, and same-width tensor parallel usually wins. Training pays when M ≫ P, stage FLOP is balanced, traffic stays point-to-point rather than full-model collectives, and pipeline is one axis of a 3D plan — not an excuse to keep adding stages.

**Follow-ups:** Why adding stages alone makes both bubbles and imbalance worse; exactly how 1F1B cuts activation memory; why a serve-time decode with almost no microbatches usually loses to tensor parallel.

**Extended questions:**
- If convergence locks global batch so you cannot fill the pipe with more microbatches, what bubble-reduction tools remain?
- Isolating a fat MLP as its own stage versus cutting by layer count — which one is more likely to create a straggler stage?
- When a stage boundary crosses two machines, which direction is more likely to become the tail, activation forward or gradient backward?

**Reasoning:** Plug P and M into the bubble formula until it reproduces the 40% idle; then choose among “grow M / switch to 1F1B / cut P” the option that still honors memory and global batch. If M cannot grow, eight stages are the wrong shape — move work into tensor parallel or reduce P.

## TRAIN-006. You have 20 billion unlabeled manual tokens but only 3,000 instruction pairs. When is continued pre-training worth the compute, and when is it just expensive forgetting?

**Answer:** When the base’s perplexity on the manuals is clearly high—terms fragment, boilerplate will not continue, and after SFT internal abbreviations still look like ordinary words—it is worth continuing causal language modeling on raw domain text (continued pre-training). If the pain is only “it can write manual-like sentences but will not answer in ticket format,” the 3,000 pairs plus a prompt are enough; CPT first only twists the model back into a completer and washes out existing alignment. After CPT you still need instruction/chat SFT, or production becomes “keep writing the manual.”

**Deep dive:** CPT and SFT optimize different losses. CPT minimizes next-token loss on raw domain prose and absorbs term co-occurrence, section boilerplate, and long tables. SFT minimizes acceptable answers under an instruction. Data path: clean the manuals (headers, OCR junk, folded duplicate clauses) → pack long document sequences → low-LR causal LM → then the 3,000 pairs in a chat template. Signals it is worth doing: domain words tokenize long and fragmented, the base is lost on internal part numbers zero-shot, and you have far more clean unlabeled tokens than instruction pairs (for example tens of billions, with room to mix some general text). Signals it is not: the “manuals” are a few million repetitive tokens, facts change weekly, or the task is classify/extract rather than “write like an insider.” Forgetting risk: domain-only CPT raises general perplexity and damages refusals; use replay (general text or a slice of the original pretrain distribution), fewer steps than pretraining, and a learning rate one to two orders of magnitude smaller. The 3,000 pairs overfit easily in the SFT that follows CPT—early-stop and keep a general-instruction mix. Cost: 20B tokens is heavy even on a small model; first measure on a manual slice whether domain PPL actually falls and general probes stay acceptable, then scale. Boundary: if retrieval already places the clause in context, do not CPT just to memorize the manuals into weights.

**Follow-ups:** Domain PPL fell but ticket format got worse after SFT—what did CPT break; manuals:general at 1:1 vs 9:1—which two probes decide; at what CPT step do you stop so safety alignment is not trained away.

**Extended questions:**
- Draw one training stack for “high domain PPL / few instructions” and one for “low domain PPL / only the format is wrong.”
- When CPT packs long sequences, what spurious dependence does stitching across manuals introduce?
- How do you evaluate unseen internal part numbers to show CPT absorbed terminology rather than memorizing one chapter?

**Reasoning:** The goal is to repair the domain language distribution first, then task behavior. The constraint is that raw text has no instruction labels, so CPT pulls the model back to completion. Pay for CPT only when domain PPL and broken terms show the base cannot read the manuals; otherwise go straight to SFT. Keep general replay in both stages and accept on domain PPL plus general probes together.

## TRAIN-007. Regulations change every month. The model must use the new clauses without wiping last year’s refusal policy or general writing style. In what order do you try retrieval, LoRA isolation, replay, and parameter regularization?

**Answer:** Ask first whether the knowledge must enter the weights. Regulatory text is retrievable, must cite clause numbers, and must be withdrawable as a block, so version-stamped, permissioned retrieval is usually first: the base stays frozen and the forgetting surface is smallest. Only tone, internal jargon, or rules that must work offline go into training. When you train, freeze the base and put new clauses in a small adapter; mix old regulations plus safety/general replay into the new data; only then regularize sensitive parameters or add a KL to the old policy.

**Deep dive:** Catastrophic forgetting is new-task gradients overwriting old decision surfaces on shared weights; even a low-rank update can hit refusal and safety directions. There is no universal replay mix: too little and old skills drop, too much and new clauses do not stick. A practical start is roughly half-and-half, then let a regression set decide. Isolation weakens when adapters are merged back or several months of adapters are mounted together. Continual pretraining on text and instruction tuning of behavior are different evaluations—do not collapse them into one “full retrain.” Every release should run old-clause QA, new-clause QA, refusal/jailbreak, and general writing, and keep data and weight snapshots for rollback.

**Follow-ups:** How do you define “too much forgetting to ship” as a number of points on the old set? Do monthly adapters merge, route, or get dropped? If retrieval cannot change tone to a new regulatory register, how do you write the training target? Is an exact Fisher regularizer affordable at billion-parameter scale, and what approximation do people use?

**Extended questions:**
- Sketch the monthly release pipeline: which metrics gate data freeze, train, regression, canary, and rollback?
- If the replay set is thin on safety examples, which behaviors usually break first?
- When a new clause contradicts an old one, should the model refuse, prefer the new text, or leave the conflict to a retrieval freshness field?

**Reasoning:** The goal is usable new knowledge; the constraints are no silent regression on old skill or safety, and reversible change. Writing shared weights is the least reversible move, so rank by reversibility: retrieval, isolated parameters, replay, then full-parameter regularization. Each layer uses a two-way old/new eval to decide whether to go further.

## TRAIN-008. After the customer-support base model ships, three tickets land together: yesterday’s price list changed, replies miss the ticket template fields, and internal abbreviations get expanded into plain language. Which tickets are actually asking you to change weights?

**Answer:** Fine-tuning continues gradient updates on a pretrained or instruction checkpoint so a class of inputs maps to a class of outputs inside the weights. Missing template fields and expanded abbreviations are stable format and jargon habits; they are worth collecting demonstrations for when prompts cannot lock them and you need short, low-latency context. Yesterday’s price change is a fact that will rot; writing it into weights makes it wrong again tomorrow. Send that ticket to retrieval or a query API, not to fine-tuning.

**Deep dive:** One fine-tuning step is demonstration (instruction + target continuation) → forward next-token distribution → cross-entropy usually on answer tokens only → backward on all or some weights. After training, the mapping lives in the checkpoint, so the system text can shrink from a couple of thousand tokens to a couple of hundred and schema variance usually drops. Order of magnitude: locking one ticket JSON and one departmental voice often starts to show a trend at 10³–10⁴ clean demonstrations. Trying to “remember this week’s SKU prices” via fine-tuning means the set rots with the price list and rollback requires another run. The boundary is sharp: if the failure is “missing a current fact,” do not touch weights; if the failure is “same intent, four of ten replies drop a field or expand an abbreviation,” and a longer prompt is still unstable or too expensive, then fine-tuning is a candidate. Fine-tuning does not provide freshness or citable sources.

**Follow-ups:** If constrained decoding with a JSON schema still drops a field 10% of the time, do you still fine-tune or add a repair pass; with a two-hundred-entry abbreviation table that barely changes, how do you rank fine-tuning vs glossary substitution vs stuffing a lookup table into the prompt; if the business insists on baking prices into an offline package, what expiry clock and rollback condition do you use to refuse.

**Extended questions:**
- When format errors and factual errors each make up half of the same ticket set, how do the two contaminate one training mix, and how do you split the adaptation paths?
- After fine-tuning you shortened the prompt and also lost refusal boundaries — which regression must run before launch?
- Traffic is only a few hundred requests a day and demonstrations need expert writing: how do you compare the fixed cost of fine-tuning with “add 800 more tokens of rules”?

**Reasoning:** Write the goal as a stable mapping versus an updatable fact, then apply the constraints: latency, context budget, half-life of the fact. Only when the mapping is unstable and context levers are exhausted do you hand the problem to weights; factual failures must be replaceable without a retrain. Accept on field-compliance rate, jargon consistency, and whether price questions still hit retrieval — not on a few pretty replies.

## TRAIN-009. Instruction-tuning budget locked at 80k examples: spread to 400 task types, or thicken 50 core types to 1,600 each? How many phrasings per task, what share of chain-of-thought and refusals do you mix in, and how do you prove held-out instruction types are not a memorized catalog?

**Answer:** Spend the budget on covering “see a spec → pick a behavior type,” not on saturating a handful of already-seen tasks. Give each type just enough examples to lock its output contract (a few hundred high-quality pairs often stabilize simple classify/rewrite; multi-constraint or multi-step work may need on the order of a thousand), then spend leftover slots on new task families and alternative phrasings of the same gold label. Keep a small slice of chain-of-thought and of refusals, each paired with “short answer only” / “this should be completed” controls, so those two behaviors are switches the instruction can flip rather than a default register. Evaluate by holding out entire unseen instruction families, plus same-family rephrasings and recombined constraints—do not call a random 10% split of seen tasks generalization.

**Deep dive:** Eighty thousand is a sample budget, not a task budget. Instruction tuning fits P(answer | spec); a changed verb, constraint order, or material placement can leave the training support. Dumping all 80k into about 50 frequent types (~1,600 each) makes those 50 formats rock-solid, but a 51st spec—e.g. “reorder events on a timeline, not by person”—gets swallowed by the nearest rewrite task: fluent, still catalog-matching. Spreading to about 400 types × 200 examples covers more mappings, but each cell barely locks a simple contract: jittery label sets or on-and-off units make within-type gradients fight. A workable cut is to list families first (extract, classify, rewrite, compare, plan, calculate, code, write, multi-turn clarify, meta-instructions such as “shorter / change person”), fill each family until the contract holds, then give the marginal budget to long-tail families and hard constraint pairs instead of cloning a template that already works. Phrasing must be varied on purpose: several surface forms per gold (imperative, question, constraints-before-material, material-before-constraints, limits in the system turn), or the model binds to the slogan. Start chain-of-thought around 5%–15% of rows, then immediately re-check by tokens—an 8% row share of drafts that are 4× longer can be about a quarter of the tokens, so the gradient leans toward “always draft first.” Keep a same-question “final answer only” twin so short instructions can shut the reasoning channel. Refusals have to be positive examples, or the complete-the-request majority pushes “always fill everything”; keep them clearly smaller than completions (try about 2%–8% first, bucketed by harm, missing critical slots, over-scope) and mix easy-to-confuse should-complete items so “looks hard” does not become close. Three hold-outs are all required: (1) instruction types whose whole family never appeared; (2) same family, new template; (3) Cartesian recombination of constraints seen separately (“≤80 words” and “as a table,” tested as “table and ≤80 words”). Report “reasoned when it should not” and “refused when it should not” as their own columns. An in-family split that reuses training templates is not an unseen type.

**Follow-ups:** Chain-of-thought is only ~8% of rows but four times as long as short answers—do you rebalance by row count or by tokens; if whole-family hold-out is poor while rephrasing is strong, are you missing the task concept or the surface form; after refusals hit ~15% and requests missing one fillable slot start getting closed, do you cut refusal count or rewrite “missing but askable” as a clarify, not a shutdown.

**Extended questions:**
- Same task, 12 phrasings vs 2, same total rows: where does held-out rephrased instruction-following come from, and how do you use embedding clusters to show the 12 still sit in one sentence pattern?
- If you lack real families to fill the budget, does rewriting instructions with another model count as a new type? How do you drop “diversity” that still lands in the original cluster?
- If almost all chain-of-thought is math and almost all refusals are safety, what bad habits move into open writing, and which two probes catch them first?

**Reasoning:** The goal is a Cond(spec) that generalizes past the training menu, not an 80k-row catalog the model can memorize. The constraint is a fixed row budget, with long reasoning and refusals distorting the nominal mix via tokens and gradient weight. So thicken a type only until its contract is stable, spend the margin on new families and phrasings, and write reasoning/refusal as gated behaviors with controls. Accept only after whole-family, rephrase, and constraint-recombination tables, with the mix corrected by token share—not by the average on seen tasks.

## TRAIN-010. In one supervised fine-tuning step, what bad habit do you teach if user tokens also enter the cross-entropy? Why is the learning rate usually a notch below the pretraining peak, and which behavior breaks first if you run extra epochs?

**Answer:** The step is the same as language-model training: pack (instruction, answer) → forward → shifted cross-entropy → backward → update the chosen parameters with a conservative learning rate. Labels on user tokens are usually ignored (for example −100); otherwise the model spends capacity copying the question and learns “echo the ask, then answer.” The learning rate sits below the pretraining peak because you are already in a usable basin; a large step shoves the general prior first. Extra epochs first break surface n-grams: the model starts quoting demonstrations verbatim, refusals loosen, or a training catchphrase becomes the task format.

**Deep dive:** Prompt tokens still enter the forward pass because the answer distribution is conditioned on them; the mask only stops gradients from the “predict what the user just said” path. Full fine-tuning updates every W; PEFT lets only the add-on or prefix receive updates; the loss definition does not change. Learning-rate magnitudes are illustrative: full SFT often starts near 1×10⁻⁵, LoRA can sit a bit higher (for example 1×10⁻⁴), both with warmup and early stopping on a validation set — do not copy the pretraining peak. A tiny effective batch makes an already narrow task gradient noisy; a huge one blows activations first. With a few hundred demonstrations, watch the train/validation gap at 2–3 epochs; more epochs rarely buy new skill and mainly raise verbatim parroting and membership-inference risk. Use this loop when format or voice must live in the weights; if you only need facts, do not pour more steps.

**Follow-ups:** In multi-turn data, should earlier assistant turns enter the loss, and what do you miss if you train only the last assistant message; loss is already low but field compliance does not move — do you inspect the mask, the template separators, or the learning rate; if you change PEFT and the learning rate together, what single contrast lets you say “update surface, not step size.”

**Extended questions:**
- Why does putting the system prompt into the loss sometimes make the model echo internal rules into user-visible text?
- Duplicating one demonstration ten times for a single epoch versus seeing it once per epoch for ten epochs — how do the overfitting shapes differ?
- If you compute loss only on the first JSON key and ignore the rest, what does training bias toward?

**Reasoning:** From “learn the answer distribution conditioned on the instruction,” the loss must point at answer tokens; from “keep the pretrained basin,” use a small learning rate and few epochs. Draw which parameters get gradients and which tokens return loss, then treat parroting and overfitting as default failures of this loop, not a separate curse. Accept on validation loss, field compliance, and a small general suite versus the base — not on training CE near zero.

## TRAIN-011. You have 200 gold pairs and expand them to 10,000 with a larger model before SFT. In which steps does the student amplify teacher hallucinations, and which filters are mandatory?

**Answer:** Amplification happens in three steps: the teacher invents slots with no evidence and nothing filters them; synthetic instructions crowd around a few templates near the gold, so the student freezes that bias; the synthetic count dwarfs 200, so the gradient is dominated by teacher style. Filters you cannot skip: near-duplicates versus gold and versus each other, schema/rule checks, entailment or tool checks on retrievable facts, toxicity and PII, and overlap with the eval set. Mix synthetic with gold on a ratio (try 1:1 first) and keep a source tag; the teacher’s self-score is not a sufficient quality signal.

**Deep dive:** A typical pipeline: extract task patterns from the 200 seeds → teacher rewrites instructions (new entities, new edges) → teacher or rules write answers → filter → mix with gold and train. Hallucinations enter at steps two and three: on “order status” the teacher invents a plausible logistics hop; without a check against system records, the same fake hop repeats across 10,000 rows and the student treats it as domain knowledge. Diversity collapse is common too: rewritten instructions look different but embeddings form one blob, equivalent to copying the 200 rows fifty times. Filter in layers: (1) string or simhash dedup and length outliers; (2) JSON schema, enums, required fields; (3) check what you can (ticket-id format, amount reconciliation) and mark the rest “not auto-trusted,” then down-weight or drop; (4) toxicity, user abuse, PII; (5) longest common substring or neighbors versus val/test, so you do not paint the score. Human spot-checks should sample by cluster, a few per cluster, not 20 random rows—random draws miss systematic errors in small clusters. Upsample gold or up-weight its loss so, for example, 9,800 synthetic rows do not drown 200 truths. Boundary: when teacher and base are the same family, the student copies teacher boilerplate and confident errors faster; open narrative tasks have weak filters, so keep the synthetic fraction lower. The aim here is coverage of rare edges, not cloning the teacher’s full distribution.

**Follow-ups:** What do you do if filters kill every long-tail edge; if the teacher is self-consistently wrong (same invented tax rate every time), will a majority vote let it through; should you deliberately generate bad answers as negatives.

**Extended questions:**
- Design a filter funnel: what error each layer drops, and the spot-check rate you will fund.
- As gold:synthetic moves from 1:1 to 1:20, which two curves tell you to stop?

**Answer:** LoRA does not insert a nonlinear layer. Rank too low underfits strict formats and multi-constraint voices; rank too high overfits a small set and grows memory and checkpoint size. Implementation trap: if the framework still builds gradients for W₀ or enables a full-parameter learning rate, memory returns to full-update levels and the run is not LoRA even if metrics look fine. Merging is an inference optimization; training must keep A and B separate or you cannot hot-swap by task.

W_a = {k: (1 - a) * W0[k] + a * Wft[k] for k in W0}
