## EMB-001. The knowledge base already has title and keyword fields. Why does the retrieval path still store a few hundred floats per object, and which later step does that column change from “matching words” to “matching a position”?

**Answer:** An embedding maps a text (or another object) to a fixed-length real vector so objects that are close in meaning or use sit close in geometry. Titles and keywords give literal hits; the float column is what still pulls an object near a query after paraphrase, synonym, or cross-sentence wording. In RAG it does not replace the body text. It only changes “who is allowed into the LLM context” from Boolean term matching into nearest-neighbor search in a vector space.

**Deep dive:** The data path is object → embedding model → \(\mathbb{R}^d\) → distance to the query vector → top-k ids → fetch source text → pack the prompt. Engineering has to lock, together: whether the object is a query, chunk, user, or item; \(d\) commonly in the 256–3072 range; a distance that matches training; exact vs approximate index; and who recomputes the vector after an edit. Order of magnitude: one 768-d float32 vector is about 3KB; a million raw vectors are about 3GB, before graph edges. The boundary is sharp: embeddings promise “looks like,” not factual correctness. Clause numbers, internal SKUs, and error codes often do not “look like” anything, so you still need an exact-match channel. An embedding is also not a summary — a summary is still text the model must read. The vector is what lets the next step do similarity with add-multiply, instead of generating another paragraph.

**Follow-ups:** One vector per document versus one per chunk — what does each miss look like; must query and document share the same model and instruction prefix; if you embed titles only and skip bodies, which detail-anchored questions drop out systematically.

**Extended questions:**
- In recommenders the objects are users and items; in RAG they become queries and chunks. What changes in update frequency and in the distance function?
- Two tickets take opposite positions (approve refund vs deny) but land close. Do you inspect chunk noise first, or a model that does not encode negation?
- Skip vectors and let an LLM score candidates one by one. At what corpus size do cost and latency break first?

**Reasoning:** The goal is “semantically close objects must be comparable in batch.” The constraint is that the LLM cannot read the whole corpus, and a term index will not cover paraphrases. So objects are written into a shared vector space and retrieval becomes geometric. Accept on three checks: paraphrases still recall, rare identifiers are not silently lost, and the top-k source text actually enters the generation context.

## EMB-002. Production embeddings are not L2-normalized, but the vector store is scoring inner product. Long documents score higher. Switching to cosine or Euclidean — which bias does each correct, and when are the three rankings the same thing?

**Answer:** Inner product \(\langle q,d\rangle=\|q\|\|d\|\cos\theta\) uses both direction and magnitude. Many encoders assign a larger norm to longer, wordier passages, so “wrote more” is treated as “more relevant.” Cosine keeps direction only and removes that length bias. Euclidean \(\|q-d\|^2=\|q\|^2+\|d\|^2-2\langle q,d\rangle\) penalizes both a norm gap and a direction gap when vectors are unnormalized. If query and document are already L2-normalized onto the unit sphere, cosine and inner-product orderings coincide, and Euclidean does too, because then \(\|q-d\|^2=2-2\langle q,d\rangle\).

**Deep dive:** If training used normalized cosine or InfoNCE, serving must do the same: normalize then inner-product, or cosine directly. If the model intentionally encodes amount-of-information in the norm, cosine throws that signal away — whether to normalize is a training contract, not a taste. A common implementation pre-normalizes documents at ingest and normalizes the query once, then uses inner product as cosine so you do not divide per comparison. A slowly growing norm with token count in 768-d is common; a sudden extra order of magnitude in one batch is when you look for a mixed-in model. The ANN graph or clusters must be built with the same metric you score with, or approximate neighbors and the fine ranker disagree. Euclidean cares about a global shift; cosine does not. If you also cluster, the two metrics’ centroids do not mean the same thing.

**Follow-ups:** If only documents are normalized and the query keeps its raw norm, what bias remains in top-k; if you build the graph with Euclidean and score with cosine, why does the recall curve fight the evaluation script; should the raw norm be passed to a reranker as an “information mass” feature.

**Extended questions:**
- Why can you not reuse the same 0.8 threshold for “score > 0.8” on a negative inner product and on \(1-\cos\)?
- After coordinates are truncated or bit-compressed, which of the three metrics scrambles ranks first?
- When empty text encodes to an all-zero vector, which metric yields NaN or pins that row at a nonsense rank?

**Reasoning:** Expand all three formulas into norm × direction. The goal is “rank by the similarity the trainer defined”; the constraint is that serving must match the loss. Check the unit sphere first, then decide whether the three rankings are identical; if not normalized, choose inner product versus cosine by whether you want to keep the norm. Accept on how one query ranks a near-duplicate short span against a padded long span.

## EMB-003. Twenty million 1024-d float32 vectors must drop to about one quarter of resident memory before the RAG service can ship. Where do INT8, per-dimension binning, and product quantization each cut, and through which cracks does recall leak?

**Answer:** Vectors alone, no graph or text: 20M × 1024 × 4 B ≈ 82 GB; a cut to about one quarter matches per-dimension INT8 (about 20 GB). Scalar binning and INT8 are the same family—one codebook per coordinate—so neighbor order usually holds and leaks are mostly clipped tail dimensions. Product quantization splits 1024 dimensions into subspaces (for example 64 × 8 bit, about 1.3 GB of codes); distance becomes a table lookup and nearby documents are easier to reorder. In production, compressed vectors do coarse retrieval and a higher-precision vector or cross-encoder reranks: you shrink the working set, you do not throw precision away in one step.

**Deep dive:** Quantization maps continuous coordinates onto a finite codebook: less bandwidth and storage, more distance error. Three stable paths: (1) per-dimension INT8 / scalar quantization, calibrated on training quantiles or a symmetric `scale`. L2-normalized embeddings have similar per-dim range, so symmetric quantization is steadier. The query must use the same scale, and the metric must match training (cosine or inner product). (2) Binarization keeps only the sign, about another 8×, Hamming as a cosine proxy. It holds up when dims are roughly symmetric; domain terms and confusable pairs die first, so it should not be the only recall path. (3) Product quantization (PQ): split d into M subspaces, a small codebook per subspace (commonly 256 centroids, 8 bit). Search usually uses asymmetric distance (ADC): query stays float, database vectors are codewords, M lookup tables are summed. Relative to float32 the code size is about `4d/M` bytes (64 B per vector at M=64). Leak cracks: two close original points fall into different subspace cells and miss the candidate window; IVF-PQ stacks “probe few lists,” so a small nprobe adds to quantization error; if the query is quantized too (symmetric distance), error grows. HNSW edges still cost on the order of `N × ~2M × 4 B`; INT8 on vectors with a full-precision graph will not fall a clean 4×. Data path: fit codebooks on, for example, 1e5–1e6 vectors → encode the corpus → keep codes and ids in memory → ADC with a float query → take 10–20× k candidates → rerank from higher-precision vectors on the side. Boundary: fit codebooks on your vectors; a new embedding model invalidates old codebooks. Do not treat someone else’s “lost one point” as your number—draw a compression–recall@k curve on a frozen business set.

**Follow-ups:** If HNSW walks on PQ/ADC distances but rerank uses full precision, how does the graph warp; if INT8 already hits the memory target, why add PQ; on binarized vectors, where do pairs like coolant vs refrigerant usually break first.

**Extended questions:**
- Under N=2e7, d=1024, HNSW M=16, estimate GB for raw vectors, INT8, PQ-64B, and edges, and show why vector-only quantization is not enough.
- Coarse-retrieve k' = 20k then rerank: what does a too-small or too-large k' hurt, and how do you choose it?
- After you change the embedding model, can the old PQ codebooks stay? Which step must be refit?

**Reasoning:** The goal is resident vector memory that fits the box while coarse retrieval still puts gold into the rerank window. The constraint is ~82 GB of raw vectors and table-lookup distances under PQ. Use INT8 for the “about one quarter” tier; more aggressive compression only with a high-precision rerank. Read recall on your frozen set; do not assume a quantizer is lossless.

## EMB-004. Someone slices a 1024-d vector to the first 256 dimensions and storage drops to a quarter. Where do retrieval quality and each distance computation break first? When is “shorter” a working point the model actually supports, rather than a cleaver?

**Answer:** Naive truncation assumes information is spread evenly across coordinates. The first 256 dims of a typical embedding are not an independent low-resolution semantic. Distances become a mutilated inner product, neighbor relations scramble, and recall usually dies first on fine distinctions (near-paraphrase clauses, confusable tickets), not uniformly on every query. Storage and distance arithmetic do drop roughly linearly with \(d\): same \(n\), memory, bandwidth, and Flat scan time all approach one quarter. “Shorter” is a supported working point only when the model was trained with nested / truncatable dimensions and you keep the official first \(k\) coords and re-normalize.

**Deep dive:** Cost: \(n=10^6\), \(d=1024\), float32 is about 4GB raw; \(d=256\) is about 1GB. Graph edge count does not scale linearly with \(d\), but distance does, so higher \(d\) burns more scan bandwidth. Random tail-chopping is usually worse than a learned projection (an official short head, or a linear reduction fit in-domain), and even those must be re-measured. Too-low \(d\) crowds unrelated documents into nearby directions and shrinks score dynamic range, so thresholds become brittle. Too-high \(d\) often hits diminishing returns: going from 768 into the thousands grows storage and latency more than recall, and ANN needs more probes to hold recall. After a cut you must re-normalize, and query and document must share the protocol; 1024 on one side and 256 on the other produces a near-random ranking. This is a different compression axis from reducing bits per coordinate.

**Follow-ups:** How you A/B the model’s official short vector against “I chopped the first 256” to prove the cleaver is unusable; after \(d\) halves, whether Flat latency truly halves or sits on index constant costs; whether fine clause pairs or coarse topic pairs degrade first.

**Extended questions:**
- Linearly reducing in-domain to 256-d versus switching to a native 256-d model: how do rebuild cost and geometry differ?
- Raising dimension leaves recall@10 flat and only post-rerank nDCG rises. Is that representation or the approximate index?
- Queries stay 1024-d, documents are cut to 256-d. What “scores collapse into a lump” symptom do you see?

**Reasoning:** Separate “cost scales as \(nd\)” from “the geometry is still the metric the model defined.” Only when the model guarantees the latter may you buy cost with a shorter vector. Accept on confusable-pair recall and on the storage bill together; never on a capacity dashboard alone.

## EMB-005. The same knowledge chunk is stored once as a learned sparse vector of (term id → weight) on an inverted index, and once as a 768-d vector on HNSW. Roughly how many bytes is each structure per document? When the vocabulary expands, the corpus grows from Chinese into English and French, and 10% of documents change every day, which side runs out of storage or update budget first?

**Answer:** A learned sparse vector is a nearly all-zero vocabulary axis: nonzeros are term ids with learned weights, served by pulling postings from an inverted index. A dense vector is a fixed-\(d\) real array, almost every coordinate nonzero, served by an ANN graph or clusters. Per document, a 768-d float32 vector is about 3KB, and a layer of HNSW adjacency usually still leaves you in the few-KB range; the sparse side depends on how many terms fire—for example about 0.6–2.4KB of postings at 80–300 nonzeros, and can overtake dense once expansion reaches five or six hundred terms. Vocabulary growth and extra languages hit sparse axes and posting width first; swapping the encoder or rewriting a tenth of the corpus daily makes dense re-embed and rewire the graph, while sparse rewrites many postings—the expensive step is not the same.

**Deep dive:** The data paths differ. Sparse: an encoder (or a statistical model) emits \(\{(t,w_t)\}\) → a dictionary maps \(t\) to a global term id → inverted lists `term → [(doc_id, weight)]`; the query is expanded to a term set the same way, only those lists are merged, and the score is the sparse dot product \(\sum_t w_q(t)\,w_d(t)\). Dense: the encoder emits \(\mathbb{R}^{768}\) → write into HNSW/IVF; the query is one forward pass, then walk edges or probe clusters. Storage (illustrative, body text excluded): dense is \(768\times 4=3072\) B; HNSW layer 0 at about \(2M\) 4-byte neighbors per point and \(M=16\) is about 128B, plus upper layers and the primary key, commonly about 3.2–4KB/doc; a million raw vectors are about 3GB, and the edges are the smaller term. Sparse is billed by nonzeros: a posting is about 8B for `doc_id + weight`, so \(L=150\) averages about 1.2KB/doc, plus a share of the term dictionary and skip lists. Learned sparse usually *expands*—related terms that never appeared in the text light up. That is how it matches paraphrases, and why \(L\) jumps from tens to hundreds. Larger \(L\) widens the index and the query merges more lists; latency tracks how many query terms activated, not \(d\). Multilingual: sparse axes are tied to the analyzer and vocabulary. 「退款」 and "refund" are two different axes unless the expansion model truly lights cross-lingual terms, so English and French documents share almost no postings. Adding a language usually means a new analyzer, a larger vocabulary, a rebuilt inverted index, and drifting IDF or expansion statistics. Dense can keep the same \(d\) and the same ANN if the encoder was trained to pull translations together; if the encoder only covers Chinese, the geometry fails first—that is not an index-type problem. Updates: a single rewrite removes the doc from its old \(L\) sparse lists and writes \(L\) new ones; dense is re-embed plus ANN delete/insert (deletes are often tombstones). With the encoder frozen and 10% daily churn, both can go incremental. If you use collection-level IDF, sparse scores drift slowly; learned sparse with a frozen encoder usually does not need a full rebuild just for IDF. Encoder swap: both sides re-encode everything; rebuilding the inverted index is usually cheaper wall-clock than rebuilding HNSW at the same \(N\). Edge: over-expansion writes weakly related terms into many lists—index bloat and topic drift. Dense does not expand a vocabulary; synonymy is purely geometric and the axes are not interpretable. Do not call learned sparse “another kind of dense embedding”: one service merges lists, the other walks a neighbor graph.

**Follow-ups:** If mean activations go from 80 to 400, by what factor do inverted size and per-query merged posting length grow, and does query P50 break first on term-heavy questions or short ones; for a mixed Chinese–English document, do you run two analyzers or one shared BPE vocabulary, and what does failed expansion look like; when HNSW tombstones reach about 20%, which drifts first from the “~4KB/doc” budget—effective storage or insert latency.

**Extended questions:**
- For the same million documents, plot “mean nonzeros \(L\) vs inverted GB” and “\(d\) vs ANN GB”. In which regime does sparse become the expensive one?
- If you only change the expansion model and leave the dense encoder alone, why must the inverted index be fully rebuilt while HNSW can stay put?
- The query expands to 60 terms and documents average 200 nonzeros. Is sparse-dot time spent intersecting or scoring, and how should postings be ordered so you can cut them?

**Reasoning:** The goal is that both representations can be served, not a contest of “who understands semantics better.” The constraints are that sparse is billed by nonzeros and vocabulary, dense by \(d\) and graph edges, extra languages mean new axes or new geometry, and an update rewrites postings or rewires the graph. Write down bytes per document and how many structures one update touches, then apply three loads: add a language, swap the encoder, change 10% a day. Check the per-document storage breakdown, recall on a cross-lingual slice, and inverted/graph size plus tombstone rate after a day of incremental writes.

## EMB-006. The same sentence “7-day no-reason returns” is sent through a dual encoder once as a user question and once as a knowledge-base passage. Which steps from tokenization to the fixed-length vector cannot be skipped, and which step freezes the dimension?

**Answer:** Text is tokenized to ids, a Transformer produces a contextual hidden state per token, and pooling (mean, CLS, last token, or similar) collapses that to a vector of length \(d\). \(d\) is the width of the final projection, not a function of how long the sentence is. In a dual encoder the query and passage forwards are separate — neither side attends over the other’s tokens — so fine-grained token alignment is weaker than a cross-encoder. The training objective pulls related question–passage pairs together, so the output is a retrieval location, not a bag-of-words count.

**Deep dive:** A typical forward: a handful to a dozen subword ids → position information → \(L\) self-attention layers → hidden state \([S, H]\) → pool to \([H]\) → optional linear map to \(d\) → often L2 normalize. \(S\) can grow; the output stays \(d\). Dimension is locked at the projection, not at input length. Passages over the max length must be chunked or truncated; truncation drops trailing obligations. After normalization, inner-product and cosine rankings coincide. Boundaries: an extra space, full-width vs half-width characters, or a `"query:"` / `"passage:"` prefix all change the id sequence and therefore the vector. Internal abbreviations that shatter into pieces sit unstably. What the dual encoder saves is query–document cross-attention, which is why document vectors can be precomputed — and why a reranker is still used for close reading.

**Follow-ups:** How mean pooling versus CLS / last-token bias short queries versus long passages; why many retrievers insist on different prefixes for query and document; when truncation hits the model cap (for example 512 or 8k tokens), what rule sets chunk overlap.

**Extended questions:**
- If you ingest unnormalized vectors but implement cosine at query time, where do you compute wrong or quietly add a divide?
- Whether “退货” and “return policy” sit close depends more on vocabulary overlap or on whether contrastive training saw cross-lingual pairs?
- If padding tokens are averaged into the pool, what “short-string scores go mushy” symptom shows up in recall?

**Reasoning:** From “output must be fixed \(d\), and query/doc must encode independently so documents can be precomputed,” the pipeline can only be tokenize → independent Transformer → pool/project. Length only changes the intermediate \([S, H]\). Accept by checking whether one extra space moves the vector, whether long-passage tails disappear, and whether a query prefix moves the point.

## EMB-007. The query stresses “no remote work on Friday,” a chunk says “remote work is allowed Monday through Thursday,” and their cosine is high, while the chunk that actually bans Friday ranks lower. How did those sentences become a single vector?

**Answer:** The encoder tokenizes the sentence, runs stacked self-attention to get a hidden state per token, then pools into one fixed vector (commonly about 384–1024 dimensions) compared with dot product or cosine. Training is usually contrastive: topically related pairs are pulled together, unrelated pairs are pushed apart. After pooling, negation, weekdays, and numbers occupy few tokens and are averaged into the sentence topic, so “allowed Monday–Thursday” and “banned on Friday” point almost the same way.

**Deep dive:** In a bi-encoder, query and document each pass through an encoder (shared or asymmetric weights). Token ids plus positions go in; mean pooling or a special marker is projected, often L2-normalized. After normalization, cosine equals inner product, which ANN indexes can search. The contrastive loss rewards same-topic sentences, not true logical constraints, so opposite polarity on the same topic, SKUs, ticket ids, and negation scope all collapse. That is a single-vector capacity limit, not a one-off implementation bug. Short queries are worse because even fewer tokens survive pooling. In practice, lexical retrieval supplies literals such as “Friday” and “forbidden,” or a short list is rescored with token-level interaction or a cross-encoder. Raising dimension to 1024 does not by itself remember negation.

**Follow-ups:** When query and document towers use different weights, what do you usually gain on short queries? If you skip L2 normalization and use raw dot product, how must score distributions and the index change? Mean pooling, a CLS position, and last-token pooling—which encoder families typically use which?

**Extended questions:**
- If you rewrite negated sentences with rules before embedding, how much reverse-polarity mis-ranking do you actually fix?
- Does going from 384 to 1024 dimensions reliably stabilize local features such as negation and numbers?
- When mixed Chinese–English text undershoots the tokenizer vocabulary, do neighbors scatter or collapse together?

**Reasoning:** Draw the computation that turns one sentence into one point: tokenize, attend, pool, optionally normalize. Contrastive learning aligns topical nearness, not logical equivalence. This mis-ranking shows local constraints dying at pooling time, which motivates lexical retrieval or a second interactive stage rather than assuming the labels are wrong.

## EMB-008. A general embedding pulls “coolant” and “A/C refrigerant” together, so the auto-parts RAG keeps mixing SKUs. Which positives/negatives and which loss separate same-spec parts from look-alikes without retraining the whole encoder?

**Answer:** This is missing fine-grained domain separation, not a language failure. Build triples of user phrasing / correct part doc / confusable part doc and use InfoNCE or a triplet loss to push hard negatives (coolant vs refrigerant, nearby OEM numbers) apart. Freeze the encoder body and train only LoRA or a projection head—usually enough to split a local neighborhood without erasing a synonym you still want (“antifreeze ≈ coolant”). After training, re-embed the corpus and build a new index; do not mix spaces.

**Deep dive:** Positives come from “query → adopted part page / manual section” and from catalog rows “part number—name—fitment.” Do not draw negatives at random: take top-20 from the current model or BM25 and label “same function, different spec” or “same platform, different year.” False negatives (truly interchangeable parts) break substitutability; label fewer rather than wrong. Dual encoders may share weights; in-batch negatives are too easy when the catalog is narrow, so inject hard negatives. A temperature too small focuses the gradient on the single hardest pair and destabilizes training; too large and confusable pairs do not move. Parameter-efficient options: LoRA of rank 8–16 on attention projections, or a same-width linear head on the last layer. Full-parameter updates on a few hundred to a few thousand domain pairs easily rewrite general synonym directions. Scale: a few hundred to a few thousand high-quality triples covering the core confusions often beat a hundred thousand weakly supervised catalog rows. Validate on paired slices: a coolant query must not put refrigerant in top-k, while “antifreeze” must still retrieve coolant; mean recall can rise while mix-ups also rise. Ship with dual-index canaries, watching mix-up rate, slice recall, and a pack of general paraphrases. On the query side, concatenate visible context (vehicle, year); on the doc side, concatenate “part number + fitment + name” so a single token collision is weaker.

**Follow-ups:** If every hard negative is mined by the old model, do you reinforce its blind spots; should the query and doc towers be asymmetric; with only a catalog and no user queries, how do you generate questions with templates or an LLM without collapsing into a few sentence patterns.

**Extended questions:**
- Write five coolant positives and five hard negatives, and explain why random negatives will not separate those two fluids.
- A 768→768 projection only versus LoRA on the encoder: which side hurts mix-ups vs general synonymy?
- After a general paraphrase drops, do you replay general pairs or lower the learning rate and early-stop?

**Reasoning:** The goal is confusable parts apart and true synonyms still close. The constraint is that general contrastive training never saw these pairs, and full-parameter updates on small data wreck the base. Use domain triples + hard negatives + small PEFT, then rebuild and canary. Accept on the confusion slice and the synonym slice together, not on the average.

## EMB-009. While training a retrieval embedding, someone treats every other row’s positive document in the same batch as a negative. What does that save, and when does it push truly related documents apart?

**Answer:** Contrastive learning writes a loss that makes a positive pair (query, relevant document) take a larger share of similarity among a set of candidates; a common form is temperature-scaled InfoNCE. In-batch negatives reuse the other rows’ positive documents, so each query gets about `batch_size − 1` negatives without a separate hard-negative retrieval store. If another policy on the same intent, or another chunk of the same ticket, lands in that batch, it becomes a false negative and the gradient pushes points apart that should have stayed close.

**Deep dive:** For a batch of \(B\) pairs \((q_i, d_i^+)\), the candidates for \(q_i\) are often \(\{d_1^+,\ldots,d_B^+\}\) (multi-GPU training can gather across devices). Scores are \(s(q,d)=q\cdot d/\tau\). Small \(\tau\) sharpens the distribution so the positive must win clearly; large \(\tau\) flattens gradients and hard cases do not move. In-batch negatives are often too easy (unrelated topics), so BM25 or an older model still has to fetch “looks similar but is wrong” hard negatives. Order of magnitude: \(B=128\) gives 127 negatives; \(B=16\) lets the model pass by excluding a few irrelevant docs. Positives can come from QA pairs, title–body, clicks, paraphrases, or queries synthesized by a generator. CLIP-style image–text training is the same loss with an image tower on one side. Boundary: too many false negatives teach “only near-literal copies are positive,” and paraphrase recall falls.

**Follow-ups:** How gradient scale differs when the denominator is in-batch only versus in-batch plus mined hard negatives; why growing the batch is often more stable than turning \(\tau\) down another notch; with no human labels, what bias you import by generating questions from titles versus taking a random window of the body as the positive.

**Extended questions:**
- If false negatives rise to about thirty percent, which way do paraphrase recall and literal hit-rate move on the validation set?
- When one query has several positive documents, what does “one positive per row” InfoNCE miss, and how do you change the loss?
- Late in training every vector collapses to a blob. Which signals in the similarity matrix and in \(\tau\) do you read first?

**Reasoning:** The goal is pull positives, push negatives. The constraint is that negatives must be numerous and hard without accusing true positives. In-batch negatives are numerous and cheap, so they are the default denominator; a “could these co-refer the same answer?” filter removes false negatives; mined hard negatives restore discrimination. Accept on ranking a hard-negative slice, not only on whether InfoNCE against random negatives went down.

## EMB-010. You have only 200 in-house ticket pairs of “question → passage that should be hit,” and three embedders: 384-d multilingual, 768-d English-only, and 1024-d domain-specific. How do you pick the one to ship?

**Answer:** Evaluate retrieval on those 200 pairs; do not let a public leaderboard decide. Use ticket questions as queries and the labeled passages as gold, with the same chunks and the same index settings, and compare recall@10, MRR, and nDCG@10 plus mean embed latency and index size. A domain model that never saw your Chinese tickets, or an English model on Chinese queries, will fail on this set immediately. Two hundred pairs are not enough to train, but they are enough to pick one of three if nothing else changes.

**Deep dive:** Freeze chunking, k, and the approximate-search config; during selection you can even use exact inner product so ANN error does not confound the model comparison. Report metrics by language and question type, not one average: an English model can look strong on English tickets and near-random on Chinese ones. Back-of-envelope size: for the same million chunks, 384-d is about 3/8 of 1024-d, which moves memory and HNSW depth and latency. If the 1024-d model is remote-only, its p95 may be an order of magnitude worse than a local 384-d model and must appear in the decision table. Cross-validate the 200 pairs (for example five folds) and see whether the ranking is stable. If recall@10 gaps sit inside sampling noise, take the looser latency and deployment constraint and leave leftover quality to rerank. Public boards differ in length, language, and ticket mix—they shortlist candidates; they do not name a winner.

**Follow-ups:** The eval has one positive passage per question, but production often has three relevant ones—how does that bias the metrics? Should same-topic wrong tickets be added as hard negatives? After a model change the vector space is incompatible—how do you run a dual-index migration without dropping retrieval?

**Extended questions:**
- Do these 200 pairs cover known weak classes—id lookups, negation, ultra-short queries—and how would you sample more?
- If you later continue training the domain model on tickets, how do you hold the eval pairs out so you are not testing on training data?
- When the 384-d multilingual model fails on mixed-language queries, how much does translate-then-retrieve recover, and what does the extra hop cost?

**Reasoning:** The objective is ticket recall and latency after launch; the constraint is a small labeled set and no public-board swap. Demote public boards to a shortlist, judge only on your gold passages, and freeze chunking so chunk differences are not billed to the model. Break remaining ties with deployment constraints.

## EMB-011. If you only judge the union of each system’s top-20 when labeling embedding relevance, which documents never enter the set? If a reranker follows, is the release gate nDCG@10 or recall@100? On four hundred queries a model wins by 1.5 points—how do you show that is not noise?

**Answer:** Judging only the union of each system’s top-20 systematically misses documents that no system retrieved but a person would mark relevant. A new model that surfaces those misses is often scored as if they were unjudged negatives, so its nDCG is biased down. When a reranker follows, the first-stage gate should match the rerank window: recall@100 (or whatever 50/80 you actually feed) asks whether gold made the window, not first-stage nDCG@10—that metric grades an order the reranker has not applied yet. A 1.5-point gap on four hundred queries needs a paired test or a bootstrap interval; if the interval covers 0, it is not a ship decision.

**Deep dive:** Labels are the support of the metric, not a marketing score for a model. Pooling bias: take the union of systems A/B/C top-k and judge 0/1/2. That is cheap, but relevant documents outside the union never enter the qrels. If a new encoder changes the neighborhood and retrieves true relevant docs the old systems never showed, those docs are “unjudged” in the old pool: counting them as 0 punishes the new model; dropping them leaves the recall denominator incomplete. Fixes: residual sampling (judge documents drawn from the corpus that never entered the pool), extra pooling rounds (send the new system’s top-k out for judgment), and an explicit unjudged policy baked into the scorer. Hard negatives must be pooled on purpose: same topic, wrong scenario; same handbook, different section; outdated wording. Otherwise every model that can reject random documents piles up on nDCG@10. Align the metric with the downstream step. **Deep dive:** An image goes through a vision tower (for example a ViT-class encoder) and a projection to \(d\); text goes through a text tower to the same \(d\); both are often L2-normalized; a temperature-scaled contrastive loss is trained on paired data. At inference: photo → image vector → neighbors (other images, or note vectors). Pixels and words need not share one Transformer; they must share the space after the projections. Failure modes: notes like “handle per process” collapse text vectors; a tiny subject against a warehouse background turns the image vector into “warehouse”; rotation, crop, and resolution split two photos of the same case. Image forwards are often more than an order of magnitude heavier than short text; budget by resolution and batch. Audio and video also need a time pool. Captioning with a generative model and then embedding the caption is a different cascade: generation error stacks, latency rises, and it is not the same as joint-space retrieval. A shared space also does not imply factual completeness — what is in the photo but absent from the note cannot be retrieved into existence.

**Follow-ups:** With only image–image pairs and no image–text pairs, what visual detail you lose by captioning first and embedding the text; whether the shared space should get a learned modality bias; when text-to-image and image-to-text recall are asymmetric, which side’s pooling or temperature you inspect first.

**Extended questions:**
- A product’s “intact front” and “damage close-up” are far in vision space but share one note. How many vectors does that case store?
- The user sends both a photo and the words “leaking.” Do you query with image, text, or a fusion, and how do you stop one modality from drowning the other?
- Alignment was trained on generic image–text pairs; production notes are internal ticket voice. Do you change the text-tower input or add a domain projection?

**Reasoning:** The goal is cross-modal neighbors. The constraint is same \(d\), same normalization, and a contrastive objective that aligned the two towers. Image-to-image may use vision space; image-to-text must use a shared space. Accept with two probe sets, image→image and image→text, so you can separate “vision features broke” from “alignment broke.”

## EMB-021. One billion 768-d vectors must return top-20 in about 50ms. Does a single-box HNSW fail first on memory, build time, or tail latency, and in what order do you add sharding, quantization, and hot/cold tiers?

**Answer:** Memory fails first: 1e9 × 768 × 4 B ≈ 3 TB of raw vectors, plus graph edges (layer 0 on the order of 0.1 TB if each point keeps about 2M four-byte neighbors at M=16). One machine cannot hold that in DRAM, and a billion online HNSW inserts will not fit a maintenance window. A 50ms P99 means each query touches a small resident slice: shard so each working set is predictable, then IVF/PQ or other quantization inside the shard, keep hot docs at higher precision for rerank, and put the tail on compressed codes or disk. Do not build one giant graph and hope a smaller efSearch will save latency.

**Deep dive:** The three walls are not simultaneous. Memory arrives first (terabytes of vectors). Build time follows (online inserts have a large constant; a billion points is days-to-weeks offline, plus room to rebuild). Tail latency appears when the working set pages or the slowest scatter-gather shard drags—P50 can look fine while P99 is the worst shard, GC, or page fault. Order: (1) hash or random shards; global semantic search scatter-gathers. Choose shard count so one shard’s raw or compressed vectors fit RAM. After, for example, 64 B PQ, the corpus is about 64 GB of codes; 32 shards are about 2 GB of codes each, plus lists or a small graph—more realistic than a 3 TB monolith. (2) Inside a shard, IVF-PQ or a quantized graph: train centroids and codebooks on a sample, then bulk-load. Tune nprobe/efSearch on your own recall–latency curve against 50ms; do not chase 100% recall. (3) Hot/cold: frequently queried ids stay in memory at higher precision; the tail is quantized on SSD. A cold miss must not consume the whole 50ms—async fill or accept compressed distance. (4) Rerank: each shard returns, for example, 5–10× k, merge, then higher-precision distance or a reranker down to 20. Build offline in batches and merge periodically; do not point-insert into a billion-node graph. Boundary: queries that can route by tenant or category should not broadcast; unroutable queries must hit every shard in parallel, and product decides whether timeout means “return what arrived” or fail. Do not invent a GPU card’s QPS; measure throughput on your hardware.

**Follow-ups:** With 32-way scatter-gather, how does one slow shard pull P99 from 20ms to 80ms, and do you shed it or retry; after the hot set grows from 5% to 40%, does tiering still save memory; if rebuilding one shard takes six hours, how do queries avoid the shard being swapped.

**Extended questions:**
- Under “1e9 × 768-d, 50ms target, 256 GB RAM,” estimate a minimum shard count and per-shard compression so the working set stays resident.
- Why can quantizing first and sharding second wreck both recall and tail latency? What justifies your order?
- With 1% new vectors per day, how often do you retrain IVF centroids, and which distribution plot decides?

**Reasoning:** The goal is a usable top-20 in 50ms, not exact neighbors on one graph. The constraint is that 3 TB of vectors and billion-scale online edge updates are not realistic. Shard to a resident working set, then spend quantization on scan volume, and keep precision on hot data. Accept on frozen-set recall@20, P99, and per-shard RSS—not on how advanced the index name sounds.

## EMB-022. Five million 768-d vectors have to land in HNSW over a weekend window. How do you estimate bulk ingest throughput, graph build wall-clock, peak RSS, and segment merges on paper before you start? Point-insert online, or build offline and cut traffic? At about 2% new vectors a day, when do you stop incremental writes and do a full rebuild?

**Answer:** Four accounts first: raw vector bytes, graph-edge bytes, wall-clock from embed throughput, wall-clock from point insert or batch graph build; leave peak RSS at 2–3× the finished index. Five million × 768 × 4B is about 14.3GiB of vectors; layer-0 edges at \(M=16\) are about 0.6GiB; the peak is often tens of GiB, not “a 14GiB box can ingest this.” For a weekend window, build a shadow index offline and cut over—more predictable than inserting one point at a time into the live graph. Daily ~2% can be incremental until frozen-set recall slips, RSS/\(N\) rises, inserts slow, or you have done a large delete; then stop incremental and rebuild.

**Deep dive:** Paper math (treat the numbers as illustrations; fit the slope on your own small sample): ① `bytes_vec = 5e6 × 768 × 4 ≈ 1.54×10^{10}` ≈ 14.3GiB. ② `bytes_graph ≈ N × 2M × 4`, about 0.64GiB at \(M=16\), plus upper layers and keys, so a steady index is about 15–20GiB plus payload. ③ Decouple embed from graph build: GPU emits vectors, CPU builds. If one GPU does about 500–2000 texts/s, at 800/s you have `5e6/800 ≈ 1.7` hours of embedding alone. ④ Graph build: online point insert has a large constant. Measure mean insert milliseconds on a 1% sample, multiply by \(N\), keep a 2× buffer; e.g. 0.8ms/point on the sample extrapolates to about 1.1 hours, then add merge and checks. ⑤ Peak memory: build buffers, unmerged segments, sometimes a second copy of the raw vectors, `peak ≈ (2–3) × (bytes_vec + bytes_graph)`—ask for a 40–60GiB-class machine, not the steady 16GiB. Segment merges: flush every 100k and you have about 50 segments on five million; merging HNSW segments is close to a local rebuild and spikes CPU and RSS again. For a weekend bulk load, enlarge flush size or disable auto-merge, ingest, then compact once so you do not merge yourself to death while writing. Online point insert is easy to ship, but the graph is worse than a single offline build, insert latency grows with \(N\), deletes become tombstones, and writers share the live graph with queries. Offline: scan all vectors from source of truth → build shadow → check frozen-set recall → atomic route flip → keep the old graph for a rollback window; disk must be sized for two indexes. Daily 2% ≈ 100k rows; with a frozen encoder, go incremental. Triggers for a full rebuild: frozen-set recall@k sliding for several days, RSS growing faster than \(N\) (fragmentation and tombstones), insert p50 clearly worse, a delete of 20%+, or an embedding change (must rebuild). Edge: if the window is too small, build shards in parallel; do not just add insert threads that fight for the same RAM. Do not take someone else’s “millions per hour” as your throughput.

**Follow-ups:** Is the 1% sample the first 50k rows or a random 50k, and how does each choice bias the insert-time extrapolation; if you are halfway through and disk only has room for one index, do you stop writes, switch to quantization, or reshard; after six weeks incremental with about 15% tombstones, how do you A/B recall and RSS on a shadow rebuild versus staying incremental.

**Extended questions:**
- Fill a weekend schedule with these magnitudes: embed hours, build hours, compact hours, cut-over and rollback reserve. Which step breaks 48 hours first?
- Why is “online insert + background compact” usually enough at 2% a day, but write amplification saturates first when one import is 40% new documents?
- If peak RSS breaks the line during merge rather than during insert, do you lower \(M\), cut merge parallelism, or move payload out of the build process first?

**Reasoning:** The goal is a graph you can cut over and roll back inside the weekend, with daily 2% growth that does not require a full rebuild every night. The constraints are wall-clock = embed + build + merge, peak RAM above steady state, and point inserts that accumulate fragmentation. Estimate whether you fit the window from bytes and a sample slope; default to an offline shadow cut-over; use recall, RSS/\(N\), and insert latency as rebuild triggers. Check a successful cut-over in-window, frozen-set recall, and that RSS tracks \(N\) after the rebuild.

## EMB-023. Next week the retriever goes from model A to model B; both emit 768-d. Why can you not mix writes in the same HNSW? During the canary, how do you run two vector spaces in parallel so you can roll back and never score an A query against B documents?

**Answer:** Matching dimension only means the arrays fit the same index layout, not that the geometries are compatible. A and B learned their own axes. An A query in a B cloud produces drifted scores and uninterpretable ranks — that is embedding drift from a model swap. Run dual indexes (or two vector columns keyed by space version): embed each document with A and with B; stamp the request with a model version and encode the query with that encoder only; cut traffic on in-domain retrieval metrics; keep a switch back to A. Cache keys, normalization, and instruction prefixes travel with the version.

**Deep dive:** A change queue backfills B, possibly over days. Shadow traffic sends the same query to A and B and records top-k overlap, score histograms, and failures. Then a small cut to B, watch adoption or human relevance, expand or roll back. Do not insert both kinds of points into one neighbor graph: edges weave two notions of “near,” and even a source tag will not stop a walk from crossing spaces. Equal dimension hides this from schema checks, so the write path must require `model_id`. Full-corpus re-embed time is \(n\times\) average tokens, often hours to days, so the old index must keep serving. B can win a public set and still lose your query mix; the cut is decided in-domain. This is not “dimensions do not match so the write fails,” and not “quality already collapsed and we are in incident mode.” The requirement here is rollback before the cut.

**Follow-ups:** Shadow top-k overlap is low but human relevance rose — cut, or inspect label bias first; only hot documents are on B and cold ones stay on A — how does query routing avoid a cross-space comparison; on rollback, do you delete the half-built B index immediately.

**Extended questions:**
- A and B are both unit-normalized, yet histogram means still differ by a chunk. Can you share one score threshold?
- Dual-write doubles storage. Besides shortening the canary, what is the main risk of cutting by document heat?
- Canary by tenant versus by request percentage: which comparison metrics does each contaminate?

**Reasoning:** The goal is a reversible model swap. The constraint is that distances are only meaningful inside one metric space. Equal dimension is not evidence of one space, so you isolate two indexes and route queries by version. Decide the cut with shadow overlap plus in-domain relevance, not with a dimension integer or a model name.

## EMB-024. Production added “if cosine is below 0.8, tell the generator the store has nothing.” After you swap the embedding model, replace FAQ copy with statutes, and go from five-character queries to whole pasted paragraphs, why does that same 0.8 start mass-killing or mass-passing? How do you calibrate the “no relevant document” decision?

**Answer:** 0.8 is not a relevance probability; it is a geometric value under one encoder and one normalization. Swap the model and anisotropy plus the score histogram shift as a block; FAQ-style short pairs pile up at the high end, while a truly relevant statute paragraph may sit around 0.5; a five-character query pushes a whole topic neighborhood above 0.75. A fixed cutoff therefore passes everything in one domain and refuses everything in another. Calibrate empty-store decisions per “model × domain × query-length bucket” on queries that do and do not have gold, using top-1 score and the gap; refit when the encoder changes, and do not feed weak chunks to the generator to “see what happens.”

**Deep dive:** After L2 normalization, cosine equals inner product: it compares direction, not usefulness. Anisotropy: many sentence embeddings sit in a narrow cone, so the mean cosine of a random pair can already be high (it varies by model; some distributions center in an illustrative 0.4–0.7 band). Relevant pairs for model A live at 0.35–0.55 and for model B at 0.72–0.90; copying 0.8 kills A’s true hits and lets B’s weak matches through. Domain: support-FAQ questions and answers share a sentence shape, so weak matches still clear 0.8+; a statute paragraph that answers the question in formal long sentences can score 0.48 and still be gold. Query length: five characters land near a topic centroid, neighbor scores are all high, and “has / has-not” will not separate; a long paste has more constraints, scores spread, and top-1 = 0.52 may be a real hit. So “0.8” does not transfer across models, corpora, or lengths. Calibrating emptiness: two query classes—those with gold in the pool, and those confirmed to have no relevant document (new feature, out-of-domain, deliberately unanswerable). Features: top-1 score, top-1 minus top-2, query token count. Fit a threshold per model, domain, and length bucket, or a logistic map from those features to \(P(\text{has relevant})\), and pick the operating point between “refused but gold exists” and “passed but nothing is relevant.” After an encoder, pooling, or instruction-prefix change, the whole histogram shifts—refit; do not keep the old 0.8. In serving, below the operating point do not stuff chunks into the LLM: it will still write an answer on low-score context. Use an “no evidence” script or a clarification. A tiny top-1/top-2 gap means a pack of similar neighbors (a topic basin), not a single hit. Edge: a threshold only handles “the whole window is too far.” High scores that are still wrong are a space or chunking problem; raising 0.8 will not fix them. Do not back out a cutoff from click-through: not clicking is not a relevance label.

**Follow-ups:** A threshold on top-1 alone versus top-1 plus the top-1/top-2 gap—which class of “both results are right” queries does each one injure; do you bucket length by characters or tokens, and where do mixed Chinese–English queries fall; with only about 150 calibration queries, how wide is the interval on the empty-store threshold, and would you ship it.

**Extended questions:**
- Plot top-1 cosine histograms for the same queries on model A and model B, and mark which percentile 0.8 sits at on each.
- If you drop an absolute cutoff and instead quantile-normalize against historical query scores, then cut at the 10th percentile, where does that still fail across domains?
- If after refusing you still quietly stuff the top-3 low-score chunks into the prompt “for reference,” how does the generator typically ignore your empty-store decision?

**Reasoning:** The goal is to block generation when the store has no usable evidence, not to preserve one global cosine number. The constraint is that the score distribution moves with model, domain, and query length, so 0.8 has no cross-distribution meaning. Calibrate top-1 and the gap on a set that includes true-empty labels, by bucket; refit on model change; on refuse, do not feed low-score chunks. Check refuse rate on empty queries and false-refuse rate on queries with gold—not whether mean cosine sits near 0.8.

## EMB-026. Nightly RAG reindex: ninety percent of chunk texts did not change. Which fields must the cache key include so you skip repeated embedding inference, yet a model swap the next day cannot write old vectors into the new store?

**Answer:** The key must bind “normalized text + model id + vector-space version” (the version spells out dimension, whether you normalize, and the instruction prefix). The value is that vector. A hit is legal only when both text and model are unchanged; a new model name, revision, or prefix invalidates the whole key space and you must re-embed. The cache saves embedding forwards or API calls, not neighbor search. It is not the same layer as “reuse the answer to a similar question”: here the normalized input must be identical.

**Deep dive:** Nightly rebuild hashes each chunk; a hit writes into the new index, a miss calls the model and fills the cache. At ninety percent hits, inference cost is about one-tenth; whether wall time drops from hours to tens of minutes still depends on index write speed. Normalization has to be stable: Unicode form, whitespace, HTML stripping, chunk boundaries — one extra space is a miss. Capacity: ~3KB per 768-d float32 row; tens of millions of distinct chunks is tens of GB, so the bulk lives on disk or object storage, hot query strings sit in an in-memory table, and eviction is by model version, which is safer than a per-key TTL. Two texts that differ by one space should not hit — they may be different chunks. If the business wants them to hit, write the normalization rule before the hash; do not fuzzy-match. On swap day, old keys may stay for rollback; the new index only accepts new keys.

**Follow-ups:** Whether the key must also include tokenizer version and max length; whether the same text as query and as passage (different prefixes) may share one entry; how a multi-host rebuild avoids a cache-stampede that refills the model.

- After normalization starts folding full-width digits to half-width, do you migrate old keys in bulk or retire the whole version?
- Hit rate is already 90% and rebuild is still slow. How do you tell index writes from source-text fetch?
- For repeated user questions, why is the embedding-cache TTL usually shorter than the document-chunk cache?

**Reasoning:** The goal is “same input, same model, do not pay inference twice.” The constraint is “different vector spaces must never be mixed on write.” So model and preprocessing live in the key, and a hit means the same geometric point is reusable. ## EMB-027. Production is 768-d; the candidate model emits 1024-d. Someone wants to PCA the new vectors back to 768 and keep the old graph. When is that a bet that neighborhoods survived, and when must you build a second index and backfill?

**Answer:** A different dimension is a different coordinate system. Old HNSW edges grew from 768-d neighbors; you cannot project 1024-d points and upsert them as if those edges still hold. PCA or any linear map to 768 is a reversible shortcut only if, on your frozen business set, the projected ranking is close to a full 1024-d new index. Otherwise you are betting that the extra dims are noise and that principal axes happen to match the old space. Default: new dimension, new collection, re-encode history with the new model, dual-write, canary, keep the old graph for rollback. Zero-pad, truncate, or force a different d into the same index silently corrupts distance.

**Deep dive:** An index assumes fixed d and one metric. Inserting 1024 into 768 errors or truncates; truncation drops coordinates the new model treated as useful. PCA minimizes global reconstruction error; retrieval needs local order—good MSE can still drop recall@10. If the model family, training objective, or instruction prefix (for example `passage:` on documents) changed, even a newly trained 768-d head must not share a graph with old vectors. Signals that force a second index: projected recall on business slices falls outside your budget versus the full new index; post-embed dim/norm stats already disagree with the old store; canary cross-search (new query vs old index) collapses the score distribution. Migration: shadow index ← heat-first full re-embed ← route queries by model version ← compare top-k Jaccard, slice nDCG, failure cases ← cut over ← keep a rollback window. Cache keys include `model_id` and `dim`. A temporary fan-out (old docs on the old index, new docs on the new) can only merge ranks with RRF; scores stay incomparable and this is not a steady state. Fit PCA on vectors your new model produces on your corpus, not on random public sentences—the principal directions will follow web text.

**Follow-ups:** If the same model ships 768-d and 1024-d heads, is truncating 1024 to 768 still a bet; if re-embed takes days, how do hot queries avoid an empty new index; when two indexes double storage, which replica do you drop and how long is the rollback window.

**Extended questions:**
- Write the migration state machine: not backfilled / hot done / full done / cut over / rolled back, and which table each state queries.
- How do you use old/new top-10 Jaccard together with business nDCG to decide a 100% cutover?
- If you still use PCA, which batch of vectors fits the components, and why not 10k random public sentences?

**Reasoning:** The goal is the new model’s gain with a way back to the old retriever. The constraint is that a different d is incompatible with the old graph, and PCA does not preserve neighborhoods. Default to re-embed plus dual indexes; take the projection shortcut only if the frozen set shows order is preserved. Accept on new-index slice metrics and rollback time, not on “the dimension numbers match.”

## EMB-028. The day you canary 10% of traffic onto a new embedding, “cited the wrong document” tickets double, while a public-style offline set barely moves. In 30 minutes, how do you tell mixed old vectors, dropped L2, or a real domain drift?

**Answer:** First confirm a one-click cutback to the old index and that the query `model_id` equals the searched index’s `model_id`. A still public-style set is exactly the eval that cannot see your term slices—do not use it to keep the canary alive.

A bimodal `embed_version` histogram inside one graph makes neighbors meaningless: some queries look fine, some look random. New query × old index Jaccard versus the old×old control is tiny, and the score histogram shifts. (3) Real drift. New×new is consistent, but failures cluster on internal names and confusable policies, with gold ranks sliding. **Extended questions:**
- Design the three control retrievals and sketch the score histogram and top-k Jaccard you expect for mix, missing L2, and true drift.
- With only 10% canary traffic, how do you collect enough failing queries in 30 minutes instead of waiting a day of tickets?

**Reasoning:** The goal is to restore citation correctness, then explain.
