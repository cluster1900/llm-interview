## OPS-001. A weekend prototype is slated for 10% of production traffic on Monday. Which lifecycle gates do you refuse to skip, and what evidence must each gate produce?

**Answer:** Refuse to skip at least: a written problem and refusal boundary, an offline eval set (safety, hallucination, format) compared to a baseline, a cost and latency budget, a smaller controlled slice before 10%, a rollback switch, and monitoring that can replay a single request. A weekend demo proves “it generates,” not “it is governable on the real distribution.” Ten percent is already a production incident class, not an internal preview.

**Deep dive:** Every stage must leave an artifact, not a vibe. Problem definition produces success metrics, prohibited actions, and human-takeover rules. Eval draws a frozen set from logs or labels covering the main path, tails, unauthorized asks, and cases that must refuse; every model or prompt change reruns it and stores scores plus failing cases. The prototype is only for integration risk. After offline pass, review ID numbers, prompt injection, and tool side effects. Pilot from shadow traffic or about 0.5%–1% and watch contrasts (complaints, takeovers, format failures, cost per request), not absolute scores. Before 10% you need a one-click revert of prompt, model, and index. After launch the loop starts: drift, prompt version, safety blocks, and cost anomalies must page. A common failure is using coworkers’ questions as the eval set — much narrower than production.

**Follow-ups:** Offline is all green but canary complaints rise — do you halt the ramp or first check distribution shift; with no labeling team, what is the smallest acceptable eval set; do you budget cost from QPS or from token quantiles.

**Extended questions:**
- Which gates can run in parallel (eval-set build vs gateway limits) and which must be serial?
- If prompts change three times a week, which lifecycle step becomes daily rather than a one-time launch?
- How do you use replay logs to prove the 10% slice is not the weekend-demo distribution?

**Reasoning:** The goal is a reversible trial on real users under quality, safety, and cost constraints. Write the lifecycle as gates that must produce evidence; 10% only after contrast and rollback exist. Accept on frozen-set regression, canary contrast, and a practiced one-click rollback.

## OPS-002. A ward tablet must still edit a chart summary in an elevator with no radio, but differential diagnosis needs the latest cloud-scale model. Which requests stay on-device versus in the cloud, and how do you merge after reconnect so you do not dirty the chart?

**Answer:** On-device work is whatever is already on the tablet: offline summaries, speech-to-text, masking of sensitive fields, and the physician’s in-progress draft. The cloud takes differential diagnosis, guideline retrieval, and anything that needs current medical knowledge or tools. Offline, diagnosis becomes “local draft + outbox”; on reconnect you merge by record version vectors, and unsubmitted local edits beat a stale cloud write-back—never last-write-wins in silence. Choose by privacy, the hard offline constraint, and model capability, not a slogan that on-device is always safer and the cloud is always stronger.

**Deep dive:** Tablet RAM and battery admit only a small or heavily quantized model and a short context: rewrite an existing paragraph, do not act as an authority on diagnosis. The cloud model can be hot-patched and can call labs, but elevator RTT is unbounded, so the product must split those intents instead of one button that “sends to the cloud if the radio is up.” Flow: write a versioned local draft → upload only physician-confirmed spans, encrypted, when the radio returns → write diagnosis back as suggestion blocks, not by rewriting the chief complaint. Conflict: local v3 versus a cloud suggestion based on v1 must show a diff for the physician to pick. Compliance: recognized patient identifiers stay on device by default; the upload set is minimal and auditable. On-device models ship through MDM; the cloud may change daily. Version prompts and safety policies separately so a cloud refusal cannot coexist with an on-device model inventing a dose. Battery and heat confine on-device inference to plugged-in or short bursts; long reports wait for the cloud.

**Follow-ups:** If the on-device summary copies a dose wrong, may the cloud diagnosis still treat that sentence as fact; after N hours offline, does the outbox drop, recompute, or keep only the physician’s prose; if the same account opens a second tablet, how do you stop an unsynced draft from becoming a second chart of record.

**Extended questions:**
- Which fields never leave the device, and which may upload only after the physician taps “request diagnosis”?
- The on-device model can only rewrite fluently; how does the UI stop that text from being read as a differential diagnosis?
- After reconnect, which logs prove an older cloud result did not overwrite a newer local chart?

**Reasoning:** The constraints are offline usability and the cost of a dirty chart beating a missed auto-diagnosis. Split intents by “is the data already local / do we need fresh weights,” and merge by version, not timestamps. Accept with conflict-prompt rate and unauthorized-upload count.

## OPS-003. Two million 7B-class chats per day, almost idle at night. Buying a hosted per-token API versus reserving your own GPUs: above what utilization does self-hosting get cheaper, and which line items do people usually omit?

**Answer:** Self-hosting wins when the cards you sized for peak run at high enough utilization across the whole day — not when the raw daily request count looks large. You provision for the daytime peak; nights sit idle and drag average utilization down. Self-hosting is cheaper only if (peak capacity × GPU price + people + spare capacity) undercuts the same period's token bill and you can absorb operations and compliance. If two million requests squeeze into about eight hours, real GPU-hours used are often well under a naive daily-average estimate, so the break-even sits later than intuition.

**Deep dive:** Illustrative arithmetic for an interview, not a vendor quote: 800 input + 200 output = 1000 tokens per call → about 2×10⁹ tokens/day. At hosted prices on the order of a fraction of a dollar to a few dollars per million tokens, the monthly bill lands in the thousands-to-tens-of-thousands-of-dollars range. On the self-host side, what a 7B INT8/INT4 card can serve is set by KV and latency SLOs; “the weights fit” is not “one card absorbs two million chats.” Omitted items usually dwarf the GPU list price: (1) provisioning for p99 peak, not the daily mean; (2) at least two replicas for deploys and failure; (3) nights and weekends idle; (4) extra memory bought for KV, not FLOPs; (5) on-call, images, eval regressions, security patches; (6) data that must stay in your environment — a veto, not a discount. A robust shape is hybrid: a self-hosted baseline plus hosted overflow. The decision artifact is a break-even curve in “average utilization / peak ratio,” plus a hard constraint that data-residency requirements skip the cost comparison entirely.

**Follow-ups:** If peak is 4× the daily average, how does break-even utilization move; does the self-host saving cover one on-call engineer; when output tokens are priced much higher than input, should you shorten prompts or move to self-hosting.

**Extended questions:**
- If you rent idle hours to internal batch work (summaries, eval), how do you credit that into self-host utilization?
- Models change every quarter: how do you book self-host sunk cost versus the hosted “swap and leave” option?
- Which SLAs (region, residency, audit) make a pure cost comparison invalid?

**Reasoning:** Convert daily calls into peak QPS and all-day utilization, add people, spares, and idle time into self-host TCO, and compare with variable per-token cost. State the inflection as a utilization, not as “we have a lot of requests, so we should self-host.”

## OPS-004. You inherited a feature-store plus weekly-retrain MLOps stack, but the product is a hosted LLM wrapped in prompts. Which pieces still earn their keep, and which control planes are missing?

**Answer:** Still useful: CI for env and config, service auth and rate limits, the registry habit of version-plus-rollback, and business-metric monitoring. Almost useless: the feature store, weekly retrains, and offline accuracy as the only gate — you are not training the weights, the input is prompt+retrieval+tools, and the output is nondeterministic. Missing control planes: versions of prompt / index / tool schema, token-level cost, trajectory eval (not a single label), safety rails, and regression when a vendor silently changes a model.

**Deep dive:** Classic MLOps assumes data → features → train → checkpoint → serve, and fixes drift by retraining. An LLM app assumes a frozen or purchased generator plus runtime assembly; drift more often comes from prompt edits, corpus updates, decoding knobs, and vendor weight swaps. The versioned artifact grows from one weight file into the tuple model id + prompt + RAG index version + tool contract + decode config. CI must run a frozen eval, format/citation checks, and safety cases, not only unit tests. Monitoring expands from feature skew to TTFT/TPOT, tokens, refusals, tool failures, and human feedback. Cluster utilization is no longer the primary KPI; whether one request can be replayed is. Shared leftovers: auth, secrets, canaries, rollback, audit. Do not keep a weekly retrain of an unused classifier just so the old stack looks busy.

**Follow-ups:** Can the feature store still feed RAG metadata filters, or should it retire; if a vendor changes the model with no announcement, what counts as “model version” in the registry; where do human review and automatic eval each sit in the release gates.

**Extended questions:**
- If you later SFT an open-weight model, which MLOps pieces become critical again?
- What does a prompt/index version mismatch look like in production, and who should block the ship?
- How do you compare “new prompt” and “new model” in one experiment framework so you do not grow two dashboards?

**Reasoning:** Test the old stack’s “we train the weights” assumption against the new product. Keep versioning, canaries, and monitoring where it still holds; replace the rest with prompt–retrieval–eval–rail. Accept when a failed request can be replayed from a five-part version tuple.

## OPS-005. Sales wrote “first token in 3 seconds, full reply in 15” into a customer contract. Which quantities must become measurable service metrics, and which notions of business correctness must not share the same availability clause?

**Answer:** Split the contract into end-to-end latency bucketed by output length, time-to-first-token, availability defined by timeouts plus 5xx/429, and goodput: completed responses that also meet the latency target. The 3-second line maps to TTFT; the 15-second line must state a max output length or a per-token time, or long answers are “legally late.” Factual correctness, retrieval recall, and user satisfaction do not belong in that availability clause: they need offline sets and sampled review, live probes cannot judge them, and mixing them either forces refusals to look “correct” or counts fluent hallucination as success.

**Deep dive:** A workable measurable set: availability (a terminal state inside the agreed timeout; safety blocks counted separately from engine faults); TTFT p50/p95/p99; full-reply latency or time per output token in length buckets; schema/tool failure rate; tokens and internal cost. Quality is a second SLO: task success, citable attributions, human-escalation rate, scored on gold sets and weekly samples, not on a ping script. RAG adds retrieval hit rate and freshness as functional SLOs. Boundary: if a streaming API treats the first space as the first token, the contract is gameable—define the first visible content token. Say whether a user cancel is a failure, or a cancel storm will trash availability. Keep dollar cost out of the customer availability clause, but track cost per successful task internally so you do not buy stability with unbounded concurrency. Do not put GPU tokens/s in a customer SLA; that is a capacity number, not a user-visible promise.

**Follow-ups:** If typical output grows from 200 tokens to 800, how do you rewrite the 15-second clause as buckets or TPOT; when a safety policy blocks an attack, is that success, failure, or its own class for the customer; what happens at renewal if you reported only mean latency and omitted p99 and buckets.

**Extended questions:**
- Short support replies and long reports share one 15-second line; how do you split a tiered SLA so short chats do not carry the reports?
- Does “available” include a successful fallback to a weaker model, and how do quality thresholds move on that path?
- How do probes prove the TTFT clause while weekly samples prove the quality clause without the two series contaminating each other?

**Reasoning:** The goal is a decidable contract; the constraint is that generation length and correctness are not the same live probe. Put user-visible latency and reachability on real-time metrics and keep right/wrong on a separate quality SLO. Accept with bucketed latency, an explicit error taxonomy, and a sampling protocol.

## OPS-006. Policy Q&A must stream text and show [n] citations. Do you wait for retrieval and rerank to finish before generating, or stream first and backfill citation numbers? If mid-stream a piece of evidence is access-revoked or dropped from the final list, what happens to the [3] already on screen, and how do you design time-to-first-glyph, clickable backlinks, and the frontend event protocol together?

**Answer:** A sentence with a clickable source may not appear until the evidence set is frozen. Before that freeze you may stream a status chip or an uncited lead-in, but not a `[3]` that will later become a link. If you generate while retrieval is still moving, the model may emit opaque slots only; bind numeric labels after permission recheck and the final list stabilize—do not weld a provisional integer into the sentence. When item 3 is revoked or squeezed off the final list mid-stream, the on-screen `[3]` must take a retract event and become a dead “source unavailable” mark that cannot open the body. Split latency into “first visible glyph” and “first backlinkable claim.” The client updates footnotes from bind/retract events; do not rely on the model talking over old tokens.

**Deep dive:** Two assemblies that actually work. Barrier: retrieval and rerank complete → recheck inject rights for this caller → freeze `evidence = [{slot, chunk_id, version, locator}]` → then generate. Numbers come from that closed set. Clicks open the snapshot at bind time via locator (page, char offset, content hash), not “whatever the file is now.” The user waits the full retrieval wall-clock before seeing words, but the canvas never shows a fake footnote. Placeholder: after a coarse first-pass, stream “checking sources” or an unnumbered lead-in. If the product insists on in-line marks, decode only slots such as `⟦s3⟧` with no URL and no click target. When the final list and recheck land, emit `cite-bind` and let the client paint `[3]`; if that chunk missed the final list or lost inject rights, emit `cite-retract`, gray the slot, tag the sentence “sources updated,” and cut later generation if needed. Branch mid-stream failure by cause. After access revoke, the locator is dead and must not open the clause; if the claim’s number is supported only by that chunk, append a correction—do not leave a footnote that still opens full text. If rerank drops the chunk before bind, leave it unbound; if it was already bound and might have been clicked, retract it the same way as a revoke and write an audit row. Minimum protocol: `status`, `text-delta`, `cite-bind`, `cite-retract`, `evidence-final`, `done`. The server speaks `slot` and `chunk_id`; `[n]` is a client-drawn index. Late events merge idempotently on `slot`; the terminal state must equal `evidence-final`. Do not make a model sentence “forget [3]” the primary path—bytes already painted are not reliably replaced. Write two latency contracts: “show a glyph now” aligns to the status chip or uncited lead-in; “first sourced sentence” aligns to the first sentence after a successful `cite-bind`. Measure: clickable citations before freeze must be zero; in a revoke drill, openable on-screen footnotes must be zero; replaying bind/retract out of order must end at the final list.

**Follow-ups:** The lead-in already said “according to the third attachment” and the later bind fails—do you rewrite the lead-in, void the paragraph, or leave an unlinkable sentence; on mobile the footnote is a chip—does retract remove it or turn it into “expired”; the same slot binds two `chunk_id`s in sequence—which one does the client keep.

**Extended questions:**
- List the minimum event types and ordering rules: which class may leave the server before the evidence freeze, and which class must never go out?
- The user opened and copied the passage before retract; what does audit store, and does the UI owe a retrospective notice?
- How do you keep “first visible glyph” and “first backlinkable claim” as two metrics so the first is not sold as the second?

**Reasoning:** The goal is perceived speed with footnotes that both deep-link and can be voided. The constraint is that the final list and inject rights are unstable until recheck, and a browser cannot retract paint on the server’s behalf. Split “text appears” from “a number becomes live,” and express the citation lifetime as bind and retract. Accept on zero clickable citations before freeze, zero openable footnotes after revoke, and two separately reported latency numbers.

## OPS-007. 200 QPS, ID numbers in prompts, input spikes to 8k tokens. Hosted API, self-hosted engine, or hybrid: what does each option force you to own?

**Answer:** Hosted API: you own the gateway (auth, quota, retry, timeout), prompt and output filters, ID redaction or a contractual processing addendum, and failover or multi-vendor routing; you do not own GPUs or kernels, but you hand latency, rate limits, and data egress to the vendor. Self-hosted: you also own weight distribution, the engine (continuous batching, KV, quantization), GPU capacity, and box replacement; IDs can stay on-prem, but 8k spikes are yours to absorb with prefix cache and chunking. Hybrid: steady-state on your cluster, overflow or a larger model on the API — request IDs, billing, and safety policy must be unified or debugging splits into two truths.

**Deep dive:** 200 QPS is not 200 HTTP connections. At a mean of about 2k in / 200 out, token rate is on the order of 200×2200 = 4.4×10⁵ tokens/s; a 70B-class self-host sizes from decode bandwidth and KV HBM, not from web QPS. An 8k spike inflates the prefill queue and KV together: cap concurrent sequences, drop by priority, or fall back to a short-context model. IDs: self-host can stay in an isolated network with disk encryption and redacted logs; hosted needs no-train, region, and delete terms — and you should still minimize egress (hash when the raw value is not required). Batching raises throughput and hurts TTFT, so interactive traffic needs its own queue. Decide who owns the data plane and the capacity plane before arguing engine implementations. Observability must run from the gateway through engine or vendor response headers (tokens, cache hit, throttling).

**Follow-ups:** On overflow to hosted, how do you degrade IDs — refuse, mask, or stay in a contracted region only; is an 8k spike a queue, an OOM, or a TTFT blow-up, and which three capacity knobs do you turn; if about 5% of the 200 QPS is 8k, how does sizing from the mean fail.

**Extended questions:**
- A self-hosted GPU dies mid-stream: how does the client resume?
- The hosted API suddenly rate-limits: do you shed load, downshift the model, or serve a cached answer?
- If hybrid routing by data sensitivity disagrees with routing by length/latency, which wins?

**Reasoning:** Invert ownership from the constraints (ID egress, 200 QPS, 8k bursts). If data cannot leave, prefer self-host or the local path of a hybrid; if you will not run GPUs, use hosted and complete the gateway and degrade path. Accept on latency quantiles, throttle counts, and egress audit — not “the endpoint answered.”

## OPS-008. A Q&A assistant launches Friday. You size the peak at 200 in-flight requests, about 2k input tokens and 400 output tokens each. How do you work backwards from “how many decode slots one GPU can hold” to cards, queues, and quotas, instead of quoting a single average QPS?

**Answer:** Capacity is not average QPS times average latency. Convert 200 in-flight requests into an arrival rate with Little’s law: if end-to-end p95 is about 8 seconds, sustainable arrivals are about 25 requests per second, then add peak-to-mean headroom. The real clamps are decode slots and KV memory—prefill burns compute, decode burns memory bandwidth, and concurrent sequences per card equal free HBM after weights divided by KV bytes per token. Provider RPM/TPM, retrieval QPS, and losing one GPU pool in a failure all need their own line in the budget; do not assume the model server keeps emitting the load-test mean forever.

**Deep dive:** Split each request in two. Prefill scales with input length; a ~2000-token prompt on a large model can take hundreds of milliseconds to a few seconds depending on parallelism and prefix-cache hits. Decode rereads the whole KV every step; 400 tokens at a few tens to a bit over a hundred tokens per second per card (illustrative—model size, quantization, and batch size move this) already costs seconds. KV is computable: for a 70B-class model with GQA, about 80 layers, 8 KV heads, head_dim=128, FP16, K+V per token is about 2×80×8×128×2 ≈ 320KB, so a 2.4k context is about 0.75GB. If ~40GB remains after weights, one card group holds on the order of 50 sequences; 200 in-flight needs about four groups, plus 30–50% peak slack and enough redundancy to survive a lost card. Queues must be bounded: length ≈ arrival rate × acceptable wait; overflow rejects or falls back to a small model instead of letting p99 grow without limit. Load tests must follow the real input/output length mix—128+128 shorts badly understate KV and decode time. Reconcile cost as token-price × daily tokens against GPU-hours; a few long-context calls often consume most of the budget.

**Follow-ups:** If prefix-cache hit rate goes from 0 to about 60%, do you drop cards or only shrink the prefill pool? Users start writing long answers and outputs grow from 400 to about 1500 tokens—what blows first? Do retrieval QPS and embedding dimensionality get sized with the GPUs?

**Extended questions:**
- 7B and 70B share a cluster: how do you isolate slots and queues so short calls are not stuck behind a long prefill?
- How do you use in-flight requests × average KV live to decide whether to add cards or truncate context?
- When provider TPM saturates before GPUs do, which fires first—local queueing or a small-model divert?

**Reasoning:** The goal is p95 latency without dropping peak traffic; the constraints are decode slots, KV HBM, and quotas. Invert concurrency to arrival rate, invert KV-per-token to per-card concurrency, and size to the tighter of the two. Accept the plan with a bounded queue and a load test on the real length mix, not a comforting average QPS.

## OPS-009. At 3 a.m., a support bot must be able to wake someone. Which four live signals deserve paging, and which "LLM metrics" are dashboard decoration?

**Answer:** Page on availability (5xx, timeouts, vendor throttle rate), SLO breaches (p99 TTFT and inter-token latency, sliced by short vs long requests), safety/compliance filter anomalies (a collapse in block rate is more dangerous than a rise), and broken business closure (tool failures, format or ticket-create failures, human-takeover spikes). Decoration: mean tokens/s, mean “satisfaction” with no contrast, a GPU-utilization chart by itself, and a quality score with no version dimension — none of them answers “can the user finish the job right now.”

**Deep dive:** Monitoring should point at a layer within about five minutes: gateway, retrieval, model, or tool. Request rate tells traffic spike versus a dead dependency; token and cost become an hourly budget alarm so you do not discover a burn at 9 a.m. Model, prompt, and index versions must tag every time series or “quality got worse” cannot be attributed. Retrieval hit rate and empty retrieval need their own plots or a retrieval outage is misread as model invention. Thumbs-down is a lagging signal for next-day review, not the only night page. Logs must be redacted. Paging needs suppression and contrast: block rate falling from about 2% to 0.1% may mean the classifier died and should outrank a rise to 3%. Capacity (KV occupancy, queue depth) informs the on-call; promote it to a page only when it threatens SLO.

**Follow-ups:** Vendor latency is ~300 ms worse everywhere — whom do you page, and is the threshold an absolute or versus yesterday’s same hour; tool success drops while model calls still return success codes — why must those alarms be split; do you alarm cost on money or on token quantiles, and how do you keep one huge prompt from paging you.

**Extended questions:**
- Sharing one p99 across short chat and 8k RAG hides which incidents?
- How do you page on human-takeover rate without false pages from shift staffing changes?
- Offline quality runs once a day — how do you stop it being mistaken for a real-time page?

**Reasoning:** Invert from “someone must fix this at night”: finish the job, do not leak, do not burn the budget. Split signals into page / ticket / tomorrow and drop unactionable averages. Validate alerts with sliced SLOs and a version dimension.

## OPS-010. A user reports that the answer cited a clause that does not exist; logs show only the final reply and HTTP 200. To split the failure back to retrieval, prompt assembly, generation, or tools, which fields must one trace keep at minimum, and which must never be persisted in the clear?

**Answer:** HTTP 200 only means the gateway did not crash; it does not say where a citation came from. A minimal trace holds: `trace_id` / `span_id`, tenant and a user pseudonym, prompt version, model version and decode parameters, retrieval query, document ids, scores, index version, the list of injected chunk ids, tool names and status, input/output tokens, TTFT/TPOT, finish reason, guardrail decisions, and citation ids on the output. Clause bodies, ID numbers, and the full raw prompt stay out of plaintext by default; when replay is required they go to a controlled store with TTL. Document ids plus the injection list are what distinguish “retrieval returned the wrong clause,” “assembly attached the wrong chunk,” and “the model invented a number that was never injected.”

**Deep dive:** Carry one `traceparent` across services: gateway span → orchestrator span → retrieval span → model-client span → each tool span. The retrieval span records the normalized query, top-k `doc_id` / `chunk_id`, scores, and filters (ACL, freshness)—not full text. The assembly span records the template version and the `chunk_id`s in order; that is evidence of what the model saw, more trustworthy than a later rerun. The model span records the provider request id, token ledger, `finish_reason`, and whether prefix cache hit. If the answer says `clause 14.3` and that id is not in the injection list, call it generation hallucination; if the wrong 14.3 was injected, call retrieval or ACL; if the id is right but the model rewrote a number, call unfaithful generation. Sampling: keep full fields on 100% of errors and user complaints; successful requests may downsample, but versions and doc ids should stay so rare hallucinations remain reconstructable. Access: being able to read a trace is not permission to read source text; source viewing is separately authorized and audited. Align clocks on server time. Do not store only the final string—that forces guesswork as root cause.

**Follow-ups:** Retrieval returned the right `chunk_id` but assembly dropped it on a length cap—how does the trace show that? The user allows replay but demands source deletion after 7 days—do id fields stay? In a multi-hop tool chain the second hop rewrites a number from the first—how are spans linked?

**Extended questions:**
- Write a span-field table: required fields for retrieval / assembly / generation / tools, and which must be redacted.
- How do you auto-label hallucination with the rule “answer citation ids ⊆ injected ids”?
- If the log system bills by request-body size, which field classes do you cut first, and which must you never cut?

**Reasoning:** The goal is to attribute a bad citation to one layer. A 200 and a final string carry no causality, and source text is privacy-constrained. Keep versions, ids, scores, and decisions; put source in a controlled store. Accept when you can name retrieval, assembly, or generation without guessing.

## OPS-011. The primary model API’s p95 drifted from about 800ms to 8s; the timeout is still 3s. The browser SDK, the BFF, the LLM gateway, and the vendor’s official SDK each retry 3 times by default. Ingress QPS is unchanged, but on-call sees about 80× the usual load on the model. Which layer may retry, and how do you install a global retry budget so the product of those fours does not explode, without treating a single blip as an outage?

**Answer:** One user request may be retried by only one layer on the whole path; every other layer pins retry count at 0 and forwards how many attempts remain in a budget header. Put that layer in the LLM gateway: it sees the vendor’s 429/`Retry-After`, the idempotency key, and whether a first token has already been streamed to the user. The browser and BFF may report 5xx/timeouts and must not fire again by themselves; disable the vendor SDK’s built-in retries, or set them to 1 and honor the budget header. When the budget is spent, fail fast or take a warmed degrade path—do not multiply by another 3.

**Deep dive:** Independently configured retries multiply: illustrative 3×3×3×3=81, then stack “timeout 3s, actual p95=8s”—each hop waits the full 3s before retrying, so the model is still being hit after the user has left. Flow: the gateway assigns each `request_id` a `retry_budget` (illustrative: at most 2 extra tries on an idempotent read, 3 in total; 0 once a streaming write has emitted a first token) → downstream SDKs read the header and stop at 0. Circuit-break per *dependency*, not per URL: when the primary’s error or timeout rate clears a threshold (illustrative: ≥50% failed in a one-minute window) flip the breaker to open and, during cooldown, fail or serve a read-only cache/template so probes do not add another wave. Hedged requests: at most one extra replica, only for not-yet-streamed idempotent reads, both counted against the same budget. Degrade is not a retry: only after the breaker is open do you read an FAQ cache or a fixed template; do not hit a backup on every hop’s timeout. Log `retries_attempted`, `budget_remaining`, and `hedged` per layer. The ratio of ingress QPS to model QPS is the first storm metric; illustrative steady state is about 1.1, and above 10 you should find which layer still retries. Boundary: a BFF refresh that the user actually clicked must mint a new `request_id` and a fresh budget, not reuse a spent key. Do not turn this into “the backup model’s tool fields do not line up”—this item is only about who is allowed to retry.

**Follow-ups:** The gateway already spent the budget, but the browser still polls a progress endpoint every 3s—is that a second storm, and should progress share the model budget; the hedged second leg returns first and shorter—which one wins; while the breaker is open, template answers have no citations—how do you rewrite the product SLO so this is not a silent quality drop.

**Extended questions:**
- Write default `max_retries` for all four layers and mark the only layer allowed to be non-zero.
- How do you use ingress-QPS / model-QPS plus timeout percentiles together to prove the storm is multiplication, not an 80× traffic spike?
- After a streaming first token, the connection drops—why must the budget be 0 rather than opening another copy of the same prompt?

**Reasoning:** The goal is fail-fast or degrade when the vendor slows down, not turning slowness into overload via multiplied retries. The constraint is that every layer will “helpfully” retry by default. So retry rights sit only at the gateway, the budget header decrements downward, and other layers disable their own retries. Accept when model QPS no longer scales with timeouts, and when an open breaker sends no further retries at the primary.

## OPS-012. Citation faithfulness on a hosted API has been sliding hour by hour since early afternoon, and the vendor published no release note. How do you use shadow replay of a frozen gold set plus the vendor's model fingerprint to tell a silent weight swap from a retrieval or prompt release?

**Answer:** Split live traffic from a frozen gold set: gold pins the prompt hash, injected chunk ids, index version, and decode parameters, then shadow-replays hourly and scores only whether citation ids land in the injected chunks. If your own `prompt_version` and `index_version` calendars are empty that afternoon, while gold faithfulness and the fingerprint jump together, you can name a silent vendor swap; if gold holds and only live traffic drops, investigate a retrieval or prompt release.

**Deep dive:** Build gold from live questions that must cite (illustrative: 80–200 items covering policy, price, and exception clauses). Freeze the template, chunk-id list, index version, `temperature=0`, and stop sequences; store bodies in a TTL-controlled object store and forbid re-retrieval on replay. Shadow uses a separate quota and a separate call to the hosted alias so it does not steal user concurrency. Fingerprints come in two layers: (1) if the API returns `system_fingerprint` or a snapshot id (depends on the API version you integrate; some aliases change snapshots with no announcement), record hourly whether the value changed; (2) if the field is missing or the alias never moves, build a behavioral fingerprint — the hash of the first 32 greedy token ids on the same gold item, or the first-token logprob when exposed. Align three charts: gold citation-grounding rate, fingerprint / behavioral hash, and your internal release calendar. **Reasoning:** The goal is to name a weight/snapshot change when there is no announcement, not to enumerate request-trace fields again. ## OPS-016. Two hours into a canary of new weights, refusal rate doubles. The old checkpoint is still on disk, but the tokenizer, quantization config, and paired prompts already followed the new version. What does a rollback have to restore to be a working state again?

**Answer:** Pointing the weight file at the old checkpoint is not enough. A working rollback restores the whole bundle: weights, tokenizer/vocab, chat template, quant bit-width and kernel, default generation parameters, and the prompt version declared compatible; for RAG, also the embedding model and the index read pointer. Before the canary starts you need a warm copy of the last good bundle, or an image that comes up in minutes, and the traffic pointer must move as a bundle. At release, the new bundle loads in its own replica pool while the old bundle keeps serving; the canary only changes routing weights. Rollback = 100% of routing back to the old pool, not a hot-swap of old safetensors inside a process that already loaded the new tokenizer. Typical mismatches: a new vocab shatters special tokens in the old prompt; a chat template that no longer puts the system turn first makes the old prompt a no-op; a 4-bit kernel will not start on 8-bit weights. **Follow-ups:** The old bundle sits in cold object storage and reload takes 40 minutes—what rollback SLO still counts as passing? Only the model rolled back, the prompt is still new—how do logs prove that this caused the refusal spike? Under tensor parallelism across machines, how do you make one bundle switch atomic?

**Extended questions:**
- List at least six manifest fields that must roll back together, and one failure for rolling back each field alone.

**Reasoning:** The goal is to restore the joint behavior of encoding, instruction template, and weights from before the canary. The constraint is that those files advanced as independent edits. **Reasoning:** The goal is uninterrupted sessions and a path back to the old joint behavior. Quantization error and index space may both change. ## OPS-022. A stream has already decoded about 200 tokens when the tenant’s per-minute dollar bucket fills. Do you cut the request and refund the unused output reservation, or let it finish? How do you release that refund so queued long summaries cannot starve short Q&A again?

If the leftover reservation is still the full cap (illustrative: 1.5k–2k output still held) and the dollar bucket is at a hard ceiling, cut with `finish_reason=budget` and refund only the unread tail. def admit(job, remain_frac, lo=0.08, hi=0.30):
```python
    return remain_frac > (lo if job.cls == "short" else hi)
```

A long summary that was waiting must still clear the high watermark after a refund; it does not sit down just because 1.8k reservation appeared. **Answer:** Split transport failures from policy failures; never key the chain on “this was not a normal completion.” For 429 / 503 / timeout: honor `Retry-After`, retry the primary, then hop to the backup — but the backup must wear the same input and output safety policy; the escape path does not get to drop filters. Every hop logs `failure_class`, `hop`, `policy_bundle_id`, and whether the original bytes were replayed; a hop after a safety class is itself an incident.

**Deep dive:** The on-call foot-gun is `if not ok: fallback(backup)`. Safety refusals are often HTTP 200 with a filtered finish reason, or 400 with a stable error code — neither is rate limiting. The branch table belongs in the orchestrator, not a wiki: (1) transport (429, gateway timeout, connection reset) → jittered backoff → bounded primary retries → backup; (2) policy (content filter, refusal template, local input classifier hit) → stop, user sees the primary refusal text and reason code; (3) schema / tool-argument breakage → bounded repair on the same model only, never hop to a “more cooperative” weakly guarded model; (4) vendor 5xx → backup allowed, but the request still passes your input policy and the response still passes output policy. A looser backup often lacks the same safety classifier or system refusal, so a raw replay delivers an already-blocked injection to a weak guard. Data path: the primary span records the vendor error code and safety class → the router switches on that enum, not on “is there text” → the backup span must cite the same `policy_bundle_id`. Metrics: `fallback_after_safety` must stay 0; transport fallback rate and backup safety-block rate are tracked separately. Drills must fire a 429 fixture and a safety-refusal fixture; pulling the network cable is not coverage. This question is whether to hop, not how to backfill missing ticket fields on a weaker backup.

**Follow-ups:** The primary returns 200 whose body is “I can’t help you” with no `content_filter` flag — do you trust a classifier, a refusal template, or treat it as transport failure; the backup’s safety policy is stricter than the primary, so a transport hop yields a second refusal — how does the product explain that; if the local input classifier is down, is automatic hop still allowed on the transport branch.

**Extended questions:**
- Draw the 429, `content_filter`, schema-failure, and 5xx branches; for each, say whether you replay the original bytes, whether you change models, and which audit fields are required.
- How do you stop a human “one-click replay” duty button from bypassing the hard “no hop after policy class” gate?
- How do you regression-test the on-call script on “hops after a safety class” rather than on “how many backup calls occurred”?

**Reasoning:** The goal is that rate limits can escape and safety refusals cannot be routed around. The constraint is that the two failures look similar at the HTTP layer, and the backup is usually looser. So branch on a failure-class enum, terminate and refuse replay on policy class, and bind the same policy bundle when transport hops. Acceptance is an audit that can name the branch, with zero hops after safety.

## OPS-035. At the evening peak p50 barely moves while p99 jumps from about 2s to more than 10s, and the logs contain a handful of 32k-input report jobs. How do you prove this is head-of-line blocking rather than slower weights, and how should the queues be split?

**Answer:** Split latency by input length and request class. If short chats replayed alone still sit near 2s TTFT/TPOT, but mixed with 32k reports their queue time grows while compute time does not, a long request is occupying the batch or the GPU—the weights are fine. Put reports and short chats on separate queues with separate concurrency caps; admit-control the long class and reserve slots for the interactive class. Chunk long prefills or move them to another pool so one report cannot consume a whole scheduling quantum. Prove it with “queue time versus pure compute” and percentile fields, not by swapping the model first.

**Deep dive:** Path: gateway enqueue → scheduler builds a batch → prefill/decode → response. A 32k prefill can own an accelerator for hundreds of milliseconds to seconds; short requests on the same batch or card wait, so p99 is a few long tails while p50 stays a short-chat number—that is the HOL signature. Contrast: strip long jobs from the peak trace and watch p99, or in staging saturate with short jobs and inject 1% 32k reports. Stable time-per-token on short jobs plus a stepped queue histogram localizes to scheduling. Policy: queue by input length or SLA class (interactive / batch reports); give each class its own concurrency and token bucket; send batch work to an offline lane or a dedicated replica. Caches and a backup vendor address repeats and provider jitter; they do not stop one local long prefill from blocking a line of short chats. Scaling out shrinks the queue but, without a split, the same HOL pattern reappears on each new replica. Required fields: input length, queue, prefill, decode, preemption. This is not “p99 doubled after a deploy with unchanged traffic”: assume config is unchanged and the peak mix grew a long-tail class.

**Follow-ups:** After the split, report TTFT gets worse—does the contract even have a batch SLA; is 1% 32k traffic enough, under continuous batching, to push short-chat p99 into the tens of seconds, and how would you estimate that with replay; how do you tell provider-side jitter from local HOL on a single trace.

**Extended questions:**
- Only p99 moved; p50 and short-request TPOT did not. Why is that more like queuing than “the model got slower”?
- After splitting long and short queues, how do you avoid idle short-request slots while reports pile up—or the reverse?
- How do you alert on short-request queue time instead of waiting for end-to-end p99 to catch fire?

**Reasoning:** The goal is stable interactive chats at peak; the constraint is that long reports are legitimate and prefill-heavy. Use a contrast replay to split queue from compute, then isolate with queues and caps. Accept with per-class queue time and p99, not a first guess that the weights changed.

## OPS-036. The synchronous chat path holds at 100 rps in load test. At 5000 rps retrieval times out first, then the GPU queue fills. How do you decide whether to add replicas, turn on continuous batching, or pull non-interactive steps off the synchronous path?

**Answer:** A 50× load fills different resources in sequence; adding app replicas is not enough. Read saturation: vector-store QPS and connections, the embedding queue, GPU KV occupancy and the scheduler queue, tool thread pools. Retrieval timing out first means the sync chain already broke before the model—cache, shard, and isolate retrieval before you buy GPUs. The GPU queue filling next means interactive decode slots are short: spread short chats with continuous batching and more replicas, and keep long summarization, re-embed, and eval out of the chat pool. Anything that can be async (writing a session summary, embedding for analytics) leaves the user-wait path; the sync path keeps only the retrieve-and-generate core.

**Deep dive:** At 100 rps a single replica or retrieval instance still has slack, and averages hide it. At 5000 rps with 1.5k input and 150 output tokens, output alone is about 750k tokens/s—not something extra web processes absorb. Even a high-throughput 7B-class engine needs replica count from sustainable QPS per replica (illustrative tens to a couple of hundred, length and batch dependent), then KV: on the order of 100–300KB per token (layers, GQA, precision), so an 8k tail fills HBM first. 5000 QPS of top-k often dies before the GPUs—connection pools, locks, or memory bandwidth. Decision tree: (1) retrieval p99 up, GPU util still low → more shards, hot cache, split embed vs retrieve pools; (2) GPU compute low but KV or the queue full → more replicas or shorter concurrent context, not a bigger batch; (3) GPU compute full and short calls stuck behind long prefills → continuous batching, chunked prefill, or split prefill/decode pools; (4) many calls are “generate then write a summary” → queue the summary. Load tests must use the real length mix and cache-hit rate; 128+128 to 5000 rps is meaningless. Put per-route limits and backpressure on the gateway so a slow retrieval cannot fill threads and then stall generation too.

**Follow-ups:** Is retrieval timeout the worst 1% of large-index tenants or everyone? Continuous batching raises throughput but worsens p99 TPOT—do you add replicas or shrink max batch? After the async split, users refresh and do not see the summary—what visible delay will product accept?

**Extended questions:**
- How do you use in-flight KV bytes to decide whether to add GPUs or truncate history?
- If embedding writes share the cluster with online retrieval, what does a bulk write do to 5000 rps reads?
- You scale the gateway to 5000 rps but leave the model pool sized for 100 rps—what error shows up first?

**Reasoning:** The goal is bounded sync-chat latency at 5000 rps; the constraints are retrieval, KV, and GPU batching, each with its own cap. Scale whichever saturates first and move non-interactive work off the user wait. Accept with a real-length load test and per-pool utilization, not with “100 rps still had headroom.”

## OPS-037. In a rewrite → generate → citation-check pipeline, the checker times out after generate has already spent about 2 seconds. Retry, skip the check and mark “unverified,” or fail the whole job—what must the state machine record so a failed output is never fed to the next step?

**Answer:** Choose by whether the failure makes the result untrustworthy. A failed rewrite can fall back to the user’s original query and still retrieve. Generate is the step worth a limited retry or a model swap. A failed check usually should not throw away the ~2s of generation: return the body marked unverified, or re-check only uncited sentences. The state machine records each step’s input digest, whether the output passed schema, the error class, and whether downstream may consume it. Never pass a timeout empty string or half JSON forward as legal context.

**Deep dive:** Orchestration is not a happy-path script. Each step declares a timeout (rewrite about 300–500ms, generate about 2–8s, check about 400–800ms, cut to the SLO), retry policy (network and 429 only, not 4xx schema), fallback, and an idempotency key. Data flow: `rewrite.ok ? rewritten : original_query` → retrieve → generate → `verify.ok ? cited : {text, verified=false}`. Failing the whole job on a check timeout spends generation cost and still shows an error; silently skipping the check ships citation hallucinations. The compromise: the check is degradable and must not fake success. State at least `step`, `status`, `attempt`, `input_digest`, `output_ref`. Downstream admission is an explicit predicate—for example generate must not run after retrieve.failed unless the product allows no-retrieval answers. Retried generate uses the same idempotency key so a mail-sending tool cannot double-fire. Partial success: if retrieval and a draft exist, stream the body and badge verification asynchronously. The dependency graph must be able to skip non-critical nodes instead of failing a linear `await` chain. Measure per-step success, fraction degraded on the checker, repeated generates, and cascade errors from dirty inputs.

**Follow-ups:** The checker times out about 30% for five minutes—auto-skip, switch a backup checker, or raise whole-job failures to protect the brand? The rewriter expands the query to about 2k tokens and retrieval dies—is that a successful rewrite, or does the orchestrator need an output budget? Generate has already streamed halfway when the check fails—what does the client show?

**Extended questions:**
- How do you state-machine-test a forced step timeout and assert downstream never receives an empty output?
- Checker and generator share one provider quota—why can retrying the check make generate worse?
- Which step must fail the job, which may return a partial, and what in the product contract decides that?

**Reasoning:** The goal is that one failed step does not burn already-paid work or treat invalid output as fact. Pick retry, degrade, or fail by step criticality, and cut cascades with explicit state and input digests. Accept orchestration with per-step fault injection and “dirty input is never consumed,” not with the happy path alone.

## OPS-038. EU users’ chats and indexes must not leave the region, but a full rebuild of the US-East index takes hours. On multi-region cutover, do you keep a stale local index or send inference across a border, and how do you promise sync lag?

**Answer:** Residency beats the “fresher” replica in another region. Raw chats, vectors, ACL tables, and audit logs for EU users stay in-region; inference defaults to in-region endpoints. Even if US-East has a newer index, you do not ship queries or document vectors out for freshness. Cut over only to an in-region standby, or to a peer region the contract explicitly allows. Publish lag as an external promise—for example, policy docs on the order of minutes, attachments on the order of hours. When lagging, say “may not be latest” or refuse time-sensitive questions; do not cross a border to catch up.

**Deep dive:** Each region is a full unit: gateway, session store, object store, vector and keyword indexes, keys, logs. The control plane may sync document ids, versions, and ACL summaries; bodies and vectors replicate only under residency rules. Disallowed replica paths are off in config, not in a prompt. Indexes that take hours to rebuild should apply a change log and re-embed per document; full rebuild is disaster recovery. If in-region inference capacity runs out, degrade to a small model, cache, or queue before asking whether any lawful out-of-region inference exists—sending personal data as model input is a transfer. - On a region failure, the read replica is out of region and writes stay in-region. What conflicts hit session appends?
- How do you turn “chat or vector bytes in cross-region payloads” into a compliance regression?

## OPS-039. In the first three minutes of a campaign, chat arrivals jump to about 20× the daily rate. New replicas are still loading weights and every KV is cold. What part of the overload do the peak-shaving queue, priority, and warmup each block—and how do you keep the spike from becoming a timeout for everyone?

**Answer:** A spike is arrivals suddenly above already-hot capacity. Loading GPU weights often takes tens of seconds to minutes, so autoscaling misses this three-minute window. Warmup makes replicas and prefix cache hot before the event. Priority keeps hot slots for interactive and paid traffic. A bounded queue absorbs only a few seconds of jitter; beyond that, reject or degrade—never enqueue the full 20× and drag every user into timeout. A replica that just came up with a cold KV still has worse TTFT, so “scaled out” is not “capacity available.”

**Deep dive:** Suppose daily 80 rps, campaign 1600 rps for 180s: about 270k extra requests. At 2s mean service time you would need about 3200 in-flight slots to drain in 3 minutes; a pool sized at 2–3× daily idle will drop work. A queue that may wait 60s already ruins the head, while the tail is still arriving. So: (1) calendar-driven warmup—preload weights, run synthetic prefixes to seat the system prompt in cache, warm connections and kernels; (2) admit by priority buckets, keep for example 30% of hot slots for P0 (checkout help, login assist), and send campaign trials to a small model or static FAQ first; (3) cap the queue at acceptable wait × hot-slot throughput, then 429 or “try later” with a retry wait. **Extended questions:**
- How do you compute a hard queue cap from hot slot count × target wait instead of picking a large integer?
- About 80% of requests share the campaign landing-page prefix—do you warm prefix cache or semantic cache first?
- Autoscaling cooldown is about 10 minutes—why does a three-minute spike almost always need warmup rather than elastic scale-out?

**Reasoning:** The constraints are cold-start time and a finite hot-slot count; the goal is that the critical path stays up through the peak. Warmup turns capacity hot in advance, priority decides who gets those slots, and a bounded queue stops the spike from becoming an all-hands timeout. Accept on real TTFT on hot replicas plus reject/degrade rates—not on “machines have started.”

## OPS-040. The order JSON schema grows a new required field every week, while the old prompt and old model are still on a 10% canary. How do you validate with forward compatibility (defaults, unknown fields, version negotiation) so a spike in parse failures is not misread as a model regression?

**Answer:** Unbind the validator from “this week’s latest schema” and bind it to the request’s own contract. The prompt bundle and model arm declare `schema_version`; the gateway picks the validator by that version: the old canary keeps the old required set, and new fields get a safe application-side default during the overlap window instead of demanding that the old model emit them now. Unknown fields are ignored or stored in an extension bag, not a whole-order failure. Parse-fail rate must be sliced by `(prompt_ver, model_ver, schema_ver, arm)`; failure only on the old arm against a new required field is a contract overlap, not a model regression.

**Deep dive:** Weekly change, illustrative: v12 adds required `fulfillment_window`. The 10% canary still runs `prompt_v11` plus the old model, which never saw that field in its instructions. If the writer suddenly validates every order as v12, fail rate jumps in the minute the schema ships and looks like a quality regression. Negotiate explicitly: the envelope is `{schema_version, payload}`; `schema_version` is written by the serving prompt bundle, not invented by the model. If undeclared, infer from which required keys are present; never default to `latest`. Compatibility has a direction: the writer is backward compatible with older payloads — v11 bodies may persist during an overlap (illustrative: 1–2 weeks), and `fulfillment_window` is filled with a business default (for example `standard`) that operations will actually honor; do not let the model invent the window. Readers are forward compatible — newly added unknown keys do not void the order; park them in `_extra` or drop them. v12 bodies from the new arm must not be killed by an old validator. Metrics: `parse_fail{arm,schema,prompt,model}` plus a `default_filled` counter. Contrast: both arms stay flat on the versions they declared, and only a control that forced `latest` validation spikes — you can reject “the model got worse.” When overlap ends and old-arm traffic is 0, close the defaulting channel; missing fields are then real errors. Do not ship a global “tighten required fields” as one release; schema, prompt, and model must roll back independently. This is version coexistence, not how you stop a half object with a missing quote.

**Follow-ups:** The new field has no safe default (the user must pick a delivery day) — during overlap do you block old-arm checkout, escalate to a human, or make the field optional again; the model writes a v12 key inside a v11 payload — do you keep or strip unknown fields; the 10% canary mixes a new prompt with the old model — does `schema_version` follow the prompt bundle or the model’s self-report.

**Extended questions:**
- How do you use an arm × `schema_ver` fail-rate table to reject the “model regression” hypothesis in five minutes?
- How do you mark default-filled fields on the order so a system-supplied window is never treated as a user promise later?
- When the schema rolls back to v11, how does the read path keep recognizing extra fields already written under v12?

**Reasoning:** The goal is that a weekly contract change still parses on the canary, and fail rate attributes to the arm rather than a “dumber model.” The constraint is that an old prompt and old model cannot know a field you invented this week. So validate against the version the request declared, default and ignore-unknown during overlap, and slice metrics by version. Acceptance is stability of the old arm on the old contract, not a single global `parse_fail`.
