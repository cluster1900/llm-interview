## SERVE-001. Two 7B replicas are packed onto one H100 with MPS, and each batch=4 decode is more than twice as slow as when the card is exclusive. How do you use L2 hit rate, HBM row-buffer conflicts, and context switches to prove cache thrashing rather than insufficient compute, and should you bind SM quotas, stagger launches, or split onto two cards?

**Answer:** First rule out “two workloads filled the Tensor Cores”: if SM throughput is only half of exclusive, yet the two weight working sets dwarf on-chip cache, this is thrashing. Compare against an exclusive baseline: L2 hit rate roughly halves, HBM row-open / conflict counts double, and MPS client context switches line up with decode steps. All three moving together closes the case. If binding SM quota or staggering step phase can recover L2, start with soft isolation; if two 7B weight streams are doomed to collide every step and hit rate never comes back, split to two cards.

**Deep dive:** MPS lets two CUDA contexts share one card’s SMs and memory hierarchy. A 7B-class decode step all but sweeps that replica’s weights: one FP16 copy is about 14 GB, while public H100 specs put L2 at about 50 MB — enough for the current layer’s tiles, not the whole net. When two disjoint weight address streams interleave, the tile A just installed in L2 is evicted by B’s next layer, and A’s next read of the same layer falls back to HBM. Evidence: (1) L2 hit rate drops from exclusive “per-layer locality” to near one-miss-per-access; (2) HBM row buffers: two sequential streams on different rows / banks raise row-open and precharge counts, so useful bandwidth per replica stays below a linear “twice exclusive traffic” expectation — the bandwidth counter can look busy while bytes/s each replica actually uses do not; (3) context switches: if both clients launch decode on the same cadence, MPS flips at kernel boundaries and instruction cache / TLB jitter with them, producing step-interval spikes that track switch counts. The counter-proof for “not enough compute” is: pause one replica and the other returns to near-exclusive step time without SM occupancy suddenly saturating. Bind SM quota (for example 40–50% each) so they stop fighting the same cache at the same instant — useful when load is asymmetric. Stagger scheduling so decode steps are not aligned — useful when neither QPS is high. If both weights must be swept every step and L2 stays near-random after quotas, soft isolation only turns jitter into a stable “each is twice as slow”; then split cards so each stream recovers single-stream locality instead of stuffing a ~28 GB working set into 50 MB of L2. Boundary: two processes that replicate the same weights still contend for L2. A single process with two logical services on one read-only weight mapping thrashes less; this question is two independent replicas — do not conflate the two.

**Follow-ups:** L2 hit rate dropped but useful HBM bandwidth did not drop in proportion — which miss class is still missing (TLB, I-cache, barriers); after a half-step stagger, row conflicts fall but tail latency rises — what does that mean; MIG into two instances versus MPS quotas — how do they differ on L2 partitioning and fault isolation.

**Extended questions:**
- How do “pause one replica → the other snaps back” and “sum of the two step times versus exclusive step time” separate cache thrashing from launch overhead?
- If the two layer loops are deliberately 180° out of phase, how much L2 hit rate can you recover, estimated from a current-layer working set of a few MB?
- Daytime needs one 7B and night spins a second for eval — how does the MPS sharing policy differ from keeping both replicas resident all day?

**Reasoning:** The goal is to explain why two batch=4 decodes are more than twice as slow as exclusive. The constraint is that one card’s L2 is far smaller than two 7B weight streams, and decode walks a new layer every step. L2 / row-buffer / switch counters against an exclusive baseline prove thrashing; whether quota or phase shift can restore hits decides soft isolation versus two cards.

## SERVE-002. If you move 70B pretraining from a GPU cluster onto a TPU Pod, which layers feed the systolic array, and which code shapes fail at compile time?

**Answer:** Dense, statically shaped GEMMs — QKV projections, MLPs, output linears — feed the systolic array at high efficiency. Dynamic control flow, per-step ragged lengths, and kernels tied to GPU shared-memory tiling fail in the XLA compile, or get demoted onto the vector unit and crawl. The migration only pays if you close the graph to fixed shapes and express parallelism with collectives, instead of replaying the GPU habit of launching a new kernel string every step.

**Deep dive:** A TPU's heart is the systolic array inside the matrix unit: weights are preloaded onto a grid of MAC cells, activations wave across rows and columns, and partial sums hand off to neighbors so each MMA does not write back to HBM. That matches training steps whose `[M,K]×[K,N]` tiles are large enough; 70B dense linears can approach array peak. Softmax, RMSNorm, and nonlinearities sit on the side vector / scalar units — second-class, and large or irregular work stalls the array. The software path is framework graph → XLA → a static executable. If sequence length, batch, or expert routing changes every step, you pad into already-compiled buckets or you recompile; cold compiles can take minutes. Host–device sync, step-by-step Python debugging, and hand-tiled GPU kernels have no counterpart. Many chips join a Pod over a fast interconnect; data and model parallel must bind AllReduce / AllGather to that topology at compile time. Versus a GPU: the TPU is “the compiler is the scheduler”; the GPU is “launch another bundle of kernels at runtime.” Batch-1 decode GEMV is equally unfriendly to the array, so a common split is pretrain on TPU and decode online back on GPU.

**Follow-ups:** Why ragged batches have to be bucketed by length; which dimension you shard when the array meets sparse expert routing; what overflow problem BF16 mainly fixes relative to FP16 on TPU.

**Extended questions:**
- If 30% of steps are decode-style generation eval, what drags the TPU training loop?
- What does a host-side shape check on every step do to the device pipeline?
- For the same AllReduce, where does a Pod link bottleneck versus a multi-node GPU network?

**Reasoning:** Filter ops by “can this become a static, dense, large-tile array compute?” Forward/backward that can, benefit; anything that needs dynamic shapes or custom kernels must be rewritten into a compilable fixed graph or the move costs more than the FLOP you gain.

## SERVE-003. A ticket only says "the model is slow"; the request is 6,000 input tokens and 40 output tokens. Do you profile prefill or decode first, and which user-visible metric does each phase own?

**Answer:** Profile prefill first. With 6,000 in and 40 out, almost all GEMM work is the one-shot pass that consumes the prompt, writes input KV, and emits the first token; decode is only about 40 steps. Prefill (plus queueing and tokenization) owns TTFT — how long until the first character. Decode owns TPOT / inter-token latency and time-to-finish — whether the rest of the reply stutters. Until “slow” is split this way, swapping engines or adding GPUs is guessing.

**Deep dive:** Prefill takes shape `[B, S, D]` with S≈6000; attention scores grow roughly with S² and the FFN with S·D²; one forward covers the whole prompt and usually produces the first output token. Each decode step has q_len=1, reads cached K/V of length S+t plus all weights, and appends one token. Wall-clock figures are illustrative: if prefill is thousands to tens of thousands of tokens/s and single-request decode is tens to hundreds of tokens/s, a 6,000-token prefill often already dominates 40 decode steps. Long-in / short-out (RAG, classify, extract) is prefill-heavy; short-in / long-out (code, long prose) is decode-heavy. Optimizations split the same way: prefill cares about chunking, prefix cache, and compute utilization; decode cares about continuous batching, KV quantization, and speculative decoding. An end-to-end average hides “2s to first byte, then smooth” and the opposite.

**Follow-ups:** For the same 6000/40, how does a 20k prompt inserted into the continuous batch drag your 40 decode steps; how much of TTFT is queueing rather than prefill compute; which slice of wall time speculative decoding actually changes.

**Extended questions:**
- How does the profiling order flip for 200 in and 2,000 out?
- On a streaming API, when the user says “slow,” do you look at time-to-first-token or time-to-token-100?
- How do you cut one request’s wall time into queueing, tokenize, prefill, and step-by-step decode on a trace?

**Reasoning:** Use the input/output length ratio to locate the work, then map the complaint onto TTFT or TPOT. Verify with a split trace, not total latency alone.

## SERVE-004. After the continuous-batch cap rises to 64, live traffic mixes greedy JSON constraints, temperature-0.9 chat, and translation with logit bias, and only about a dozen sequences actually fuse into the same GEMM each step. How do you split kernel groups by sampling / constraint compatibility, and decide whether to run several pipelines, unify sampling plus post-process, or admit that “64” is a memory cap rather than a compute cap?

**Answer:** 64 is a KV / page-slot cap, not a promise of one fat matrix every step. Greedy plus a vocab mask, high-temperature multinomial, and biased translation have different control flow and extra tensors feeding the sample kernel. If the scheduler insists on compatibility, the sequences that can share one GEMM+sample are often a subset. Draw the compatibility matrix: presence of a mask, whether temperature is 0, whether a nonzero logit bias exists, whether the FSM must return to the host. One kernel group per cell that can share those. Then choose: split groups into pipelines (smaller GEMMs, simple isolation); unify `logits + bias`, apply mask, sample at T as one kernel so differences become data not branches; or accept that the useful compute batch is about a dozen and 64 only packs HBM — do not expect tokens/s to scale with slot count.

**Deep dive:** The forward GEMM mostly does not care how you sample later — same model, same dtype, lengths in the same bucket, and 64 sequences can theoretically form one fat matrix. The split is after GEMM: the constrained group must apply a stepwise mask before sampling, sometimes pulling logits to the host; chat scales by temperature and draws multinomial (maybe top-p); translation adds a vocab-sized bias before softmax. If the implementation is “one sample path, one graph / one host loop,” the scheduler pulls only the compatible dozen in a step and leaves the rest for the next iteration: the dashboard shows in-flight=64 and effective GEMM batch≈12. Group by extra tensors and control flow, not by product name: temperature-0 chat with no bias can join greedy JSON if JSON’s mask is all-ones on chat; biased translation can join a unified kernel if bias is a dense vector add on logits. Unify then post-process: the device always runs `logits ← logits + bias; logits ← logits + mask_penalty; sample(T)`, and post-process only does checks that do not change the next token (for example a JSON bracket audit). Real constraints cannot be post-process only — an illegal token would already be in KV. So a unified kernel fits only differences you can tensorize (mask / bias / T). The group whose FSM must return to the host should be its own pipeline so 64 sequences do not eat a D2H every step. Multiple pipelines make each GEMM thinner and occupancy drop, but stepwise taxes stop cross-contaminating. Admitting 64 is a memory cap: watch “sequences that actually joined this step’s GEMM” versus “occupied slots.” If that gap is stable, reduce incompatible paths (tensorize masks that do not need the host) instead of raising max_num_seqs again. Boundary: this is not “static wait-for-N versus iteration enqueue” — that is the admission model. Even with iteration-level batching, incompatible sampling still shatters a step.

**Follow-ups:** In the matrix, can “T=0.9 with an empty mask” share a sample kernel with “T=0.9 with a sparse JSON mask,” and how do you measure warp divergence; may three pipelines still share one chunked prefill; effective GEMM batch sits at 12 — what do you ask before adding a fourth logit processor.

**Extended questions:**
- Build a compatibility table (greedy, T=0.9, logit bias, host FSM) and mark which cells tensorize together and which must be separate pipelines.
- After max_num_seqs=64, KV occupancy grows linearly but GEMM shape does not — which two missing fields make you misread that as “plenty of compute”?
- If the unified kernel also multiplies an all-ones mask as a dense `[B, vocab]`, at vocab 128k can that extra bandwidth turn sampling from “negligible” into a new per-step tax?

**Reasoning:** The goal is to explain “64 slots but only about a dozen sequences in the same GEMM.” The constraint is that sampling and constraint extra tensors and control flow do not match. Split kernel groups by compatibility, then compare separate pipelines, a tensorized unified kernel, and accepting compute batch < memory batch, using effective GEMM width — not the slot cap — as the decision variable.

## SERVE-005. A support bot needs 200 tokens/s on a single stream with jitter under 5%. Do you bet on an SRAM LPU or an HBM GPU, and which roof blocks the other?

**Answer:** For single-stream tokens/s plus hard real-time jitter, bet on an SRAM-style LPU: weights live on-chip, decode no longer pays an HBM trip every step, and the compiler statically places instructions and chip-to-chip moves, so latency is predictable. An HBM GPU at batch 1 is capped by a few TB/s of off-chip bandwidth; a 70B-class weight file is tens of GB per step, so even the math struggles to hold 200 tokens/s, and queues plus cache misses add jitter. If the goal flips to high-concurrency aggregate throughput rather than a single-stream ceiling, GPU batching is the better buy.

**Deep dive:** Decode's roof is “weight bytes you must touch per token ÷ available bandwidth.” On HBM, take 70B × 1 byte (FP8) ≈ 70 GB over ~3 TB/s: the ceiling is a few tens of tokens/s, and kernel efficiency plus KV reads push a single stream well short of 200. An LPU parks weights in on-chip SRAM, whose bandwidth is typically an order of magnitude above HBM and whose latency is much lower, so intensity is no longer stuck on the off-chip wall. The cost is capacity: a single chip's SRAM is usually tens to a few hundred MB, so 70B fans out across many chips that also move activations on a compile-time beat; chip count scales roughly with “weight bytes / useful SRAM per chip.” Deterministic issue has no dynamic cache misses and no runtime preemption, so jitter can sit at a few percent; it also means you cannot freely change batch at run time, flexible queue jump-ins are hard, and training's backward pass plus optimizer state do not match this serve-only design. For high-concurrency offline summarization, a GPU reads weights once for tens of streams and often wins on tokens/s per unit of silicon. Pick from the SLA: hard real-time single stream → LPU; elastic throughput → GPU.

**Follow-ups:** How many chips a 70B needs from SRAM capacity, and what that does to failure rate; how a static schedule avoids idling on variable-length outputs; whether speculative decoding is still worth doing on an LPU.

**Extended questions:**
- If the same hardware must train and serve, why does an LPU almost never make the shortlist?
- If you quantize a GPU model to INT4 and raise batch to 32, what happens to single-stream latency versus cluster throughput?
- After the compile-time communication topology is frozen, how painful is a hot update of a low-rank adapter?

**Reasoning:** Back out the bytes-per-token budget that 200 tokens/s allows; HBM cannot fund it and on-chip SRAM can. Then price multi-chip partitioning and static scheduling against jitter, flexibility, and training, which puts interactive hard-real-time on the LPU and throughput jobs on the GPU.

## SERVE-006. You must colocate high-QPS 13B support chat and occasional 70B deep answers. How do you mix A100 80GB, H100, and L40S instead of buying a single SKU?

**Answer:** High-QPS 13B wants card count, memory bandwidth, and tokens/s per dollar, so a 48 GB-class inference card such as an L40S is usually the better fit. Occasional 70B wants per-node memory and intra-node interconnect, so A100 80GB or H100 can hold the weights at a small tensor-parallel degree and keep step latency down. A mix is cheaper than an all-flagship fleet, provided routing splits the two flows so 70B KV cannot evict the 13B concurrency pool.

**Deep dive:** Size “does it fit” before “how fast.” 13B BF16 weights are about 26 GB; one ~48 GB inference card still has room for tens of 4K sessions. Those cards earn their keep on purchase cost and serve density, not training peak FLOP. 70B BF16 weights are about 140 GB, so one 80 GB card is not enough and you need at least TP=2. A100 80GB and H100 both expose 80 GB of HBM, but using published figures as an illustration, H100 SXM HBM3 is about 3.35 TB/s versus about 2.0 TB/s of A100 SXM HBM2e, which shows up on batch-1 decode and even more on long prefill Tensor Core work. If 70B runs FP8, weights drop to about 70 GB and H100 FP8 MMA can fill prefill; A100 usually stays on an INT8/FP16 path. Interconnect is a hard filter: TP=2/4 for 70B wants in-node high-speed links. On PCIe-only cards the per-step AllReduce can erase the compute you just saved. Confirm the target precision and parallel degree actually exist in the driver and compiler. Score SKUs on tokens/s per dollar plus KV bytes per in-flight session, not peak TFLOP alone.

**Follow-ups:** If you only have an H100 quota, how do you stop the large model from starving the small one; can 70B INT4 even run on one L40S, and what quality gate do you set; how do multi-node tensor parallel and single-node multi-GPU differ as failure domains.

**Extended questions:**
- If inference must stay on-prem, which extra interconnect and isolation constraints enter the SKU choice?
- Both cards have 80 GB — why does training care more about BF16/FP8 compute and fast links, while serving looks at bandwidth and total memory first?
- What tail-latency risk do you take if seasonal 13B load is soaked up with preemptible cheaper cards?

**Reasoning:** Split the workload into “small model, high QPS” and “large model, low QPS,” pick cards from the capacity formula and the bandwidth roof, drop any SKU whose links cannot carry TP, and keep the two pools from stealing each other's HBM via routing.

## SERVE-007. Your hand-written RMSNorm CUDA kernel is 3× slower than the library. In what order do you inspect occupancy, coalescing, and warp divergence?

**Answer:** Treat RMSNorm as a bandwidth wall: it reduces a hidden vector and rescales it, so intensity is low and a 3× gap usually means you are not filling HBM or you added extra round-trips. Inspect in order: whether the warp issues vectorized, coalesced loads on contiguous addresses; whether the reduction finishes in registers / shared memory; whether occupancy is too low to hide memory latency; and whether per-token branches diverge the warp. Library kernels typically bind those details to 16-byte loads.

**Deep dive:** After `<<<grid, block>>>` on the host, each thread claims work with `blockIdx/threadIdx`. For `[B, T, H]`, a sane map is one warp or one block per length-H vector: vectorized loads to accumulate squares, a tree reduction via warp shuffle or shared memory to get σ, then a second pass writing `x * rsqrt(σ²+ε)`. Typical slow paths: (1) strided row access that will not coalesce, so effective bandwidth is a fraction of peak; (2) every thread scanning the whole vector with no `__shfl_down_sync`, exploding instruction count; (3) a tiny block or too many registers per thread, so too few active warps and HBM latency shows (occupancy e.g. under 20%); (4) lots of `if (tid < len)` on padding, so some lanes work and some wait inside one warp; (5) splitting Norm, residual add, and SiLU into three kernels and paying three HBM trips instead of two. When T is small, launch overhead itself is visible. Read DRAM throughput, scoreboard stalls, and achieved occupancy — not just “the launch succeeded.”

**Follow-ups:** Why intra-warp branches hurt throughput more than inter-warp ones; which HBM trip shared-memory tiling removes in a GEMM; when you should let a compiler emit the kernel instead of keeping a hand-written one.

**Extended questions:**
- An elementwise SiLU kernel is almost always bandwidth-bound; does adding Tensor Cores inside it help?
- If you fuse RMSNorm with the residual add, how do four memory passes become two?
- Under dynamic sequence lengths, how do you avoid padding-induced warp divergence without giving up coalescing?

**Reasoning:** RMSNorm's bytes-to-FLOP ratio says it should fill bandwidth; walk the chain “coalesced addresses → on-chip reduction → enough warps to hide latency → lockstep branches → no extra kernel trips” until the 3× shows up.

## SERVE-008. One 80 GB GPU must serve 70B support chat at 16 concurrent 4K-context sessions. How do you prove OOM or not with the weight / KV / activation ledger?

**Answer:** Split memory into weights, KV cache, activations, and runtime slack — skip any line and you cannot sign off. BF16 weights are about 140 GB, already over 80 GB, so the answer is no. Only after weights drop to about 8-bit (~70 GB) or 4-bit (~35–40 GB) do you even ask whether KV still fits. Sixteen 4K sessions on a typical 70B GQA layout cost about 20 GB of KV: INT4 weights fit on one card, FP8 weights are tight, BF16 needs more than one GPU.

**Deep dive:** Weights ≈ parameter count × bytes/parameter. 70B×2 B ≈ 140 GB; ×1 B ≈ 70 GB; ×0.5 B ≈ 35 GB, plus scales and the embedding table, so budget INT4 at 35–40 GB. KV per token ≈ 2 × layers × KV heads × head dim × bytes. A common 70B GQA layout (for example 80 layers, 8 KV heads, head dim 128, FP16) is 2×80×8×128×2 ≈ 320 KiB/token ≈ 0.31 MB/token. 16 × 4096 × 0.31 MB ≈ 20 GB. Full 64-head attention is about 8× that, ~160 GB for the same concurrency — impossible on one card. Serve-time activations usually keep the current layer only; decode looks like `[16, 1, 8192]` (hundreds of KB), and a full 4K prefill is about 1 GB per layer, still far below training's full-graph activations. Reserve 5–10 GB for context, allocator fragmentation, and scratch. Close the books: INT4 40 + KV 20 + slack 10 ≈ 70 GB, so an 80 GB card runs, with a separate quality gate; FP8 70 + KV 20 already overflows unless KV also drops to FP8 (~10 GB) and max length is capped; BF16 needs tensor parallel ≥ 2. Plan against “target concurrency × max context.” Averages estimate cost; peaks decide OOM.

**Follow-ups:** Which line blows first when context goes from 4K to 32K; at TP=2, is KV sharded too and along which axis; can activations briefly exceed decode during a large-chunk prefill.

**Extended questions:**
- Two of the 16 sessions suddenly fill a 128K window — can paged allocation save this card?
- 8-bit KV versus 4-bit weights: which quality failures does each one cause?
- Why can the same 70B fail to train at batch=1 on 80 GB, while serving is “only” short on KV?

**Reasoning:** First ask whether weights already exceed 80 GB at the chosen precision; then multiply the GQA per-token KV formula by concurrency and length; add activation and fragmentation slack. All three lines in budget means one card is viable; otherwise name the precision to drop or the parallel degree to add.

## SERVE-009. A GPU is advertised at about 300 TFLOPS and 1 TB/s HBM (illustrative). For decode of a 13B bf16 model at batch=1, are you still bandwidth-bound? Show the arithmetic-intensity account.

**Answer:** Still bandwidth-bound. Each decode step is a matrix–vector multiply of the weights with one token’s activations: you nearly scan the whole weight tensor while FLOPs barely grow with sequence length (KV reads are extra). Arithmetic intensity ≈ useful FLOPs / bytes read from HBM. bf16 is 2 bytes per parameter and about 2 multiply-adds per parameter per token, so intensity is about 1 FLOP/byte — far below this card’s ridge point 300e12 / 1e12 ≈ 300 FLOP/byte. The roofline therefore sits on the bandwidth side: the speed cap is roughly weight bytes / bandwidth, not peak TFLOPS.

**Deep dive:** 13B bf16 weights are about 26 GB. Ideally one decode step streams the weights once, so a cap is about 26e9 / 1e12 ≈ 26 ms/token, ~40 token/s, before KV, fragmentation, and kernel launch. Saturating 300 TFLOPS on ~2×13e9 ≈ 2.6e10 FLOPs would take ~0.09 ms — two orders of magnitude less — so compute waits on HBM. Prefill is different: weights are read once and GEMMed with S tokens, so intensity scales about with S; at a few hundred to a thousand tokens you often cross 300 FLOP/byte and become compute-bound. Decode at batch=B shares one weight read across B requests and multiplies intensity by about B; B must reach the hundreds to near this card’s ridge, and interactive latency usually breaks first. Quantization cuts bytes per parameter from 2 to 1 or 0.5 and speeds decode at the same bandwidth; once prefill is already compute-bound, the speedup is less linear. Long context adds a KV read each step: layers × H_kv × Dh × current length × 2 (K and V) × width; at tens of thousands of tokens KV traffic can match the weights, and the bottleneck shifts from reading weights to reading KV — the reason for GQA and KV quantization.

**Follow-ups:** How large must batch be before decode on this card flips from bandwidth-bound to compute-bound; how does the roofline move after 4-bit weights; at 32k context do you still estimate TPOT from weight bandwidth.

**Extended questions:**
- On the same card, does prefill at S=4096, batch=1 cross 300 FLOP/byte?
- Why does adding GPUs that add FLOPs but not bandwidth barely help batch=1 decode?
- When speculative decoding verifies several tokens at once, which intensity term did you raise?

**Reasoning:** Compute the hardware ridge (FLOP/byte), then decode intensity (~2 FLOPs per parameter-byte). Far below the ridge means bandwidth-bound; cross-check with weight bytes / bandwidth as a token/s cap.

## SERVE-010. Why is the roof that binds prefill so often not the same one that binds decode?
**Answer:** Prefill processes input tokens together and is often more compute-bound; decode generates a few tokens per step and is often limited by weight and KV read bandwidth. Long context, large batches, or different hardware can change the bottleneck.
**Deep dive:** Profile the stages separately; do not treat "prefill is always compute-bound" as a law.
**Follow-ups:** Why can a larger batch improve throughput but hurt latency? Higher parallelism can amortize some overhead, but it increases per-step work, resource contention, or queueing time.
**Extended questions:**
- How do you use compute utilization, memory bandwidth, and kernel time to identify the actual prefill and decode bottlenecks?
- Why do long-context decode and short-context decode have different memory-access costs?
**Reasoning:** Adjust scheduling from utilization and latency breakdowns, rather than applying the same optimization to every stage.

## SERVE-011. If a serving benchmark only publishes tokens/s, what user-visible failure does omitting goodput hide?
**Answer:** Goodput counts only useful work that meets the agreed quality and latency SLOs; a large number of queued or timed-out requests can make aggregate throughput look good while failing user experience.
**Deep dive:** Make clear whether the unit of measure is the request or the token, and report load, failure rate, and TTFT and ITL quantiles.
**Follow-ups:** What queuing problems does closed-loop sending hide? The client waits for a response before sending a new request, so arrival rate falls when the system slows, which can understate the queuing that independent real traffic would cause.
**Extended questions:**
- If two configurations have the same tokens/s but different timeout rates, how do you define and compare request-level goodput?
- Why is reporting SLOs stratified by input length and output length more interpretable than a single overall quantile?
**Reasoning:** Increase load according to a realistic arrival process, and find the capacity that meets the SLO rather than a single peak throughput.

## SERVE-012. One 80GB GPU runs a 13B base and must host 48 tenant LoRAs (ranks 8–64) at about 80 in-flight. Adapters cannot all stay resident. What do paging, rank-grouped batching, and merging into the base each fix, and when does any of them blow TTFT?

**Answer:** Keep one copy of the base; page each tenant’s low-rank delta into a small HBM cache and leave cold adapters on host or local disk. Paging removes “all 48 resident.” Grouping isomorphic requests by rank or attach set removes tiny-kernel fragmentation. Merging into the base is only for a **hot tenant that owns the card**—you can materialize one W′ at a time, not 48. TTFT usually breaks when tenants are uniform, the head is not pinned, and almost every request waits on an adapter H2D before prefill.

**Deep dive:** A 13B bf16 base is about 26GB; KV and runtime take tens of GB more, so the resident budget for adapters is often only a few GB. Illustrative (measure your attach set; not a card spec): q/v-only, hidden width ~5k, ~40 layers, rank 8 is often around a dozen MB; rank 64 on q/k/v/o plus gated FFN can be hundreds of MB, and 48 fully resident copies then fight KV. Page with LRU or QPS-weighted pins: keep the head-N tenants in HBM, H2D on miss. The missing adapter must be in place **before prefill**, or TTFT pays a host-to-device copy (illustrative: tens of MB is milliseconds to low tens of ms, worse once queued). In a continuous batch the LoRA path is a second `(xA)B` after the base GEMM. Mixed ranks in one step need padding to that step’s max r, or rank buckets each running a smaller kernel—too many buckets thin the effective batch, occupancy drops, TPOT rises. Merge `W′=W+(α/r)BA` and decode is one dense GEMM: fastest on a single-tenant replica. On a shared card, 48 merged W′ copies OOM immediately, and rewriting 26GB on every tenant switch is worse than paging. Do not conflate this with training-time weighted merges of several LoRAs: that emits one new checkpoint; this serves many live, non-interfering deltas. Boundary: adapters whose base checksum or insert set disagrees must not share a process; mixed ranks can zero-pad into one kernel if you account for the wasted columns.

**Follow-ups:** If tenant QPS is almost uniform, does pinning the head 8 still help, or do you sticky-session replicas versus living with misses; 12 ranks inside one 80-way step—bucket by rank or pad everyone to 64; a tenant hot-swaps a 200MB adapter, do in-flight decodes keep the old delta.

**Extended questions:**
- Write the HBM formula “base + pinned N + KV” and mark which term blows first as N goes 8 → 48.
- Why is “merge 48 W′ copies at start” a different failure domain from “one base plus paged deltas”?
- Adapter cache hit rate is 99% but TTFT is still bad—which other miss (compiled graph, rank buckets, KV) do you profile?

**Reasoning:** The goal is 48 tenants on one GPU at ~80 in-flight without losing TTFT. The constraint is a single base, adapter bytes that grow with rank and attach points, and no 26GB clone per tenant. Page residency, batch by rank, merge only on a dedicated hot replica. Accept on adapter H2D counts, per-tenant TTFT quantiles, and zero loads of the wrong delta—not on whole-GPU used bytes.

## SERVE-013. A 70B decodes with 2-way tensor parallel; the single-card HBM roof is about 50 token/s but you measure only about 28. **Deep dive:** Using a typical 70B (for example 80 layers, hidden 8192, BF16): TP=2 usually does two all-reduces per layer (after the attention projection and after the MLP). The ring factor is `2(TP−1)/TP = 1`, so communication bytes per step per sequence ≈ 80×2×8192×2 B ≈ 2.6 MB, times batch B. Peak intra-node interconnect on an H100 is hundreds of GB/s in public specs, so 2.6 MB looks far above a 50 token/s bandwidth cap — but decode payloads are tiny and you actually hit the latency roof. Add unhidden launches and waits, and a step that was ~20 ms on the HBM roof (50 token/s) stretches to 30–40 ms, about 25–33 token/s, the same order as 28. Write the third roof as `min(B / (N_AR × t_AR), BW_eff / (N_AR × hidden × bytes × 2(TP−1)/TP))`. Overlap is limited in decode — the next layer usually needs this layer’s residual — so you can only hide “this AR with the next layer’s prefetch / RMSNorm,” not all 160 collectives. Boundary: a large prefill GEMM hides AR easily; a healthy TP=2 prefill trace does not excuse decode.

**Follow-ups:** After batch goes from 1 to 16 the comm roof flips from latency-bound to bandwidth-bound — how does aggregate token/s bend; KV offload shares the same NVLink — how do you remeasure effective bandwidth; after TP=1 the KV no longer fits — do you keep TP=2 and overlap, or cut KV precision to buy a TP reduction.

## SERVE-017. After JSON constrained decoding is turned on, p99 climbs from 800 ms to 3 s at the same QPS while GPU curves barely move. Split a step into GEMM → fetch logits → vocabulary mask → sample / reject-and-resample, and measure host mask wall time, device–host trips for logits or masks, and illegal-token resamples per step. Whichever term times output length accounts for 800 ms → 3 s is the tax. If the host scans a 100k-class vocabulary every step or keeps bouncing tensors over PCIe, fold the FSM into the device and fuse it with sampling. If the model already emits valid JSON at low temperature and the reject rate is near zero, generate freely and validate afterwards, retrying only on failure.

**Deep dive:** Constrained decoding runs the current prefix through a grammar automaton (JSON bracket stack, string escapes, schema field state), builds the legal token set, writes −∞ over illegal logits, then softmax / argmax. A CPU-side logit processor is more expensive still: `[batch, vocab]` logits come back to the host (for example vocab=128k, FP32, batch=16 is about 8 MB). Eighty output tokens at +25 ms/step is already about 2 s, which matches “p99 800 ms → 3 s, GPU curves flat.” The third counter is illegal-token resampling: some implementations sample the unconstrained distribution, reject illegals, remask, and draw again. In a narrow state (only `"`, `}`, or a comma left) that loop can spin a dozen times without launching a new GEMM, so the GPU stays idle. An in-kernel FSM keeps transitions and bitmasks on device and fuses them with the sample kernel; the host uploads the automaton once at request start. That path fits stable schemas that must be legal at every token (tool arguments). Generate-then-validate pays zero per-step tax and owes a full regenerate on failure, so it only wins when historical validity is already very high (for example temperature-0 short objects, validity >99%). **Follow-ups:** If the host mask is only 200 µs and p99 is still 2 s high, do you profile D2H sync or a lock inside the sampling loop next; resample count p99 is 20 while p50 is 0 — which JSON states grow that tail; when a request is free text and then enters a schema, at which step does the tax appear.

**Extended questions:**

- If the constraint path `cudaStreamSynchronize`s every step, why does GPU utilization approach 0 while the GEMM itself is not slow on a kernel timeline?
- For a long order object that is valid 97% of the time, how do you compare expected retry latency of generate-then-validate with in-kernel per-step masks before choosing a path?

**Reasoning:** The goal is to explain “latency exploded while the GPU did not get busier.” The constraint is that stepwise decode now has a serial legality stage outside GEMM. Host mask time, processor placement, and resample counts locate the tax on the control plane or in the sample loop; then “must be legal every step” versus “almost always legal already” chooses in-kernel FSM versus generate-then-validate.

## SERVE-018. Mid-decode you must squeeze 16 in-flight KV caches from FP16 to FP8 to reclaim concurrency, and streaming cannot stop. How do you choose the quant boundary (rewrite the whole sequence versus compress only the completed prefix), keep a scale discontinuity from drifting later tokens, and how is this different from the offline “quantize versus drop tokens” three-way choice?

**Answer:** Those 16 streams are already attending over the current KV, and streaming cannot pause, so this is not capacity planning’s “quantize / drop history / offload” triad — it is a live migration while new tokens are still appended. Prefer freezing scales on already-written blocks and compressing only closed prefix pages, leaving the tail page that is still being written in FP16. Rewrite the whole sequence only with a double buffer and flip the read pointer in a step gap. Scales must be pinned per block or per token; never re-encode old K/V under a new global scale, or later softmax reorders historical attention and the user sees “the second half changed voice,” not an OOM recovery.

**Deep dive:** Each sequence has a completed prefix (prompt + accepted output) and a tail block still being appended. A full rewrite allocates an FP8 buffer of the same token count, reads FP16 per block → estimates scale → writes, then atomically switches the block-table pointer at a decode-step boundary and frees the old pages. Sixteen sequences, for example 4k each, at roughly 0.1–0.3 MB of KV per token (varies with layers and KV heads) means several to more than ten GB of device copies. Slice that into “migrate N blocks per step” or a single step’s TPOT spikes into a user-visible hole. Compressing only the completed prefix is cheaper: the tail stays FP16, so the attention kernel must mix two element widths in one softmax, or briefly cast the tail up to the prefix compute type. The classic scale-discontinuity failure is recomputing a per-tensor scale from a new whole-sequence max and rescaling old vectors, which shifts every later dot product. Keep each old block’s write-time scale in the block header; new FP8 tokens carry their own scale; dequantize into a common FP16/FP32 accumulator. Difference from the offline triad: offline you may drop the oldest tokens or offload a whole sequence to CPU before the next request, because nobody is reading that stream. Mid-flight, dropping tokens rewrites context that already left the socket, and offloading the tail makes the next attention wait on PCIe — both are a visible stall or a semantic jump. The only allowed “drop” is refusing a 17th request; these 16 streams may change element width, not visible history. Boundary: some layers are sensitive to 8-bit KV (long-range references); you may compress middle layers and leave the first/last in FP16 — a layer boundary, not a time boundary. During the switch, a sequence’s block table must never be half old pointers and half new.

**Follow-ups:** When only the prefix is compressed and the tail stays FP16, does attention mixed-read or cast first, and which one gives back the concurrency you just reclaimed; a new token arrives halfway through a double-buffer rewrite — in what order do you commit the block table so you never read half-old/half-new; two of the 16 streams are already 32k — will a full rewrite spike their TPOT alone, and should whale requests be excluded from this migration.

**Extended questions:**
- After a rewrite, how do per-block versus per-token frozen scales differ in the error shape of the first new token’s attention distribution?
- Why is “delete the earliest 1k tokens, then quantize” forbidden on a live stream even though it frees more pages?
- During migration, is the newly arrived 17th sequence queued, cold-started in FP8, or first placed on remaining FP16 short pages?

**Reasoning:** The goal is to halve per-token KV bytes on 16 live streams without stopping the tokens. The constraint is that already-emitted prefixes cannot change meaning and the tail is still read on the next step. Choose the boundary as closed prefix versus in-write tail, freeze scales at block granularity, and treat this as a different problem from the pre-serving quantize / evict / offload choice.

## SERVE-025. Continuous batching wants a captured CUDA graph, but the live sequence count and each sequence’s page-table length change every step. How do you split variable page tables from the static graph (indirect tables, bucket padding, a graph pool) so you keep paged concurrency without recapturing on every iteration?

**Answer:** Graph capture wants a stable launch topology; paging wants a block table and live count that change every step. Those cannot live in one graph that bakes page numbers into constants. Keep a static shell in the graph — “read an indirect block table from a device pointer, then run attention / GEMM” — and rewrite table contents before each launch. Snap live batch and max pages to a few buckets (for example 8/16/32/64 × page-count buckets), one pre-captured graph per bucket, pad unused slots. Paging still charges real tokens in HBM; the graph is captured when a bucket misses, not on every iteration.

**Deep dive:** A continuous-batch step may reclaim three sequences on EOS and insert two new prefills; each sequence’s physical block list also grows by a page on decode. If you capture the current block-table address as a graph constant, the next pointer change invalidates it. Recapture often costs milliseconds to tens of milliseconds and eats the decode step. Split in three layers. (1) Indirect table: a fixed-capacity `block_table[max_batch][max_pages]` on device; the graph records kernels that read this table, not one frame’s page ids; the CPU or an H2D updates dirty rows. (2) Bucket padding: actual batch=11 uses the 16-slot graph and masks the extra five; page count rounds up to a 64/128/256-style bucket; extra entries on short sequences are marked invalid. Padding wastes a little empty-sequence launch width and buys graph hits. (3) Graph pool: capture the first time a bucket is seen; pool size is the number of buckets, not QPS; inside a bucket you only refresh the table, not the grid. Paged concurrency still comes from “as many blocks as tokens used” — padding is the index table and kernel dimension, not a contiguous max_model_len reservation. Boundary: too few buckets (only 64) make small steps carry a fat grid; too many grow the pool and the first visit to a new bucket still hitch-stops — warm the hot buckets with dummy requests. Do not realloc the page table every step: preallocate to max_pages and keep current length in `seq_len[]`. Only if this step’s max_pages exceeds every graph in the pool may you capture once synchronously or punt that request to eager; the rest of the batch must not sit through a recapture.

**Follow-ups:** Does the indirect table live on host or device, and who is on the critical path; after padding to the 64 bucket, is the empty-slot mask applied in attention or in sampling, and what breaks if one layer is missed; why must the whole graph pool be discarded after a driver upgrade.

**Extended questions:**
- Sketch batch 7→12→9 and max pages 20→21: which steps hit the pool, and which step is forced to capture.
- Why does “pin the page table in graph constant memory” look like it saves a load, yet is incompatible with continuous batching?
- Eager path for whale contexts, hot-bucket graphs for median sessions — can the two paths share one KV block allocator?

**Reasoning:** The goal is paged variable concurrency and graph-low launch cost at once. The constraint is that a graph cannot swallow a block table and batch that change every step. Move mutable state behind an indirect table, discretize the rest into a bucket pool, and pay capture only on a bucket miss.

## SERVE-032. A colleague says extra decoding heads are enough; you want a one-layer draft net that autoregresses the next hidden state and reuses the original LM head. What signals show that feature-level autoregressive drafting is worth the extra sequential steps versus independent multi-heads?

## SERVE-034. The same 7B ships as an FP16 server build and an INT4 edge pack. How do you explain that BF16/FP16 and INT8/INT4 damage different error modes, and which tasks decide which layers must stay at higher precision?

**Answer:** FP16/BF16 are floating formats: they change mantissa and exponent width, so matmuls pick up rounding but rarely wipe the logits of rare identifiers. INT8/INT4 pack a real range into a short integer grid and recover it with a scale (and often a zero-point); outlier weights and spiked activations saturate. Multiple-choice can still pick the right letter from a coarse semantic cluster; copying a clause number, a name, or a line of code needs fine logits that, once clipped, lose to a fluent hallucination. **Deep dive:** FP16: 5-bit exponent, 10-bit mantissa — good precision, narrower range than FP32, rare overflow, common rounding. BF16: 8-bit exponent (FP32-like range), 7-bit mantissa — favored in training for range; inference is usually close to FP16, not bit-identical. INT8 has 256 bins; a per-tensor scale hurts when channels differ, per-channel or per-group is safer. Heavy-tailed activations (some MLP layers) need per-token or per-group dynamic scales or they clip. INT4 has 16 bins and is almost always grouped (group sizes in the 32–128 class) with higher precision for outliers. These are method families; bit width does not promise "no loss" or a fixed speedup. Citation breaks first because the correct continuation is a low-frequency token sequence; noise in attention/MLP can drop the right logit under a more fluent neighbor, while a multiple-choice key still sits in the coarse cluster. Tensors commonly kept out of the lowest bits are the embedding, the LM head, LayerNorm scales, and sometimes the first and last blocks — mixed precision exists for this. Calibrate on domain activations: Wikipedia-clean scales will be wrong for legal RAG. Error accumulates over long generations; a short multiple-choice item will not show it. Toggle weight and activation quantization separately: weight-only may still pass citation, then activation clip collapses it. If BF16-trained weights are run as FP16, watch a few layers for inf/NaN — that is not the same accident as INT4.

**Follow-ups:** Which fails citation first, weight quant or activation quant; how do quality and kernel speed trade when group size goes 128→32; which layers do you inspect for inf/NaN when a BF16-trained checkpoint is served in FP16.

**Extended questions:**
- Design ~50 held-out "must quote verbatim" items and explain why they expose INT4 damage better than multiple choice.
- Which layers stay out of INT4 by default, and why protect the embedding and output head before an arbitrary MLP?
- If the business says "a bit worse but faster is fine," which online metric proves it is no longer acceptable?

**Reasoning:** The goal is to explain "generic scores hold, copy tasks are already broken." The constraint is that an integer grid clips outliers and fine logits. Match format capacity to the task, then use mixed precision and domain calibration to protect the identifier path.

**Extended questions:**

## SERVE-039. You have one week and no retrain budget. Can post-training quantization get a 7B chat model to 4-bit production? If the product then asks for 2-bit, which capabilities crack first?

**Answer:** With one week and no retrain, the only path is post-training quantization (PTQ): estimate per-layer or per-group scales on a small calibration set, write the existing weights into a 4-bit codebook, and compare on chat, math, code, and safety-refusal sets. 4-bit with grouped scales (for example one scale per 64/128 weights) and protected outlier channels can be shippable for many 7B-class models, but only if the task set — not perplexity alone — agrees. 2-bit has about four representable values; the error is no longer “a little off.” Reasoning chains, arithmetic carries, and rare proper nouns break first. **Deep dive:** PTQ does not backprop; wall time is a calibration forward (illustrative: hundreds to a few thousand samples) plus one weight rewrite, which fits frozen open weights. QAT quantizes the forward pass during training and uses a straight-through estimator so weights learn to live on the grid; quality is better, but it needs data and GPU time that a one-week freeze-the-eval schedule rarely allows. The shared 2–4-bit problem is dynamic range: a few large weights sharing one scale with the layer crush everything else toward zero. Grouping, rotations/transforms, and protecting critical channels move that error without retraining. 7B is more brittle than 70B because there is less redundancy. Quantizing activations to 4-bit as well hurts more than weights alone. Low-bit also needs a dedicated kernel or decode does not speed up. Illustrative, not a guarantee: 8-bit is often near-lossless; 4-bit plus a decent PTQ is acceptable for much generation; 3-bit is case-by-case; 2-bit is usually “needs QAT.” Flat perplexity with a falling business metric usually means a tail slot — format, tool JSON, multilingual — broke.

**Follow-ups:** A calibration set of about 128 generic documents misses which parts of a chat product’s distribution; given one week, do you run a layer-wise least-squares method or a channel-protection method first, and how do you A/B them; if 2-bit is applied only to attention or only to the FFN, which side becomes unusable first.

**Extended questions:**
- Shrinking groups from 128 to 32: how do you trade accuracy against extra per-layer scale storage?

**Reasoning:** The constraint is “no retrain + one week,” so PTQ to 4-bit first, and the task set decides the ship. 2-bit turns the problem from error into an undersized codebook; refuse it without QAT evidence. Accept on sliced tasks, not PPL alone.

## SERVE-040. Serving 70B, tensor-parallelize every layer across 4 GPUs versus 4 full replicas: who wins on TTFT, and who wins on cluster throughput?

**Answer:** Tensor parallel shards each layer's GEMM and attention heads across 4 GPUs, so one request's compute and memory drop by about 4× and TTFT/TPOT usually fall — if the AllReduce is cheaper than the compute you saved. Four full replicas have no in-layer communication and aggregate throughput ≈ ×4, but each replica still needs the whole weight file. 70B BF16 does not fit on one GPU, so the pure-replica plan is out immediately. Use tensor parallel when memory does not fit; use replicas when it does and you want throughput.

**Deep dive:** Column/row-split an MLP: `Y = SiLU(X W1) W2`. Shard W1 by columns so each GPU owns 1/4 of the inner channels and applies SiLU locally; shard W2 by rows and AllReduce the partial sums to recover Y. Attention is usually split by heads (1/4 of the heads per GPU) and the outputs are merged. A 70B hidden size of about 8192 becomes N=2048 at TP=4, so compute is ~1/4 and so are weights and head-sharded KV. Decode pays one or two AllReduces every step on a `[B, H]` activation. At B=1 that is tens of KB, but the cost is collective tail latency — hundreds of microseconds to milliseconds on PCIe — which can erase the compute win. So tensor parallel belongs inside a node at 2/4/8, not as a high degree across machines. Replicas run a full forward on each GPU, communicate nothing in-layer, schedule simply, and isolate failures; BF16's 140 GB must fit first, or you quantize first. A common hybrid is TP=2/4 inside the node for capacity and single-stream latency, plus copies across nodes for QPS. Higher is not always faster: at TP=8 the collective count stays the same but each GEMM is thinner, occupancy drops, and decode can slow down.

**Follow-ups:** Why decode fears tensor-parallel communication more than prefill does; how you shard when GQA has fewer KV heads than the parallel degree; with tensor and pipeline parallel both on, how many cross-stage transfers sit on one request's path.

**Extended questions:**
- Why is failing one GPU in a 4-way tensor-parallel group harder to fail over than failing one of 4 replicas?
- Can an AllReduce in this layer overlap unrelated work in the next? Why is that hard in decode?
- If you switch to expert parallel instead of tensor parallel, what does the AllReduce turn into?

**Reasoning:** Ask whether one GPU holds 70B; if not, pure replicas are not an option. If yes, trade “in-layer communication for single-stream latency” against “zero communication for linear throughput”: tensor-parallel inside the fast domain, replicas outside it for QPS.

## SERVE-041. Even INT4 leaves a 70B working set too large for one GPU. When should you shard the model across cards instead of pushing precision further or switching to a smaller model?

**Answer:** Sharding solves “the full working set does not fit on one device.” It is not a default accelerator. First exhaust options that keep the model intact: a smaller model that still hits quality, weight quantization, and smaller max context or concurrency to shrink KV. Only when quality or latency SLOs forbid further compression, and you accept cross-device communication plus operational complexity, should you split weights (and KV if needed) across devices. Shard too early and collectives at small batch blow the latency SLO; shard too late and you only OOM or reject.

**Deep dive:** Working set ≈ weights + KV + activations + runtime. 70B bf16 weights are about 140 GB and will not fit an 80 GB card; INT4 weights are about 35 GB, leaving tens of GB for KV. Many “does not fit” incidents are actually high-concurrency long-context KV — cap concurrency or quantize KV before sharding. When you do shard, typical cuts are by layer or by matrix dimension, or by MoE expert; each device keeps only a slice of parameters and uses point-to-point or collective communication to assemble activations or shards when that slice is needed. Illustrative communication: a matrix split pays a cross-card sync every layer every step, including every decode step; a layer split ships activations between stages and loses utilization to bubbles. Single-request latency often falls as you add devices (more compute) then rises when communication and bubbles dominate. That is the opposite of replicating a full copy on N cards: replicas do not reduce per-request memory, they only add throughput. Sharding optimizer state in training is a different decision; do not fold it into serving-time weight splits.

**Follow-ups:** INT4 already holds the weights but 32k context × 64 concurrency still OOMs — do you shard the model or the KV pool; on inter-node links around 10–25 GB/s, what does an 8-way split do to interactive decode; if neither quality nor latency can drop further, how do you use an eval set to choose 2-way sharding versus switching to 32B.

**Extended questions:**
- Putting only the embedding and LM head on a second card, leaving the middle layers on one card — is that a useful shard, or worse communication?
- After sharding, per-GPU utilization drops about thirty percent; how do you tell bubbles, sync waits, and missing compute-communication overlap apart?
- When should you refuse to shard and instead run the large model asynchronously offline, keeping only a single-card model on the live path?

**Reasoning:** Write the working-set formula and decide whether the wall is weights or KV. If quantization, admission control, or a smaller model removes the wall, do not introduce communication. Confirm “should shard” (not merely “can shard”) with single-request latency, communication share, and OOM rate.

## SERVE-042. You are shipping a minor inference-engine upgrade that also changes KV block size and scheduler defaults. What canary and replay gates do you put on throughput, VRAM, time-to-first-token, and same-prompt output drift? When greedy decoding is no longer token-identical, how do you tell numerical nondeterminism from a real regression and decide whether to roll back?

**Answer:** Canary the engine bundle (kernels + block size + scheduler defaults) as one unit, and replay with frozen prompts and a frozen concurrency mix. Hold four gates together: sustained throughput / in-SLO completion, KV and workspace VRAM, TTFT percentiles, and token sequences on the same prompts at `temperature=0`. If greedy is no longer byte-for-byte identical, do not roll back yet: measure logit gaps on near-tie tokens and task-level metrics (slots, refusals, schema). Roll the whole bundle back only when task metrics drop or VRAM/TTFT break the line. String inequality alone is not a regression.

**Deep dive:** Illustrative minor bump: KV block 16 → 64 tokens, `max_num_seqs` 256 → 128, default chunked-prefill flipped. Larger blocks change intra-page fragmentation and kernel tiling; the new scheduler changes batch-mates; both change GPU reduction order. fp16/bf16 add is not associative, so the last bits of attention accumulation drift and greedy flips when the top-2 gap is tiny. That is not a weight change, and it is not a question of how a paged block table allocates. Gates: (1) replay yesterday’s peak length mix; compare tokens/s and the share finished inside the latency SLO, not peak throughput alone; (2) VRAM: used KV, reservation, OOM rate — larger blocks often raise internal fragmentation and cut concurrency first; (3) TTFT p50/p95, split cache hit vs miss; (4) output drift: freeze 100–300 prompts, greedy-run old and new, score token agreement on mismatch positions. Discrimination: repeat each prompt N times on the new engine (illustrative N=5); if it already disagrees with itself, record “engine nondeterminism” before calling it a cross-version regression. Where old and new diverge and logprobs exist, treat `logp1-logp2` below about 0.05 (illustrative; calibrate to your dtype) as a near-tie numerical flip. Task gate: JSON parse, key-slot F1, refusal agreement — if those hold and only wording synonyms move, accept or pin RNGs and ship. A flipped number, tool name, or refuse/comply flip is a real regression no matter how close the logits. Rollback granularity is the whole engine bundle; do not revert block size while leaving the new scheduler behind. Do not use speculative decoding as the control (that is a different speed path), and do not make “did the block table save memory” the primary gate here.

**Follow-ups:** Greedy is token-identical at batch=1 and starts drifting at production batch sizes — do you still call that numerical; TTFT improved but fragmentation causes rare OOM — do you keep the throughput win or roll back; if replay omits the real prefix mix, which class of “scheduler default” regression do you miss.

**Extended questions:**
- How do you use a “near-tie flip share” table and a slot-F1 table to choose ship, watch under a cap, or roll the whole bundle back?
- Which single factor do you replay first, block size or scheduler defaults, to learn whether fragmentation or batch shape is hurting TTFT?
- Greedy already drifts and production temperature is 0.7 — do you still put token agreement in the gate, or keep only task-level metrics?

**Reasoning:** The goal is a revertible engine bump that can separate “reduction order changed” from “serving behavior broke.” The constraint is that block size and scheduling move both the numeric path and the queue shape, and greedy token identity was never a cross-kernel contract. So run four gates in parallel, classify drift with near-ties plus task metrics, and roll the bundle back only on a broken line. Acceptance is the task contract and the SLO, not whether two strings match exactly.

## SERVE-043. After you stop assembling operators at runtime and start compiling an engine, swapping to a different NVIDIA GPU architecture forces a rebuild. What does that compile step freeze in place, and why is the engine file not a portable checkpoint?

**Answer:** Compilation pins the graph to this card, this Tensor Core generation, this precision, and this parallelism cut: it fuses small ops, picks autotuned attention and GEMM kernels, inserts quantization scales, and plans workspaces for paged KV and in-flight batching. The artifact is kernel choices and shared-memory layout, not a portable weight container, so a different SM architecture, precision, or tensor-parallel width needs a rebuild. You gain fewer runtime kernel searches and fewer extra memory round-trips on that NVIDIA GPU; you pay build time, hardware lock-in, and a lag until new model structures are supported.

**Deep dive:** Typical path: load weights → pick precision (for example FP16 / FP8 / INT8 / INT4, depending on your compiler version) and sharding → build the engine → load it in the runtime or serving stack. Fusion commonly targets QKV plus attention, residual plus norm, and the small kernels around the decode sampler, to avoid writing intermediates back. Kernels are searched for the target GPU’s compute, shared memory, and Tensor Core generation; the best choice on generation A can be illegal or slower on generation B, so you cannot treat the engine as a “copy to any card” checkpoint. In-flight batching stays a runtime concern: compile owns the step kernels, the scheduler owns admit/evict. Boundary: a structure change or a new max sequence length needs a rebuild; replicas that share architecture, compiler version, and config can be distributed; this path does not apply off NVIDIA. Do not put an unverified speedup figure into a capacity plan; replay your own length mix and concurrency.

**Follow-ups:** If you only change max batch size and not precision, do you rebuild; does an FP8 build fail or silently fall back on a GPU without matching Tensor Cores; when engine builds live in CI, do you archive artifacts by GPU SKU or by machine label.

**Extended questions:**
- The same engine is loaded on two same-generation cards with different memory sizes; which workspace or max-concurrency limits will you hit?
- Which intermediate writebacks does fusion remove, and why does that make a ordinary profiler worse at attributing a single layer?
- A new open-source architecture must ship tomorrow and the compiler has no matching layer yet: wait, write a plugin, or serve with an eager engine first?

**Reasoning:** The goal is to use that GPU’s low-precision units and fused kernels; the constraint is reproducible deploys and rebuilds when hardware changes. Keep portable weights separate from the tuned executable graph and rebuild on card changes. Accept with TTFT/TPOT under the same traffic plus build time, not engine-file size.

## SERVE-045. Chat, embedding, and an overnight eval job share one GPU pool. At the chat peak the embedding service starts OOMing. How do you carve memory quotas instead of buying another row of cards?

**Reasoning:** Start from “KV grows, weights must stay pinned,” size the chat-peak KV, then choose isolation (quota, process, MIG, or off-peak). Accept the design when embedding OOM rate is zero, chat latency percentiles hold, and weight regions no longer cross.

## SERVE-046. A troubleshooting agent resubmits the system prompt, tool schemas, and the full trajectory on every step, and by step 12 time-to-first-token is already seconds. With a radix tree indexing KV, which prefixes hit automatically, and what happens if you insert a timestamp or shuffle message order?

System prompts, tool schemas, few-shots, and unforked dialogue history usually hit; a per-step timestamp, a request id, or a reshuffled message order cuts the shared prefix at the first differing token and forces the rest to recompute. **Deep dive:** The runtime treats in-flight requests as paths in the tree: a new request matches from the root, and hit length is how much prefill you skip. Scheduling can prefer requests with deep hits so a hot prefix is not evicted. If the frontend describes branches and parallel calls as one program, the runtime can see which sub-calls share a prefix, which is stronger than treating every generation as an unrelated HTTP call. Constrained decoding can also skip schema-determined tokens with a compressed state machine; that is separate from tree hits—the tree saves historical KV, the machine saves constrained decode steps. Do not store the answer itself in the tree; you reuse intermediate KV and still resample the output.

**Follow-ups:** If every step writes the current time into the system prompt, at which layer does the hit rate collapse; if eviction counts tokens versus requests, can a long-tail agent push out the hot support prefix; do deterministic tokens skipped by constrained decoding still need to be inserted into the radix tree.

(3) Inspect batch-size histograms and per-step prefill/decode duration. A batch stuck at 1–2 with a cheap decode step is an arrival-rate or gateway problem; a single step that contains a huge prefill is head-of-line blocking — those few steps may saturate SMs while the rest of the window is idle, so a 30% average lies. (4) Only then use engine traces or system sampling on kernels: whether prefill GEMMs are fed, whether decode is HBM-bound. Keep TTFT and inter-token percentiles, throughput, SM and HBM, KV-block use, batch, queue wait, cancels, and OOMs on the board. Profiling must separate prefill from decode; their bottlenecks often oppose. When utilization is low, chase scheduling and memory before “not enough FLOPs.”

**Follow-ups:** Queue time is short but TTFT is still 4 s — what do you cut next; SM is 30% while HBM bandwidth is already maxed, is that still “idle”; how do you prove in a postmortem that the spike was KV allocation failure rather than a larger model.

**Extended questions:**
- Why can GPU sampling alone, without request-level timestamps, almost never explain 800 ms → 4 s?
- Safety filters and tool calls sitting outside the decode loop will pollute which metric into “the model got slower”?
- How would you design an on-call panel that shows queue vs compute vs memory in thirty seconds?

**Reasoning:** Treat low SM plus high p99 as a scheduling or memory problem first. After request-level splits rule out queueing and KV wait, profile the compute step. Quantization is a tool for when compute or memory is already saturated, not the first hypothesis here.

## SERVE-061. Online 13B chat is about 80% prompts ≤512 input tokens and 20% 8k-class RAG. After you write a global TTFT p99 of 800ms, long prompts page constantly and on-call never sees a real slowdown on short chats. How do you bucket TTFT/TPOT by input length, and set error budget plus burn-rate alerts?

**Answer:** Write latency SLOs as **bucket × quantile**, not one mixed p99. Short bucket (illustrative: input ≤512) TTFT p99 ≤ 800ms and TPOT p99 ≤ 40ms. Long bucket (illustrative: input 4k–8k) gets its own wider TTFT (for example 2–3s, from your prefill), while TPOT stays a per-step gap, not whole-response wall time. Error budgets are per bucket: 99.9% over 30 days on the short bucket is about 0.1% budget. Page on fast-burn short windows and slow-burn long windows; long-bucket misses must not debit the short-bucket budget, or 8k RAG drowns short-chat pages.

**Deep dive:** Under mixed traffic a global p99 is almost always the shape of long prefill, not a slower GPU: even “healthy” 8k calls often sit at hundreds of milliseconds to seconds of TTFT and already cross an 800ms short-chat line. Bucket on **tokens actually sent to the model** (system + history + retrieval + this turn), not characters and not output length—output length belongs in a separate whole-response or TPOT×N report. Illustrative SLOs (replace with cluster replay): S0 input <256, S1 256–1023, S2 1024–4095, S3 ≥4096; S0/S1 align to interactive 800ms TTFT; S2/S3 align to prefill capacity with a higher but finite TTFT so queues cannot grow unbounded. Error budget: one per latency SLO, 30-day window, 99.9% ≈ 43 minutes of equivalent miss if you counted minutes—but count **requests**, because LLM traffic is strongly diurnal. Burn rate (illustrative, tune to how hard you page): 1-hour window ≥14 means the monthly budget would vanish in about two days at that pace—page now; 6-hour window ≥6 is a slow leak for daytime work. Compute “misses in window / (bucket requests in window × budget fraction × window/30d)” with the **bucket** request count in the denominator, never site-wide QPS. Short-bucket burn pages the interactive rotation; long-bucket burn pages capacity/retrieval, and the text names the bucket so two teams do not fight one page. Probes must be generated per bucket or synthetic short chats paint the long SLO false-green. Cancels and safety blocks are their own counters, not latency misses. GPU utilization and tokens/s are not inputs to the error budget.

**Follow-ups:** A call with 400 input tokens and 2k output—which TTFT bucket, how is TPOT reported; canary at 10% burns the short bucket first—do you cut traffic or check that arm’s length mix was biased; budget on requests or on users, and how retries and mid-stream cancels count.

**Extended questions:**
- Sketch short-bucket burn thresholds for 1-hour and 6-hour windows and why the long bucket cannot reuse those numbers.
- With only a global TTFT p99 and no per-bucket request counts, how do you show you cannot tell a short-chat regression from RAG getting longer?
- When the budget is gone, do you refuse S3, move S3 to an offline queue, or add replicas—and which SLO does each choice hurt?

**Reasoning:** Short chats that slow down must page; healthy long prefills must not flood the board. TTFT tracks input length, so a mixed p99 has no explanatory power. Bucket SLOs on input tokens; keep error budget and burn rate per bucket. Accept when the short bucket stays quiet if only long calls worsen, and when a real short-chat regression pages inside the fast-burn window.
