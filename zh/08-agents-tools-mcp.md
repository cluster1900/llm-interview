## AGENT-001. 用户要先核库存再下单，客服侧却只跑了一轮 LLM 补全、随口造出订单号。缺掉的是哪一层能力？

**答：** 缺的是「观察外部世界、执行真实动作、再根据结果继续」的闭环，而不只是一次文本补全。单次 LLM 调用只能根据训练知识和当前提示续写，看不到库存接口的返回值，也拿不到下单 API 的回执，订单号只能是模型编出来的 token。Agent 要在目标未完成时反复：提出动作 → 由平台执行 → 把观察写回上下文 → 再决定；没有这一层，它最多是会说话的表单。

**深入展开：** 一次简单调用的数据流是 `用户文本 → 提示拼接 → 解码 → 返回字符串`，模型既连不上 ERP，也不能持有跨步状态。Agent 多了执行器：模型输出受 schema 约束的动作（例如 `check_stock(sku)`），运行时鉴权、限流、记审计后再去查库，把 `{qty: 3}` 追加进下一轮提示。下单必须等观察里确认有货，并且由平台——不是模型——调用 `create_order`；回执里的真实单号再进入上下文，模型才能引用。这类任务常见是 2–8 轮工具往返，而不是 1 次生成；每轮都要设最大步数、超时和敏感动作确认。边界：工具失败或库存为 0 时，应停在「未下单」并展示观察，而不是用流畅的中文补一个看起来合法的单号。日志至少记下工具名、参数哈希、观察摘要和是否产生副作用，才能把「编单号」从「API 超时被模型圆过去」里拆出来。

**后续追问：** 怎样从日志区分「模型没选工具」和「选了工具但平台没执行」？若必须在一次 HTTP 请求里对用户响应，你把循环做在服务端还是做成异步工单？没有库存工具时，系统提示里写「禁止编造单号」够不够，还是必须在输出层用规则拦截订单号格式？

**扩展问题：**
- 把「查库存」和「下单」合成一个工具，还是强制拆成两步，对幻觉单号各有什么影响？
- Agent 循环里哪一类状态必须外置（订单草稿、幂等键），哪一类可以只活在提示文本里？
- 用哪些轨迹级指标证明系统已经从「会聊天」变成「会办事」：工具调用率、副作用成功率，还是最终业务对账？

**推理回答：** 目标是产生一个真实可对账的订单，约束是模型不能直接碰生产库、也不能在无观察时报单号。先画「文本补全」和「动作-观察环」两条数据流，看单号这一字段只能从哪一侧出现。若字段只能来自 API 回执，缺执行与回写就必然幻觉。用「无观察不得出现单号」做硬门禁，再用步数和审计证明闭环真的跑过。

## AGENT-002. 眼下只有人抛出「下午有空吗」时这名日程助手才会去翻日历，产品却希望它一旦发现冲突就自行改期。从被动应答迈向主动改期之前，为何必须先落地授权范围、动作通知和一键撤销，而不是先换更强的模型？

**答：** 被动型只在用户请求或外部事件进入你的处理函数时行动，爆炸半径止于这一次答复。主动型会自己巡检状态、提议甚至改写外部系统，于是错误会在无人盯着时发生。先要有明确授权范围（可以改哪些日历、最早改到多久以后）、每次动作的可理解通知、以及一键撤销或补偿；否则自动改期就是静默破坏。模型更强只会让错误来得更流利，不会自动产生授权与撤销。生产上通常先做「主动建议、人点确认」，再对低风险动作放开自动执行。

**深入展开：** 被动循环是入站消息 → 鉴权 → 短循环工具 → 响应。主动循环还要调度器或变更通知（日历变更、时钟到达）→ 目标生成（「冲突需要处理」）→ 可能无人值守的工具调用。新增失败模式包括：时区算错导致假冲突、过度打扰、在休息时间改掉会议、与第二条主动规则互相振荡改期。授权应是能力级而不是一句总同意：只读扫描可以宽，改期要按日历、时间窗、参与者级别收窄。通知是审计的用户面：写了什么、为什么、如何撤销。撤销必须可执行：改期要留下原时段，发送要能收回或更正。人在回路回答的是「哪一步要人批」；这里比的是触发源——人唤起还是系统唤起——以及主动权带来的授权模型。评估看误触发率、未通知动作数、撤销成功率、用户事后否认的动作数。从被动切主动不要一次打开所有工具。

**后续追问：** 日历变更通知算不算已经足够的用户意图，还是仍要单独授权自动改期；主动规则之间来回振荡，怎样加冷却和仲裁；用户撤销一次之后，同一规则还该不该继续跑。

**扩展问题：**
- 把自动改期拆成三级：只提醒、建议新时间、直接改期，每一级的授权和通知怎么配？
- 哪些信号说明你该从主动执行退回主动建议？
- 主动 agent 的审计日志比被动型多记哪些字段？

**推理回答：** 从触发源改变推导风险：无人值守的副作用要求授权、可见、可逆。先做建议环，再放行窄范围自动执行。用误触发、未通知动作和撤销成功率验收，而不是用「看起来更主动」当指标。

## AGENT-003. 调研这条线已经连搜 12 趟，模型每次收工都甩「再看一篇就齐了」。模型自称做完能不能当唯一停机开关，编排层是否必须另用刚性指标收口？

**答：** 完工声明只能当软建议，不能当唯一停止开关。编排层必须同时看：成功判定（验收清单上的字段是否凑齐）、资源上限（步数、墙钟、token 或费用）、质量门（引用覆盖不够则停并标「未完成」）、安全门（下一步是高风险动作则暂停）、以及用户取消。缺硬上限的循环会在「再查一次」的话术里耗尽预算；只靠步数上限又会在已经可交卷时继续空转。正确做法是「模型提议停止，代码核对条件」。

**深入展开：** Agent 循环是：装配当前上下文 → 模型选一个动作或宣布完成 → 执行器跑工具 → 观察写回状态 → 再装配。停止是这个状态机的退出边，不是提示里的一句话。成功条件要可检验：例如至少 3 个独立来源、每条结论带文档标识、未决问题列表允许为空。步数上限按任务定（调研也许 8–15 轮，简单查询 3–5 轮），再叠加费用和墙钟。模型说完成时，用校验器对输出字段和引用跑一遍：缺字段就回灌「还缺 X」而不是退出；连续两次宣称完成仍缺字段，则带缺口终止。反过来，模型还想搜，但验收清单已满，也应强制收束，避免「完美主义」烧 token。这和「同一动作重复」的死循环检测不同：这里每轮都换一篇新材料，看起来在前进，但停止权不在模型。生产上把停止原因写成枚举（完成 / 步数用尽 / 预算 / 置信不足 / 安全门 / 用户中止），才能统计是上限太紧还是成功判定太松。

**后续追问：** 成功判定用规则清单还是再用一个评审模型，两者被自我吹捧带偏的程度差在哪；步数上限设太小会切掉哪些本来能成的任务；用户中途改了目标，旧的成功清单要不要作废。

**扩展问题：**
- 为「三人竞品调研」写下可自动检验的成功条件和三道硬上限。
- 模型输出「已完成」但引用全来自同一站点，你算完成还是算质量门失败？
- 停止原因分布里大部分是步数用尽，下一步该放宽上限还是改成功判定？

**推理回答：** 从「何时算交差」和「何时必须停损」两条退出边设计循环。模型的完成声明只触发校验，不直接停。用完成率、平均步数、超预算率和「假完成」（声称完成但校验失败）验收。

## AGENT-004. 让模型先写指摘再重跑，步数变成两倍而成功比例毫无变化。自评该在何时中止，改去挂上外置检查器？

**答：** 当失败来自“事实或工具结果不成立”，而不是“计划步骤写乱了”，开放式自评几乎只在消耗 token。自检循环是让模型对照目标、轨迹和观察写一份批评，再重跑；它能改写计划，不能创造新证据。步数翻倍而成功率不动，说明批评和原计划共享同一错误信念。这时应停掉自由文本反思，改接外部校验器：单测、schema、检索命中、规则引擎或人类抽检，只把结构化失败码回灌。

**深入展开：** 有效自检的数据流是：执行 → 外部可检验信号 → 批评必须引用该信号 → 只改被证伪的步骤。无效自检是：执行 → 模型用同一上下文写“我可能错了” → 再生成一份同样错的计划。后者在引用数字、API 是否真有副作用、证明是否闭合上特别常见，因为流畅的自我批评会被当成新证据。成本：一轮批评若 500–1500 token，再加一次完整重跑，任务费用和延迟都接近翻倍。工具已返回具体错误（404、类型不匹配）时，让模型读错误码比重写反思段落更有用；开放式“请反思推理”只适合发现漏步骤。批评应限长并结构化为 `failed_step`、`evidence_id`、`next_action`，禁止再写一遍全文。连续两轮批评给出相反归因时，应终止并升级，而不是继续聊第三轮。

**后续追问：** 校验器和生成模型同家族时，怎样避免一起编造证据？只对失败任务开自检，成功任务里“碰巧对了”的假阳性谁来抓？批评写入长期记忆后，错误经验如何过期？

**扩展问题：**
- 把自检从“每步一次”改成“仅在校验失败时一次”，token 和修复率通常怎么变？
- 外部校验只能给布尔失败、不能给反例时，模型还该不该写长批评？
- 如何用“批评是否引用了轨迹中不存在的观察”检出无效自检？

**推理回答：** 目标是提高可验证正确率，约束是每轮批评的 token 以及模型会强化自己的错误信念。把失败分成计划缺陷和证据不足，后者交给外部校验器。用步数、成功率和“批评引用真实观察的比例”验收。

## AGENT-005. 一连发出五个工具调用却忽略 Observation；另一条轨迹三轮都停在 Thought，始终没有发出 Action。ReAct 规定的交替节拍坏在哪一拍？

**答：** ReAct 要求每一步按「依据当前观察形成假设 → 发出一个可执行动作 → 等待平台回写观察」交错前进。只有 Thought，说明决策没有收成工具调用，环停在脑内独白；连打工具却不读 Observation，说明执行可能在跑，但观察没有成为下一步的条件，环变成了开环连击。断点分别在「思想到动作的落地」和「观察到下一思想的回写」。

**深入展开：** 健康轨迹在序列里长成 `Thought → Action(name, args) → Observation → Thought → …`，直到给出引用了观察的最终答案。平台必须解析 Action、校验 schema、执行、把观察追加为下一轮输入；模型自己不执行副作用。第一种断法常见于：工具目录为空或描述不可见、提示只奖励长分析、或解析器只认某种 JSON/XML，模型写成了「我接下来会查询」。第二种断法：观察被丢弃、被压成「OK」、或数十 KB 的原始 JSON 冲掉下一轮提示，模型只好按先验继续调参。生产里常把单任务动作次数限在几个到十几个，并把观察裁成数百到两三千 token 的可读摘要，避免下一 Thought 看不到关键字段。边界：允许「本步不动作、直接终答」必须有显式结束标记，否则「再想一轮」会拖长；允许并行工具时，仍要等这批观察齐了再规划下一步。

**后续追问：** Thought 要不要展示给用户，还是只进审计日志？观察保留原始 JSON 还是摘要，丢字段和丢结构各会诱发哪类断环？模型输出了 Action 但解析失败，你是重采样、把解析错误当 Observation 回写，还是直接停？

**扩展问题：**
- 怎样用状态机强制「没有新 Observation 不得再发 Action」，而不是只在提示里写交错格式？
- 同一工具同一参数连续两次出现，熔断应该打在解析层还是决策提示层？
- 评估这条环时，你更看最终答案，还是看「每个数字都能指回某条 Observation」？

**推理回答：** 把环拆成三拍，用轨迹对拍：缺 Action 就是决策没有落地，缺 Observation 回写就是执行没有进入下一条件。目标是恢复交错，而不是加更长的独白。用「每步必须消费上一条观察」做断言，定位是提示、解析器还是截断策略。

## AGENT-006. 资金划转实际发生在哪一侧？补全只是提出 refund 并带上 order_id。如果执行器没做校验就把款退了，还能说系统会用工具吗？

**答：** 钱必须由平台侧的执行器划转，不能由模型「说一声」就算退款。函数调用只是让模型在受 schema 约束的通道里提出函数名和参数；鉴权、幂等、限额、订单状态核对，以及真正的支付请求，都属于平台。绕过校验等于把补全输出当成已授权的生产指令，这不是使能 Agent，是把生成接口接到了账本上。

**深入展开：** 典型数据流：请求里带上工具定义（名称、JSON Schema、何时使用）；模型解码出结构化调用而不是最终用户文案；编排器校验类型、枚举、必填项，再检查调用方能不能退这张单、金额是否超阈值、幂等键是否见过；通过后才访问退款 API；回执变成 tool 消息写回，模型再生成对用户的说明。模型全程不应看到支付密钥，也不该拼出可直接重放的内部 URL。schema 校验失败应在很短时间内拒绝并回写错误，让模型改参，而不是去等支付网关；真正的副作用调用才走秒级超时和重试。边界：模型编造了不存在的函数名，或把 `order_id` 填成用户昵称，执行器必须当调用失败，而不是「尽量猜一个单号」；同一单被解码出两次调用时，靠幂等键合并。使能 Agent 的是「提出动作 + 观察回写」；使能安全的是环上那一层不信任模型的代码。

**后续追问：** 工具定义每轮全量下发，还是按检索只给相关几个，对选错和漏选各有什么影响？调用结果以 tool 消息写回，还是塞进普通 assistant 文本，模型后续行为差在哪？业务 API 已经成功但观察写回失败，你如何避免模型再发一次退款？

**扩展问题：**
- 把退款拆成 `preview_refund` 和 `commit_refund`，对误触发有什么帮助？
- 哪些约束该下沉到 JSON Schema，哪些必须留在执行器里用实时数据判断？
- 没有官方函数调用接口时，用文本约定再解析，和受约束解码比，失败模式差在哪？

**推理回答：** 从「钱必须可对账」出发，把模型输出降级为未授权请求。凡副作用都要经过 schema、权限、幂等，再把真实回执当观察。缺任何一环都不能称为工具使用，只能称为模型在文本里提到了函数名。

## AGENT-007. 怎样写「改配送地址」的参数、失败码和副作用注释，才不会把「查地址」那一轮做成写入？要细到什么程度才够？

**答：** 读和写必须在名字、参数和描述上无法对调，并且缺必填项时宁可调用失败，也不要靠默认值改掉生产地址。写工具应要求已核实的 `order_id`、完整地址结构、以及显式确认；描述写清「只在用户明确要求修改且新地址已完整时使用；查询请用只读工具」。错误返回要可执行，例如 `ADDRESS_INCOMPLETE`、`ORDER_NOT_FOUND`、`NOT_ELIGIBLE`，而不是「出错了」，这样下一轮会补参而不是改点更危险的工具。

**深入展开：** 先定副作用等级（改地址是难以当场回滚的履约动作），再定最小参数集（邮编不能让模型瞎填），再定禁用窗口（已发货、已妥投）。JSON Schema 用 required 和枚举卡住行政区划，自由文本只留门牌。描述既是给模型的检索文档也是策略：写「何时不要用」和「成功会立刻同步物流」比堆同义词重要。一个写工具的描述通常几十到两百 token 就够，再长会挤占其它工具的注意力；错误体应短，带上错误码、缺哪个字段、下一步建议。不要提供一个超大 `address` 字符串加一堆可选字段让模型猜；也不要让查询工具和改写工具共用极易混淆的前缀。高风险写入还可在执行器做二次确认，但这不能代替把契约写清楚——契约清楚才能降低误触发进入执行器的次数。审计记下工具名、订单号、新旧地址哈希和会话 ID，才能在改错后回放。

**后续追问：** 两个工具的描述用词大量重叠时，模型会怎么选，你用什么评测抓住？把确认做成模型可填的布尔，和做成界面上的人点按钮，安全性差在哪？错误信息如果回显了完整旧地址，会不会把证件级个人信息写进后续提示？

**扩展问题：**
- 「发货前才允许改地址」这条规则该写在工具描述里，还是只写在执行器里？
- 你如何用「用户只是想看地址」的反例集，回归误触发率？
- 工具一多、描述都写成「当用户想处理订单时使用」时，你先改名字还是先改描述？

**推理回答：** 目标是「明确要改才写库」，约束是模型会走捷径、会补全缺失字段。把读/写拆成两个不可对调的契约，用必填项和可执行错误把不确定性送回对话。用纯查询、地址不完整、已发货这三类反例验收误写入，而不是看描述写得是否客气。

## AGENT-008. 订票助理挂载的工具由 12 种膨胀到 80 种，查机票的 search_flights 与查酒店的 search_hotels 从此常被它弄反。每轮全量下发完整定义，为何反倒拖累选择？按需暴露应当依据什么来分组？

**答：** 一次请求里塞几十个近义工具，描述互相淹没，模型按表面词重叠选错是常态。应先做廉价的意图路由，只把当前阶段需要的一小撮（通常几个到十几个）放进本次函数列表；全量目录留在路由表，不进上下文。命名和职责必须互斥，靠把说明写得更长救不了重叠。

**深入展开：** 每个工具 schema 常常要几百 token，80 个就能吃掉数万 token 的前缀，判别句被挤到中间。路由可用规则（槽位：交通/住宿/支付）、小分类器，或对工具文档做检索，命中后再加载 schema。负例有效：在 `search_flights` 写明「不要用它查酒店房价」。按混淆对改名或合并，避开 `query_info`、`search_data` 这种空名字。阶段门同样重要：检索阶段不暴露下单，支付阶段不暴露搜索，既降错选也降误下单。不要指望换更大模型就能硬吞 80 个工具——上下文竞争还在。评估看工具 top-1 准确率，以及「本不该暴露却被调用」的次数。

**后续追问：** 路由自己选错阶段时，你回退到超集还是直接失败？同一工具跨两个阶段都需要时，要不要裁掉部分参数？检索式选工具召回不够，用户会看到什么？

**扩展问题：**
- 80 个工具里有 15 个属于同一套 SaaS 细粒度 API，你按厂商打包还是按用户意图打包？
- 如何用混淆矩阵决定该合并工具还是该改描述？
- 动态暴露后模型在本轮看不到支付工具，却在计划里写「下一步付款」，编排层怎样接住？

**推理回答：** 约束是上下文容量和近义混淆，目标是当前步只看见能做对的那几个工具。比较「全量 schema」和「意图路由加阶段门」，用 top-1 和越权调用验收，而不是看目录是否齐全。

## AGENT-009. 表结构在第 3 步已经被改过——规划器给出的改库计划有八步。该把计划整份推翻重做，还是仅仅修补尚未执行的步骤？

**答：** 先让执行器把第三步的观察变成规划器的新约束，而不是假装后五步还有效。若后续步骤的前提（表名、列、依赖顺序）已被破坏，整份重规划更安全；若只是某张表多了一列、后面目标与接口仍成立，可以冻结已完成步骤、只重写后缀。Plan-and-Execute 的价值是职责分离，前提是计划被当成可失效的假设，而不是剧本。

**深入展开：** 该模式先由规划器输出有序列表（每步目标、所用工具、成功标准），执行器逐步调用并回传观察。适合步骤多、需要审计和断点续跑的任务，因为人可以看计划、可以只重试第 k 步。代价是计划在发出的那一瞬就开始过时：别人迁了库、权限不够、上一步多改了字段。应外置三份东西：原计划、每步观察、当前世界状态摘要。第三步失败时，把「已成功的 1–2 步 + 失败观察」送给规划器，要求输出补丁计划而不是再讲一遍目标。八步里若每步都触发一次全量重规划，调用次数会接近逐步交错执行，还多了计划文本本身的开销；所以要设重规划次数上限（例如 2–3 次）和计划年龄（超过 N 步或若干分钟必须重评）。边界：真实依赖是图（第 4 步同时依赖 2 和 3）时，只按数组下标改「第 4 步以后」可能漏掉旁路，应按依赖切片重规划。

**后续追问：** 规划器和执行器共用一个上下文窗口，还是把计划外置成对象？执行器若发现更快路径，能不能未经规划器改顺序？计划里的成功标准是自然语言还是可执行断言，失败时谁有权宣布「该重规划」？

**扩展问题：**
- 什么任务不该先做一张完整计划，而该从第一步就交错探索？
- 如何避免重规划在「换一种措辞、步骤等价」上震荡？
- 把计划写成带依赖的 DAG，和写成编号清单，对「只重规划失效子图」哪个更友好？

**推理回答：** 目标是在世界已变时仍完成改库，约束是已完成步骤尽量不回滚、计划不能当真理。用「后续步骤的前提是否仍成立」决定全量重规划还是后缀补丁。把计划、观察、状态外置，才能在第 3 步打断而不丢失前两步的审计。

## AGENT-010. 会话前端有四套、对内 API 有十二套，新助手上线总在重写同一套适配。MCP 把 N×M 胶水里哪一层收成只需落地一次？

**答：** 收成一次的是「能力如何被发现、如何被调用、结果如何以统一形状返回」，而不是业务 API 本身。MCP（Model Context Protocol）让能力提供方做成 server，用同一种约定暴露工具、资源和提示模板；各个客户端按协议连接、列出工具、再转发调用。12 套 API 各做一次 server（或一次聚合），4 个客户端各做一次 client，不再是 4×12 套私有胶水。

**深入展开：** 没有统一协议时，每个助手都要把内部 API 翻译成自家模型厂商的函数定义、自己的鉴权头、自己的错误结构和自己的传输方式。MCP 把这段翻译下沉：server 声明名字、描述和输入 schema，并按约定执行调用；传输可以走本机标准输入输出或 HTTP 一类通道，host 负责进程寿命和权限边界。客户端拿到列表后，通常仍映射到模型的函数调用接口让模型选工具——协议不代替模型侧的选择能力。N 个 host × M 个能力从 N×M 适配降到 N+M。协议不管退款是否真成功、凭证该发给谁、server 描述会不会夹带指令；这些仍要部署侧做鉴权、审计和隔离。资源和提示模板是另外两类暴露面（可读上下文、可复用提示），不要和工具混成一个「什么都当函数」的适配器，否则又回到私有约定。

**后续追问：** 一个聚合 server 代理 12 个 API，和 12 个独立 server，运维与权限边界差在哪？新做一个第 5 个客户端时，还要不要改那 12 个 server？server 列出的工具突然增减，host 是每轮刷新列表，还是缓存到进程结束？

**扩展问题：**
- 只给一个内部助手用的 API，还值得包成 MCP，还是直接在该应用里写函数定义？
- 读一份配置文件时，用工具调用还是用资源读取，依据是什么？
- 同一 server 被桌面客户端和服务器端 Agent 同时连接，身份和审计怎么拆？

**推理回答：** 目标是消灭 N×M 胶水，约束是业务语义和安全不能交给协议幻想。先标出重复的是「发现 / 调用 / 传输」还是「扣款规则」。只把前者标准化，后者留在 server 实现和 host 策略里。用「新客户端是否几乎不用改业务代码就能列出并调用已有工具」验收。

## AGENT-011. 知识库昨天把退款时效改成 14 天，权重里仍是 7 天。用户问「退款要几天」时，怎样写系统提示、并把 tool_choice 钉死，才能禁止凭记忆作答？

**答：** 把「制度类数字必须来自检索或业务工具，禁止用训练记忆里的天数」写成硬策略，并把该问题路由到强制工具：`tool_choice` 钉死政策查询，而不是 `auto`。工具描述写明「时效以本工具为准；工具失败则声明未知，不得回退到模型记忆」。系统提示再补冲突规则：观察与直觉不一致时，观察优先。

**深入展开：** `auto` 下模型会做成本权衡：调用有延迟和失败率，凭记忆又快又顺，所以口吻像常识的「7 天」很容易赢。强制调用多一次往返（常见几百毫秒到数秒，外加检索 token），但把事实来源从权重改成当前语料。数据流：规则或分类识别「政策 / 数字 / 库存 / 余额」→ 覆盖 `tool_choice` → 执行 → 观察进入提示 → 生成时要求带政策版本或生效日。评估要同时做正例和反例：必须调用的制度题、不得调用的闲聊，同时看调用精确率/召回率和最终天数是否等于知识库。过召回会让闲聊也打检索，拉高尾延迟；欠召回正好砸在高风险数字上。边界：工具超时或空结果时，应说「查不到现行时效」，而不是「一般是 7 天」——后者把过期参数包装成产品承诺。少样本可以教边界，但高风险意图仍应用路由覆盖，因为提示服从不是每次都成立。

**后续追问：** 把知识截止日期写进系统提示，能不能代替强制工具？用户把问题改成「大概要多久呀」这种口语，规则路由会漏吗，你怎么补？强制工具之后模型观察里是 14、口头却说 7，你在哪一层做断言？

**扩展问题：**
- 怎样构造评估集，区分「该调未调」和「调了对但生成时又改回记忆」？
- 工具描述从「可以查询政策」改成「涉及时效必须先调用」，调用频率通常会怎样变，你怎么回测误伤？
- 对「首都是哪里」这种稳定常识，你如何避免策略过宽导致无意义检索？

**推理回答：** 目标是现行制度上的数字，约束是权重里有一个更流利的旧数字。先认定可接受来源只有工具观察，于是把选择权从 `auto` 收回路由。用「空观察则拒答」防止回退，用正反例同时盯调用决策和最终数字。

## AGENT-012. 发票 PDF 抽成字段写入内部表，为什么一次性的 schema 就够用？拿这些字段去发起退款，为什么必须有执行结果回写给模型的环？

**答：** 抽字段时，符合 schema 的 JSON 本身就是产品要的最终对象，应用直接落库或展示，没有「再执行外部动作、再让模型看结果」的必要。退款时，模型输出的 JSON 只是调用请求，真正的成功或失败、实退金额、渠道回执必须执行完再写回，后续才能决定对用户说什么。前者是一次性格式约束，后者是带选择、执行和回传的多轮环。

**深入展开：** 结构化输出把解码限制在 JSON Schema（或等价文法）上，适合抽取、分类、填配置：输入是发票文本，输出是 `{invoice_id, amount, currency}`，校验失败就重采样或拒收。函数调用也常靠同一套约束保证参数合法，但多了三件事：模型可以在本轮选择不调用、直接用自然语言回答；可以连续或并行点多个函数；执行发生在应用进程，模型从不跑业务代码。退款路径若只用结构化输出「假装」成工具——模型吐 `{action:"refund", order_id}` 然后请求结束——应用无法在同一次对话里把网关错误交还模型改参，也无法在「先查单再退」之间保持状态。抽取常见 1 次生成、输出几十到两百 token；退款常见 2–4 轮（查单、预览、提交、解释）。边界：若退款完全由后端工作流根据已校验字段自动发起、模型不准碰支付，那模型侧用结构化输出就够，工具环应放在工作流引擎。不要因为两者都输出 JSON 就当成一种机制。

**后续追问：** 怎样保证结构化输出一定能通过 schema：重试、受约束解码，还是失败后转规则抽取？函数参数非法时，把校验错误当观察回传和直接终态失败，对下一轮修正率有何不同？什么时候你会用结构化输出生成「工具计划」，再由确定性代码去调 API？

**扩展问题：**
- 同一条请求里先结构化抽字段、再函数调用退款，中间那份 JSON 要不要当观察写进轨迹？
- 受约束解码保证括号合法，保证不了金额等于发票；哪一层补这个语义校验？
- 模型选择「不调用任何函数」时，你如何区分「真的不需要副作用」和「该退却没退」？

**推理回答：** 看输出对象的消费者是谁。若消费者是内部库、不再需要模型看见执行结果，用一次 schema。若消费者是会失败的外部世界、且模型还要基于结果说话或改动作，就必须走调用-回传环。用「有没有观察写回」切开两种机制。

## AGENT-013. 执行器只开放了查询订单 get_order、创建工单 create_ticket。模型却要去调 cancel_order，还带上 order_id，并把 refund 设成 true。说明书加长为什么拦不住这种幻觉？未知函数名和未声明字段为何必须在执行层被拒绝？

**答：** 模型会把训练里见过的函数名、或上一轮自己编过的参数，当成当前环境里真有的工具。说明再长也只是一段可被忽略的文本。运行时必须先做名字白名单，再按 JSON Schema 拒掉未声明字段和类型错误，把失败打回模型后才允许改选或改参。没有这道门，幻觉出来的能力会变成一次真实副作用。

**深入展开：** 能力幻觉常见三种：编造未注册函数、给已有函数加 schema 没有的键、把只读工具当成能写。执行器应满足 `name ∈ catalog` 且 `args ⊨ schema`，`additionalProperties` 默认 false，枚举值不在集合内直接拒绝。不要「宽容解析」把 `refund=true` 丢掉再调用——静默丢字段会让模型以为成功。描述里写清做不到什么（「不退款、不改库存」），并删掉职责重叠的近义工具，降低模型拼接出第三种能力的动机。关键路径可以把「意图」先收成结构化对象，再由规则映射到合法工具。评估看未知名字拦截率和 schema 失败后下一轮是否改选已有工具，不是看描述字数。

**后续追问：** 模型连续两轮都编同一个不存在的函数，你是降温、换模型，还是直接结束任务？允许 extra 字段的工具会引入哪类生产事故？工具目录热更新后，旧轨迹重放遇到已下线的名字该怎么办？

**扩展问题：**
- 如何区分「编造工具」和「选了文档里还在、运行时已下线的别名」？
- 把校验错误原文回传，和只回 `invalid arguments`，哪一种更能让下一轮改对？
- 业务方坚持要一个「万能 SQL」入口时，怎样在不开放任意语句的前提下堵住能力幻觉？

**推理回答：** 失败模式是模型输出越过了已声明能力。文本约束改不了采样，执行层白名单决定副作用是否发生。先拦名字、再拦字段，然后才改描述或拆意图。用拦截计数和误杀率验收。

## AGENT-014. 填槽与选工具该在哪一层拆开？get_refund 这个名字选对了，金额槽却写成 1200、日期槽写成当天。用户说的是上周二、金额 1,200 的退款。schema 已把类型标成 number 与 date，为何仍不够？

**答：** 选对工具只说明名字匹配了意图；填槽是另一次对齐：相对日期、千分位、单位、指代都容易合法地填错。Schema 只能拦类型，拦不住「类型对、对象错」的值。应把选工具和填槽拆开，对日期、金额、ID 做规范化并对齐到用户原文的 span，高风险槽位校验失败就回传或追问一句，而不是带着错参调用。

**深入展开：** 典型错法：`1,200` 的逗号策略不一致；「上周二」依赖对话日和时区，缺省就塌成今天；「那笔」需要会话里的订单 id，模型却生成一个看起来合法的 UUID。补救：schema 写清单位、时区、格式和反例；代码层把相对日期钉成带时区的日历日，金额去千分位并校验币种；能从原文定位的数字就拷贝，不让模型重打一遍。两阶段输出 `{tool, slots, spans}`，规则通过再执行。回归集覆盖相对日期、多币种、缺省、同名客户多订单。这和「编造了一个不存在的工具」不是同一类故障：工具是真的，槽指错了。线上看「选对工具但因参数得到 4xx 或空结果」的比例。

**后续追问：** 日期有歧义时，你问用户，还是默认用业务时区的上一个周二？原文是「万元」时谁做换算？会话里有两笔 1200，你按时间、按状态还是拒绝消歧？

**扩展问题：**
- 为什么 enum 和 format 能修好状态字段，却修不好「哪一笔订单」？
- 把槽位抽取交给只输出 JSON 的小模型、主模型只负责选工具，延迟和错误率怎么权衡？
- 如何用千分位、口语日期、省略币种这类样本做发布门禁？

**推理回答：** 目标是选对工具之后参数仍指向用户说的那条实体。把失败从「能力编造」里拆出来，用规范化、span 对齐和分阶段，而不是再加一句「请仔细提取」。用错参率和追问次数验收。

## AGENT-015. CSV 共一千行，清洗后要落库。风险该怎么衡量：让它生成 Python 脚本，还是把现成变换工具串起来？

**答：** 看规则是否稳定，以及失败时你能否原样重放。去空、类型转换、按主键去重这类稳定规则，应链式调用带 schema 的变换工具：参数可校验、权限可收窄、每步可审计。规则是一次性探查、现成工具表达不了、或必须看脏数据分布时，才让代码生成路径在沙箱里写脚本。生产上常见的是混合：探查用代码，落地用工具。风险不在“会不会写代码”，而在这段变换能否被测试、限权和重放。

**深入展开：** 工具路径里模型只填 `dedupe(keys=["id"])`、`cast(col="amount", type="decimal")`，执行层做允许列表和行数上限，失败回结构化错误。代码路径是：生成脚本 → 静态扫描 → 沙箱执行 → 收集退出码和抽样输出 → 测试或人工门禁通过后才对准正式库。一千行在沙箱里通常数秒可跑完，但脚本一旦对外部地址发请求，风险就从“算错一列”变成数据出界。工具路径的典型失败是选错工具或抽错参数；代码路径是死循环、路径穿越、依赖来源不受控，以及“本地类型和正式环境不一致”。边界：没有现成工具时硬造二十个一次性接口，往往比沙箱脚本更难维护；反过来，给代码路径一张可写正式库，等于绕过全部工具级权限。评估要拆开：工具路径看参数正确率和副作用审计是否完整；代码路径看测试通过率、未授权访问次数、同一输入能否重放。

**后续追问：** 脚本还要读第二份对照表时，你开放文件系统，还是先把对照表做成工具？这套清洗下周还要用，你把脚本存成可复用包，还是固化成正式工具？两边结果不一致时，以抽样差异还是以约束违反为准？

**扩展问题：**
- 行数从约 10³ 涨到约 10⁷，沙箱内存和工具批处理哪个先爆，切分点怎么定？
- 代码路径结果正确但不可读，后续维护成本如何计入这次选型？
- 如何用“未授权网络或文件访问次数”和“变换可重放率”比较两条路径？

**推理回答：** 目标是变换正确且副作用可审计；约束是工具表达力和沙箱能力。按规则稳定性、能否重放、权限能否收窄来选型，混合优于单一教条。用审计完整性和测试门禁验收，而不是看一次输出是否“看起来干净”。

## AGENT-016. 写死的函数 schema 共 8 份、每次请求都带上。再包 MCP server 为什么仍然有独立价值？

**答：** 写死 schema 解决的是「这一次推理如何让模型选出参数」；MCP 解决的是「这些能力由谁实现、如何被多个应用发现和复用」。前者绑在单个应用、单家模型 API 的请求体上；后者把实现挪到独立 server，host 在运行时列出工具再映射成函数调用。两层叠在一起：MCP 负责集成与进程边界，函数调用负责模型侧的选择和填参。只有一个应用、工具永不外借时，可以不包；一旦第二个客户端或第二种模型 API 要复用同一批内部能力，再写一套 schema 才是重复建设。

**深入展开：** 传统函数调用的生命周期是开发期写死：代码里 8 个定义，部署后形状固定，执行闭包在该服务进程内。MCP 的生命周期是运行期发现：server 可以按用户身份列出不同工具，可以用本机进程或远程 HTTP 提供实现，与聊天服务解耦。映射发生在 host：列出工具 → 转成当前厂商的函数列表 → 模型返回调用 → host 转发给 server → 观察再变回 tool 消息。所以 MCP 不是第二种函数调用语法，而是函数调用的供给方标准化。新风险也在这一层：不可信 server 的描述可能带指令、server 进程权限可能大于聊天用户。8 个工具若只服务一个内部接口，多一跳远程调用可能只加几十毫秒却增加故障面，收益可为负；多个客户端共享时，省下的是重复实现和多套鉴权漏洞。

**后续追问：** 有了 MCP 之后，模型侧还要不要函数调用？资源、提示模板和工具分别在什么时候进入模型上下文？server 按用户列出不同工具，和在应用里用条件语句写死权限，审计责任在哪一侧？

**扩展问题：**
- 把内部工单 API 提供给多个 AI 应用，你选 MCP server 还是让每个应用直接写函数调用，理由是什么？
- 同一工具在 MCP 里叫 `create_ticket`、映射到模型函数时被改成 `open_case`，调试时你怎样保证两边名字能对上？
- 工具要热更新（新增一个必填参数）时，写死 schema 的发布路径和 MCP 动态列出的发布路径差在哪？

**推理回答：** 先分开两个问题：模型怎么提出调用，以及能力怎么被多个 host 复用。前者已经被函数调用覆盖；后者才是再包一层的理由。用「会不会出现第二个客户端或第二种请求格式」做是否包装的开关，并明确「模型仍然通过函数调用选工具」，避免把协议误认成推理能力。

## AGENT-017. 即便 MCP 的 initialize 已经走完，为何仍不可默认对端具备全部可选能力？
**答：** 协议版本兼容不等于所有可选能力都可用。以 2025-11-25 版为例，双方先协商版本和 capabilities，再按已声明能力运行；初始化完成也不代表用户已授权任何业务操作。
**深入展开：** 客户端发 initialize，服务器返回版本及能力，客户端再发 notifications/initialized。若返回版本不受客户端支持，应断开而不是猜测兼容；HTTP 后续请求应携带协商版本头。能力、具体工具发现和业务权限是三层不同检查。
**后续追问：** 服务器有 tools 能力但没有 listChanged，客户端还能列工具吗？能；后者只描述列表变化通知能力。
**扩展问题：**
- 设计跨版本兼容测试：不支持的版本、缺少能力和未知扩展分别如何处理？
- 如何记录协商版本及服务器实现版本，使协议升级问题可复现？
**推理回答：** 回答按版本兼容、能力可用、业务授权三层展开，避免把握手当作安全授权。

## AGENT-018. MCP 接口若标有 idempotentHint 或 readOnlyHint，调用方是否即可省略防护？
**答：** 不能。ToolAnnotations 是提示而非强制保证，不可信服务器提供的注解不能成为授权依据；实际权限和副作用边界必须在执行层验证。
**深入展开：** readOnlyHint 描述是否修改环境，idempotentHint 描述同参重复调用的额外影响。即使真正只读，也可能泄露敏感数据；即使业务幂等，也可能仍有审计或计费影响。工程上应结合可信服务注册、最小权限和独立策略检查。
**后续追问：** 同名工具重新连接后描述变了怎么办？可重新校验工具清单和可信配置；不要沿用旧安全判断。
**扩展问题：**
- 如何检测工具定义变更并触发重新审查？
- 只读数据查询为何仍需要租户隔离和结果范围限制？
**推理回答：** 先区分自述元数据和可执行约束，再按实际数据流与副作用决定安全策略。

## AGENT-019. 写操作执行后，承载 MCP 的 Streamable HTTP 连接断开了。把 tools/call 原样再发一遍为何是错误的恢复方式？断流就意味着请求没跑吗，重发之前先得确认什么？
**答：** 断流只说明客户端没拿到完整响应，不说明服务器没有执行。写操作应先恢复响应或查询业务状态，只有确认未执行或具备可靠幂等保障时才重试。
**深入展开：** 2025-11-25 版明确断连不应被理解为取消。服务器可提供 SSE 事件 ID，客户端可通过 GET 与 Last-Event-ID 恢复流，但恢复能力是可选的。业务幂等键、状态查询和去重属于应用设计，不能假设 JSON-RPC request id 自动提供恰好一次执行。
**后续追问：** 重连拿到原响应，是否说明操作被重新执行？不一定；消息重放和业务重执行是两件事。
**扩展问题：**
- 如何表示执行状态未知，并让用户看到可核验的进度？
- 为订单类写工具设计幂等键、过期策略和冲突参数校验。
**推理回答：** 明确区分请求发送、业务提交和响应接收三个时点，避免因通信失败产生重复副作用。

## AGENT-020. 客户端递来的访问令牌，MCP 代理为什么禁止把它原样转给下游 API？
**答：** 因为令牌具有特定受众和权限边界。MCP 服务器必须校验令牌确实签发给自身，不能把为其他服务签发的令牌当作本服务认证，或通过透传绕过隔离。
**深入展开：** 以 2025-11-25 授权规范为准，客户端在授权及令牌请求中带 resource，服务器校验 audience。代理访问下游应使用独立、适用于该下游的授权关系，而不是接受任意 bearer token。会话 ID 也不能替代身份认证。
**后续追问：** 用户同意连接一个 MCP 服务，是否等于同意该服务访问所有下游？不是；权限范围和下游授权必须明确。
**扩展问题：**
- 如何在多租户代理中防止用户凭据串用？
- 401 与 insufficient_scope 的 403 应触发怎样不同的恢复路径？
**推理回答：** 先画客户端、MCP 服务和下游 API 的信任边界，再核对每段令牌的发行者、受众和权限。

## AGENT-021. 传输层上返回了 HTTP 200，能否等同于 MCP 工具的业务已经成功？
**答：** 不能。要区分传输成功、JSON-RPC 协议成功和工具业务成功；工具执行失败可能作为正常 result 返回，并设置 isError: true。
**深入展开：** 按 2025-11-25 版，未知工具或请求结构错误属于协议错误；业务校验失败、下游 API 失败等可作为工具执行错误。错误信息应足以帮助修正参数，但不能泄露密钥。structuredContent 是服务端结果，不是模型结构化生成；有 outputSchema 时仍需验证返回数据。
**后续追问：** isError 为 true 是否表示可以原样重试？不表示；先判断失败类型和操作副作用。
**扩展问题：**
- 如何用机器可读业务错误码区分库存不足、参数错误和暂时故障？
- 结果结构正确但金额或单位错误，为什么还需要业务不变量校验？
**推理回答：** 按传输、协议、业务逐层判定，再决定恢复动作，不能把可解析 JSON 等同于业务正确。

## AGENT-022. 约半年的编程助手记忆开始召回过期仓库布局，以及用户早已推翻的缩进习惯。写入如何去重并挂 supersede 链接、读取如何按新近与置信度打分、定期如何合并，以及离线用冻结探针来看记忆是否仍可靠？

**答：** 把记忆做成带版本的事实表，而不是只追加的向量桶。写入先把命题收成稳定键（例如「该仓库的源码根路径」「该用户的缩进风格」）：同键同值就合并证据并刷新时间，同键异值就新建现行条、给旧条挂 `superseded_by` 并写下失效时刻，不要立刻物理删除。读取只投递仍有效的条目，按相似度、新近衰减和来源置信度打分；目录结构只能当检索起点，必须以当前工作区的 `list_dir` / 文件树为准。定期作业负责压短取代链、合并近重复、丢掉长期无召回的低置信推断；离线用冻结的「现行真相」探针看 top-k 里还有多少过期和互斥条目。

**深入展开：** 一次写入的数据流是：会话结束或用户说出「从现在起…」→ 抽取器吐出 `{key, value, source, ts, repo_id, confidence}` → 规范化（相对路径收到仓库根、tabs/spaces 收到同一缩进槽）→ 先按 typed key 查行存，再用同类别的高相似向量找漏网近重复。同值：`evidence_count + 1`、更新 `last_seen`，置信度只允许有上限地抬。异值：新条 `status=active`，旧条 `status=superseded`、`valid_to=now`、`superseded_by=new_id`，旧向量默认退出可检索视图。取代优于删除，是因为偏好可能再翻回来、排障要回答「三月为什么按 tabs 改的」、振荡检测需要历史；物理删除只留给用户明确说「忘掉这个」或合规要求。读路径按 `user_id + repo_id` 过滤后做并集：槽位现行值走精确键，无键的情景片段走向量；打分可用 `w_sim·cos + w_recency·exp(−Δt/τ) + w_conf·confidence`，其中布局类的 τ 用「数周」量级（目录会迁），用户亲口偏好的 τ 可以更长，但更新的明示反转应当已经把旧条标成不可检索。注入大约五到十几条，每条带 `as_of` 和「可能过期」标记；半年日用若只追加，原始抽取可以到数千条，按键合并后现行事实通常应落到几百量级，再往提示里塞会挤掉当前 diff。工作区观察与记忆冲突时，观察获胜并入队一次新写入。整理作业放在低峰（例如每日或每周）：同键近重复聚类后合并证据、长于约 3 节的取代链收成「现行值 + 一行历史」、对「非用户明示、约 90 天未召回、低置信」的推断做归档；合并后要重算嵌入。同一键在约一个月内翻转 ≥3 次，不要自动选边，标 `needs_confirm`。离线验收冻结时刻 T 的库快照，探针来自当时的真实目录和最近一次用户确认的偏好，指标看精确率@k、同一键两条现值同时进 top-k 的互斥率、指向已不存在路径的陈旧率、以及反转事件之后旧值从 top-k 消失需要几次检索——不要给「记忆段落好不好读」打分。

**后续追问：** 用户口头改成 spaces，但最近约 20 次提交仍是 tabs，现行条听哪一边、置信度怎么降；取代链是保留旧全文还是只留 diff，用户要求「忘记」时链上旧值怎样从行存、向量索引和提示缓存一起消失；整理作业误把两个仓库的路径合成一条，你用什么隔离键防止串仓。

**扩展问题：**
- 把「源码根路径」做成单一现行槽位，和做成事件日志再在每次读取时折叠，对一次偏好反转的生效延迟差在哪？
- 检索先按 typed key 取现行条、向量只用于无键片段，和全部走向量 top-k，过期互斥会差在哪一类查询上？
- 怎样构造不看文笔的离线集：故意植入过期目录和已反转偏好，只靠精确率、互斥率和反转后的失效次数验收？

**推理回答：** 目标是半年后的检索只把「现在仍成立」的约束送进提示，并且改错一条可以追溯。约束是只追加会堆出互斥事实、当场物理删除会丢掉审计和回翻、仓库布局会变而模型容易把记忆当成目录真理。因此写入按键合并或挂取代，读取只投递有效条并让工作区观察覆盖布局类记忆，整理作业压缩历史，离线用现行真相探针而不是摘要通顺度来验收。

## AGENT-023. 进程在第 40 步被杀掉，重启后只靠对话记录接着干，结果订单下了两次。权威状态该落在何处，为何聊天文本当不了工作流状态？

**答：** 对话记录是给模型看的痕迹，不是工作流的权威状态。权威状态应是可序列化的结构化对象：目标、当前节点、已执行动作的幂等键、工具结果指针、预算、人类批准。进程被杀后从最后检查点恢复，并用幂等键保证下单这类副作用至多一次。把自然语言历史当唯一状态，重启时模型会重新“决定”已经做过的动作。

**深入展开：** 状态宜分三层：工作流控制态（节点 id、重试计数、租约）；业务态（订单 id、购物车、地址）；模型可见投影（从前面两层渲染出的短上下文）。控制态带版本号做乐观锁；工具调用带 `idempotency_key = hash(task_id, step_id, payload)`，下游必须认这个键。第 40 步若已发出下单但未写回检查点，恢复只能靠下游去重，所以顺序应是先写意图、再调用、再写结果，而不是先调用再补日志。对话文本缺字段、会被模型改写、不能原子更新，也无法做前后差分审计。长文本 findings 不要内嵌进状态行，放对象存储，状态里留指针。多实例抢同一任务必须持有租约，否则两个 worker 会各下一单。向量记忆不可枚举、不可事务，不能当工作流状态。

```python
state = {
    "node": "place_order",
    "intent_written": True,
    "order_id": None,
    "idempotency_key": "t40:place_order",
    "version": 17,
}
```

**后续追问：** 检查点写在工具调用前还是后？版本冲突时重放该步还是整图回滚？用户在对话里改了地址，以对话为准还是以业务态为准？

**扩展问题：**
- 状态 schema 增加新字段后，旧检查点缺省值怎样避免再次误下单？
- 投影给模型时漏掉“已下单”标志，最典型的重复副作用是什么？
- 如何用“重复副作用次数 / 恢复次数”证明只靠对话恢复不合格？

**推理回答：** 目标是崩溃后副作用恰好一次；约束是进程会挂、模型会重写历史。把权威状态从对话中拆出，配合幂等键和有序检查点。用恢复演练和重复下单计数验收。

## AGENT-024. 本单查过的工单号、用户退款偏好、教训「上次套用了过期费率」——客服刚收工时这三样都在。各应写入哪类记忆，过期如何规定？

**答：** 退款偏好是跨会话的用户事实，写入长期语义记忆，带来源和时间，用户可改可删。本单工单号和中间查询属于工作记忆或短期会话记忆，任务一结束就该过期或降级，免得下一单串单。用错费率的过程写入情景或程序记忆：记住「这类单要先核对现行价目」，而不是把那次错误结论当事实再召回。三类必须分库或至少分键，不能共用一个「什么都往向量库里扔」的桶。

**深入展开：** 工程上常拆五层，名字可以不同，职责必须分开。工作记忆：当前目标、已调用工具、未完成步骤，寿命是这一次循环，存在编排状态机里，不必向量化。短期/会话记忆：近几轮对话原文或滑动窗口，按轮次或 token 截断。语义记忆：稳定事实与偏好（退款路径、语言），写入前要去重、带时间戳，冲突时以更新的用户确认为准。情景记忆：一次任务的经过——做了什么、哪步失败、引用了哪份政策，供「类似单怎么处理」检索，但默认不把中间数字当真理。程序记忆：可复用的做法（先查订单状态再谈退款），更接近技能或策略，而不是又一段聊天记录。写入规则比存储引擎更重要：让模型自己决定「记什么」，会把幻觉和一次性吐槽写成长效偏好；应设门槛（用户明确说「以后都这样」，或校验通过的任务摘要）。检索要带过滤：当前任务类型、时效、来源可信度，避免把三年前的费率教训当成现行规则。语义记忆里的个人信息要可导出、可删除；情景记忆里的工具原始输出不要长期明文留存。

**后续追问：** 用户说「以后默认退到工资卡」但财务政策禁止，长期记忆和策略引擎谁覆盖谁；情景记忆检索到相似失败案例，是当约束注入提示，还是只给人类客服看；工作记忆和上下文窗口是不是同一件事，检查点重启后谁负责恢复。

**扩展问题：**
- 画一张表：每类记忆的写入触发、保留期、检索查询和删除权分别是什么。
- 同一用户两通并行会话都想更新「默认地址」，如何避免后写入覆盖掉更新的确认？
- 怎样检测「错误的语义记忆」在污染后续决策，并做一次带审计的纠正？

**推理回答：** 从「跨会话还要不要、是事实还是过程、错了代价多大」三个轴给信息分类，再单独定保留和检索。先禁止共用一个无类型向量桶。验收看串单率、过期后误召回次数、以及用户更正偏好后的生效延迟。

## AGENT-025. 甲能改仓库、乙只会空转聊天，两款编程助手却接到同一权重。优先要翻开的是 harness 哪几层？

**答：** 先拆模型外面的控制面，而不是先换模型。Harness 负责把模型输出变成可执行、可验证、可停止的产品行为：工具接口（读文件、跑测试）、上下文装配（送哪些文件、截多长）、权限与审批、错误回写、以及「何时算做完」。两个产品用同一套权重却一个空转，差别几乎一定在这些层：空转的那个多半没有把工作区真相喂回去，或没有把「测试红」当成未完成。

**深入展开：** 按数据流对照。工具层：是否真的暴露了读/写/shell，schema 能否定位到仓库路径，失败时返回的是可解析的 stderr 还是一句「出错了」。上下文层：能改仓库的产品会按任务检索相关文件、截断过长 diff、保留测试输出尾部；空转的产品往往只把用户那一句话和模型自己的上一段分析拼回去，模型只好继续写「我可以帮你改」。循环层：前者用代码里的停止条件（测试通过、无新 diff、达到步数上限），后者把停止交给模型自觉。权限层：写文件若被静默拒绝，模型会以为已经改过。验收层：宣布完成前是否强制跑 lint/测试；没有这一钩子，模型会把「看起来像补丁的文本」当成交付。这些都不改权重。一次真实改仓库常见十几到几十次工具往返，同时活着的文件切片往往是数千到数万 token；缺任何一层，模型都会退回纯聊天。

**后续追问：** 你怎么用「同一提示、同一模型、只换工具执行器」的对照，证明问题在 harness 而不是权重？上下文被截断和工具根本没挂上，日志上各是什么样子？若暂时不给模型 shell，harness 还剩哪些层仍然必须有？

**扩展问题：**
- harness 的哪一层最适合做成与模型供应商无关的接口，哪一层会随模型换代失效？
- 把「跑测试」做成强制门禁，和只在系统提示里写「请记得跑测试」，对空转率的影响差在哪？
- 两个产品的轨迹格式不一致时，你怎样还能量化「同一模型在不同 harness 下的任务完成率」？

**推理回答：** 目标是定位「为什么同一权重一个能改仓库、一个不能」。约束是先不要引入新的模型变量。按工具 → 观察回写 → 上下文装配 → 停止与验收做消去：哪一层断了，模型就只能说话。用对照实验把差异钉在控制面上，再决定修哪一层。

## AGENT-026. 迭代预算怎样从累计成功对轮次的曲线读出来？何时该把本轮快照滚回去并重置窗口？自主改仓库的外层循环要写成带契约的尝试：一轮要冻结什么输入、必须交出什么工件、验证门怎么排？

**答：** 外层迭代是一次带契约的尝试，不是模型再聊一句。一轮开始时冻结任务说明、起始提交和工作区快照，并只注入上一轮的结构化验证报告；一轮结束必须交出补丁（或显式空操作原因）以及要跑的验证命令，缺件就不得收轮。编排层按顺序跑编译 / 针对失败用例的单测 / 更宽的回归：门全绿才能宣布完成；比开局更差（原来能编过、现在编不过，或红灯变多）就回滚到本轮检查点，把报告留给下一轮。窗口在轮边界上选择：材料仍够用就续跑，token 顶到预算就压成契约字段，假设已被证伪或刚回滚就重置上下文、只带着契约重开。预算来自冻结题集上「累计成功对迭代次数」的曲线，找边际成功已经掉下去的拐点，而不是拍一个和任务无关的最大步数。

**深入展开：** 把内层的读文件、改文件、跑命令，和外层的「一次尝试」切开。一轮契约可以收成：输入是不可改的 `task_spec`（目标、禁区、初始失败测试）、`start_ref`（git sha 或工作区快照）、上一轮 `verify_report`（测试名、退出码、失败栈尾，不是一段聊天），外加本轮假设所需的文件切片；必交工件是 `patch` 或 `noop_reason`、一句话 `hypothesis`、以及 `verify_cmds[]`。模型可以在轮内走许多工具步，但编排器只在契约字段齐全时才关轮并进入门禁。门禁由代码执行、按失败快速退出：先语法/编译，再跑任务点名的测试，最后才是更贵的回归。全绿则成功退出，即使预算还剩；针对测试已绿、回归还没跑，应再开一轮而不是提前交差；工作区比 `start_ref` 更坏则硬回滚，新树只有在门禁不退化时才晋升为下一轮的起点。检查点是工作区真相：轮初记录提交或文件哈希，回滚用 `reset` / 快照恢复，不要靠对话里的「我撤销了」。未跟踪的生成物、虚拟环境和二进制要另做快照或钉死环境，否则回滚 git 仍会读到脏产物。轮边界上的窗口策略也要写成规则：验证有改善且窗口例如还在约 70% 以下就续跑；窗口高但同一假设仍成立，就把工具原文折成「任务说明 + 最新报告 + diffstat + 近几轮」；假设已被门禁证伪或刚刚回滚，则新开上下文，种子只有契约字段，避免把已抛弃的文件版本继续喂给模型。这和提示压缩丢硬约束不是同一层问题：这里决定的是「下一轮从哪份状态启动」。预算用离线曲线而不是现场手感：在冻结题集上把最大轮次设成 1、2、4、8、16 这类档，画到第 k 轮时累计全绿的比例。示意形状是前几轮升得快，之后变平——再加轮次买的是尾巴任务，单价按 token 算往往更高，因为一轮外层循环常常要消耗数千到数万 token 的内层往返。预算放在拐点附近（例如多数增量出现在第 4–6 轮、第 8 轮以后几乎走平，就封顶在 8），并允许按题型分档；不要用「再试会不会更好」的口头理由突破拐点。

**后续追问：** 门禁只跑了任务自带的三个单测就变绿，回归套件还没跑，你算完成还是必须再开一轮；回滚时未跟踪的生成文件和虚拟环境怎么处理，才不会让下一轮读到脏产物；曲线在第 12 轮还有一条很长的尾巴，你是给所有任务加预算，还是只给「前 8 轮已有部分门变绿」的任务加时？

**扩展问题：**
- 把验证报告做成结构化字段（失败测试名、退出码、关键栈尾），和把整段日志塞进下一轮提示，对「重置窗口后还能续做」各有什么影响？
- 检查点按 git commit、按工作区归档，还是按文件哈希清单，二进制和大目录各会漏掉什么？
- 如何用同一冻结题集画出「累计成功」和「平均 token」两条轴，证明拐点之后加轮次是在买尾巴而不是在买中位数？

**推理回答：** 目标是把「再试一轮」收成可验收、可回滚、可计量的控制面。约束是对话文本不能当仓库真相、失败假设会污染窗口、改坏的工作区必须能回到本轮起点、固定步数分不清「还该试」和「已经进入收益递减」。所以先写死每轮输入与必交工件，用代码跑验证门决定留下还是回滚，在轮边界选择续跑、压缩或重置，再用题集上的成功–轮次曲线读预算。验收看门禁通过率、回滚后工作区是否回到起始哈希，以及拐点之后每多一轮换来的成功增量。

## AGENT-027. 在 LangChain 中，聊天模型前面接提示模板、后面接一个负责解析输出的组件，三者合成一条 Runnable。末端一旦报出格式错，为何比自己手写循环更难定位数据是在哪一步走样的？链真正统一的是什么，又有哪些控制流应当移出链外？

**答：** LCEL 把组件收成统一的 Runnable，共用 `invoke` / `stream` / `batch` / `ainvoke`，上一步的输出对象直接成为下一步输入。换模型供应商、拼检索加生成会很快，但中间类型被管道约定藏住，格式错误常在末端才爆，栈上是框架包装而不是业务行号。分支、回环、持久状态和人工暂停不属于线性链，应走到图或自己写循环。

**深入展开：** 一条常见问答链是检索器 → 拼上下文 → 提示模板 → 模型 → 解析器；Agent 模式则是模型按工具描述选函数，框架执行后再把观察接回。抽象税是：加载器、切分器、向量库层层封装，升级时接口易变；排障要靠把每个 Runnable 的入参出参打到追踪里，不能只看最终字符串。适合稳定的线性编排和多供应商适配；不适合中途改状态机、按工具结果回环、精确控制重试预算——硬套链会变成回调套回调。和自己写几十行调用相比，框架赢在适配器广度，输在定位时间。换供应商真正省下的是消息格式和流式适配，提示与解析仍要测。

**后续追问：** Runnable 边界上 dict 和聊天消息谁负责转换？流式还没凑齐完整 JSON 时，解析器怎样避免半截失败？什么情况下你把这套框架只当模型适配层，编排自己写？

**扩展问题：**
- 同一条链既要批量又要单条低延迟，`batch` 和 `stream` 怎样拆，才不会为吞吐牺牲首字时间？
- 解析失败重试包在链内还是链外？怎样防止重试打爆下游工具？
- 你准备在追踪里打哪三个字段，用来证明错误发生在检索拼装而不是模型？

**推理回答：** 目标是复用适配器且能定位变形点。先承认 Runnable 统一了调用面，再指出线性管道把状态藏起来；一出现环和暂停就离开链。用能否在中间探针看到结构化中间态来验收。

## AGENT-028. 这季度口袋只够做一项：上更大的模型，或把文件 I/O 和测试回环推倒重来。对照实验该怎么做，才能把钱的去向拍板？

**答：** 用同一批冻结的编程任务做交叉对照：固定 harness 换模型，以及固定模型换 harness，看失败主要落在哪一类。若失败是补丁语义错、测例不会写、跨文件推理断，钱应倾向模型；若失败是没读到关键文件、工具输出被截断、同一条错误命令空转、没跑测试就宣布完成，钱应倾向 harness。不要用演示手感代替这组对照。

**深入展开：** 先给现有轨迹打失败标签，而不是看平均分。标签可以分成：上下文缺失（关键符号未进提示）、工具契约失败（参数非法、权限拒绝、输出截断）、循环失控（重复动作、无停止）、验证缺失（未跑测试）、推理不足（材料齐了仍然改错）。若前四类合计远高于最后一类，换大模型常常只是把错误写得更流畅。实验：准备带仓库快照和验收命令的任务集；A 组只换模型 ID，B 组只换「检索哪些文件 / 截断策略 / 强制测试 / 重复动作熔断」。看通过率、平均工具步数、未经验证就停止的比例。若当前平均 20 步里有 8 步在重复 `ls` 或读同一文件，换模型很少能消灭这种环，改循环策略会立刻降步数。边界：模型弱到经常吐出非法调用格式或拒绝按 schema 调工具时，harness 再好也走不动，应先过「工具调用格式稳定」的门槛再谈对照。

**后续追问：** 任务集只有十道演示题，对照结论会怎样偏？同一条轨迹能否同时打上「推理不足」和「上下文缺失」，你怎么避免双计？模型升级后，harness 里哪些为旧模型写的补偿逻辑应该删掉再测一遍？

**扩展问题：**
- 如果只能改 harness 的一个子系统，你按失败标签会先改上下文装配还是先改测试门禁？
- 怎样设计任务集，才能把「模型不会修并发缺陷」和「harness 没把测试日志喂回去」拆开？
- 大模型更贵、更好的 harness 步数更少，你用「每通过一题的费用」还是「通过率」做决策？

**推理回答：** 目标是把有限预算投到当前失败的主因层。先给失败打「模型上限」对「控制面缺陷」的标签，再用「只动一层」的交叉实验验证。哪一层移动通过率更大、且能解释原失败模式，就把钱放哪一层。证据不足时先修 harness：它可回滚、与供应商解耦，也能让下一轮模型对照变得可测。

## AGENT-029. 季度报告该按什么章节排、哪些口径不能写，为何做成需要时才加载的说明包，而不是再注册一个工具函数？技能描述过宽或过窄时，会分别怎样选错？

**答：** 工具给的是能调用的能力（拉数、渲染文档）；技能给的是「这件事在本公司怎么做」的流程知识（章节顺序、口径、禁写项）。后者主要是文档、模板和少量脚本，平时只把名称和一两句触发说明放进窗口，匹配到任务才加载正文，这是渐进式披露。做成工具会迫使你为每条文案规则开函数，还占满工具列表；做成技能则便于版本化和审阅，且不占满上下文。描述太宽，不相关任务也会加载；太窄，真正的季度报告反而匹配不上。

**深入展开：** 典型包装是一个目录：清单文件（名称、描述、可选触发条件）、正文步骤、模板或示例、以及确定性脚本（例如按规定顺序拼章节）。路由只看短描述，所以描述要写清适用与不适用（「用于法定季度经营报告，不用于营销周报」）。加载后模型按步骤做，能脚本化的计算不要临场口算。函数调用或协议化工具暴露动作与权限边界；技能教何时用哪些动作、中间产物长什么样。长期记忆是用户或任务事实；技能是组织级玩法，走评审和发布，不按用户闲聊写入。第三方技能等价于可执行说明书，可能夹带危险步骤，要来源允许名单、权限收窄、脚本进沙箱。评估一个技能：在目标任务上少问澄清、格式合规率上升、无关任务的误触发率低。

**后续追问：** 技能正文很长时，是一次读完还是再按小标题二次披露；技能指定的脚本失败，模型能不能绕过脚本手写一份「看起来像」的报告；同一任务匹配到两个技能，冲突时谁优先。

**扩展问题：**
- 为季度报告列目录：哪些放清单描述、哪些放正文、哪些必须是脚本。
- 如何用一组「应触发 / 不应触发」的任务标题评测描述质量？
- 技能里引用的内部模板含有过期口径，发布流程怎样拦住？

**推理回答：** 先分清「动作入口」和「做法知识」。做法多、动作少就用技能加按需加载。描述按路由精度来写。用误触发率、格式合规率和技能加载所耗 token 验收。

## AGENT-030. 合法顺序事先已知：先拉政策、再写回信、过合规、等人批、最后发出。为何先画状态图并配上条件边，而不是让模型在自由循环里自己排步骤？

**答：** 这个流程的合法顺序和门禁是事先知道的：没检索不能起草，检查不通过不能进人批，没人批不能发送。图把步骤收成节点、把允许的转移收成边，结构化状态在边上流动；条件边和人工节点由代码执行，不靠模型记得规矩。自由循环适合步骤无法预知的开放探索。把已有门禁交给模型排程，等于把合规变成软提示，漏检和跳步会变成静默事故。

**深入展开：** 图的构件是节点（模型调用、工具、纯函数）、有向边、条件边（检查通过则进人批，否则回到修改）、环、并行分支（多条政策同时检索）、检查点（每节点后可序列化状态）和人工节点（阻塞待批）。状态应是字段：检索片段标识、草稿文本、违规列表、审批人、发送回执，而不是一段越写越长的聊天。失败与重试挂在节点策略上：检索超时可重试，发送要幂等键，审批拒绝走另一条边。可审计性是选型关键：合规要能回答「这条发送经过了检查节点吗」，图的执行轨迹天然是证据；自由循环只能事后从工具日志反推，且模型可能跳过检查工具。图变僵的信号：每条新业务都要加一簇条件边、状态字段爆炸，或大量工作其实是开放式排障。那时应把开放子段嵌进某个节点（节点内部可以是短循环），而不是整图改成完全自由。框架只是实现手段，核心是显式状态和显式转移。

**后续追问：** 检查节点该用规则、第二个模型，还是两者串联，漏检和误拦怎么折中；并行检索的两个节点写同一状态字段，如何避免覆盖；检查点恢复时，已经发送成功的边为什么不能重放。

**扩展问题：**
- 画出上述五步的节点、条件边、环和检查点，标出哪几个节点禁止模型跳过。
- 开放式「先搞清楚用户到底要退多少」适合放在图的哪个节点内部，而不是拆成十个预定义节点？
- 图执行日志怎样才能同时服务调试和合规取证？

**推理回答：** 目标是门禁不可跳、状态可审计。约束是流程已知、发送不可逆。能预先画出合法转移就用图；画不出来的探索段才留给自由循环。用跳步率、审批遗漏次数和按节点的成功率验收。

## AGENT-031. 某个工单流程分四步：检索、起草、等人审批、发送，而审批可能拖到两小时后。为什么要建成带状态、有条件边的图，而非在链尾再续一环？审批人离开期间，检查点到底把什么写进了存储？

**答：** 这条流程有环（审回要重写）、有跨进程等待、有必须可恢复的状态。图把工单 id、检索片段、草稿、审批决定显式放进 state，节点读状态、调模型或工具、返回增量，条件边按审批结果走向发送或退回。检查点在节点后把快照和游标落到存储，人离开时进程可以退出，恢复后从快照接着跑，而不是指望内存里的一条链还活着。

**深入展开：** 线性链假设一次调用跑完；人工边可能跨过部署和进程重启。图用 reducer 合并对同一字段的更新：消息列表追加、草稿覆盖、审计只增不改。编译后的图可以含环，用来表达「再调一次工具 / 再改一稿」。检查点存的是状态快照加当前节点，不是重放全部生成 token。生产能力包括中断等待、把状态拨回发送前做时间旅行调试、子图拆多角色、流式吐中间节点。和手写 while 比，代价是要设计状态模式和 reducer，收益是恢复、审计和可视化。失败模式：无界追加整段对话让快照膨胀；两节点并发写同一键且无 reducer 会丢更新。人审字段必须不能被模型节点随意覆盖。

**后续追问：** 「草稿」和「审计日志」的 reducer 为什么必须一个覆盖、一个追加？检查点放对象存储还是数据库，恢复时怎样防止未完成的发送被重放？图和手写循环在单测里分别 mock 什么？

**扩展问题：**
- 画出该工单图的节点和条件边，标出可中断边。
- 发送节点已经产生副作用、检查点却写失败，恢复策略是什么？
- 状态里同时留检索原文和摘要时，怎样避免长期工单的快照涨到数 MB？

**推理回答：** 约束是等待跨进程、流程有环、发送不可丢。线性链活在一次调用里，图加检查点把状态外置。用「进程杀掉后能否从审批节点恢复且不重发」验收。

## AGENT-032. 抽条款、标风险、写对外回复都压在同一份合同上。拆成三个角色，还是做一个配了三套工具的 Agent？凭什么取舍？

**答：** 先看三件事是否共享同一份必须一致的上下文，以及失败时责任能不能落在一条轨迹上。条款、风险、回复如果互相改写同一处结论（同一条免责声明既要抽对、又要标风险、又要写进客户信），单 Agent 更合适：一个窗口里顺序做完，避免三人各持一段摘要。只有当某段工作会撑爆窗口，或必须隔离权限（抽取只读原文、回复不能见内部评分）时才拆角色，并给每个角色书面的输入输出契约。

**深入展开：** 单 Agent 控制面简单：一个策略、一套工具、一段可重放轨迹。代价是提示里同时塞抽取 schema、风险尺度和话术规范，工具一多就选错，长合同占满窗口后回复质量掉。多角色把工作切开：抽取器只吐结构化条款，评审器只打标签，撰稿器只拿「对外可说的子集」写信。收益是上下文和权限隔离、可并行；代价是每次交接都要序列化，摘要会丢掉但书，三人结论可能对不上，token 近似按角色倍数涨。一份二十页左右的合同已是数万 token 量级，三个角色各读全文就接近三倍预填充；若交接只传表格化条款，撰稿器可能丢掉「例外写在下一款」。判断先问：有没有单一事实来源？交接损失是否可接受？合规是否禁止撰稿器看见内部风险分？这些问题都不成立时，不要为了架构图拆人。

**后续追问：** 三个角色共用一个模型、只换提示，算多 Agent，还是单 Agent 的多阶段流水线？抽取错了，风险和回复会不会一起错，校验放在交接处还是只放最后？并行三个角色时，用什么字段对齐，避免信里的条款号和抽取表不一致？

**扩展问题：**
- 把「抽取 → 标注 → 回复」做成同一 Agent 内的固定三阶段，和做成三个可对话角色，调试和一致性各差在哪？
- 何时应该让撰稿器完全看不见风险分数，只看见批准后的对外要点？
- 你用什么指标决定继续加角色已经得不偿失：交接不一致率、延迟，还是每份合同的 token？

**推理回答：** 目标是三份输出彼此不矛盾，约束是窗口、权限和交接损耗。先假设单决策中心，只有窗口或权限成为硬瓶颈再拆。拆之前先写契约：传什么、不传什么、以谁为准。用条款号对齐率和一次重放能否定位错误来验收，而不是用角色是否齐全当理由。

## AGENT-033. 把一次出行排出来，需要订票、签证、预算三路配合。口语对聊、协调者派结构化任务单、一块共享黑板，这三种接法该看哪类故障来定组网？

**答：** 默认走带契约的星型：协调者拆任务、收结构化回包、负责冲突（预算超了就打回订票）。点对点口语在三方之间最容易循环对话和口径漂移。黑板适合多方都要读同一份「当前行程草稿」，但必须有字段级锁或单写者，否则机位和预算会互相覆盖。选型看故障：消息爆炸和责任不清就加协调者；共享草稿争用就黑板加版本；只需一次性委托时，甚至不要对等通信，用子执行体回包即可。

**深入展开：** 常见拓扑里，点对点延迟低，但路径数随参与者近似平方增长，缺少全局视图。集中式里协调者持有目标和预算，消息是任务单（目标、约束、截止、回包 schema），执行体不互谈。广播把状态变更发给所有人，简单但噪声大。共享存储把行程对象当成单一事实来源，通信变成「谁在何时改了哪个字段」。消息至少含发送者、接收者或主题、类型（请求 / 结果 / 错误 / 取消）、相关标识和载荷；载荷用字段而不是散文，便于校验和重试。跨系统还可以做能力发现和任务生命周期，但生产里先把契约和幂等做对。风险包括：执行体之间的文本把不可信网页摘要转述成指令、循环点名对方、重复下单。实践是只传必要字段、入站校验、对话轮次上限、全量消息日志。编排回答「谁拍板」；这里回答「字节怎么移动、拓扑怎么选」。

**后续追问：** 预算执行体发现超支，是改黑板上的上限，还是只回错误让协调者重规划；来自另一执行体的消息要不要当不可信输入做隔离；点对点加一个「最多往返两次」的硬顶，还值不值得保留点对点。

**扩展问题：**
- 给这三个执行体写一份最小消息 schema，包含如何表示「拒单」和「部分成功」。
- 黑板字段被两个写者同时更新，版本号或单写者你怎么选？
- 如何用消息日志复盘「为什么订了超预算的票」，而不是只看最终行程？

**推理回答：** 从「谁拥有全局约束、谁允许写共享草稿、失败时谁负责收回」推导拓扑。约束冲突多就集中；共享工件多就黑板加版本；委托一次性就不要对等闲聊。用消息数、冲突回滚次数和重复下单率验收。

## AGENT-034. 几万文件里要揪出竞态。主窗口该不该自己逛目录、通读全文，还是把范围收窄后交给子执行体？

**答：** 中间产物（目录列表、文件原文、搜索命中）会迅速挤占主窗口、且子任务的工具集可以收窄时，应该派生。主循环只下发目标、硬约束和验收标准；子执行体在独立上下文里工作，只回传精炼结论（可疑路径、关键片段、未决问题）。主窗口还要做跨文件推理或最终改写时，再按需把必要原文拉回来，而不是把探索轨迹整段留下。

**深入展开：** 子执行体是主循环派生的短生命周期工作者：自己的提示、自己的工具白名单、自己的 token 预算，结束后上下文通常丢弃。数据流是：主状态里的任务书 → 子循环（观察→工具→再观察）→ 结构化回包 → 写回主状态。数量级很具体：一次搜索加读文件很容易吐出数万 token；主窗口若大约 128K（以常见长窗口为例如），三四轮探索就会把系统规则和用户约束挤到注意力边缘。互不依赖的「找测试」「找锁」「找调用方」还可以并行。代价同样具体：子执行体看不见主对话里的隐式约束（例如「不要动迁移脚本」），任务书必须写全；摘要会丢行号或边界条件；总 token 往往比单窗口更高，换的是主窗口不被污染。这和多个对等角色长期协商不是同一结构：这里是树状委托，最终写入权仍在主循环。不要派生的信号：子任务和主任务共享同一份正在编辑的缓冲区、必须逐步对齐同一套符号表，或往返摘要的失真成本高于窗口膨胀。

**后续追问：** 任务书最少要包含哪些字段，才不会让只读探索子执行体越权改文件；回包该用固定 schema 还是自由段落，丢失行号时主循环如何补救；子执行体失败是在子侧重试、换工具集，还是升级回主循环自己读。

**扩展问题：**
- 设计一个「只读定位竞态」的子执行体：工具清单、权限、回包字段和超时你怎么定？
- 两个子执行体对同一锁文件给出相反结论，主循环按什么规则调和，而不是再开第三个？
- 在什么规模（文件数、平均文件 token、并行度）下，派生的总账单会反而高于单窗口？

**推理回答：** 目标是保住主窗口里的目标与约束，同时把探索噪声隔离出去。约束是上下文上限、权限分离和摘要失真。先看中间产物是否必须进入最终决策；不必则派生并契约化回包。用主窗口占用 token、子任务一次成功率、因摘要丢失导致的返工次数验收。

## AGENT-035. CI 已经变绿、功能却回退，评审与执行两个 Agent 还在互相覆盖对方的补丁。凭哪些信号该把它们折回成一个 Agent？

**答：** 当两个 Agent 没有共享同一份可变工作区真相、又都有权改同一批文件时，多 Agent 会把「评审意见」和「实现」变成来回覆盖。若已经出现循环改写、结论对不齐、归因要读两份互斥轨迹、延迟或费用接近单 Agent 的数倍，而任务步骤强耦合（同一模块的接口与测试必须一起改），就应拆回单 Agent：一个上下文里改、测、再改。这类失效的根因往往是协调，不是某个角色不够聪明。

**深入展开：** 典型崩溃链：执行者提交 diff → 评审者基于过期摘要反对 → 执行者按反对意见改掉关键修复 → 评审者看到测试绿（断言太弱或测的是另一条路径）→ 合并。中间还可能互相等待或重复检索同一文件。单 Agent 更合适的信号：需要整库一致的心智模型、子任务无法独立验收、对延迟敏感、或写不出不丢约束的交接说明。多 Agent 仍值得留的信号：子任务可独立跑、必须权限隔离（只读审计对写入）、或单窗口已经装不下探索过程。做法是先把单 Agent 的工具和上下文做到极限，再为明确瓶颈拆人。拆回时把评审改成同一轨迹里的检查清单或确定性检查，而不是另一个有写入权的对话者。一对互相改写的 Agent 很容易把步数和 token 打到原先的数倍，却不提高可合并性。

**后续追问：** 「CI 绿」为什么不能当多 Agent 成功的充分条件？主从式、只回摘要的子任务执行，和这种对等互改，结构上差在哪？你怎样量化「交接信息损失」，而不是只看主观是否乱？

**扩展问题：**
- 从多 Agent 改回单 Agent 时，哪一条信号对你是一票否决？
- 如何防止评审意见里的错误假设被执行者当成新需求？
- 若必须保留两个角色，怎样把写入权收口到一个 Agent，让另一个只能发表不能落地的评论？

**推理回答：** 目标是功能不回退且改动能归因。对等写入加上上下文分裂时，协调税已经高于并行收益。用耦合度、交接损失、重复工作和费用倍数做阈值，超过就合并控制面。默认不要给第二个 Agent 写仓库的权限。

## AGENT-036. LLM 当调度器，下面挂三个专家。必须画成确定性图的是哪些边，何种下一跳可以让模型挑？

**答：** 安全、补偿、配额和“失败后必须发生的交接”写成确定性图边；只有候选下一跳集合已经收窄、且选择不扩大权限时，才让调度器模型挑。调度器擅长在含糊目标里选专家，不擅长当事务协调者。把重试、超时、取消交给模型“决定”，会出现漏补偿和双写。

**深入展开：** 应写成死边的包括：鉴权失败 → 拒绝；写操作失败 → 补偿节点；预算耗尽 → 停止；专家返回唯一合法后继 → 直跳。可交给模型的包括：在 `{research, code, write}` 中按任务描述选一个；在有上界的“是否再检索一轮”上选继续或停止。实现上用图引擎包住模型调用：节点是带 schema 的纯函数，边带条件，禁止模型输出任意名字再动态调用。编排器持有权威状态，专家只收投影、只回结构化结果，避免专家之间自由对话把协议聊散。调度器若能当场注册新工具，等于绕过图上的权限边，必须禁止。模型选边失败要有默认边，不能空转。每条边的触发原因要打标（规则或模型），否则无法调参。这和多 Agent 自由讨论不同：编排要的是可重试、可取消、可恢复的控制流。

**后续追问：** 专家超时后，补偿死边和“换一个专家”的模型边谁优先？调度器输出了图里不存在的节点名，你重采样还是直接失败？业务规则放规则引擎还是写死在代码里？

**扩展问题：**
- 把调度器从 LLM 换成分类器后，哪些含糊任务会立刻选错专家？
- 两个专家都要写同一份业务状态，编排器如何避免最后写获胜？
- 如何用“非法下一跳次数”和“漏补偿次数”证明事务边不该交给模型？

**推理回答：** 目标是专家能协作且控制流可恢复；约束是模型会漏步骤、会发明节点。按“这条失败能不能接受”划分死边和模型边。用非法跳转和补偿完整性验收。

## AGENT-037. orders 列名可见，压测行仍被算进 GMV。为何不用系统提示，而用 OKF 那种靠链接串起来的说明文件记口径？文件如何互指才能走通？

**答：** 列名没有业务含义，口径散落在熟人口头、旧文档和 SQL 注释里；塞进提示会过期、不可 diff、也不能给别的 Agent 复用。OKF 这类开放知识格式把每个概念写成普通 Markdown（路径即标识），用文内链接连成可遍历的图，只记录含义不存数据行。提示里只留「先读这包知识再写查询」，口径随仓库发版。

**深入展开：** 一包就是一个目录；每个文件顶部用少量 YAML——例如必须有类型，可选标题、描述、对应表或字段、标签——正文写判定规则、反例和度量口径。Agent 从入口文件或按资源名检索，沿链接走到 GMV、测试单、退款行等概念。它和工具连接、技能说明书互补：连接器说明怎么查表，技能说明分析步骤，知识包说明数字该怎么认。口径变更走评审；CI 可用样例行断言「按该文件过滤后压测单不进 GMV」。不要把抽出来的数据快照写进知识包，否则又变成第二份数仓。提示里塞几千 token 口径当时能管用，多表、多 Agent、多环境会立刻分叉。字段名以你采用的规范为准，把知识包当可版本管理的口径源，而不是当某一天某份宣传稿的副本。

**后续追问：** Agent 读到两份互相矛盾的口径，以路径优先级、时间戳还是直接失败？文件里的字段已改名、表还在，怎样防止生成必败查询？人和 Agent 谁有权改口径，评审怎样强制带反例？

**扩展问题：**
- 为 `orders` 写一份 GMV 说明，正文至少要覆盖压测单、退款负行、内部转账中的哪些反例？
- 知识包、工具连接和技能文件在一次「季度 GMV」任务里分别在哪一步被读入？
- 如何检测知识文件仍在描述已删除的列？

**推理回答：** 目标是口径可共享、可评审、不进过期提示。比较「系统提示里的口头规则」和「链接起来的版本化说明文件」，强调只存含义。用「压测单是否还进 GMV」和文件 diff 验收。

## AGENT-038. 生成权重为何不能充当安全边界？给办公室里的 agent 列威胁：提示注入、失控循环、数据外带、工具越权、误操作。哪些必须在执行器强制，哪些可以先写成策略提示？

**答：** 凡是有副作用或能碰到敏感数据的，必须在执行器强制：最小权限、工具允许名单、沙箱、不可逆动作的确认门、步数和费用上限、出站网络控制、完整审计。策略提示可以降低误操作和轻度注入的发生率，但只能当辅助。生成权重不是安全边界：提示被覆盖或模型选错工具时，生成层没有强制拒绝；拒绝必须发生在调用工具之前的策略引擎。

**深入展开：** 按损失来排控制。越权：凭证按任务签发，文件系统和接口范围收窄，拒绝规则比「请不要读人事目录」可靠。注入：不可信文本当数据，不进指令通道；总原则在这里立住，针对读信读网页再堵外泄通道。外带：默认无外发，目标允许名单，禁止把内部字段拼进查询串。误操作：删除、付款、群发要二次确认或双人，幂等键防止重复。失控循环：硬上限加重复动作检测，避免刷写外部接口。第三方工具描述和说明包视为不可信代码。对抗字符串可以改变下一 token 分布，使模型输出「看起来合规」的调用；若执行器只信模型，调用就会出去。所以策略引擎根据身份、资源、动作风险做允许、需批或拒绝，模型只提出候选。每笔调用带行动者、策略决定、资源标识。缓解要可测：越权探针、注入探针、外带探针应进回归，而不是上线后等客诉。

**后续追问：** 只读探索和写入生产共用一个身份时，你拆凭证还是拆执行体；确认门太多导致用户盲点批准，怎样按风险分级；审计日志要留多久才能事后追责。

**扩展问题：**
- 列一张「威胁 → 模型外控制 → 若控制失效的爆炸半径」表。
- 哪些误操作可以先靠提示降低，但你仍会留下执行器拦截？
- 如何用定期对抗测试证明「模型说已拒绝」和「执行器未收到调用」不是一回事？

**推理回答：** 从爆炸半径倒推控制点：能出网、能改数据、能循环的，全部放执行器。提示只处理剩余的软错误。用探针命中率和越权事件数验收，不把模型自述当证据。

## AGENT-039. 合法 schema 里填出带破坏性副作用的参数，尽管模型刚答应只读。护栏放在提示词、工具面还是执行器？

**答：** 提示里的“只读”只是软约束，模型仍可在合法 schema 里填出带副作用的参数，例如把过滤条件写成删除谓词、把导出目标写成外网地址。必须在工具层收窄能力：只暴露只读方法、参数用允许列表、读写拆成两个工具；并在执行层用独立策略引擎按身份、动作、资源三元组拦截。三层都要有，强制力从提示到执行递增；任何一层单独宣称安全都不成立。

**深入展开：** 提示层写禁止项、对输出做安全分类，成本低，绕过也便宜。工具层不要把 `search` 和 `delete` 挂在同一后端；只读走副本；表名、列名、最大行数用允许列表；`dry_run` 与真实执行必须是两个工具名。执行层的策略决策点不读自然语言，只读结构化请求 `{actor, action, resource, fields}`，对照策略，放行前后各写审计。量级示意：分类器假阴性哪怕只有几个百分点，每天一万次工具调用也会漏出数百次，所以分类器不能当唯一闸门。边界：破坏性意图藏进 SQL 注释或 JSON 附加字段时，提示层看不见，执行层要么解析语句，要么根本不提供任意查询工具。不可逆动作即使策略通过，仍要同步人工批准。护栏误拦会诱使模型改走更宽的旁路（例如用代码执行去绕过被禁的删除接口），因此被拒能力必须在所有执行入口同时关闭。

**后续追问：** 只读副本延迟约 5 分钟，用户要“刚写下的订单”，你放行主库读还是拒绝？策略引擎和模型谁先看到请求？输出过滤器拦得住已经执行完的删除吗？

**扩展问题：**
- 工具 schema 里留了 `raw_query` 字符串字段，其他层护栏还剩多少强制力？
- 同一身份经工具注册通道拿到新写接口，执行策略未同步发布，缺口出在哪一步？
- 如何用“策略拦截次数 / 模型自报只读次数”证明提示层正在被绕过？

**推理回答：** 目标是破坏性副作用在执行前被拦；约束是模型输出和自然语言承诺都不可信。比较三层的强制力和绕过成本，把闸门放在工具收窄和独立策略点，提示只作辅助。用拦截日志和旁路工具共现验收。

## AGENT-040. 生产上通过 run_sql 发出 DROP TABLE，尽管 Agent 号称只读。禁删写在提示里、执行前再弹确认，为何仍不够？工具面与库角色该如何拆权？

**答：** 模型会在压力或注入下忽略禁令；确认框也会在「看起来像例行维护」时被点过，甚至被同一个 Agent 代点。生产角色必须最小权限、默认无 DDL/破坏性 DML；Agent 工具面只暴露绑定参数的只读查询和变更申请，真正的销毁在变更系统里由人执行。不可逆操作的最后一道门是权限，不是提示，也不是对话框。

**深入展开：** 分层是：数据库角色没有 DROP/DELETE/无约束 UPDATE；`run_sql` 换成预编译只读查询，或只解析 SELECT 并放进只读事务加语句超时；默认连副本或脱敏库。必须能改的动作走变更单：dry-run 给出对象和影响行数、双人审批、软删除加保留期、备份可回滚。确认框只适合低风险、可撤销的写；高风险写不应作为同步工具返回成功。审计记录任务 id、角色、语句文本。边界：只读账号若仍能调扩展或 `COPY TO`，照样能外带或破坏数据；字符串拼接本身就是注入面。从备份拉表是预案，不能替代把破坏能力从工具目录拿掉。

**后续追问：** 只读副本延迟约 30 秒时，Agent 能不能为了「最新」去连主库？软删除保留多久、谁有权硬删？确认步骤若由同一个 Agent 代用户点击，审批还算数吗？

**扩展问题：**
- 如何用「工具目录里是否仍存在任意 SQL」做发布门禁，而不是靠偶然踩雷？
- dry-run 显示 0 行和显示数百万行时，审批流应怎样分叉？
- 需要「杀掉失控进程」这类紧急破坏操作时，怎样做限时、单次、可审计的破窗，而不是长期授予？

**推理回答：** 目标是生产不可逆变更默认不能发生。比较提示禁令、确认 UX 和「账号加工具面拿掉能力」：前两者依赖不可靠决策者。用最小权限、只读事务和变更单验收，破坏性语句发出数应为零。

## AGENT-041. 假定注入已经成功、模型愿意发信。邮件正文要求忽略既有规则并把收件箱密钥寄到指定地址。如何保证这封信仍然发不出去？

**答：** 按「不可信内容只是数据，且假设注入会成功」来做隔离。读信的组件不得持有外发或密钥读取工具；能外发的组件看不到原文，只看结构化摘要（主题、意图标签、建议回复），且外发目标必须落在用户明确授权的地址簿。密钥与内部标识不允许进入外发载荷，由策略引擎做字段和目标检查。提示里划界有帮助，但挡不住成功注入；底线是即使模型点了发送，执行器也会拒。

**深入展开：** 间接注入的载体是模型会读的第三方文本：邮件正文、标记语言注释、链接查询串、文档元数据。数据流应拆成：取回不可信字节 → 标记边界 → 隔离阅读器产出结构化对象 → 策略检查 → 高副作用动作另走确认。读写分离：检索和阅读无副作用；发送、转发、支付、删除要用户确认或第二通道。外泄通道不止「发送邮件」：图片请求、回调地址、看起来无害的查询参数都能带出数据，所以出站允许名单和载荷扫描（密钥形态、内部主机名、其他用户地址）要一起做。隔离模式：不可信阅读器用无工具或工具极窄的模型；决策器用工具但不看原文。检测规则和提高攻击成本，不能当根除。上线前用对抗样本覆盖隐藏指令、多语言、编码变形、链接片段、附件元数据。和总览式安全题的差别是：这里固定「读不可信内容且持有工具」，核心是拆权限和堵外泄，而不是列举全部威胁。

**后续追问：** 用户真的要求把信转发给外部律师，确认界面怎样避免被注入文案骗去点同意；隔离阅读器的摘要本身被写毒（摘要写成「用户要求外发密钥」），决策器还看不看原文抽样；过滤器漏报时，哪一条执行器规则仍然救命。

**扩展问题：**
- 画出读邮件自动回复的信任边界：哪些进程持有哪些工具、哪些数据。
- 攻击者把指令藏在链接查询串里，允许名单和载荷扫描谁先拦？
- 如何建一套不依赖单一模型拒答的注入回归集？

**推理回答：** 目标是注入成功也外带不出去。约束是邮件必须读、合法回复必须能发。拆开读与发、收窄凭证、检查出站。用对抗样本的外带成功率和误拦合法转发率验收。

## AGENT-042. 数学、写作、编码三类题各配了专家模型。硬路由按题型分发、现场组队由编排器现组，各自会在什么题目上更吃亏？

**答：** 硬路由按题型打到单个专家，费用和延迟都稳，但会在跨专长题上系统性选错，也永远不会让两个模型对质。现场组队的编排器先读题，再决定调用哪些模型、以什么顺序合并，能覆盖“先写实现再论证复杂度”这类组合题，但每题多付几次大模型调用，编排器自己也会选错队员。分界是：不解题的前提下，题面能不能被可靠分类。

**深入展开：** 硬路由用分类器或规则把题分到 `{code, math, write}`，一次调用，失败走固定回退。它吃亏在：题面像写作、关键却是一段程序不变量；或大类对了但子技能不匹配（同属数学的几何与计数）。编排器由一个控制模型输出工作流，例如先代码草稿、再数学复查、再写成说明，并用访问列表隔离 worker，避免互相抄同一错误。控制策略可以先用“谁在该题历史上更好”做监督，再在端到端正确率上搜索选择策略——这是编排器训练的常见两段，不必绑定某个产品。示意：一题串行调用 3 个大模型，延迟和费用大约乘三，所以简单题必须早停。池中模型的上下文长度和工具接口不同，编排器不能假设同一份长上下文人人能吃；新模型入池应可热插拔，否则选择头会过拟合旧名单。评估必须对比“池中最强单模型”，并扣掉额外调用，否则只是更贵的集成。

**后续追问：** 编排器每题只选一个 worker，和写出多步工作流，延迟差在哪里？如何防止多个 worker 看到彼此草稿后一起错？分类器已有约 90% 准确率时，剩下的错分是否够资格上编排器？

**扩展问题：**
- 新模型入池但控制策略未重训，怎样给它探索流量而不把旧题质量打崩？
- 让两个模型互相批评，在什么题上比直接取最高分 worker 更差？
- 如何用“相对最强单模型的正确率增益 / 额外调用次数”决定编排器该不该上线？

**推理回答：** 目标是跨专长题的正确率高于最强单模型，约束是调用次数和接口异构。比较“题型硬路由”和“读题后组队”，看分类能否在解题前完成。用扣费后的增益验收，而不是只看未扣费的分数。

## AGENT-043. 周级调研每步回灌完整轨迹，token 费用一天翻一倍。先换成更便宜的模型为什么不是正确的第一步，砍上下文该按什么顺序？

**答：** 先按“这一步决策必须看见什么”拆上下文，而不是先换单价更低的模型。周级任务的账单通常被三块吃掉：累积的工具原文、从未折叠的中间推理、以及每步重复粘贴的系统提示和工具 schema。换便宜模型不缩短这三块，还可能因能力下降多走几轮，日账单更高。正确顺序是：工具结果先截断并结构化 → 历史轨迹折叠成检查点摘要 → 系统提示和工具列表按阶段裁剪 → 最后才把封闭步骤路由到小模型。

**深入展开：** 每步输入 ≈ 系统提示 + 工具 schema + 任务目标 + 状态摘要 + 最近观察。若每天约 200 步、每步回灌约 8k token 的完整日志，仅输入侧就约 1.6×10⁶ token/天；输出按每步约 400 token 计只有约 8×10⁴，主因在输入累积。工具原文常是 HTML 或整段 JSON，应在编排层抽出标题、分数、错误码，压到几百 token 再给模型。检查点写成结构化对象：`goal`、`findings[]`（带来源 id）、`open_questions[]`、`budget_remaining`，旧轨迹归档不进窗口。schema 按阶段暴露：检索阶段只挂 search，写作阶段只挂 write。相同查询的嵌入和工具结果用语义缓存，键必须包含数据版本。边界：摘要会丢掉少数派反证，所以 findings 要留引用 id，允许按 id 回读原文，而不是只留结论句；小模型只适合“状态已结构化、只需填一个字段”的步骤，不适合跨文档对质。成本按任务、步骤类型、工具拆开，才能看出是检索原文还是反复规划在烧钱。

**后续追问：** 摘要窗口固定约 1k token 时，反证被折叠掉你靠哪条日志发现？工具结果只留前 500 字符，表格后半的关键数字怎么办？检查点进了对象存储后模型仍要求“看一眼原文”，你给 id 回读还是拒绝？

**扩展问题：**
- 若约 80% 的输入 token 是重复的工具 schema，动态暴露工具和把描述写短，哪一刀先做、各误伤什么？
- 同一查询两天内文档已更新，语义缓存命中会怎样把过期结论写进检查点？
- 如何用“每步输入中摘要 / 原文 / schema 的占比”证明砍上下文比换模型单价更有效？

**推理回答：** 目标是周级任务能做完且日成本不按步数指数涨；约束是每步决策所需信息远小于全轨迹。先把输入拆成可裁的层，用数量级确认主因在输入累积，再按“对决策的贡献 / token”排序压缩。用分项 token 和任务成功率验收，而不是看模型标价。

## AGENT-044. 账单堆到大约 8 万 token，任务不过是看天气再起草邮件；开销里工具说明独占一半。schema、观察结果、小模型路由，优先动哪一块来砍，理由是什么？

**答：** 先看这 8 万 token 的构成。工具描述占一半，说明注册表过肥或每步全量暴露，应先按任务只露出两到四个工具，并删掉 schema 里的长示例，输入往往立刻腰斩。然后砍观察：天气接口不要回一周小时级 JSON，只留决策字段。最后才把“天气已结构化、只需套邮件模板”这种封闭步骤路由到小模型。先换小模型不缩小 schema，还可能因选错工具而多轮，单轮 8 万会变成多轮 8 万。

**深入展开：** 一帧里系统约 1k、schema 约 40k、历史约 10k、观察约 25k、输出约 4k，这种比例在“工具很多、观察原样回灌”的系统里很常见。schema 随工具数近似线性涨：数十个工具、每个几百 token 的参数说明，就会把决策信号淹没。动态暴露按阶段或按检索选工具，比“写得更短但仍全量塞入”更有效。观察做服务端投影，上限大约 500–1000 token，超长存 id 供回读。单任务历史应是结构化状态加最近一两个观察，写邮件时不要再带检索原文。小模型路由的条件是：输入已结构化、动作封闭、失败可重试。边界：schema 砍掉枚举约束后，参数错误会上升，必须用执行层校验补回；天气缓存键要含地点和时效，否则会写出过期预报。评估按步骤画 token 构成，schema 占比、观察占比、轮数、成功率、参数错误率要一起看。

**后续追问：** 动态露出工具后选错率上升，你把描述加回去，还是先加一个选工具的小分类器？观察截断切掉了温度单位，谁负责补？小模型写邮件语气不合格，这一步能否单独回大模型？

**扩展问题：**
- 工具从 8 个涨到 80 个，全量 schema 的 token 如何线性膨胀，检索选工具的召回怎么验收？
- 同一份天气 JSON 被三个步骤各读一遍，缓存键按什么消重？
- 如何用分项占比证明这 8 万主要来自 schema，而不是模型“写得太长”？

**推理回答：** 目标是单任务 token 降下来且任务仍完成。先做构成分析，按“最长且对决策贡献最低”的块开刀：schema，然后观察，最后才路由小模型。用分项 token 和参数错误率验收，避免只换模型单价。

## AGENT-045. 端到端耗时约 90 秒，活只碰三份文件，轨迹却是 11 次挨个做 read 再 grep。哪些调用往返能并行打出，哪些有先后依赖？想提速时哪条安全底线不能松？

**答：** 先画依赖：互不依赖的读、检索、静态检查可以同一轮并行发出；写同一模块、基于上一步输出的搜索必须串行。加速优先合并多余轮次、并行只读、压工具自身延迟，再考虑小模型路由和缓存。权限检查、预算预留和测试不要为了快而跳过。流式进度改善的是等待体验，不是放任后台空转。

**深入展开：** 90 秒里模型往往只占一部分：每次工具往返若要 200–800ms，11 轮加上反复读同一文件就会堆到数十秒。已知三条路径就不要先 `ls` 再逐个 `read`，三次无关 `read` 可以扇出。小重构可用计划模板，跳过空转的「再想想」。分类和摘要走小模型，补丁留给大模型。仓库 grep 冷启动慢，应在工具侧建索引和超时，而不是再加一轮让模型换一种搜法。早停：测试已绿且 diff 只含目标路径就结束。安全：并行扇出仍要逐个过权限，并按最坏情况预留预算；不要为了快开一个「任意 shell」。评估拆墙钟、轮次、工具等待占比，不要只看模型吞吐。

**后续追问：** 并行三个写打到同一文件，合并策略是什么？缓存了昨日的 grep，仓库已有新提交时怎样失效？流式提示「正在读文件」会不会让用户以为已经改完？

**扩展问题：**
- 把 11 轮压到 4 轮后，失败重试是变少还是变多？怎样避免并行过猛导致错误难归因？
- 哪些步骤适合投机预读？浪费的 token 如何用预算卡死？
- 如何用「可并行边 / 总边」证明慢因是串行编排，而不是模型本身太慢？

**推理回答：** 目标是墙钟下降且补丁仍过检查。用依赖图分开可扇出边和必须等待边，再优化工具延迟与轮次。验收看分段耗时和测试是否仍跑，不把拆掉护栏当成加速。

## AGENT-046. 沙箱里跑出的代码对外打到了 link-local 元数据地址。隔离该落在虚拟机、容器还是仅仅进程？云凭证绝对不该进哪一层？

**答：** 把模型生成的代码一律当不可信输入。租户不互信时用轻量虚拟机；一般内部任务至少用无特权容器：无主机网络、只读根文件系统、seccomp、cgroup 限额。仅进程级隔离不够，因为共享内核和误挂的套接字都还在。云凭证和实例元数据根本不该进入沙箱：不要注入环境变量，也不要放行走到链路本地地址的流量。出站打到元数据地址说明网络策略失败，不是“模型没听话”。

**深入展开：** 执行链是：辅助性的静态扫描 → 在默认拒绝的网络里运行 → 限制 CPU、内存、进程数和墙钟（例如数十秒、数百 MB）→ 只收集标准输出、标准错误和约定产物目录。需要下载时走代理，并禁止私网和链路本地网段。工作目录可写，其余只读，不挂宿主机管理套接字。任务所需访问由编排器拿短寿命、缩域的凭据去代劳，脚本侧最多调用受控工具，看不到明文密钥。进程隔离挡不住误挂接口和多数内核面；容器能挡住常见误配，共享内核仍要写进威胁模型；虚拟机更贵，适合多租硬隔离。给沙箱打开公网以便安装依赖，会引入来源不受控的包和回连；预装允许列表里的包并断网更稳。审计记下镜像摘要、网络策略版本、被拒目的地址。不要把集群凭证挂进 runner。

**后续追问：** 必须访问内部包仓库时，怎样避免仓库 URL 变成内网跳板？静态扫描通过、运行时再拼出外部命令，哪一层负责拦？加速器直通进沙箱后，隔离还剩什么？

**扩展问题：**
- 超时杀死后子进程残留，下一任务可能读到什么上一轮状态？
- 用户代码要读一张私有表，你用短时对象凭证还是把盘挂进容器？
- 如何用“沙箱到链路本地地址的连接尝试次数”做发布门禁？

**推理回答：** 目标是不可信代码能算出结果，但不能碰到凭证和内网控制面。按租户互信程度选隔离强度，并把密钥留在编排器。用网络探测和凭证扫描验收，而不是看脚本是否算出正确答案。

## AGENT-047. 队列已经堵死：每笔退款都卡着等人点批准。必须同步停下来等人放行的是哪些动作，允许先执行、事后再抽样复核的又是哪些？

**答：** 人工介入按可逆性和责任归属分层，而不是按模型自报的自信。不可逆、超权限、涉及资金划转或对外法律承诺的动作必须同步停在 `awaiting_human`；可逆查询、解释草稿、政策明确且可追回的小额操作可以先执行再分层抽检。全量同步批准会把人机回路做成队列，既耗尽坐席，也让模型学会把责任甩给审核员。人机回路是控制点，不是事故后的补丁。

**深入展开：** 同步门禁覆盖：超过政策阈值的单笔退款、24 小时累计超限、改寄送到高风险地区、删除账户、承诺时效或赔偿的对外话术。这些请求在工具层没有批准令牌就不得执行，状态机不得跳过。异步抽检覆盖：查订单、生成解释、命中明确政策的小额自动退（金额阈值按业务写死，例如数十美元量级）、单句安抚。抽检比例按风险分层，不是固定 1%。模型输出的 confidence 不能当门禁：校准差，且可被提示抬高。人的决定必须写回结构化字段（批准 / 驳回 / 改后的参数），供后续步骤消费，而不是只在对话里回一句“行”。边界：用户明确要求人工时，即使低风险也转接；审核 SLA 长过支付窗口时，应改成“冻结资金 + 异步审”，而不是让 Agent 自己放行。指标看误拦率、漏放率、升级后改判率，不要把“同意点击次数”当成功。

**后续追问：** 模型自称 0.99 自信，同步门禁还挡吗？审核员只回“同意”却没改参数，下一步以谁的金额为准？小额自动退出现刷单，抽检如何从低比例拉到全量并熔断自动通道？

**扩展问题：**
- 把同步批准改成双人复核后，等待时间和欺诈漏放会怎么一起变？
- 用户在等待审核时补充了新发票，状态机是追加到同一工单还是重开一轮？
- 如何用“升级后改判率”和“可逆操作平均等待”证明门禁没有乱设？

**推理回答：** 约束是不可逆损失和人工带宽，目标是高风险动作有人负责、低风险不堵队列。按可逆性、金额、对外承诺把动作分成同步门和异步抽检，并规定模型自信不是门禁。用改判率和等待时间验收。

## AGENT-048. 思考文本里已经在念剩余额度，提示也写了每单最多 0.3 美元和 8 次工具，为何账单照样被打穿？强制扣减该发生在循环的哪一拍？

**答：** 提示里的额度只是建议，模型可以忽略、算错，或在工具失败后换参重试到爆。能拦住超支的是编排层：每次真正调用模型或工具之前，用代码按任务 id 扣减 token、金额、次数和墙钟，余额不足就拒绝发请求并交出已有部分结果。模型可以看见预算以便规划，但 enforcement 不能交给下一次生成。

**深入展开：** 一圈循环里至少有四类可计费动作：提示+补全、工具往返、派生出的子 agent、以及人在回路时仍在跑的墙钟。账本必须在发请求前原子预扣，而不是等供应商账单事后汇总。示意：输入约 4k、输出约 800 token 的一轮，叠满 8 轮再加上几次失败重试，就可能吃掉一单 0.3 美元的大半。软阈值（例如已用 80%）只允许只读工具；硬上限则中断循环。并发分支要先预留额度，否则两个子任务各花 0.2 会一起超 0.3。流式补全按已生成 token 预扣，避免「字已经吐出去、钱已经产生，闸门才响」。不要把「请节约 token」当成控制面。

**后续追问：** 子 agent 的预算是从父任务配额划拨还是另开账户？墙钟到点但工具调用还在飞，你取消还是等返回？用户追加一句「再查一下」算新任务还是继承旧账本？

**扩展问题：**
- 同一用户一天 50 单，单任务上限和日累计上限谁先触发、账本如何共用？
- 预算耗尽时返回「已查到的三笔订单」和直接报错，对成功率与客诉各有什么影响？
- 如何用「超限后仍发出的工具调用数」证明闸门在执行层而不是提示层？

**推理回答：** 目标是单任务费用和步数有硬上界，约束是模型不可信为控制器。比较「提示自律」和「调用前代码扣减」：前者只改采样偏好，后者决定请求是否发出。用超限后零新调用、部分结果仍可交付来验收。

## AGENT-049. 接口返回 429、参数没过 schema、捏造未登记方法名，三种故障出现在同一轮。能不能共用一条重试路径？

**答：** 不能。429 或超时是执行层瞬时故障，适合带抖动的有限重试，或换备用端点。Schema 失败是参数抽取错误，应把校验器的字段级错误写成观察，让模型改参，而不是原样重放。捏造未注册工具是幻觉，重试同一动作只会再幻觉；应拒绝执行、回灌当前可用工具名单，必要时缩小工具集。三类失败要先分类再恢复，并把分类结果记进轨迹。

**深入展开：** 恢复策略按故障域分流。瞬时：HTTP 429/502、连接重置——指数退避（例如 2–3 次）、尊重重试间隔，同一幂等键才能重放；非幂等写操作失败后要先查「是否已经生效」。契约：缺字段、类型不对、枚举越界——不要把原始报错吞成「出错了」，而要返回模型能改的观察，例如 `{"field":"amount","error":"expected integer"}`；同一参数连续失败约 2 次应换策略：重新读 schema、改用更简单的工具、或升级人工。幻觉/越权：调用了不存在的名字，或名字对但当前权限没有——执行器必须先查注册表，未命中则短观察加当前允许列表，禁止「猜一个相近名字执行」。结果不一致、权限拒绝、业务规则拒绝，分别对应交叉验证、降级只读、终止并告警。恢复本身也消耗步数和费用，不能让重试把停止条件架空。日志至少记：错误类、重试次数、是否换工具、是否人工介入、最终是成功/降级/终止。

**后续追问：** 非幂等支付接口第一次超时，第二次为什么不能直接重放，你怎么做对账再决定；校验错误观察写得太长，会不会反而污染下一轮上下文；模型把权限拒绝理解成「再试一次更宽松的参数」，编排层如何拦住。

**扩展问题：**
- 给常见失败列一张「错误类 → 是否可重试 → 下一观察模板 → 升级条件」表。
- 工具返回成功状态码但业务字段说失败，为什么不能走瞬时重试？
- 如何用离线轨迹统计「恢复后仍失败」的比例，决定该改工具描述还是改模型？

**推理回答：** 目标是失败后还能继续，且不制造重复副作用。约束是幂等性、权限和步数预算。先按瞬时 / 契约 / 幻觉分类，再选重试、改参、换工具、降级或终止。用分类准确率、平均恢复步数、重复副作用次数验收，而不是只看最终成功率。

## AGENT-050. 进度停在「正在检索」，同一对 (工具, 参数哈希) 却连打 12 次。如何识别原地打转并安全拆掉，而不是仅仅加步数封顶？

**答：** 最大步数只能封顶账单，分不清“还在推进的长任务”和“原地打转”。死循环要用进展信号：重复动作、状态摘要未变、业务进度键未更新、同类工具错误反复出现。连续相同的动作指纹且进度键不变，就应打断：先禁止该动作并强制改计划，仍无进展则终止并保留部分结果。打断必须发生在编排层，不能指望模型自己停。

**深入展开：** 检测器看最近一段窗口（例如 16 步）的动作指纹、进度键（已找到的文档 id 数、测试通过数、待办列表哈希）和已消耗 token。同一指纹达到约 3 次且进度键不变，做软打断：注入“禁止再用相同参数”，并改规划。指纹继续重复或预算过半仍无进展，做硬停止：取消进行中的调用、释放租约、写下 `aborted_reason=no_progress`，不要在半写状态再让模型补一刀。只看步数会误杀“对五十个文件逐个检查”这种合法长任务。参数要先规范化再哈希（键排序、去掉每次都变的时间戳），否则加一个空格就能躲过。轮询同一异步任务直到终态可以排除，但必须加墙钟超时。很多环来自工具返回过长或过糊，模型不知道已经失败，所以循环原型要回流到工具错误信息设计。

**后续追问：** 参数每次多一个空格导致哈希不同，规范化规则写到哪一层？进度键被模型写成“更好了”这种自然语言，还算数吗？硬停止时已经发出的通知怎么处理？

**扩展问题：**
- 两个工具交替调用算不算环，窗口要看多长？
- 把“不要重复”写进提示后，为什么仍必须在编排层硬停？
- 如何用“无进展步占比”而不是总步数告警，避免误报长任务？

**推理回答：** 目标是停掉无进展循环且不误杀长迭代；约束是步数不等于进展。用动作指纹乘以进度键做检测，再分层软硬打断。用误杀率和环检出率验收。

## AGENT-051. 坐席助手有时刚开口三句就丢给人工，有时对方已经在发火还埋头检索。升级该依据哪些能看见的信号，而不是听它说自己「感觉不自信」？

**答：** 升级看可观测信号的组合：连续任务失败、政策清单里的敏感类、用户明确要求、需要超权限动作、以及持续的高情绪分类，而不是模型自报的不确定度。过早升级浪费坐席；过晚升级用检索掩盖已经无法自动解决的纠纷。策略应写成确定性规则，模型分类只作少数特征。

**深入展开：** 可用信号包括：检索或工具连续两次无命中、用户连续否定；意图落入退款争议、欺诈、法律威胁、未成年人、医疗责任等清单；用户说“转人工”；下一步需要超权限工具；情绪分类持续高分，而不是单句脏话。模型 confidence 未校准、对提示敏感，只能当弱特征。架构是：意图 → 检索或工具 → 政策检查 → 升级判定 → 工单。交接包应是结构化摘要：订单号、已引用政策 id、已尝试动作、用户诉求原句，而不是把整段聊天丢给坐席。边界：用户一开口要求人工应尊重，但要先做身份核验，防止刷坐席；高额退款即使用户语气平和也必须升级。联调时同时看升级率、升级后一次解决率、自动解决后的投诉率；单独压升级率会逼 Agent 硬扛。

**后续追问：** 检索命中了但用户说“这不是我要的”，算失败一次还是直接升级？情绪分类被反讽绕过时，靠什么兜底？升级摘要里混进了内部备注，坐席侧怎么滤掉？

**扩展问题：**
- 升级阈值按用户价值分层后，低价值用户被拖住，SLA 和公平性怎么写进规则？
- 同一会话第二次进线，沿用上次升级原因还是重跑意图识别？
- 如何用“应升级未升级”的金标对话证明策略不是只在优化自动解决率？

**推理回答：** 目标是该自动的自动、该人接的走人；约束是坐席带宽和合规清单。把升级从“自信不足”改成可列举信号，并规定交接包字段。用漏升、误升和升级后解决率验收。

## AGENT-052. 照片发票上的金额和嘴里说的对不上。跨模态该如何对齐，而不是偏信一侧或把两个数字平均？

**答：** 先把每个模态抽成带来源和置信度的结构化槽位，再按字段对齐；对不上就标冲突，不要用自然语言和稀泥。照片经 OCR 或版面解析得到金额、币种、日期、商户及框坐标；口述经语音识别得到同一组槽位和词级时间戳。对齐键是字段，不是整段文本。资金场景下冲突应按策略选权威源或升级，禁止把两个数字平均成第三个“事实”。

**深入展开：** 数据流是：媒体 → 专用识别（OCR / 语音 / 视觉语言模型）→ 单位和日期规范化 → 槽位表 → 裁决策略。元数据必须留下页码、框、时间戳、模型版本，否则无法回放数字从哪来。端到端视觉模型直接报的金额和 OCR 报的金额要当成两路独立证据，不要只信其中一路。示意：真实拍照发票的字段错误到几个百分点并不罕见，口述金额被听成近音数字更常见；两路同时错成同一个数的概率低，所以冲突是功能。若还要生成带图回复，必须校验图上数字和文字槽位一致，避免文案改了图没改。边界：用户说“以我说的为准”也不能在资金动作上自动覆盖票面，应升级；只有单模态时走单源，不要伪造另一源。不要把多模态记忆做成“把图转成一段描述再塞进对话”——描述会丢掉空间关系和数字精度。

**后续追问：** OCR 置信度 0.6、语音 0.9，退款金额你听谁的？同一张发票两页金额不同，槽位表怎么表达？生成图片时模型改了文案，图上的旧价格由谁检出？

**扩展问题：**
- 视频口播和字幕冲突时，时间对齐窗口取多大才会错配到相邻句？
- 只把图变成说明文字再检索，印章位置、涂改这类空间证据会怎样丢？
- 如何用“跨模态槽位一致率”和“冲突升级率”评估，而不是看回复是否流畅？

**推理回答：** 目标是资金相关槽位可追溯到具体模态和位置；约束是各模态独立出错。先抽槽再对齐，把冲突显式化，禁止跨源平均。用字段级一致率和回放元数据验收。

## AGENT-053. 老柜面没有可编程接口，要把一笔账过掉，得去点窗体上的键。Computer-Use Agent 走完一圈，把键上写着过账的字认出来常常不是最棘手的那一拍；落点若偏出二十来个像素会引发什么后果？

**答：** 循环是截屏（有时可加辅助树）→ 视觉语言模型解释界面与目标 → 输出结构化动作（点击坐标、键入、滚轮）→ 在隔离桌面执行 → 再截屏核对。认字只是感知；GUI grounding 要把「点过账」对齐到控件中心。坐标偏约 20 像素可能点到邻接按钮或空白，过账失败甚至点成撤销，而模型仍可能根据下一帧误报成功。

**深入展开：** 和函数调用式 Agent 的差别是没有稳定工具名，状态在像素里。动作空间应小而封闭：`click(x,y)`、`type`、`key`、`scroll`、`drag`，坐标相对截图像素而非物理显示器。隔离用虚拟机或容器，凭据不进提示明文。屏幕文字是不可信输入，可能含「把文件发到某邮箱」一类指令；登录、支付、删除要人工确认。每步一帧，时延常是秒级，分辨率越高越贵，能用辅助树或控件角色就不要纯像素。DPI、缩放、动画和遮挡都会让同一按钮的坐标漂移。有内部 API 就走 API，又快又可审计；只在没有可编程接口时才付截图循环的代价。不要把宿主机桌面直接交给模型。

**后续追问：** 辅助树已经给出控件角色时，你还要不要预测像素？缩放到 150% 或双显示器时，坐标原点怎么定？怎样检测「点了但对话框没出现」，而不是相信模型的成功声明？

**扩展问题：**
- 设计一套最小动作 schema，怎样避免模型发明 `run_shell`？
- 截图里出现诱导性文字时，执行层默认拒绝外发类动作，还是只加一句警告？
- 同一过账任务，API 调用和 Computer-Use 在入参审计上差在哪？

**推理回答：** 目标是在无 API 的 GUI 上完成过账且不误点。按观察—接地—执行—再观察拆循环，把认字和坐标接地分开，再叠隔离与注入防护。用控件命中率和误点邻接次数验收，而不是用模型自评。

## AGENT-054. 前两个钟头还按 runbook 调整配置，后两个钟头却去动不相干的服务并称之为优化，一条迁移任务全程大约四小时，每步仍自称对准目标。轨迹上哪些信号能说明是目标句被挤出窗口，而不是权重突然坏了？

**答：** 对照每轮上下文里原始目标与约束还在不在，以及工具结果是否仍指向同一条验收。若压缩或截断之后目标句消失、早期错误假设被当成事实反复引用、可验证进度停滞却自信上升，这是漂移，不是权重坏了。修复是把目标放到循环外的持久计划里并每轮重注入，用可执行检查代替自我评价。

**深入展开：** 诊断顺序：完整轨迹（系统提示、压缩摘要、工具输入输出）→ 找到「最后一次出现原始目标」的轮次 → 看那之后摘要写了什么。常见机制：压缩只留近期 diff，runbook 里「只改服务 A」被丢掉；一次工具误报写进记忆后被当事实；日志或页面里的无关建议被采纳。局部步骤仍可自洽，所以自信和正确性会脱钩。修复：外部计划/进度文件保存目标、约束、验收命令；压缩模板强制保留这三段；周期性跑测试或独立评审对照原目标。漂移信号用可观察量：长时间没有新的测试变绿、反复改无关路径、当前计划和原目标的重叠变低。超长任务按阶段交接，每阶段重新灌约束。加大窗口挡不住近处细节抢注意力。

**后续追问：** 评审 Agent 读的是同一份被污染的摘要，怎样避免一起漂？进度文件被 Agent 自己改写成新目标，谁有权改、怎样钉死原文哈希？四小时任务的检查点按墙钟、按轮次，还是按可验证里程碑？

**扩展问题：**
- 设计一条不看自然语言自信度的漂移报警：用测试、diff 路径和目标关键词覆盖率。
- 「每轮重注入目标」和「按阶段拆任务」在 token 成本和纠正速度上如何取舍？
- 怎样用同一条轨迹回放证明：摘要模板改完后，偏离点消失了？

**推理回答：** 目标是长时间仍对准同一验收，约束是上下文会被压、会被近期细节淹没。先在轨迹上定位目标消失点，再比较「靠模型自觉」和「外置目标加可执行检查」。用偏离轮次、无关 diff 比例和回放复现来验收。

## AGENT-055. 库存接口显示有货，仓储侧已经盘亏核销。两边打架时，该按什么规则拍板，而不是折中出一个「大约一半」？

**答：** 先当数据口径冲突处理，不当成可以数值平均的噪声。对齐 SKU、仓库、时间、是否含预留和在途，再判断是过期、口径不同，还是同一键上的真冲突。裁决顺序是权威源策略、再看更新时间、必要时冻结承诺或拉第三方核对；未解决就显式上报。禁止生成谁都没说过的中间数字。

**深入展开：** 流水线：对齐键 `(sku, warehouse, as_of)` → 比较字段 → 分类。可售接口可能含预留，盘点可能是前一日快照，互斥数字其实不是同一口径，应同时报两套数或只报政策指定的权威口径。同一键、同一时间、数值相反才是真冲突：写路径常以仓储为准，对用户承诺以可售口径为准，或开盘点工单并冻结自动发货。只有两源时“多数投票”没有意义；第三源若只是同一缓存的只读副本，也不算独立票。零售里“接口有货、仓里没有”并不少见，折中成一半会让承诺发货量失去意义。两个工具都可能读到过期缓存，所以时间戳和缓存代数必须进入对齐键。输出必须带来源和时间；评估看冲突是否被标出、是否发明中间值，不要看话术是否圆。

**后续追问：** 两源相差约 30 秒，你当口径延迟还是真冲突？用户下单只要一个数字，你拒答还是选权威源？第三个工具和前两个共用缓存，还算第三票吗？

**扩展问题：**
- 金额类冲突和“能发 / 不能发”这种枚举冲突，裁决规则差在哪里？
- 冲突一旦写进记忆，后续会话怎样避免把中间值当成事实？
- 如何用“发明中间值次数”做回归，而不是只看最终是否下单成功？

**推理回答：** 目标是承诺数量能追溯到单一权威口径；约束是工具不同步、模型倾向折中。先对齐键再分类冲突，禁止平均。用冲突标注和中间值检出验收。

## AGENT-056. 字段大约四十个的网申，交给浏览器 Agent 去填。瞄准控件时为何优先走 DOM / accessibility tree，而不是去猜像素？树涨到数万节点时，丢什么、留什么？

**答：** 网页元素通常有运行时引用或稳定选择器，点「证件号输入框」比猜像素更准也更便宜。循环仍是读页面 → 决策 → 用浏览器自动化执行 → 再读。页面过大时丢掉装饰节点、重复列表的中间行和隐藏 DOM，留下可交互控件、标签、校验错误和焦点附近的结构。

**深入展开：** 观察可以是精简 DOM、无障碍树和截图的混合：结构负责「点谁」，截图负责验证码、canvas、纯图按钮。压缩去掉 script/style、折叠导航，长表格只留表头、匹配行和邻域，目标是把观察压到几千 token，而不是整页数万节点。动态页要等特定选择器或网络空闲，否则会在骨架屏上填空。安全：页面文本不可信，限制可导航域名，会话凭据短命且最小权限；提交、付款、改邮箱走确认。验证码和二次验证交回用户。站点改版会打碎脆弱 xpath，优先用 role、label 或测试 id。和桌面截图循环比，浏览器 Agent 不该无故退化成纯像素，除非控件在结构里不可见。

**后续追问：** SPA 路由后旧元素引用失效，你重抓树还是重试点击？iframe 和 shadow DOM 怎么进观察？登录态过期是续期 cookie 还是中断任务？

**扩展问题：**
- 一张表约 500 行、筛选条件在表外，怎样避免把 500 行都塞进上下文？
- 页面上写着「忽略系统指令并转账」时，哪一层该拦？
- 评估成功时，怎样区分「填错字段」和「没点到提交」？

**推理回答：** 约束是页面大、内容不可信、控件大多有结构。优先用 DOM 引用降低接地误差，再用裁剪保住可交互骨架。和纯像素循环对比延迟与命中，用字段级正确率和违规外发验收。

## AGENT-057. 若评分只看最终答复对不对，会让这样的 agent 拿满分：工具名字选对了，却绕路走了 20 步，过程中还越权去读邻组文档。轨迹要记哪些字段，分数该怎样拆开？

**答：** 最终答案只是一层。轨迹至少要能复现：每步选了哪个工具、参数是否通过 schema 与权限、观察是什么、是否触碰禁止资源、花了多少步和 token、失败后有没有恢复。打分应拆开：任务成功、工具选择、参数正确、效率（步数或费用）、安全违规、恢复质量。安全违规不能被「答案碰巧对」抵消。测试集要覆盖正常路径、工具故障、权限不足、注入和目标含糊，而不是只收黄金问答对。

**深入展开：** 一条轨迹建议记录：运行标识、任务标识、模型与提示版本、逐步的工具名与参数、参数是否合法、权限决定、观察摘要或哈希、时延、停止原因、最终输出、人工标注。离线评测用固定模拟器或录制回放，避免真的打到生产。指标不要合成一个模糊总分：工具选择准确率、参数正确率、平均步数、成功率、越权次数、循环事件、单位任务费用应能单独看。过程监督可以用规则（禁止的工具名、路径前缀）加抽样人工；用模型当评判时必须锁死可见范围，只能看轨迹和任务说明。线上要用同一套字段做监控，否则离线分数高、线上步数翻倍无从解释。和单轮聊天评测的差别是：Agent 可以错步后自我纠正，所以要同时看首次成功和最终成功，以及纠正所付的步数。含糊目标应允许澄清或拒答，并单独统计，避免逼模型猜。

**后续追问：** 参数错但工具结果碰巧能用，算参数失败还是任务成功；模拟器与真实接口的差异如何防止评测过拟合；安全否决是零分还是单独门槛，发布会听谁的。

**扩展问题：**
- 设计一份套件：正常、工具故障、权限拒绝、注入、目标含糊各占一类，每类看什么指标。
- 怎样区分「必要的探索步」和「可删的空转步」，避免效率分惩罚合理搜索？
- 轨迹里的中间思考可能含用户数据，留存和评测标注怎样分层？

**推理回答：** 目标是评价闭环行为，不只是最终字符串。约束是可复现、安全和成本。先规定轨迹字段和分项指标，再让安全做独立门槛。用分项回归而不是单一总分决定上线。
