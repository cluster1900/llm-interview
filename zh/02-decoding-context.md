## GEN-001. yes 与 no 是产品唯一合法回复。LM head 已写出词表分数、采样尚未启动，要对 logits 做何种屏蔽，maybe 才进不了抽样？

**答：** Logits 是 softmax 之前、对整个词表的未归一化分数。把除 `yes`/`no`（以及必要的结束符）以外的所有维设为 −∞，或加上足够大的负 bias，再做温度和采样，概率质量就只剩合法 token。只靠提示“请只回答 yes 或 no”不够，因为采样仍可能抽到其他词。

**深入展开：** 数据流：最后隐状态乘 LM head（有时与 embedding 绑权）得到 |V| 维 logits，|V| 常见数万到十余万；然后才是 temperature、频率惩罚、bias、文法 mask，再 softmax、采样。禁词、JSON schema、只能选 yes/no，都作用在这一层，而不是改权重。分词陷阱：`yes` 可能不是单 token，要 mask 的是真实 token id；多 token 答案要用状态机按前缀允许下一步。结束符若被一起 mask 掉，生成会顶到 max_tokens。若日志只存最终文本、不存 top logits，很难证明 bias 生效。

**后续追问：** logits、概率和 log-prob 分别处在哪一层；词表里 `Yes`/`yes`/` YES` 多个 id 时如何合并约束；约束与温度谁先作用更数值稳定。

**扩展问题：**
- 写出对非法维赋 −∞ 后的 softmax，说明它们的概率为什么精确为 0。
- 合法答案是多 token 短语时，单步 mask 不够，状态机该维护什么状态？
- 如何用 top-5 logits 日志确认 bias 或 mask 已经生效？

**推理回答：** 目标是闭集输出。随机性来自 logits 变成分布。在 softmax 前把非法支持集清零，比事后正则更硬。再用结束符和多 token 状态机补齐边界，用 top logits 日志验收。

## GEN-002. 固定 k=50 的 top-k 与固定 p=0.9 的 top-p，遇到 p_max=0.95 的尖峰步、以及累计 20 个 token 才到 0.6 的平坦步，失败模式分别是误纳还是误删？

**答：** 分布很尖时（p_max=0.95），top-k=50 仍会放进 49 个极低概率词，一采样就可能蹦出无关 token；此时 top-p=0.9 往往只留 1–2 个候选，更稳。分布很平时（前 20 个才到 0.6），top-p=0.9 会纳入很长的尾巴，噪声大；top-k=50 则可能在合理同义词还没进集合时就截断。k 是硬窗口，p 是按质量自适应的窗口，尖和平两个极端下失败模式相反。

**深入展开：** 对概率降序排列后，top-k 取前 k 个再重归一化；top-p 取累计质量 ≥ p 的最短前缀。两者通常叠在 temperature 之后。常见组合：先除 T，再用 top-k 做安全帽，再用 top-p 做核。事实或代码任务应收紧核，甚至直接贪心；开放写作可把 p 放到约 0.9–0.95。陷阱：p=1 等于不截；k 过大等于没开；尖分布下大 k 是“看起来在核采样，实际在抽垃圾”。调试时看每步候选集大小的分布，再对重复率、非法 token 率和任务正确率一起验收。

**后续追问：** 同时设置 k 与 p 时实现上通常谁先过滤；为什么聊天解码很少只用固定 k；怎样从一步的概率直方图判断该收 p 还是收 k。

**扩展问题：**
- 画出尖分布和宽分布两条 CDF，标出 k=50 与 p=0.9 各自的截断点。
- 对代码补全，你会把 p 放到什么量级，并配什么停止条件？
- 采样出词表尾部乱码时，怎样用日志里的候选集大小反推是 k 过大还是 p 过大？

**推理回答：** 先给尖、平两种直方图，再看固定集合与固定质量谁在该点失效。结构化任务收紧核，开放生成放宽核但留 k 作上限。用候选集大小当调试信号，而不是只调一个魔法数。

## GEN-003. 温度由 0.2 升到 1.2，JSON 字段抽取的键就开始漂移。logits 经温度缩放到抽样，分布怎样变？多次调用在 T=0 时为何仍可能不一致？

**答：** Temperature T 在 softmax 前把 logits 除以 T：T<1 拉大差距，分布更尖；T>1 压平差距，低概率 token 更容易被抽中。0.2→1.2 会让“正确键名”和“近义错键”的概率比明显缩小，字段和标点开始抖动。T=0 在数学上应取最大 logit，但批处理、非确定核和浮点归约会让并列最大值每次不同，所以 T=0 不等于可复现。

**深入展开：** pᵢ = exp(zᵢ/T) / Σⱼ exp(zⱼ/T)。两个 logits 差 Δ 时，概率比从 exp(Δ) 变成 exp(Δ/T)；T 从 0.2 到 1.2，等效把差距缩小 6 倍。结构化任务应低温，并配合合法 token mask 或文法约束；创意写作才提高 T。T 只改尖锐度，不改变 token 排序——改排序要靠 bias 或 mask。T 过大时长尾会破坏 JSON；T 过小加贪心容易在错误局部最优上重复。应把 T 与 top-p、重试、schema 校验一起看，并用同一输入的自一致率衡量稳定性。

**后续追问：** T 和 top-p 同时开时先缩放再截断还是反过来；为什么有的服务写明 T=0 仍不保证逐字相同；怎样用自一致率和 schema 通过率选 T。

**扩展问题：**
- 给定 logits [4.0, 3.5, 0.1]，计算 T=0.2 与 T=1.2 时前两名的概率比。
- 什么任务你会把 T 固定为 0，关掉核采样，改用约束解码？
- 线上偶发 JSON 损坏，怎样用日志里的 T、top-p 和 finish_reason 归因？

**推理回答：** 目标是字段稳定。约束是 softmax 对尺度敏感。先看 T 如何改概率比，再排除 T=0 的系统非确定性。验收用多次调用一致率和解析成功率，而不是单次“看起来对”。

## GEN-004. 无频率惩罚且温度等于 0.7 时，输出在约 800 个 token 处把同一句循环播放。应先动哪一侧，拿什么指标确认不是近义反复？

**答：** 先分清是低温下的短循环，还是采样时高概率短语自我强化。立刻加上频率/存在惩罚或重复 n-gram 禁令，并检查提示是否在要求「继续展开」「尽量详细」，从而在没有新信息时逼模型自我续写。若惩罚后变成近义反复或列表项复制，说明只是换了皮，要改停止条件、限制长度，或换在长输出上更稳的解码和模型。用重复率、distinct-n 和最长连续重复 n-gram 一起看，不要只看那句原话还在不在。

**深入展开：** 自回归里已写出的 token 会回到上下文，某个高概率短语一旦出现，条件分布会再次抬高它，形成稳定环；temperature 0.7 仍可能环，因为环上相对概率可以远高于长尾。频率惩罚降低已出现 token 的 logit，对词级循环有效，对「换两个同义词再循环」较弱，这时要用序列级检测，例如 8-gram 第二次出现就停或降权。训练语料若含页脚或抓取噪声，基座本身就会复读，解码惩罚只是推理补丁。评估应在强制长输出的集合上算 repetition-2/3 和 distinct-2，并人工确认没有改成废话堆砌。

**后续追问：** 开放式生成里束搜索为什么更容易写出平淡重复的句子？频率惩罚和存在惩罚分别惩罚什么？代码里括号和重复标识符还能套同样的惩罚吗？

**扩展问题：**
- 给一段陷入循环的 token 序列，指出条件概率从哪一步开始自我锁定。
- 在 JSON 抽取上开重复惩罚，可能打断哪些合法的重复字段名？
- 流式输出时怎样实时检测循环并截断，同时尽量不误伤排比句？

**推理回答：** 重复是解码动态和「写长」目标叠在一起的结果。先用廉价解码约束止血，再用 n-gram 指标确认不是换皮重复；多种惩罚下仍复读，就归到模型和数据，考虑换模型或缩短任务。用长输出集合上的重复率和任务完整度一起回归。

## GEN-005. 工单 JSON 抽取、术语对译、开放域闲聊这三条 API 上，温度采样、greedy、top-p、beam、top-k 里你分别关掉哪一种，为了躲开什么翻车？

**答：** 术语翻译优先 beam 或低温贪心，禁用高温度核采样，避免用词乱跳；beam 适合“有较明确对应”的序列。开放闲聊禁用纯 greedy 和大切 beam——前者容易重复循环，后者常又安全又无聊；改用中低温度加 top-p。JSON 抽取禁用高温度、宽 top-p 和 beam（beam 不擅长硬格式且更贵），用接近 0 的温度加 schema/文法约束，必要时直接 greedy。

**深入展开：** Greedy 每步取最大 logit，快、最接近可复现，失败是重复 n-gram 和局部最优。Beam 同时保留 B 条部分假设，失败是长度偏置、套话、开放生成多样性差，算力大约乘 B。Top-k 固定候选数：尖分布掺垃圾，平分布砍合理词。Top-p 按质量截：p 太大就变长尾噪声。Temperature 只调尖锐度，高 T 会放大上面所有噪声。常见处理顺序：惩罚或 bias → 除 T → 合法 mask → top-k/top-p → 采样。T=0 仍可能因浮点非确定而不逐字相同。选参要在任务集上同时看正确率、重复率、多样性和解析成功率。

**后续追问：** 聊天产品几乎不用 beam，除了输出平淡还有哪些延迟和目标不匹配的原因；top-k 与 top-p 同时开时过滤顺序是什么；如何用一份评估集扫参数又不过拟合该集。

**扩展问题：**
- 给出 greedy 陷入“是的是的是的”循环的提示特征，以及重复惩罚、停条件和改温度三种缓解。
- JSON 任务上比较“T=0 无约束”和“T=0 + 正则文法”的 schema 通过率该怎么测？
- beam 不调长度惩罚时，短参考翻译会被怎样系统性偏向？

**推理回答：** 按“有没有较唯一的对应、能不能忍受随机、有没有硬格式”给三个接口分类，再映射到各解码器的失效模式。先禁会破坏任务约束的策略，再在允许集合里用指标扫参。

## GEN-006. 线上刚换了推理运行时，助手这一轮说完不收口，反而接着仿写下一轮的 User: 前缀，接口返回的结束原因也常常是 length。对话模板、结束 token 的 id、生成长度上限这三处，你会按什么先后顺序排查？

**答：** 先对模板：训练时助手轮末尾学的是特定结束 token，推理模板若没在同一位置收束、或把下一轮用户格式泄漏给模型，它就不会发结束符，只会接着模仿 `User:`。再查框架是否把该 id 放进停止集合——有的模型 eos 与对话结束符不是同一个。最后看 max_tokens：一直采不到结束符就会顶格停，`finish_reason=length` 表示截断，不是正常结束。

**深入展开：** 停止来源有三类：模型自己发出训练学过的结束 token；调用方的字符串 stop；长度上限。对话模型对模板极度敏感，模板不一致是“不停 + 替用户说话”的第一嫌疑。tokenizer 里的 eos id、生成参数里的停止 id、以及是否把 special token 过滤掉，必须一致。应用层要分流：`stop` 可直接用；`length` 要检测残缺，再续写、加预算或修模板。微调样本若从未在末尾放结束符，损失仍可能下降，但推理会无限续写。

**后续追问：** 为什么有的模型要把 eos 和对话结束符同时列入停止集；`length` 截断时怎样续写才不会重复已输出前缀；如何用 finish_reason 分布做上线门禁。

**扩展问题：**
- 设计一条最小复现：只改模板分隔符，预测 finish_reason 从 stop 变成 length。
- 多个结束 token 并存时，停止集合和返回文本里要不要包含被命中的那个 token？
- 微调数据漏写结束符，训练损失还会降吗？推理会看到什么现象？

**推理回答：** 生成要停下，必须有人发出可检测的结束信号。先对齐训练时的信号（模板 + 结束 id），再确认框架在监听，最后才加长 max_tokens。用 finish_reason 比例验收，而不是主观觉得“有点啰嗦”。

## GEN-007. 手机只要两句收口，生成却能拖到几百 token。长度惩罚、提示模板、stop、max_tokens 各自掐在哪一层，压过头会丢掉什么？

**答：** 长度要分层控：推理层用 max_tokens 做硬顶、用 stop 在段落结束符或字段闭括号处截断；提示层用“先结论后依据、恰好两句”和填空模板减少自由发挥；解码层可用长度惩罚或对超长完成降分；产品层可先回短答案再按需展开。只说“请简短”不够，因为聊天对齐偏向详尽。压太狠会砍掉限定条件和出处，事实错误上升，所以关键任务应允许最短必要从句，回归看信息是否丢失，而不是只看平均 token 数下降。

**深入展开：** max_tokens 会在句子中间切断，必须配合前端“未完成”状态或二次续写，不能把半句当最终结论。stop 对列表、JSON 有效，对散文则要选不会误伤缩写的序列。模板把生成从开放补全变成填槽，方差最小，但槽位本身仍可能被写成长段。长度惩罚改变的是解码目标，不改变模型以为“详尽=有帮助”的先验，极端惩罚会重复短句或提前 EOS。两段式“先写长、再摘要”能保信息，但多一次前向，移动端首包延迟更差。token 数≠字数：中英文、数字、markdown 的 token 密度差一截，产品应用字符/句数验收。评估要成对看压缩率和关键限定词保留率，避免上线后出现“很短但说反了”。

**后续追问：** 先出两句再让用户点“展开”，和一次生成长文再截断，缓存和计费有何不同？stop 和 EOS 同时存在时谁优先，模型学到的结束行为和硬截断如何冲突？结构化字段上的字符预算，要做在 schema 里还是做在解码器里？

**扩展问题：**
- 给同一批问题分别加 max_tokens=64、加两句模板、加长度惩罚，预期哪一种最容易切掉否定词？
- 如何检测“看起来短、其实在用密集术语堆砌”的规避行为？
- 流式输出时，怎样在第一句话结束就推送结论，同时保证后面不推翻第一句？

**推理回答：** 目标是两句内可执行结论，约束是对齐后的冗长先验和硬截断会破句。把控制按协议层/提示层/解码层/产品层拆开，每层只保证自己能保证的（上限、句式、偏好、交互）。最后用“限定词是否还在”约束压缩率，防止优化成空话。

## GEN-008. 下单通道要可解析 JSON，右花括号后面却多出一句口语，解析器直接报废。只在提示里禁止解释，为什么仍是软约束？解码阶段有没有办法把合法符号锁死？

**答：** 提示是软约束：采样一旦跳出 schema，后续 token 会在错误前缀上继续圆场，低温和 few-shot 只能降低尾巴解释、尾逗号、markdown 围栏，消灭不了。要把合法符号表下沉到解码：用 JSON Schema / 函数调用协议，或用文法/自动机逐步屏蔽非法 token，使右花括号之后不能再出现自然语言。服务端再做 schema 校验和有限次重试，失败不要把原文交给下游。评估要单列“多了前后缀”的案例，只看字段语义对会漏掉这类事故。

**深入展开：** 约束解码在每一步用栈或正则自动机算当前合法 token 集合，把其余 logits 置为 −∞ 再 softmax，成本是每步一次状态转移，换来的是语法级保证。函数调用则让运行时先拿到结构化参数对象，模型根本不经过“自由文本再解析”。temperature=0 仍可能因空格、全半角、字段顺序、多余 null 失败，所以解码锁的是语法，校验锁的是类型和必填。修复策略可以先截取第一个完整对象再 parse，但截取本身会吃掉模型想说的警告，业务上要规定“警告走独立字段”。重试会加延迟，应设次数和降级（规则模板/人工）。不要用“请输出 JSON”当唯一防线。

**后续追问：** 文法约束能保证合法 JSON，能保证金额字段是业务允许的枚举吗？校验失败是该重试同一 prompt，还是改成工具调用？约束解码和事后正则抽取，在首 token 延迟和失败率上如何取舍？

**扩展问题：**
- 给一个带可选嵌套数组的订单 schema，指出哪些错误 prompt 几乎防不住、必须靠自动机。
- 模型在合法 JSON 里编造了不存在的 SKU，这还是格式问题吗？哪一层该拦？
- 如何在评测集里构造“爱加解释/爱包 markdown/爱尾逗号”三类样本并分别计分？

**推理回答：** 目标是解析成功率接近硬保证，约束是采样过程本身会偏离。先承认 prompt 只能改概率，再把格式移到“每步允许的 token 集合”和“解析后 schema”，最后用分类评测把语法失败和语义失败拆开。若业务不允许偶发解析错误，就不要停留在提示层。

## GEN-009. 用 ReAct 跑循环时，Action 一输出完，模型就接着自行编造 Observation。截断要交给结束符，还是事先登记停止字符串？流式输出下，停止串若被拆到两个词元里，需要防住哪些问题？

**答：** 应注册 stop sequence，例如 `"Observation:"`。结束 token 表示整轮回复结束，模型不一定会在工具交接处发出它，反而可能把观察也编出来。Stop sequence 是调用方在解码后的文本上匹配的字符串，不要求是单 token，也不依赖模型学过它。匹配到就停，把动作交给工具，再把真实观察写回上下文。

**深入展开：** 结束 token 是词表里的特殊 id，属于训练信号；stop sequence 是 UTF-8 字符串，可以跨多个 token，通常在 detokenize 之后做子串匹配。命中片段是否回传要因实现而异，必须用测试钉死。流式风险：stop 的前缀可能先发出去（例如先吐出 `Observ`），需要缓冲尚未确认的后缀，确认不是 stop 前缀再下发给用户。Stop 设得太宽（例如单独的换行）会切断正常段落。字符串截停不能替代正确模板和结束 token：整轮自然结束仍应靠结束 token。ReAct 交接、少样本里“下一例”隔离，是字符串截停的典型用途。

**后续追问：** 跨 token 匹配如何做成每步增量、避免全量重扫；流式下怎样保证半截 stop 不显示给用户；命中后返回文本是否应剥掉该字符串。

**扩展问题：**
- 画出 ReAct 状态机，说明为什么工具交接触发点更适合字符串截停而不是结束 token。
- 把 stop 设成单独换行会破坏哪些合法输出？
- 列一组流式与非流式对照用例，保证两种模式的最终文本一致。

**推理回答：** 用“谁定义、在哪一层生效、是否要模型学会”区分两种停止。工具边界是协议，不是模型的自然结束，所以用调用方字符串。再补上流式缓冲，避免半截协议泄漏。用轨迹是否在 Action 之后停下验收。

## GEN-010. 一次请求标称上限是 8K，系统提示吃掉 2K、历史吃掉 4K、检索吃掉 3K，回复还没占位置。额度为何已经爆掉，各块要怎样让位，生成才写得进去？

**答：** 8K 是一次请求里系统提示、历史、检索、当前用户句和预留输出的总和上限，不是“输入可以单独用满 8K”。2+4+3 已经是 9K，还没算当前问题和回复，服务端会截断或拒请求；即便塞进去，中间段落也更容易被忽略。应先锁输出预算（例如 512–1024 token），再压缩系统提示，历史改滑动或摘要，检索按分数截到剩余配额。

**深入展开：** Tokenizer 下中文、代码、表格的 token/字比往往高于英文散文，同样 4K 汉字可能远超 4K token，所以预算必须按 token 而不是按字。窗口决定可见范围：被截掉的内容等于从未发生。Prefill 成本大致随输入长度上升，注意力在长序列上还会超线性。把检索从 2K 堆到窗口顶，噪声和中间信息丢失会让正确率下降，所以“用满窗口”不是目标。生产要分别盯截断率、输入 token 分位数，以及证据放在前/中/后时的答题正确率。

**后续追问：** 输出预算算不算进上下文窗口；接口是否把 max_tokens 从窗口里扣除；怎样用长度扫描找出该任务的有效窗口，而不是看标称值。

**扩展问题：**
- 给 32K 窗口的合同问答，写出系统提示、条款原文、问题、输出四段的 token 配额和截断策略。
- 历史摘要容易丢掉哪类约束，怎样用结构化记忆补回来？
- 检索命中很多时，是扩窗口还是先重排少塞，你用什么指标做决定？

**推理回答：** 约束是窗口 = 全部可见 token + 输出预留。先保证输出和系统约束不被挤掉，再按对正确率的边际收益分配历史和检索。用截断日志和位置敏感评测验收，而不是看标称 8K。

## GEN-011. 32K 长度上全量注意力把训练显存打爆，任务是审 200 页合同。硬拉长窗口、换滑窗、换稀疏注意力、先检索再生成，你怎么选？

**答：** 标准自注意力对长度 n 是 O(n²) 计算，训练时若物化注意力分数，32K 下中间存储会到数 GiB 每头的量级，多层多头立刻不可行。推理侧的分块注意力降低的是显存读写和峰值中间张量，算术量仍近似二次。若任务是从已知章节抽出几条条款，先检索再放进短窗口通常比硬扩窗口更省、更好拆开评测；只有必须全局对照或跨章依赖时，才上长窗或滑窗/稀疏结构，并且要用本任务的长文评测，而不是看接口能不能把全文收进去。

**深入展开：** 粗算：FP16 存满一张 [n,n] 分数，n=8192 时单头大约 128 MiB，n=32768 时大约 2 GiB，所以训练必须走分块、重计算或缩短有效可见范围。n 翻倍，QKᵀ 的 FLOPs 大约翻四倍。滑窗把每层可见范围限制在 W，复杂度变成 O(n·W)，KV 也可只环形保留 W，但远处的精确定义往往只能靠多层间接传递，精确引用第 1 页的术语时容易断。文档问答里按标题或条款分块检索，把 top 证据放进大约 4K–8K 的窗口，失败可以分记：漏召回是检索的，胡编是生成的。标称能吃下 128K 只说明位置编码和服务限制放开了，不说明夹在中间的例外条款还能被用上。

**后续追问：** 分块注意力有没有把复杂度变成线性？滑窗堆 32 层后理论感受野怎么算，为什么仍可能找不到文首定义？长窗和检索同时做时，额外成本应记在 prefill 还是记在检索召回？

**扩展问题：**
- 估算 n 从 8K 扩到 128K 时，全注意力 FLOPs 和 KV cache 各自大约放大多少倍。
- 合同里「第 3 章定义、第 12 章例外」必须联合理解时，纯滑窗会在哪一步丢掉约束？
- 怎样用证据位置扫描区分「放得下」和「用得上」？

**推理回答：** 先问任务是定位、对照还是全文综合，再问瓶颈是训练中间存储、推理 KV，还是质量。二次复杂度决定「硬吃全文」的成本曲线；证据稀疏时，先改任务形态（检索）比改核函数更划算。拍板后用长度扫描和位置扫描验收，而不是看请求是否返回 200。

## GEN-012. 三处风险披露要交叉核对，文档是约 200 页的招股书，窗口仅 8k。一条路是检索相关页再对着原文读；另一条是先做层级摘要。各自会丢掉什么？

**答：** 交叉核对要保留条款编号、限定词和跨节指针，应切块（按标题或页，块与块重叠一段）、检索把相关原段落拉回 8k，再在原文上对齐，而不是先摘要再推理。层级摘要 / map-reduce 适合“列出风险主题”，会抹掉“除……外”“参见第 11 节”这类短限定，导致假一致。约 200 页通常是 10⁵ token 量级，8k 窗口一次塞不下；长上下文模型能少切几次，但仍要把低相关页挡在窗外，并为每条结论留出处，避免在压缩句上编页码。

**深入展开：** 切块过大则噪声占满窗口，过小则一句话的条件从句被切断，重叠就是为了保护跨块从句。检索之后应再排序，只留与三个披露点同指的段，而不是 top-k 各不相干的热段。map 阶段可以并行问“本段有没有回购/诉讼/关联交易”，reduce 做合并列表——这解决覆盖，不解决“第 3 节与第 11 节是否矛盾”，后者必须把两段原文同时放进同一窗口。滑动阅读整份文件能扫到，但没有检索指针时模型记不住 80 页前的数字。验收用“能否引用原句+条款号”，而不是摘要是否通顺。预算紧时先检索三处再精读，不要对 200 页做均匀摘要。

**后续追问：** 块大小该跟嵌入模型窗口走，还是跟生成模型窗口走？两处措辞不同但指向同一风险，检索如何避免漏召回？如果必须用摘要，怎样在摘要里强制保留数字、否定词和交叉引用？

**扩展问题：**
- 设计一个“三处互引是否一致”的标注集，说明为什么只用主题摘要分数会虚高。
- 长上下文模型把 200 页一次喂进去，仍可能在中间页丢失针状事实，补救是检索还是重排？
- 出处链接丢失时，如何防止模型生成看起来合理但不存在的条款号？

**推理回答：** 任务约束是跨节对齐原句，不是产生可读综述。由窗口 8k 对 10⁵ token 推出必须取舍进窗内容；再比较“原文片段”和“摘要”谁保留限定词与指针，选定检索+精读。若验收改成“写一页投资摘要”，层级摘要才成为主路径。用引用命中率和矛盾检出率验证，不用摘要 BLEU。

## GEN-013. 语料按 4K 截断打包做预训练，服务侧靠位置插值对外标成 64K。短续写还顺，可放在下标 40000 处的证据却看不见。训练分布上还有哪三点挡住 4K 权重直接当 64K 用，而不是算力或 KV？

**答：** 模型只在位置 0…4095 上优化过下一 token 损失，而且打包进 4K 的文档大多数远短于 4K，优化器几乎没见过“必须回看一万 token 之外”的监督。位置插值只让 40000 这个下标在公式里有定义——绝对表不会越界、旋转相位被压回训练过的角度范围——并不自动产生长距对齐信号。语料里真正前后依赖的长文档（整本书、整仓、跨章合同）相对网页短片段很少；再把多篇短文拼进同一 4K、并用文档块对角 mask，模型学到的是“远处是另一篇，可以忽略”，和“证据在 40K 处”正好相反。所以 64K 推理同时是长度越界、位置越界、依赖距离越界，不是把核函数乘得动就算会用。

**深入展开：** 三件独立的事不要并成一件。①长度直方图：固定窗打包时，500 token 的页面占一个槽，20 页 PDF 常被截断；位置 t≥4096 的隐状态从未进过 LM head，插值后这些位置是新流形。②位置几何：可学习绝对向量没有第 40000 行；旋转位置把下标按 L_train/L_target 缩放后，近邻分辨率被压、远处相位仍可能离开训练分布。无论哪种，改的是“公式能否算出分数”，不是“分数是否还表示训练时那种相对距离”。③数据与 packing：长而自洽的文档在 token 占比上薄；为了填满 4K 而拼接，再加跨文档不可见，等于教模型把远距离当噪声。中间丢失（lost-in-the-middle）在这种分布上几乎是默认行为——窗中间位置既少作为“必须检索的键”，也少作为“必须带着远证据的查询”。把 L 提到 64K 却不提高长文档采样、不加针状/跨段目标，多出来的上下文是空容量。这和 prefill 二次、decode 读 KV 涨几倍不是同一条问题：就算算力和显存都够，4K 监督也撑不起 64K 检索。补救是中段继续训（上采样长文档、打开跨段可见、用针状/多跳目标），而不是只改推理接口上的最大长度。

**后续追问：** 只换线性偏置类位置、仍用 4K 短文打包，40K 处的针能不能自己好；怎样改 packing 才不会学成“其他文档无关”；token 里要有多大比例来自超过 16K 的真长文，针状任务才开始动。

**扩展问题：**
- 画一张 90% 文档短于 1K、再拼进 4K 的长度直方图，标出损失里实际出现过的依赖距离。
- 只做位置插值、不加长文数据时，局部抄写探针和 40K 处的 ID 检索哪个仍应能过、哪个应失败？
- 为什么对 4K checkpoint 先检索再塞 2K 证据，常常比直接打开 64K 窗口更稳？

**推理回答：** 把训练支撑写成“长度≤4K × 见过的位置 × 见过的依赖距离”。64K 推理在三个轴上都离开了支撑；插值只修位置公式。因此缺的是长文档采样和奖励远距检索的目标，不是更大的注意力核。用“局部续写仍通、远针失败”这对探针验收，而不是看接口是否还报长度错误。

## GEN-014. KV cache 一旦关闭，生成进行到第 2048 步时延迟为何会数量级变差？

**答：** 自回归每一步都要用当前 Q 去对全部历史 K 做点积，再用 V 加权。KV cache 把已经算过的 K、V 留在显存，新步只投影 1 个 token 的 Q/K/V 再读 cache。关掉 cache 等于每吐 1 个 token 就把长度为 t 的前缀重新跑完所有层的 QKV 投影和 FFN；到第 2048 步，线性层工作量大约是第 1 步的 2048 倍。注意力即使有 cache 也仍是每步 O(t)，但那只是读一遍历史 K、V；无 cache 时连投影和 FFN 都按 O(t) 重复，这才是数量级恶化的来源。

**深入展开：** 有 cache 时 decode 步：新 Q/K/V 为 [B, 1, d]，cache 为 [L, 2, B, n_kv, t, d_h]，FFN 只作用于这 1 个位置。无 cache 时输入变成 [B, t+1, d]，每层 GEMM 的序列维是 t+1。生成 n 个 token：有 cache 时投影/FFN 总量约 O(n)，无 cache 时约 O(n²)。示意：t = 2048、d = 4096、FFN 中间维约 1.1×10⁴，单层 FFN 无 cache 就要处理约 2048 倍于单 token 的 matmul，32 层叠起来，单步 decode 从毫秒级变成接近一次短 prefill。边界：prompt 很长时 prefill 本身就贵，cache 省的是后续 decode，不是 prefill；cache 不把注意力变成线性；若实现只 cache 了最后一层或只 cache 了 K，表现会介于两者之间——典型日志是首 token 时间正常，每输出 token 时延随长度线性变差。

**后续追问：** Prefill 和 decode 各自对 cache 是写还是读？cache 里存的是投影后的 K/V，还是 softmax 之后的注意力权重？多轮对话怎样靠前缀复用避免把历史再 prefill 一遍？

**扩展问题：**
- 画出有 / 无 cache 时第 t 步各张量的形状。
- 为什么说“有 cache 后注意力仍要算，只是不必重算历史的 K/V”？
- 若把 cache 量化到 INT8，延迟和显存各变多少，质量风险更偏 K 还是 V？

**推理回答：** 从“每步必须看见全部前缀”出发，列出必须保留的状态就是 K 和 V。比较保存它们与重算它们：重算让投影/FFN 变成对长度求和，故第 2048 步爆炸。用单步耗时对输出长度作图，斜率接近线性即说明 cache 未生效。

## GEN-015. 无法重新训练，KV 把 GPU 显存顶满。你是先做 KV 量化，先把块卸到 CPU，还是先扔掉旧 token？

**答：** 权重冻结、不能改结构时，先做对可见历史伤害最小的 KV 量化（BF16 → INT8 或 FP8，并用长上下文任务盯质量），再考虑把暂时不用的块卸载到 CPU，最后才用丢掉旧 token 换窗口。量化减少每元素字节，卸载减少 GPU 驻留，淘汰改变模型真正看见的历史，三者安全程度不同。针在草堆、多跳引用对淘汰最敏感，对 INT8 KV 通常更耐；无限流式会话既要保近期细节又不能 OOM 时，淘汰或滑动窗口几乎不可避免。

**深入展开：** 推理期能做的：①按头或按 token 量化 K/V。K 的动态范围常比 V 更极端，朴素对称 INT8 可能让注意力分数漂移，实践中往往对 K 做分通道缩放，或先只量化 V。②分页分配解决碎片，不改变理论占用。③把冷 block 迁到 CPU/NVMe，命中冷块时延迟变成 PCIe 量级（数十微秒到毫秒），吞吐下降但答案集合不变。④保留开头几个 sink token 加最近 W 个位置，或按历史注意力分数丢掉“不重要”token——后文若回指被丢实体，事实会错。训练期才能做的分组注意力、低秩潜变量 KV、跨层共享，这题先排除。验收必须同时看显存、tokens/s 和长上下文正确率；只看显存会选出“能跑但不会答”的策略。

**后续追问：** 为什么 K 通常比 V 更难量化？分页分配和压缩是不是同一件事？卸载到 CPU 后，p95 延迟尖峰通常来自哪类访问模式？

**扩展问题：**
- 设计实验，专门检验“按注意力分数淘汰”会不会漏掉文档前部的约束条件。
- INT4 KV 和丢掉约一半历史 token 都能省大约一半显存，法律合同问答里你选哪个？
- 系统提示的前缀复用能省多少显存，它算不算压缩？

**推理回答：** 约束是权重冻结、尽量不改变可见 token 集合、GPU 显存必须下降。按“是否改写历史集合”排序：量化/卸载保集合，淘汰不保。再按实现成本和失败模式排试点顺序，用长上下文评测而不是短对话分数做门禁。

## GEN-016. TPOT 几乎持平，可 TTFT 随 prompt 由 1K 增至 16K 而恶化。这把瓶颈钉在哪一段，该先动哪些旋钮？

**答：** 首 token 之前必须完成 prefill：整段提示一次前向，并为每一层写入 KV。提示变长，这段计算和写缓存都变重，所以 TTFT 涨。之后 decode 每步只算 1 个新 token、读已有 KV，步间隔（TPOT）主要受读权重和读 KV 的带宽限制；KV 从 1K 到 16K 会增加一些访存，但通常远小于再跑一遍 16K prefill。先缩短或缓存提示前缀、做分块 prefill，而不是先去抠 decode 微内核。

**深入展开：** Prefill 计算密集，长序列矩阵乘可并行，算力利用率高；decode 访存密集，每步几乎扫一遍权重，算术强度低。TTFT ≈ 排队 + 调度 + prefill；TPOT ≈ 单步 decode。降 TTFT 的旋钮：压缩系统提示、前缀缓存、多轮复用同一前缀、prefill 与 decode 分池、把简单请求分给小模型。流式输出改善体感，但不减少 TTFT 本身。若 TTFT 抖动而 TPOT 稳定，更像排队或长提示抢占，而不是 kernel 回归。量级上，prefill 时间随提示长度接近线性到超线性；KV 尚未极大时，decode 步时变化较缓。

**后续追问：** TTFT 和 TPOT 分别从哪个时间戳量到哪个时间戳；前缀缓存命中时消失的是哪一段；batch 增大时 TTFT 和 TPOT 谁先恶化。

**扩展问题：**
- 同样生成 1000 个 token，提示 1K 对比 32K，你预期哪段延迟主导用户等待？
- 语音通话为什么比异步摘要更不能忍 TTFT？
- 如何用追踪区分“在等 KV 槽位”和“prefill 本身算得慢”？

**推理回答：** 把延迟拆成 prefill 与 decode，对照压测：只随输入长度变差的是 TTFT，瓶颈就在提示前向。优化对准提示长度和前缀缓存。用分离的 TTFT/TPOT 直方图验收，避免只看端到端平均值。

## GEN-017. 九个会话加起来 KV 其实还在额度里面，可系统给每路都划了 32K 一整段连着的坑，第十个会话就申请失败。切到固定块表后，共享前缀、块内碎片、抢占换出分别消灭哪类浪费，又在何时抬高 p95？

**答：** 连续预留按 max_seq_len 给每条请求划一整段，九条实际只有约 8K 的对话也会按 32K 占坑，第十条在“账面上还有空位”时失败。改成每 B 个 token 一块（例如 16）的块表后，只为 ceil(len/B) 块建映射，消掉的是预留尾巴上的外部碎片。系统前缀让多条请求的块表指向同一组物理块，谁先写出分歧谁拷贝该块（写时复制），消掉的是重复前缀。显存再紧时按策略暂停一条：块换到 CPU，或丢掉后重做 prefill——消掉的是活请求把池子钉死。代价是每条最后一块内部空洞、写时复制的突发拷贝，以及某步 decode 碰到换出块时整批等待，p95 会从“算得慢”变成“在等 PCIe 或重算”。

**深入展开：** 块表把逻辑位置 i 映到物理块 `table[i // B]` 与块内偏移 `i % B`，注意力核按表 gather，不再要求整段 KV 连续。B 太小则间接寻址和表项变多，B 太大则最后一块空洞变大：例如 B=16、长度 17 占两块，空 15 个槽，空洞按每 token KV 字节计。前缀共享对 1K 系统提示 × 64 路并发只物化一份 1K 的 KV；第 1001 个 token 若各会话不同，只新分配（或 COW）那一块，已共享的 1K 仍只读别名。租户改了系统提示或注入了不同检索段，共享在该请求上断开，不要误伤别人的物理块。抢占是调度策略而不是压缩算法：空闲块不够写下一条 token 或新 prefill 时，选最低优先级/最闲的序列，memcpy 到 pinned host 或直接丢弃。换出按块走 PCIe，量级从数十微秒到毫秒；若同一 decode batch 里混进一条冷序列，同步等待会抬高整批延迟。交互式工具轮次中途不要抢，否则用户以为模型死了。规划看“已分配块数 × B”和“存活 token 数”的差，那就是内部碎片；不要再用“剩余 GiB ÷ 满窗 KV”去解释这次分配失败——失败发生在预留策略，不是理论字节公式。

**后续追问：** 两条请求共享 1K 前缀后在第 1001 个 token 分手，新分配和拷贝的各是多少块；永远抢最新进来的序列，为什么会饿死一条 200 token 的高优先级补全；怎样从分配器计数读出内部碎片率。

**扩展问题：**
- 流量是 200 token 短聊混 8K 检索提示时，B=8 和 B=128 谁更浪费槽位、谁更吃 gather 开销？
- 写出一条写时复制规则，保证往共享前缀追加时绝不会改掉另一租户的 K/V。
- 什么情况下你宁愿丢掉被抢占序列的 KV、重新 prefill，也不换到 CPU？

**推理回答：** 故障是分配策略而不是每 token 字节公式。把浪费拆成预留尾巴、重复前缀、末块空洞三类，分别用分页、别名、接受内部碎片来对症；再把压力下的动作定义成抢占策略，并单独记账换出/重算的尾延迟。验收用已分配槽位数对存活 token 数，以及换出发生时的 p95，而不是只看还能不能再启动一条满窗请求。

## GEN-018. 权重把 GPU 占满后空闲额度 24 GiB。按 token 计的 KV 公式来估，长度为 8K 的上下文最多能同时跑多少路？

**答：** 每 token 的 KV 占用 ≈ 2 × 层数 × KV 头数 × 每头维度 × 每元素字节。举例：40 层、8 个 KV 头、head_dim = 128、BF16（2 字节）时，2×40×8×128×2 = 163840 字节 ≈ 160 KiB/token；一条 8K 序列约 1.25 GiB。24 GiB 余量理论上约 19 条满 8K 序列，扣掉激活、碎片和运行时预留，线上常按约 12–16 并发来定上限。并发、上下文长度、KV 精度乘在同一笔预算上，拉长窗口就必须降并发。

**深入展开：** 公式必须用 KV 头数而不是查询头数：查询头 32、KV 头 8 的分组注意力，cache 按 8 算。总账：GPU 显存 − 权重 − 驱动上下文 − 激活 ≈ KV 可用。Decode 时激活很小（序列维为 1），prefill 激活大，所以容量规划要留 prefill 峰值，而不是只按 decode 稳态。若改成 KV 头 = 32 的满头注意力，每 token 变成 640 KiB，8K 序列约 5 GiB，24 GiB 只能塞下约 4 条。边界：变长流量按 p95 长度估，按均值会在长尾 OOM；分页分配减的是碎片，不减小每 token 字节；张量并行度为 p 时，单卡 KV 要按切分方式除以 p。规划输出是一条双曲线：batch × ctx ≤ 可用显存 / 每 token KV。

**后续追问：** KV 头从 8 改回 32，并发上限怎么变？为什么按平均 2K 上下文排产，线上仍会 OOM？张量并行度为 2 时，单卡 KV 怎么改写公式？

**扩展问题：**
- 精度从 BF16 改到 FP8 后，24 GiB 能支持的 8K 并发如何变，质量上你担心什么？
- 同一余量下选 4 并发 × 32K 还是 16 并发 × 8K，分别适合哪类产品？
- 如何用框架上报的 KV block 占用反推公式有没有漏项（例如位置编码的查找表）？

**推理回答：** 目标是在固定余量下最大化并发 × 长度。先写出每 token 字节公式并代入给定结构，得到单序列体积，再做整数除法并留峰值余量。最后用 batch × ctx = 常数说明两者互斥。用实际已分配 KV 字节与公式对比验收。

## GEN-019. 采用 GQA 时，KV cache 的字节占用应按什么公式来算？
**答：** 对每层均为全注意力且 K/V 维度相同的模型，近似字节数为 2×层数×已缓存 token 总数×KV 头数×head_dim×每元素字节数。用 KV 头数而不是 Query 头数。
**深入展开：** 另加块对齐、量化尺度、临时缓冲及并行布局开销；滑窗或异构层需逐层计算。
**后续追问：** 为什么不能仅用隐藏维度估算所有模型？GQA/MQA 的 KV 头数可能少于 Query 头数，异构层和并行布局也会改变实际存储。
**扩展问题：**
- 采用滑窗与全注意力混合层时，应怎样逐层估算 KV 上限？
- 张量并行中的 KV 分片或复制会怎样改变单卡容量估算？
**推理回答：** 先明确注意力结构和并行复制方式，再核算可用并发。

## GEN-020. 名义上的上下文长度和实际有效的长度各自衡量什么？后者为何只能在具体任务上实测，不能照抄规格？
**答：** 标称长度表示接口或架构允许接收的范围；有效长度表示在特定任务、质量门槛和干扰条件下仍能可靠使用的信息范围。后者必须实测。
**深入展开：** 按长度、证据位置、任务复杂度画质量曲线，不只记录能否接收请求。
**后续追问：** 128K 输入不报错能否证明支持可靠的 128K 推理？不能，这只验证接口容量，仍须测试该长度下的证据利用和任务质量。
**扩展问题：**
- 怎样为同一模型分别定义检索、聚合和跨文档推理的有效上下文长度？
- 质量随长度下降时，如何排除输出预算不足或输入被静默截断的影响？
**推理回答：** 容量是必要条件，任务正确率才说明信息被有效利用。

## GEN-021. 即便单针检索已经测通，为何仍不能据此宣称具备长上下文实力？
**答：** 单针测试主要检验定位显式信息；真实任务还包括多证据组合、干扰消解、聚合和多跳推理。应增加多针、重复实体、否定信息与无答案样本。
**深入展开：** 固定生成预算并记录输入长度，避免不同预算掩盖退化。
**后续追问：** 检索正确但汇总错误该归因给哪个环节？先检查证据是否完整传入，再定位聚合或推理阶段，不能一概归因于检索失败。
**扩展问题：**
- 如何构造多个相关针、相似干扰针与无答案情况，避免测试只奖励字符串匹配？
- 同一长上下文测试更换实体名称后性能骤降，可能暴露什么捷径？
**推理回答：** 把找到证据与使用证据分开打分，避免用单一通过率替代综合能力。

## GEN-022. 只把 RoPE 的缩放配置拧了一下，长上下文质量为什么仍然没有着落？
**答：** 位置缩放改变位置表示的使用范围，但模型仍可能缺乏长序列训练和任务适应；还受注意力计算、KV 容量及服务限制影响。
**深入展开：** 需同时测试长输入能力和原始短上下文能力，避免只验证配置可加载。
**后续追问：** 插值与直接外推分别改变了什么？插值把更长序列的位置映射到较熟悉的范围；直接外推使用训练范围外的位置，两者都需任务验证。
**扩展问题：**
- 扩窗后短上下文质量下降时，应怎样设计对照实验定位原因？
- 如何区分模型的位置泛化失败、服务端长度限制和 KV 显存不足？
**推理回答：** 配置允许长度扩大，不等于权重学会利用该范围的信息。

## GEN-023. 要看出事实挪到上下文不同位置后模型会不会漏掉，证据位置扫描实验该怎样设计？
**答：** 保持问题、答案证据和干扰内容基本不变，把证据移动到开头、中间、结尾及多个随机位置，比较正确率与引用准确率。
**深入展开：** 改变位置时控制总长度和局部格式，并多次采样报告不确定性。
**后续追问：** 证据复制到首尾会引入什么混杂因素？它同时改变证据出现次数和总长度，因此不能把性能变化仅归因于位置。
**扩展问题：**
- 移动证据时，怎样保留标题、段落衔接与局部格式，避免产生新的提示线索？
- 如何用多位置、多随机种子试验区分稳定的位置效应与采样波动？
**推理回答：** 只有控制内容与长度后，质量差异才更能归因于位置。

## GEN-024. 长文摘要要保住关键例外，对照原文回查和专项探测该怎么做？
**答：** 建立条款、例外、时间与实体的覆盖清单，对摘要逐项回查原文；单独测试否定句、限制条件和跨段落依赖。
**深入展开：** 摘要流畅或与参考摘要相似，不能保证保留所有关键约束。
**后续追问：** 例外在文档中间时如何做压力测试？固定条款和问题，将例外移到不同位置并增加干扰，检查摘要是否仍保留其适用条件。
**扩展问题：**
- 如何设计“主规则正确但例外遗漏”的摘要反例，检验评分器是否足够敏感？
- 跨段落限定条件被分别摘要后，怎样验证其逻辑关系仍被保留？
**推理回答：** 把下游决策所需的关键事实作为验收标准，而不是只看文笔。

## GEN-025. 线上窗口并没有耗尽，可第 12 轮机器人又来要订单号（用户早就给过）。是截断、是摘要写偏、还是检索根本没召回，三者怎么拆开，长期记忆该落成什么形态？

**答：** 窗口未满却忘掉已报事实，应先查应用层有没有用摘要覆盖原文、槽位被写坏，或检索根本没召回早期轮次，而不是先怪模型记性差。把订单号、承诺和未决动作写成带时间戳、来源轮次的结构化字段，每轮只注入相关槽位加最近若干轮原文；不要把整段对话反复压成一段越来越短的散文。若已经在做滚动摘要，对照订单号首次出现的原文和当前摘要，看是压缩丢了字段，还是提示里根本没有把记忆塞回去。

**深入展开：** 三条管道要分开查。按轮数或 token 截断会让早期轮次直接消失，但窗口仍有余量时这条往往不是主因，必须转储实际送进模型的提示才能确认。摘要改写常丢掉数字和否定词，例如「不在保修」变成「在保修」。向量记忆若只按最新一句检索，第 2 轮的订单号在语义上不像「当前问题」，会漏召回。结构化记忆用字段合并更新，未提及的字段保持原值；标识符用关键词或精确匹配，不要只靠向量。评估用「第 N 轮能否复述第 k 轮实体」的探针，而不是单轮流畅度。

**后续追问：** 同一段对话被摘要三次之后，数字和否定词通常怎样退化？用户更正了订单号，旧值如何作废？记忆写入若被提示注入污染，怎样鉴权或过滤？

**扩展问题：**
- 设计一张对话记忆表（字段、更新规则、注入模板），保证订单号在任意时刻只有一个当前值。
- 怎样用探针区分「模型看见了但没用」和「提示里根本没注入」？
- 高敏感对话里，哪些字段禁止写入长期记忆？

**推理回答：** 先拿到真实提示，确认事实是否在模型可见范围内。不可见则修截断、摘要或检索；可见仍不问，再查指令是否要求复用槽位，以及上下文是否被无关轮次稀释。长期记忆选结构化合并，是因为散文摘要没有字段级更新和过期语义。用实体复述探针和提示日志闭环验证。

## GEN-026. RAG 线下命中率写着 82%，人工却看到约 25% 所谓答对的内容在召回片段中并无支持。不可回答样本怎么单列评，检索闸门和生成闸门分别怎么设？

**答：** 这个准确率被「蒙对」和「用参数记忆补全」抬高了，必须单列一组检索中故意不含答案的题，正确行为是拒答或声明资料不足。检索段设相关性和覆盖率门槛：最高分都低，或关键实体对不上，就不要生成。生成段强制引用，并用蕴含检查对齐数字和实体；引用撑不住就拒。发布看可回答正确率、不可回答拒答率、误拒率，而不是一个混合准确率。

**深入展开：** 不可回答集可以这样造：抽走证据、换成同主题干扰段，或问超出文档时间范围的事实。训练和提示里要有对等的拒答示范，否则下一步预测损失会逼模型总吐出一个跨度。检索不要只看向量余弦，对专名和数字做关键词对账。生成后做跨度对齐：答案里的数字、日期、实体必须能在引用中定位。两段门槛分工不同：检索门槛减少「无中生有的上下文」，生成门槛捕获「有上下文但仍在编」。线上同时看拒答率和用户追问率：拒答过低可能在瞎编，过高可能门槛过紧。

**后续追问：** 问价格却只检索到产品描述，算可答还是不可答？蕴含模型自己也会错，怎样当辅助而不是唯一判官？把不可回答题混进训练，会不会让可回答题变得过短、过拒？

**扩展问题：**
- 写一份可回答与不可回答各数十条的标注规范，并规定「部分证据」怎么标。
- 只靠提示「没有依据就说不知道」，和加上引用校验，拒答率通常差在哪里？
- 怎样防止评估者把「听起来合理」标成正确，从而掩盖无依据回答？

**推理回答：** 生产上错答的代价高于拒答，所以不可回答必须当成一等公民指标。从抽查里「无依据却判对」倒推，要在检索覆盖和生成蕴含两处设门。用三元指标做发布门禁：可答正确、不可答拒答、误拒。

## GEN-027. 营收数字在 ROUGE 看起来还行的财报摘要里凭空出现。不要靠再写「不要编造」做验收，怎样把实体和数字强制对齐回源文档来抓幻觉？

**答：** ROUGE 只奖励 n-gram 重叠，编造一个量级相近的数字往往仍能得分。把摘要里的数字、专名和同比/环比方向抽出来，强制回原文定位；定位失败或极性相反就判事实错误，并改写或删句。解码降低随机性，结构上先抽证据句再压缩，高风险数字尽量保留原文用词并附出处。提示里的「不要编造」只能降低先验，不能当验收。

**深入展开：** 常见形态包括数量张冠李戴、把预测写成已发生、把「不包含」写成「包含」。可行流水线是分节摘要、合并、再跑事实校验。校验不必是大模型：用规则抽出数字并做字符串或模糊匹配，对「增长/下降」做极性核对；摘要中首次出现、原文没有的数字，默认不得自动通过。低温或贪心解码减少同义改写带来的数字漂移，但挡不住模型补「常识」。评估改报事实一致性：摘要拆成原子命题后，能被原文蕴含的比例；并单独准备脚注和例外条款样本，因为流畅摘要最常丢掉否定和限制。

**后续追问：** 原文有两处互相冲突的营收口径，摘要只写其中一个，算幻觉吗？改成抽取式摘要能否避免编造，代价是什么？校验器漏掉「原文只是并列、摘要写成因果」时，怎样补一层检查？

**扩展问题：**
- 写一个最小数字对齐程序：从摘要抽出全部数字，汇报无法在原文命中的项。
- 如何构造「主结论对、脚注例外被丢掉」的评测用例？
- 人工审核应该重点抽检哪类摘要，而不是随机抽一个固定比例？

**推理回答：** 读者会按摘要里的数字做决策，所以数字和实体必须可回源。ROUGE 与此不对齐，必须另建对齐检查。能自动对齐的先自动拦截，对不上的进人工。提示只改变生成先验，不替代检查。

## GEN-028. 多任务客服里，退货正卡在运单号，用户突然问黑色 SKU 是否有货。怎样发现话题已经切走，把旧任务挂起，并且不让旧槽写进库存查询？

**答：** 把任务状态和当前话语分开处理：对正在填的槽位做「继续 / 插入新任务 / 取消」判别，不要默认每一句都写进旧表单。识别到新意图时，把退货任务连同已填槽位快照挂起，用新意图的干净上下文去查库存；用户再说「继续退货」再恢复。绝不能把退货单号静默带进库存查询的工具参数。

**深入展开：** 典型故障是整段历史无差别拼接，模型把「运单号」和「黑色那款」塞进同一次函数调用；或只按最近实体续槽。检测可以叠加：当前节点期望的槽位类型和本句实体对不上时的规则；输出 continue/switch/cancel 的分类器；先产一个结构化对话行为再决定是否调工具。挂起栈要记录任务编号、已填槽和下一问，不能只靠一段自然语言摘要。边界情况是用户其实在问「这件黑色的运单号填哪个」——字面像切换，实际是澄清——高风险切换应先短确认一句。评测集要覆盖中途插入、澄清、取消再开，分别打任务完成率和错误工具调用率。

**后续追问：** 短确认会多一轮延迟，什么场景可以静默挂起？用户想同时退货和查库存时，两套上下文如何隔离？分类器把切换判成继续，怎样用工具参数校验兜底？

**扩展问题：**
- 写出 continue/switch/cancel 的标注指南，并各给一条易混例句。
- 旧任务挂起超过数十分钟再恢复，要不要重新校验订单状态？
- 如何在日志里打话题边界，方便离线统计多轮鲁棒性？

**推理回答：** 任务型槽位带副作用，填错会打到退货接口，所以必须先判断本句是不是给当前任务的槽，再决定挂起还是填充。检测可以廉价，恢复必须显式。用错误工具参数率和任务完成率验收，而不是单轮是否说得流畅。
