## SERVE-001. MPS 把两份 7B 塞进同一块 H100，各自 decode 取 batch=4，耗时相对独享卡翻倍还多。要坐实瓶颈是片上缓存互相踩踏、而不是算力没吃满，L2 命中率、HBM 行打开冲突、上下文切换这三项该怎么读？救法是给 SM 绑定额度、错开发射节奏，还是把副本分到两块加速卡？

**答：** 先排除「两份负载把 Tensor Core 加满」：若 SM 吞吐只有独占时的一半、但两条进程的权重工作集加起来远超片上缓存，这是缓存颠簸。对照独占基线看 L2 命中率是否腰斩、HBM 行打开/冲突计数是否翻倍、以及 MPS 客户端之间的上下文切换是否和 decode 步对齐；三者同时恶化就能定案。L2 还能靠绑 SM 配额或错开步频救回一截就先软隔离；两套 7B 权重大小注定每步对打、命中率救不回来，就拆到两张卡。

**深入展开：** MPS 让两个 CUDA 上下文共享一张卡的 SM 和存储层次。7B 级 decode 每步几乎按层扫过自己的全部权重：单份 FP16 大约 14 GB，H100 公开规格里 L2 只有约 50 MB，本来就只能缓冲当前层的 tile，不能缓冲整网。两份互不相同的权重地址交错进来后，A 刚装进 L2 的 tile 会被 B 的下一层挤掉，下一次 A 再读同一层只能回 HBM。证据链：①L2 hit rate 从独占时的「按层有局部性」掉到接近一次一失效；②HBM 行缓冲：两条顺序流落在不同行、不同 bank 时，行打开/预充电次数上升，有效带宽低于「两倍独占流量」的线性预期——带宽计数器可以很高，但每副本拿到的有用字节/秒上不去；③上下文切换：两个客户端若按同一节拍 launch decode，MPS 在内核边界来回切，指令缓存和 TLB 跟着抖，步间隔出现和切换次数相关的尖刺。算力不够的反证是：把其中一个副本暂停，另一个立刻回到接近独占的步时，SM 占用并不出现「突然打满」。处置：绑 SM 配额（例如各 40–50%）把并发从「同时抢同一套缓存」改成时间片更可预期，适合一主一备、负载不对称；错开调度让两个 decode 步不要对齐，减少同拍行冲突，适合 QPS 都不高的时候。两份权重每步都要扫、L2 命中在配额之后仍接近随机失效，软隔离只是把抖动换成稳定的「各慢一倍」，这时拆卡——每卡恢复单流局部性，比继续在 50 MB L2 上塞 28 GB 工作集更老实。边界：同一份权重复制的两个进程仍会争 L2；若改成单进程多模型共享只读权重映射，颠簸会轻一档，但本问是两份独立副本，不要和「一张卡两个逻辑服务共用一份权重」混谈。

**后续追问：** L2 命中率掉了但 HBM 有效带宽并没有按比例掉，你还缺哪一类缺失（TLB、指令缓存、barrier）；错开半个 decode 步之后行冲突下降、尾延迟却升了，说明什么；MIG 切成两实例和 MPS 绑配额，对 L2 分区和故障隔离各差在哪。

**扩展问题：**
- 怎样用「单副本暂停 → 另副本步时回弹」和「两副本步时之和 vs 独占步时」判断是缓存颠簸而不是启动开销？
- 两个副本的层循环故意错相 180°，L2 命中率最多能救回多少，用当前层工作集约几 MB 来估？
- 若白天只要一份 7B、夜间第二份做评测，MPS 共卡的切换策略和全天双副本常驻有何不同？

**推理回答：** 目标是解释「两份 batch=4 为什么比独占慢一倍以上」。约束是单卡 L2 远小于两份 7B 权重、decode 又每步换层扫参。用 L2 / 行缓冲 / 切换三次对照独占基线证明颠簸，再按「命中率能否被配额或错相救回」决定软隔离还是拆卡。

## SERVE-002. 在 TPU Pod 上重做原本跑在 GPU 集群里的 70B 预训练：脉动阵列吃得下的是哪几类层？哪些写法会让 XLA 在编译期直接失败？

**答：** 稠密、静态形状的大 GEMM——QKV 投影、MLP、输出线性层——会吃到脉动阵列的高能效。动态控制流、每步变长的序列、以及绑在 GPU 共享内存上的手写核，会在 XLA 编译期失败，或被降到向量单元上慢速执行。迁移的前提是把图收成固定形状、用集体通信表达并行，而不是把“每步发射一串核”的 GPU 习惯原样搬过去。

**深入展开：** TPU 的核心是矩阵乘单元里的脉动阵列：权重预载到网格上的乘加单元，激活沿行列流动，部分和传给邻居，避免每次 MMA 都回写 HBM。这对 `[M,K]×[K,N]` 且 M、N 足够大的训练步很合适，70B 的稠密线性层能接近阵列峰值。Softmax、RMSNorm、非线性走旁边的向量 / 标量单元，它们不是第一公民，过大或不规则会拖住阵列。软件路径是框架图 → XLA → 静态可执行文件：序列长度、batch、专家路由若每步变化，就要 pad 到已经编译过的桶，否则会反复重新编译，冷启动可以到分钟级。主机–设备同步、Python 侧逐步调试、依赖手工 tiling 的核，在 TPU 上没有对应物。多芯片靠高速互联组成 Pod，数据并行和模型并行要用 AllReduce / AllGather 在编译期绑到拓扑上。和 GPU 比：TPU 更像“编译器即调度器”，GPU 更像“运行时再发射一堆核”。batch=1 的 decode GEMV 对脉动阵列同样不友好，所以常见做法是预训练放 TPU，在线解码仍回 GPU。

**后续追问：** 为什么变长 batch 必须做长度分桶；脉动阵列遇到稀疏专家路由时该切哪一维；BF16 相对 FP16 在 TPU 上主要解决了什么溢出问题。

**扩展问题：**
- 若 30% 的步是解码式生成评测，TPU 训练循环会被什么拖慢？
- 主机上每步做一次形状检查，会怎样破坏设备侧流水线？
- 同样的 AllReduce，在 Pod 互联和多机 GPU 网络上的瓶颈差在哪里？

**推理回答：** 用“能否映射到静态、稠密、大 tile 的阵列计算”当过滤器：能映射的前向 / 反向会受益；依赖动态形状和手写核的路径要先改写成可编译的固定图，否则迁移成本会高于算力收益。

## SERVE-003. 剖析该先打哪一段：decode 与 prefill 谁先？在报障只写「模型很慢」、流量却是 6000 进、40 出时，两段分别对应使用者能感觉到的哪项指标？

**答：** 先剖 prefill。6000 进、40 出意味着绝大部分矩阵乘发生在一次吃完整提示、写出全部输入 KV 并吐出首 token 的阶段；decode 只循环约 40 步。用户感知上，prefill（加上排队和分词）决定 TTFT——「开始出字要等多久」；decode 决定 TPOT / 词间延迟和读完时间——「后半段卡不卡」。没把「慢」拆成这两段之前，换引擎或加卡都是盲打。

**深入展开：** Prefill 输入形状 `[B, S, D]`，S≈6000，注意力分数大约随 S² 涨，FFN 大约随 S·D² 涨，一次前向覆盖整个提示，并通常产出第一个输出 token。Decode 每步 q_len=1，读已缓存的 K/V（长度 S+t）和全部权重，再追加 1 个 token。墙钟只作示意：若 prefill 按每秒数千到数万 token、单请求 decode 按每秒数十到数百 token 估，6000 的 prefill 往往已是 40 步 decode 的数倍时间。长输入短输出（RAG、分类、抽取）是 prefill 主导；短输入长输出（写代码、写长文）才是 decode 主导。优化也分家：prefill 看切块、前缀缓存、算力利用率；decode 看连续批处理、KV 量化、投机解码。不要用端到端平均值掩盖「首包两秒、之后很顺」或反过来。

**后续追问：** 同样 6000/40，若连续批处理里插进一个 20k 提示，你的 40 步 decode 会怎样被拖；TTFT 里有多少是排队而不是算 prefill；投机解码改的是哪一段墙钟。

**扩展问题：**
- 输入 200、输出 2000 时，剖法会怎样翻转？
- 流式接口上用户说「慢」，你看首包时间还是看第 100 个 token 的到达时间？
- 如何用一次请求的 trace 把墙钟切成排队、分词、prefill、逐步 decode？

**推理回答：** 用输入/输出长度比判断计算落在哪一段，再把用户投诉映射到 TTFT 或 TPOT。验证靠分段 trace，而不是只看总耗时。

## SERVE-004. 调度把连续批的同时在飞上限放到了 64，线上并行着带 logit 偏置的翻译、0.9 温度闲聊和 JSON 贪心约束，每拍能并进同一 GEMM 的活请求大概十几条。怎样按采样与约束是否兼容来划分采样核分组，并在组间拆成多条流水、先统一采样再后处理、承认 64 只是 KV 槽位上限而不是每步一张大矩阵的保证这三条路里取舍？

**答：** 64 是 KV / 分页槽位上限，不是「每步一张大矩阵」的保证。贪心+词表 mask、高温度多项采样、带偏置的翻译，控制流和要喂给采样核的附加张量不同，调度器若按兼容性硬拼，真正能共享一次 GEMM+sample 的活序列往往只剩一个子集。先画兼容矩阵：相同的 mask 有无、温度是否为 0、是否存在非零 logit bias、是否要回主机做 FSM，能画进同一格的才是一个 kernel group。然后三选：组与组拆成多条流水（各自小 GEMM，隔离简单）；或统一「logits + bias、乘 mask、再按 T 采样」一条核，把差异收成数据而不是分支；或接受有效计算 batch 就是十几，64 只用来把显存塞满，不再幻想 tokens/s 随槽位数线性涨。

**深入展开：** 前向 GEMM 其实不太在乎你稍后怎么采样——同一模型、同一精度、长度落在同一桶，64 路理论上可以拼成一张胖矩阵。拆开发生在 GEMM 之后：约束组要在采样前应用逐步 mask，甚至把 logits 拉回主机；闲聊组要做温度缩放和 multinomial，还可能 top-p；翻译组要在 softmax 前加上按词表的 bias 向量。若实现是「一种采样路径一张图 / 一条主机循环」，调度器会在一步里只取出兼容的那十几路，其余路等到下一 iteration，于是仪表盘上 in-flight=64、有效 GEMM batch≈12。切 group 的依据是附加张量和控制流，不是业务名：温度 0 且无 bias 的闲聊可以并进贪心 JSON 组，只要 JSON 的 mask 对闲聊是全 1；带 bias 的翻译若 bias 能当成稠密向量加到 logits 上，也可以进统一核。统一采样再后处理：设备上始终走 `logits ← logits + bias; logits ← logits + mask_penalty; sample(T)`，后处理只做 JSON 括号检查这类不改下一 token 的事——注意：真正的约束不能只靠后处理，否则非法 token 已经进 KV。所以统一核只适合「mask/bias/T 都能张量化」的差异；FSM 必须回主机的那组，应单独成流水，以免 64 路每步都陪着 D2H。拆多条流水的代价是每条流水的 GEMM 变瘦、占用率下降，但逐步税不再交叉污染。承认 64 是显存上限：用「每步实际参与 GEMM 的序列数」和「槽位占用数」两个计数器看缺口；若缺口稳定，优化应是减少不兼容路径（能张量化的 mask 不要走主机），而不是再把 max_num_seqs 往上调。边界：不要和「静态等齐 vs iteration 入队」混为一谈——那是入队模型；这里即使已经 iteration 级组批，采样不兼容仍会把一步拆碎。

**后续追问：** 兼容矩阵里「温度 0.9 且带空 mask」和「温度 0.9 且带稀疏 JSON mask」能不能共用采样核，warp 分歧代价如何量；三条流水的 prefill 是否还允许拼在一次 chunk 里；有效 GEMM batch 长期是 12，你加第四种 logit processor 之前要先问什么。

**扩展问题：**
- 设计一张兼容表（贪心、T=0.9、logit bias、主机 FSM）并标出哪些格子可以张量化合并、哪些必须拆流水。
- 为什么「max_num_seqs=64」涨上去以后 KV 占用线性涨、GEMM 尺寸却不涨，监控少了哪两个字段就会误判成算力够用？
- 统一核把全 1 mask 也当成稠密 `[B, vocab]` 来乘，词表 128k 时这笔额外带宽会不会把采样从「可以忽略」变成新的逐步税？

**推理回答：** 目标是解释「槽位 64 但同一步 GEMM 只有十几条」。约束是采样和约束的附加张量、控制流并不相容。用兼容性切 kernel group，再比较拆流水、张量化统一核、以及承认计算 batch 小于显存 batch 三条路，用有效 GEMM 宽度而不是槽位上限做决策。

## SERVE-005. SRAM 型 LPU 对比 HBM GPU：客服要单流每秒 200 个 token、抖动压在 5% 以内，你押哪边，落选者卡在哪条屋顶？

**答：** 单流超高 tokens/s 加硬实时抖动，押 SRAM 型 LPU：权重量在片上，decode 不再每步付 HBM 往返，编译器静态排好指令和片间传输，延迟可预测。HBM GPU 在 batch=1 时受大约数 TB/s 的片外带宽限制，70B 级权重每步要读几十 GB，理论上就很难稳定打到 200 token/s，队列和缓存未命中还会加抖动。若目标改成高并发总吞吐而不是单流极限，GPU 的批处理反而更划算。

**深入展开：** Decode 的屋顶是“每 token 必须触及的权重字节 ÷ 可用带宽”。HBM 路径：例如 70B × 1 字节（FP8）≈ 70 GB，除以约 3 TB/s 量级带宽，理论上限大约几十 token/s，再扣内核效率和 KV 读取，单流很难到 200。LPU 把权重放进片上 SRAM，带宽比 HBM 高一个数量级以上、延迟低得多，算术强度不再被片外墙卡住。代价是单芯片 SRAM 通常只有几十到几百 MB 量级，70B 必须切到很多芯片，芯片间也按编译期节拍传激活；芯片数大致按“权重大小 / 每芯片有效 SRAM”线性增长。确定性执行没有动态缓存未命中、没有运行时抢占，抖动可以压到几个百分点；但也意味着不能在运行时随意改 batch，很难做灵活插队，训练所需的反向和优化器状态更对不上这种推理专用设计。高并发离线摘要里，GPU 一次读权重服务几十路，总 tokens/s 往往用更少的硅面积打赢。选型看 SLA：硬实时单流用 LPU，弹性吞吐用 GPU。

**后续追问：** 按 SRAM 容量估算 70B 要多少芯片、故障率怎么变；静态调度下变长输出如何避免空转；LPU 上再做投机解码还有没有必要。

**扩展问题：**
- 若必须同一套硬件既训练又推理，为什么 LPU 几乎不会进入候选名单？
- 把 GPU 权重量到 INT4 并把 batch 拉到 32，单流延迟和集群吞吐分别发生什么？
- 编译期固定通信拓扑之后，热更新一个低秩适配器有多痛？

**推理回答：** 从单流 200 token/s 反推每 token 可读的字节上限，发现 HBM 带宽不够而片上 SRAM 够；再权衡多芯片切分和静态调度对抖动、灵活性、训练的代价，得出交互式硬实时押 LPU、吞吐型业务留 GPU。

## SERVE-006. A100 的 80GB 规格、H100、还有 L40S，在同一机房既要扛高 QPS 的 13B 客服、又要偶尔接 70B 深度问答时，该如何混配而不是只采购单一型号？

**答：** 13B 高并发吃的是卡的张数、显存带宽和每美元吞吐，48 GB 级的 L40S 一类推理卡通常更合适。70B 吃的是单机显存和卡间互联，A100 80GB 或 H100 才能用较小的张量并行度放下权重并保持低单步延迟。混布比全上旗舰卡便宜，前提是路由把两类流量切开，避免 70B 的 KV 把 13B 的并发池挤爆。

**深入展开：** 选型先算“放得下”再算“跑得快”。13B BF16 权重约 26 GB，一张约 48 GB 的推理卡就能留出 KV 做几十路 4K 会话；这类卡的价值在采购成本和推理密度，不在训练峰值算力。70B BF16 权重约 140 GB，单张 80 GB 卡放不下，至少需要 2 路张量并行。A100 80GB 与 H100 都是 80 GB HBM，但以公开规格为例，H100 SXM 的 HBM3 带宽大约 3.35 TB/s，A100 SXM 的 HBM2e 大约 2.0 TB/s，batch=1 decode 会差出明显一截，长 prefill 的 Tensor Core 差距更大。若 70B 走 FP8，权重约 70 GB，H100 的 FP8 MMA 能把 prefill 打满，A100 则多半停在 INT8/FP16 路径。互联是硬约束：70B 的 TP=2/4 需要机内高速互连，PCIe-only 的卡做张量并行时，decode 每步的 AllReduce 很容易把省下的计算吃光。软件栈还要确认目标精度和并行度在驱动与编译器上可用。算账用“每美元 tokens/s + 每路 KV 显存”，不要只用峰值 TFLOP。

**后续追问：** 只有 H100 配额时如何避免大模型饿死小模型；L40S 上用 INT4 单卡跑 70B 是否可行、质量闸门怎么设；多机张量并行和单机多卡在故障域上差在哪。

**扩展问题：**
- 若合规要求推理不出域，卡型选择还要加哪些互连和隔离子条件？
- 同样是 80 GB，为什么训练更看重 BF16/FP8 算力和高速互连，推理却先看带宽和总显存？
- 季节性流量用抢占式低端卡扩 13B 副本，对尾延迟有什么风险？

**推理回答：** 把负载拆成“小模型高 QPS”和“大模型低 QPS”，分别用容量公式和带宽屋顶选卡，再用互联能否支撑 TP 过滤候选，最后用路由保证两池显存互不抢占。

## SERVE-007. 占用率、合并访存、warp 分歧，排查自己写的 RMSNorm 在 CUDA 上比官方库慢三倍时，优先级顺序该怎么排？

**答：** 先认定 RMSNorm 是带宽墙：它对隐向量做归约再缩放，算术强度很低，慢三倍多半是没吃满 HBM 或引入了多余往返。按顺序查：warp 内是否对连续地址做向量化合并读取、归约是否在寄存器 / 共享内存里做完、占用率是否低到藏不住访存延迟、以及是否按 token 走了发散分支。库实现通常把这几件事和 16 字节加载绑在一起。

**深入展开：** 主机 `<<<grid, block>>>` 启动后，线程用 `blockIdx/threadIdx` 认领元素。对形状 `[B, T, H]`，合理映射是一个 warp 或一个 block 处理一根长度为 H 的向量：先向量化加载算平方和，用 warp shuffle 或共享内存做树状归约得到 σ，再第二遍写 `x * rsqrt(σ²+ε)`。慢的典型原因：①按行跨步访问，无法合并，有效带宽只剩理论值的一小截；②每个线程自己扫完整根向量做归约，没有 `__shfl_down_sync`，指令数爆炸；③ `block` 太小或每线程寄存器太多，活跃 warp 不足，HBM 延迟暴露（占用率例如低于 20%）；④对 padding 写大量 `if (tid < len)`，同一 warp 里有的线程在算、有的在等，锁步效率下降；⑤把 Norm、残差加、SiLU 拆成三个核，三次读写 HBM，融合核只走两趟。T 很小时，内核启动本身也会占可见比例。应用计数器看 DRAM throughput、scoreboard stall、achieved occupancy，而不是只确认“核已经 launch 成功”。

**后续追问：** 为什么 warp 内分支比跨 warp 的分支更伤吞吐；共享内存 tiling 在 GEMM 里省掉的是哪一次 HBM 往返；什么时候该让编译器生成核，而不是继续手写。

**扩展问题：**
- 逐元素 SiLU 核几乎永远是带宽墙，再往里面加 Tensor Core 有用吗？
- 把 RMSNorm 和残差加写成一个核，访存量如何从四趟变成两趟？
- 动态序列长度下，怎样避免 padding 造成的 warp 分歧，又不牺牲合并访存？

**推理回答：** 从 RMSNorm 的访存/计算比断定它该打满带宽，再沿“地址是否合并 → 归约是否片上完成 → 有没有足够 warp 藏延迟 → 分支是否锁步 → 是否多余内核往返”这条链定位三倍差距。

## SERVE-008. 16 条并发、每条 4K 上下文的客服 70B，要压进一张 80 GB 的卡。权重、KV、激活三本账摊开来，怎么论证会不会 OOM？

**答：** 把显存拆成权重、KV cache、激活和运行时余量四笔，缺一笔都不能签字。BF16 权重约 140 GB，已经超过 80 GB，结论直接是否。只有把权重量到约 8 bit（约 70 GB）或 4 bit（约 35–40 GB）之后，才进入“KV 还够不够”的阶段。16×4K 的 KV 在常见 70B GQA 上大约 20 GB：INT4 权重时单卡可行，FP8 权重时余量很紧，BF16 必须多卡。

**深入展开：** 权重 ≈ 参数量 × 每参数字节。70B×2 B ≈ 140 GB；×1 B ≈ 70 GB；×0.5 B ≈ 35 GB，加上缩放因子和词表，INT4 按 35–40 GB 估。KV 每 token ≈ 2 × 层数 × KV 头数 × 头维度 × 字节。以常见 70B GQA 为例（例如 80 层、8 个 KV 头、头维度 128、FP16）：2×80×8×128×2 ≈ 320 KiB/token ≈ 0.31 MB/token。16 路 × 4096 × 0.31 MB ≈ 20 GB。若改成 64 头满注意力，KV 大约再涨 8 倍，同一并发可到约 160 GB，单卡立刻不可能。激活在推理期通常只留当前层；decode 时形状接近 `[16, 1, 8192]`，只有数百 KB，prefill 若一次吃满 4K 则一层大约 1 GB 量级，仍远小于训练时整网激活。CUDA 上下文、分配器碎片和临时 workspace 建议预留 5–10 GB。结账：INT4 40 GB + KV 20 GB + 余量 10 GB ≈ 70 GB，80 GB 卡能跑，但质量要单独回归；FP8 70 GB + KV 20 GB 已超，除非把 KV 也降到 FP8（约 10 GB）并卡住最大长度；BF16 必须张量并行 ≥ 2。规划用“目标并发 × 最大上下文”，平均值只能估费用，峰值决定 OOM。

**后续追问：** 上下文从 4K 升到 32K 时哪一笔先爆；张量并行 2 路时 KV 是否也切分、切的是哪一维；激活在大 chunk prefill 时会不会短暂超过 decode。

**扩展问题：**
- 16 路里有 2 路突然打满 128K 窗口，分页分配能否救这张卡？
- 把 KV 量化到 8 bit，和权重量化到 4 bit 比，各自更伤哪类质量？
- 为什么同一个 70B 训练时 80 GB 卡连 batch=1 都可能不够，而推理却只差在 KV？

**推理回答：** 先用精度判断权重是否已经超过 80 GB，再代入 GQA 的每 token KV 公式乘以并发和长度，最后加激活与碎片余量；三笔都进预算才说单卡可行，否则给出该降的精度或该加的并行度。

## SERVE-009. 13B 用 bf16 在 batch=1 下做 decode，面对算力宣传值 300 TFLOPS、片外 HBM 约 1 TB/s（仅作示意）的卡。是否仍落在带宽墙上？算术强度的屋顶线该怎么摊开写明？

**答：** 还是带宽墙。Decode 每步对每个请求只做一次「权重 × 单 token 激活」的矩阵-向量乘：几乎要把权重扫完，算力却不随序列线性涨（注意力读 KV 另算）。算术强度 ≈ 有效 FLOP / 从显存读的字节。bf16 每参数 2 字节，每参数对单个 token 大约 2 次乘加，强度大约 1 FLOP/字节，远低于这块卡的平衡点 300e12 / 1e12 ≈ 300 FLOP/字节。屋顶线因此落在带宽一侧：速度上限大约是权重字节 / 带宽，不是峰值 TFLOPS。

**深入展开：** 13B bf16 权重大约 26 GB。理想情况下一步 decode 至少扫一遍权重，上限约 26e9 / 1e12 ≈ 26 ms/token，即约 40 token/s（尚未计 KV、碎片、内核启动）。若真能吃满 300 TFLOPS，同一步算量大约 2×13e9 ≈ 2.6e10 FLOP，只需约 0.09 ms——差两个数量级，算力在等 HBM。Prefill 不同：一次读权重，和 S 个 token 做 GEMM，强度大约乘上 S；S 到数百上千时很容易越过 300 FLOP/字节，变成算力墙。batch=B 的 decode 让 B 个请求摊一次权重读取，强度约乘 B；B 要到上百才接近该卡平衡点，交互延迟往往先爆。量化把每参数字节从 2 降到 1 或 0.5，同等带宽下 decode 更快；prefill 已算力受限时，量化加速就没那么线性。长上下文时每步还要读 KV：层数 × H_kv × Dh × 当前长度 × 2（K 和 V）× 宽度字节；长度到数万时 KV 流量可以和权重一个量级，瓶颈从读权重转成读 KV，这才是 GQA、KV 量化要打的点。

**后续追问：** batch 要大到多少，这块卡的 decode 才会从带宽墙翻到算力墙；权重量化到 4 bit 后屋顶线怎么移；上下文 32k 时你还按权重带宽估 TPOT 吗。

**扩展问题：**
- 同一张卡上 prefill S=4096、batch=1，强度有没有跨过 300 FLOP/字节？
- 为什么「加卡」若只加算力不加带宽，对 batch=1 的 decode 几乎没用？
- 投机解码一次验证多个 token，相当于把哪一项强度抬上去了？

**推理回答：** 先算硬件平衡点 FLOP/字节，再算 decode 的强度（约 2 FLOP / 每参数字节）。强度远低于平衡点就判带宽墙，并用权重体积/带宽给出 token/s 上限做对照。

## SERVE-010. 卡住 prefill 的那道屋顶，为什么常常不是卡住 decode 的那一道？
**答：** Prefill 同时处理输入 token，常更偏计算密集；decode 每步生成少量 token，常受权重及 KV 读取带宽限制。长上下文、大批量或不同硬件会改变瓶颈。
**深入展开：** 应分别 profile 阶段，不把“prefill 必然计算瓶颈”当定律。
**后续追问：** 增大 batch 为何可能改善吞吐却伤害延迟？更高并行度可摊薄部分开销，但会增加单步工作量、资源竞争或排队时间。
**扩展问题：**
- 如何用算力利用率、内存带宽和 kernel 时间识别 prefill 与 decode 的实际瓶颈？
- 长上下文 decode 与短上下文 decode 的访存成本为什么不同？
**推理回答：** 依据利用率与延迟分解调整调度，而不是对所有阶段使用同一优化。

## SERVE-011. 推理服务压测为何不能只报 tokens/s，还要把 goodput 写进结果？
**答：** Goodput 只计入满足约定质量与延迟 SLO 的有效工作量；大量排队或超时请求可以让总吞吐好看，却无法满足用户体验。
**深入展开：** 明确统计单位是请求还是 token，并报告负载、失败率、TTFT 和 ITL 分位数。
**后续追问：** 压测采用闭环发送会隐藏什么排队问题？客户端等响应后才发新请求，系统变慢时到达率也下降，可能低估独立真实流量造成的排队。
**扩展问题：**
- 若两个配置 tokens/s 相同但超时率不同，如何定义并比较请求级 goodput？
- 按输入长度和输出长度分层报告 SLO，为什么比单一整体分位数更有解释力？
**推理回答：** 按真实到达过程增加负载，找到满足 SLO 的容量而不是单一峰值吞吐。

## SERVE-012. 同一个 13B 在线服务，瓶颈在 HBM 容量占满时与在张量核心算力跑满时，各自的优化清单为何几乎相反？

**答：** 显存打满时优先减驻留字节：权重量化、KV 量化、GQA/MQA、分页分配、缩短最大上下文和压低并发。算力打满时优先减 FLOP 或摊薄启动开销：拉大有效 batch、融合核 / FlashAttention、投机解码、蒸馏到更窄或更浅的模型。把“常见优化”列成一张清单没有用，必须先判断当前屋顶是容量、带宽还是算术强度。

**深入展开：** 推理期有三类屋顶。容量屋顶：权重 + KV + 激活 + 碎片超过 HBM，表现为 OOM 或被迫把并发打到极低。13B 用 BF16 时权重约 26 GB；若每 token 的 KV 落在约 0.2–0.5 MB 量级（随层数和 KV 头数变），64 路 × 8K 上下文就可再吃掉数十 GB。这时 INT8/INT4、KV 8bit、下调 `max_seq`、限流比换一张峰值 TFLOP 更高的卡更有效。带宽屋顶：decode 每步几乎要把权重扫一遍，算术强度约为 2 FLOP/参数 ÷ 每参数字节，BF16 大约 1 FLOP/B，远低于现代 GPU 的屋顶，量化（少读字节）和增大 batch（一次读取服务多请求）同时有效。算力屋顶：长 prefill 或很大 batch 的 GEMM 能打满 Tensor Core，FlashAttention 减少 HBM 往返、融合 RMSNorm/SiLU 减少内核启动、蒸馏减少层数和隐宽才是主杠杆；继续把权重量到 INT4 对算力屋顶帮助有限，还可能增加反量化开销。剪枝和结构化稀疏只有在内核真正跳过零时才兑现，否则只是纸面参数变少。

**后续追问：** 如何用 roofline 或 DRAM throughput 判断当前是带宽墙还是算力墙；GQA 减的是哪一块显存、对 prefill 的 FLOP 影响有多大；投机解码在已经算力打满的 prefill 阶段为什么几乎没好处。

**扩展问题：**
- 为什么分页 KV 能缓解容量碎片，却几乎不改变带宽屋顶？
- 蒸馏和量化同时做时，你如何拆开各自对质量的贡献？
- 训练期的激活重计算、混合精度和推理期的 KV cache，分别在优化哪一类内存？

**推理回答：** 先画“容量 / 带宽 / 算力”三屋顶，再把每项技术映射到它真正减少的资源（驻留字节、HBM 往返、FLOP、内核次数），同一技术在不同屋顶上的优先级自然相反。

## SERVE-013. 实测大约 28 token/s，对照一张卡 HBM 封顶大约 50。70B 正以 2 路张量并行做 decode。如何把 all-reduce 在每一层的 payload 字节与 NVLink 实际吞吐折成第三道封顶，并在降低 TP、通算重叠、承认这个 batch 已碰到通信天花板之间抉择？

**答：** 单卡 HBM 屋顶只按「每步读完本卡权重」计价，TP=2 之后每层还要为注意力输出和 MLP 输出做 all-reduce，这是第三条屋顶。用层数 × 每层集合通信次数 × 单次 payload（batch × 隐宽 × 元素字节 × 2(TP−1)/TP）除以实测 NVLink 有效带宽，再和「通信次数 × 单次尾延迟」取较紧的那个，得到通信上限。28 贴近这条通信上限就不要再加 batch；通信上限仍远高于 50 而实测 28，优先重叠或砍同步；模型能放进更少卡时减 TP，让逐步集合通信从关键路径上消失。

**深入展开：** 以常见 70B（例如 80 层、隐宽 8192、BF16）示意：TP=2 时每层常见两次 all-reduce（注意力投影后一次、MLP 后一次），环 all-reduce 体积因子是 `2(TP−1)/TP = 1`，故每步每条序列的通信字节 ≈ 80×2×8192×2 B ≈ 2.6 MB；batch=B 则乘 B。H100 机内互联峰值以公开规格约数百 GB/s 计，2.6 MB 的带宽上限看起来远高于 50 token/s，但 decode 的 payload 很小，真正打的是延迟屋顶：若一次集合通信尾延迟在约 20–50 µs（示意，用你自己拓扑上的集合通信剖析），160 次就是约 3–8 ms，叠上无法隐藏的 launch 和等待，步时会从 HBM 屋顶的约 20 ms（对应 50 token/s）被推到 30–40 ms，约 25–33 token/s，和 28 同一量级。第三条屋顶应写成 `min(B / (N_AR × t_AR), BW_eff / (N_AR × hidden × bytes × 2(TP−1)/TP))`。判定：①通信屋顶 ≈ 28，且加大 B 时步时几乎按 B 涨、每请求 TPOT 变差——已经撞上通信墙，加 batch 只让 NVLink 更胖，不抬单流；②通信屋顶仍 ≥50 但实测 28，查是否每层 `synchronize`、all-reduce 没有和下一段无关 GEMM 重叠、或用了跨 PCIe 的慢路径；③减 TP：若量化后单卡放得下，TP=1 删掉逐步 AR，单流应回到 HBM 屋顶附近；TP 从 2 提到 4 会让 `2(TP−1)/TP` 接近 2、通信次数不减，decode 往往更慢。重叠在 decode 里空间有限——下一层通常要等本层残差，只能重叠「本层 AR 与下一层可提前做的预取/RMSNorm」，不要指望藏掉全部 160 次。边界：prefill 大 GEMM 容易把 AR 藏进计算，同一套 TP=2 在 prefill 上看起来很健康，不能拿来给 decode 开脱。

**后续追问：** 把 batch 从 1 拉到 16 之后通信屋顶从延迟界换成带宽界，token/s 总吞吐会怎样拐；同一条 NVLink 上还跑着 KV 换出，有效带宽该怎么重新测；减到 TP=1 后单卡放不下 KV，你是保 TP=2 做重叠，还是切 KV 精度来换减 TP。

**扩展问题：**
- 写出用 `n_layers、n_ar、hidden、dtype、TP、t_AR、BW_eff` 计算第三条屋顶的式子，并标出 B=1 和 B=32 分别落在哪一段。
- 为什么 decode 的 all-reduce 很难和「下一层主 GEMM」完全重叠，而 prefill 常常可以？
- TP=2 的实测 28 和「两卡数据并行、每卡完整 70B」的单流速度比，通信项差在哪次集合操作？

**推理回答：** 目标是解释「低于单卡 HBM 屋顶的 28」。约束是 TP 把逐步集合通信绑进每一层。把 AR 字节和有效互联带宽收成第三条屋顶，用它和 28、50 的相对位置在减 TP、重叠、停止加 batch 之间选择。

## SERVE-014. GPU 利用率看着不差，每分钟完成数却远差于压测。怎样确认是最长那条回复把整批钉死？聊天接口用固定 batch，凑满 8 条才一起 decode。改成每个 iteration 准入和退出之后，多出来的吞吐从何处来？

**答：** 静态 batch 会把整批钉在最长那条序列上：短回复早已结束，槽位和步数却不能让给队列里的新人。利用率高只说明 decode 内核还在跑，不说明每步都在产出有效 token。改成按 iteration 调度后，某条一结束就释放 KV、立刻补进下一条，平均有效 batch 上升，吞吐来自少空转，而不是把单步算得更快。

**深入展开：** 数据流应是：到达 → 等待凑齐 B 条 → 整批 prefill → 同步 decode 到所有人结束。设 8 条输出长度为 20、30、40、50、80、120、200、400，整批要走 400 步；第 20 步之后已有序列空转。空转序列步 ≈ Σ(L_max − L_i)，此例约 7×320 = 2240，相对 8×400 = 3200 总步大约七成浪费（示意分布，不是某业务的实测）。Iteration 级调度每步看队列和 KV 预算，能放多少活序列就跑一步，EOS 或触顶立刻回收块。新请求的 prefill 可以插在 decode 步之间，但长 prefill 会抬高在途请求的 token 间隔，所以要给每步一个 prefill token 预算，必要时切块。异构长度还要求无 padding 的注意力内核，否则「连续批」只是把浪费从时间挪到 padding。离线、长度接近、到达同步的批任务，静态 batch 更简单且差距不大；在线聊天长度方差大时，空转才是主因。验收看有效生成 token/s、时间平均活序列数、padding 占比和 p95 间隔，不要只看 SM 利用率。

**后续追问：** 如何用「每步实际有效序列数 / 配置的 max batch」量化浪费；插入一次长 prefill 时怎样避免正在流式输出的用户卡顿；KV 预算满了是抢占长请求、换出到 CPU，还是直接拒绝新请求。

**扩展问题：**
- 画出 3 条长度差一个数量级的请求在静态 batch 和 iteration 级调度下的时间线。
- 为什么 SM 利用率高仍可能吞吐差，真正该看的有效 token 占比怎么算？
- 连续批打开后 TTFT 变差，如何拆排队等待、prefill 插入和 decode batch 变胖三部分？

**推理回答：** 目标是单位时间完成更多请求。约束是 decode 按步推进、输出长度高度偏斜。先用 L_max 空转步数解释「看起来很忙」，再说明 iteration 入队能填回空槽，最后用有效 batch 和间隔延迟验收，而不是再堆更大的静态 B。

## SERVE-015. 闲聊请求的 p99 逐 token 间隔突然出现尖峰——这是把 prefill 可调度预算抬到能整段吞掉 20k RAG 提示之后发生的。原因是什么，块大小该如何往回调？

**答：** 连续批处理里，一次 20k 的 prefill 会把 GPU 占满数百毫秒甚至数秒，同批里正在逐步 decode 的短对话只能空等，词间延迟出现尖峰，p99 被这几次「大象 prefill」拉爆。Chunked prefill 把长提示切成固定 token 块，每个调度步只做一块，并和其它请求的 decode 步拼进同一 batch，短请求每步都能往前走。块太大，干扰回来；块太小，长提示自己的 TTFT 变差、调度开销涨。

**深入展开：** 调度器每个 step 的 token 预算有限。若预算=20000，一个 RAG 请求独占一步，decode 请求的词间延迟就等于这次 prefill 的墙钟。若预算=512，20k 提示大约拆成 40 步，每步还可以塞若干 decode token。混合还有屋顶线好处：prefill 块是高算术强度 GEMM，decode 是带宽墙，拼在一起更能吃满 GPU。代价是长提示 TTFT ≈ 步数 × 步间隔，步数变多则首包变慢。选型只作示意：交互为主的集群常见 256–1024 token/块；RAG 很多且能容忍首包，可以更大。监控必须对「短 decode」和「长 prefill」分层看 p99 ITL / TTFT，不要看混合平均值。它和 PD 分离是两条路：切块是同卡细粒度混部，分离是物理隔离。中小规模先切块。

**后续追问：** 块大小从 512 改到 4096，你预期 TTFT 和 ITL p99 各自往哪边走；如何证明尖峰来自大象 prefill 而不是 KV 换入换出；和「暂停 prefill、插进 decode」的抢占比，切块的实现成本在哪。

**扩展问题：**
- 流量是 10% 的 20k RAG 加 90% 的 200 token 闲聊，怎样用在线实验选块大小？
- 切块后同一请求的 KV 是逐步写成的，中途取消如何保证已写块被释放？
- 为什么「提高 tokens/s」和「降低短请求 p99 ITL」在这里会打架？

**推理回答：** 失败模式是长 prefill 独占调度步，把 decode 尾延迟抬上去。用逐步预算把两类工作交错，再按分层 p99 回调块大小。验收看短请求 ITL p99 下降，且长请求 TTFT 仍在 SLO 内。

## SERVE-016. 把长输入的 prefill 拆成可调度块后，TTFT 与 ITL 会怎样联动变化？
**答：** 把长输入的 prefill 拆成可调度块，可减少其对正在 decode 请求的阻塞；块太小可能增加调度开销或延长该请求的首 token 等待。
**深入展开：** 在输入长度与并发分布下测试块大小及 token budget，不盲目照抄默认值。
**后续追问：** 长短请求混合时怎样设置公平性门槛？分别约束各长度组的首 token 延迟、流式间隔和最长等待，避免只优化总体平均值。
**扩展问题：**
- 减小 prefill 块后 ITL 改善但 TTFT 恶化，应如何按业务 SLO 决定是否接受？
- 如何用固定到达率和相同长度分布比较不同 token budget 配置？
**推理回答：** 用整体吞吐、首 token 和流式间隔的分位数共同判断收益。

## SERVE-017. 流量没变，显卡监控也几乎一条直线，然而结构化输出约束一打开，p99 便从 800 毫秒窜到 3 秒。主机端每一步建词表掩码花的时间、logit 处理是否在 GPU 上、非法 token 被重新采样的次数——如何靠这三项查清约束带来的额外开销？随后是把 FSM 融进 kernel，还是先生成后校验？

**答：** GPU 利用率、HBM 带宽和 SM 占用几乎没变，说明多出来的 2 秒多半不在矩阵乘里，而在 decode 每步前后的约束路径上。把一步拆成「GEMM → 取 logits → 词表 mask → 采样 / 拒绝重采」，分别量主机 mask 墙钟、logits 或 mask 的设备主机往返、以及每步非法 token 重采样次数；哪一项乘上输出长度能对上 800 ms→3 s，那一项就是约束税。主机每步扫十万级词表或反复 D2H，就把 FSM 收进核内与采样融合；模型在低温度下本来就能出合法 JSON、拒绝率接近 0，就改成自由生成再校验，失败才重试。

**深入展开：** 约束解码的数据流是：当前前缀进入文法自动机（JSON 的括号栈、字符串转义、schema 字段状态）→ 得到本步合法 token 集合 → 非法位置 logits 置为 −∞ → softmax / argmax。词表常见 32k–128k：若在主机上物化一张 dense mask，每步至少扫一遍词表；再乘连续批里的活序列数，很容易到数毫秒。更贵的是 logit 处理器留在 CPU：要把 `[batch, vocab]` 的 logits 拉回主机（例如 vocab=128k、FP32、batch=16 约 8 MB），PCIe 往返加 Python/控制面同步后，一步多出几毫秒到十几毫秒都常见。输出 80 个 token、每步多 25 ms，仅这一项就约 2 s，和「p99 从 800 ms 顶到 3 s、GPU 曲线不动」对得上。第三条计数器是非法 token 重采样：有的实现先按未约束分布抽样，非法再拒绝、改 mask 重抽，最坏在狭窄状态（只剩 `"`、`}`、逗号）里空转十几次，却仍不发新的 GEMM，所以 GPU 还是闲。核内 FSM 把状态转移和 bitmask 放在设备上，与采样核融合，主机只在请求开始时下发自动机；适合 schema 稳定、每步必须合法的工具参数。生成后再校验则零逐步税，代价是一次失败要整段重跑，只有历史合法率已经极高（例如温度 0 的短对象、合法率 >99%）才划算。边界：schema 每周加必填字段时，核内自动机和校验器必须同版本发布；不要用「提示里写了请输出 JSON」代替 mask 剖面。

**后续追问：** 主机 mask 只有 200 µs 但 p99 仍多 2 s，你下一步剖的是 D2H 同步还是采样循环里的锁；重采样次数 p99 到 20、p50 是 0，哪类 JSON 状态在制造长尾；同一条请求前半段自由文本、后半段切进 schema，约束税会从哪一步突然出现。

**扩展问题：**
- 词表 128k 时，dense bitmask 和「只写合法 id 的稀疏允许表」在主机和核内各自的时间复杂度差在哪？
- 约束路径每步都 `cudaStreamSynchronize`，为什么 GPU 利用率会接近 0，而内核时间线里 GEMM 本身并不慢？
- 合法率 97% 的长订单对象，生成后校验的重试期望时延怎样和核内逐步 mask 比，才能决定切哪条路径？

**推理回答：** 目标是解释「延迟炸了、GPU 却没更忙」。约束是逐步 decode 在 GEMM 之外多了一段必须串行的合法性工作。用 mask 主机耗时、处理器所在设备和重采样次数三项把税定位到控制面或采样环，再按「每步必须合法」还是「几乎已经合法」在核内 FSM 与生成后校验之间做选择。

## SERVE-018. 输出流不能停，却必须在逐步生成中途把正在飞的 16 路 KV 由 FP16 改写成 FP8，好把并发槽位要回来。量化切分选整段重写还是只压已经封闭的前缀？尺度一断后面的 token 会漂，怎么避免？这和离线容量规划里在量化、丢历史、换出之间做三选一，差别在哪里？

**答：** 在途 16 路已经在用当前 KV 算注意力，流式不能停，所以这不是容量规划里的「量化 / 丢历史 / 换出」三选一，而是一次活迁移：新 token 还在往缓存尾上写。量化边界优先「冻结已写块的尺度、只压已经封闭的前缀页，尾页和正在写的页留 FP16」，必要时才对整段做一次双缓冲重写并在步间隙切换读指针。尺度必须按块或按 token 固化，禁止用新全局 scale 去重编码旧 K/V，否则后续 softmax 会把历史注意力重排，用户看见的是「后半句突然换口吻」而不是 OOM 恢复。

**深入展开：** 数据流：每路有一段已完成前缀（提示 + 已接受输出）和一页正在追加的尾块。整段重写 = 分配同等 token 数的 FP8 缓冲，按块读 FP16 → 估 scale → 写出 → 一步 decode 结束时原子地切块表指针、释放旧页。16 路、每路例如 4k、每 token KV 约 0.1–0.3 MB 量级（随层数和 KV 头变），整段重写是数 GB 到十几 GB 的设备复制，必须切成「每步迁移 N 块」，否则单步 TPOT 会尖出一个用户能察觉的空洞。只压已完成前缀更轻：尾块仍 FP16，注意力核要能在同一次 softmax 里混读两种元素宽度，或先把尾块临时升到与前缀同一计算精度。尺度不连续的典型事故：用整段新 max 重算 per-tensor scale，旧向量被重新缩放，与新 token 的点积全面偏移；正确做法是旧块保留写入时的 scale（写死在块头），新 FP8 token 用自己的 scale，反量化后在 FP16/FP32 累加里对齐。和离线三选一的差别：离线可以在下一次请求前丢最旧的 token 或把整段换出到 CPU，因为没有人正在读这条流；在途流式里丢 token 等于改写已经出口的上文，换出尾块会让下一步注意力等 PCIe，两者都会造成可见停顿或语义跳跃。这里唯一允许的「丢」是拒绝新请求、不再让第 17 路进场；对这 16 路只许改变元素宽度，不许改变可见历史。边界：有的层对 KV 8-bit 敏感（长距离引用），可以只压中间层、首尾层留 FP16，这是按层边界不是按时间边界。切换窗口里同一序列的块表不得出现「一半旧指针一半新指针」的中间态。

**后续追问：** 只压前缀、尾页仍 FP16 时，注意力核是混精度读还是先 cast，哪一种会把你刚收回的并发又吐回去；双缓冲重写到一半来了新 token，块表提交顺序怎样保证不读到半新半旧；16 路里有 2 路已经 32k，整段重写会不会单独把它们的 TPOT 打穿，该不该把鲸请求排除出这次迁移。

**扩展问题：**
- 按块固化 scale 和按 token 固化 scale，重写后对「第 1 个新 token 的注意力分布」各有什么误差形态？
- 为什么在途迁移禁止「先删最早 1k token 再量化」，即使这样收回的页数更多？
- 迁移期间新到达的第 17 路是排队、用 FP8 冷启动，还是先占仍是 FP16 的短页？

**推理回答：** 目标是在不停流的前提下把 16 路 KV 的每 token 字节减半以收回槽位。约束是已出口前缀的数值不能改写语义、尾块还在被下一步读取。用「封闭前缀 / 在写尾页」选边界、用块级冻结 scale 防漂移，并明确这和开服前的量化-淘汰-换出决策不是同一道题。

## SERVE-019. 硬件一共 32 张卡，短闲聊（200 进 / 200 出）约占 80%，16k RAG 约占 20%。decode 被长 prefill 堵住会抖成什么样、16k KV 跨机拷贝要多少毫秒，估完这两笔再决定分不分池？

**答：** 先算干扰和搬运，再决定拆不拆。两成 16k prefill 已足以在混部时周期性堵住 decode，闲聊的 TPOT SLO 会抖；拆池能让 decode 卡只做带宽墙工作、prefill 卡只做 GEMM。但 16k 的 KV 要从 prefill 池拷到 decode 池，体积大约是层数 × KV 头 × 头维 × 长度 × 2（K/V）× 宽度字节；跨节点若只有几十 GB/s 量级的网，拷贝本身就能到数十到上百毫秒，可能吃掉 TTFT 收益。小集群、普通以太网时优先 chunked prefill；互联是 NVLink 或 RDMA 量级、且两边 SLO 都很紧，才值得拆。

**深入展开：** 示意账：70B 级、GQA、8k–16k 上下文，单请求 KV 常见数 GB（精确值随层数、头数、是否量化变）。节点内 NVLink 数百 GB/s，拷 2GB 大约 10ms 量级；跨机 25–100 GbE 则可能 200ms–1s，拆了还不如同卡切块。配比按负载形状：闲聊 200/200 是 decode 重，RAG 16k 短输出是 prefill 重——32 卡里 decode 池应更大，prefill 池按「16k × RAG QPS / 单卡 prefill 吞吐」估，并留突发。系统要多管调度钉扎、传输失败和 decode 节点宕机后的 KV 重算或重路由。监控拆开看 prefill 队列、传输等待、decode ITL；传输等待一旦和 TTFT 一个量级，就该缩回混部或先量化再传。中小流量时两个池都可能空转，利用率反而更差。

**后续追问：** KV 先量化到 8 bit 再传，质量和时延各怎么变；prefill:decode 卡数比你用哪三个在线指标调；decode 池满、prefill 池空时，要不要允许 prefill 卡临时改角色。

**扩展问题：**
- 16k 提示若有约 50% 前缀命中，传输量怎么减，拆池还值得吗？
- 故障演练：prefill 节点在传输到一半时掉线，进行中的请求如何恢复？
- 同机多 GPU 用 NVLink 做卡间分离，和跨机分离的决策阈值差在哪？

**推理回答：** 目标是稳 TPOT 且不牺牲太多 TTFT。先用大象 prefill 的干扰证明有拆的动机，再用 KV 体积/互联带宽证明搬得起。搬不起就切块混部；搬得起再按输入/输出长度比定池大小。

## SERVE-020. 拆开 prefill 与 decode 之后，什么流量或互联条件下反而慢过混部在一起？
**答：** 分离增加 KV 传输、调度与网络开销；短输入、低并发或互联较慢时，这些成本可能超过隔离收益。分离不是默认的吞吐倍增器。
**深入展开：** 测量 KV 传输量、网络拥塞和两个池的负载失衡。
**后续追问：** 何时应扩 prefill 池而不是 decode 池？当排队和首 token 瓶颈主要在 prefill，且 KV 传输与 decode 尚有余量时，才优先扩该池。
**扩展问题：**
- 如何估算一次分离请求的 KV 传输量，并与网络实际带宽和尾延迟对照？
- 一个池故障或过载时，如何避免另一个池继续接收无法完成的工作？
**推理回答：** 先确认阶段互相干扰是主要瓶颈，再评估分离是否覆盖新增成本。

## SERVE-021. 白天对话服务的 SLO 一点都不能让，而夜间那一万份摘要得在早上六点以前交差。可延期的时间窗口加上过往实测的 tokens/s，怎样拿来倒推夜班最晚几点开跑、要预留多少 GPU 小时，而不是另起一套对话优先、批量降级的排队规则？

**答：** 把夜间摘要当成带硬截止的可延期作业：它可以使用「聊天到达率低于日间基线」的窗口，但不能借用白天为 SLO 锁住的槽位。用近几周同窗口的有效 tokens/s（只计摘要池、且已扣除当时残留的聊天）去除这一万份的预估总 token，再乘安全系数，得到需要的墙钟；从 6:00 往回减，就是最晚开工时刻，同时锁定「预留 GPU 小时 = 墙钟 × 专属卡数」。这是容量和开工闹钟问题，不是再发明一条优先级队列。

**深入展开：** 先估工作量：每份摘要输入+输出 token 用历史分位（不要用均值，p90 更接近截止风险），一万份总 token `W`。再估供给：专属摘要副本在可延期窗口内的历史有效 tokens/s `µ`，窗口定义为聊天 QPS < 日间 p50 的一段时间（常见是 23:00–6:00 中的一段，以你自己的曲线为准）。需要墙钟 `T = (W / µ) × s`，`s` 取 1.2–1.4 一类余量，覆盖长度偏斜、失败重试和一次短中断。最晚开工 `t_start = 06:00 − T`；若 `t_start` 落到白天聊天高峰，说明预留卡数不够，应加摘要卡或把一部分摘要提前到更早的低谷，而不是去抢聊天槽。预留 GPU 小时 = 专属卡数 × T，必须和聊天池分账：这些卡在窗口内可以空转等待开工闹钟，但白天不得被调度器当成闲聊扩容来源。验收看三件事：连续多夜的实际完工相对 6:00 的余量、摘要池 tokens/s 是否仍落在用来做计划的 `µ` 附近、以及白天聊天 p95 TTFT 在「摘要开工过早/过晚」对照夜是否不变。边界：某一夜 `µ` 因故障腰斩，闹钟应改成「按剩余 token / 当前 µ 重算能否赶在 6:00 前」，赶不上就减份数或降到更小模型，而不是临时把聊天副本改成摘要。不要在这个决策里再写「聊天优先级更高所以摘要排队」——那是另一道题已经覆盖的调度规则；这里只回答什么时候必须已经开工、要锁住多少卡时。

**后续追问：** 历史 `µ` 用中位数还是用最差的那个工作日夜间，对最晚开工各偏到哪一边；一万份里 10% 是 16k 输入，W 该用哪条分位；开工后聊天突发把「可延期窗口」提前结束，重算公式哪一项先改。

**扩展问题：**
- 用 `W、µ、s、deadline` 写出 `t_start` 和 GPU 小时，并说明为什么 `µ` 不能取白天混部时的集群总 tokens/s。
- 可延期窗口从「固定 23:00–6:00」改成「聊天 QPS 低于阈值才开门」，最晚开工怎样从静态闹钟变成跟随曲线的动态闹钟？
- 预留的 GPU 小时夜间没用完，第二天白天能不能临时借给聊天，归还约束怎么写才不影响次日 6:00？

**推理回答：** 目标是 6:00 交齐一万份且白天 SLO 不动。约束是摘要只能吃可延期窗口里、已被隔离的产能。用历史 tokens/s 反推墙钟和卡时，得到最晚开工点；窗口装不下就加专属产能，而不是改聊天与批处理的排队优先级。

## SERVE-022. 两个字被收回，是因为投机草稿还没被目标模型核过就被送到了前端浏览器。吐出边界该改成只放出已被接受的前缀，还是先攒着再一次性刷出？缓冲又会让用户感知的 TPOT 变差多少？前提是不调草稿长度、也不关闭投机。

**答：** 撤回是发送边界错了：流式通道把「草稿猜想」当成了「已对用户承诺的文本」。把套接字边界改到目标模型接受之后——要么逐步只 flush 已接受前缀，要么在网关按验证窗缓冲、整窗接受再一次刷出。感知 TPOT 变成「验证周期 / 该窗接受个数」，平均值仍是投机后的有效间隔，代价是窗口内的停-走抖动，而不是平均变慢一倍。不要用缩短草稿或关掉投机来掩盖一次回删；那是在改提议器经济学，不是改交付契约。

**深入展开：** 投机循环是：草稿先写 γ 个 token → 目标一次前向按位置接受最长前缀 k̄（含 bonus）→ 拒绝点之后的草稿作废。若 HTTP/WebSocket 在草稿阶段就 `data:` 出去，拒绝点落在用户已经看见的第 2 个字，前端必须发删除或整段重绘，中文还会碰到一个字跨两个 token、撤回「两个字」其实是一个字加半个后续。两条发送边界：①引擎只把 `accepted` 环出队，草稿留在内部环，套接字上永不出现未验证字节；②引擎仍出草稿事件，网关按 `speculative` / `committed` 分通道，浏览器只渲染 committed，speculative 最多用来预热排版但不落可复制文本。缓冲伤害的估法：设目标步墙钟 T_v（例如约 30–50 ms），窗内接受 k̄（例如 2–4），不缓冲、错误流式时用户先以约 T_v/γ 的假速度出字，再在拒绝时卡死并回删；改为整窗提交后，用户每隔 T_v 收到 k̄ 个字，感知间隔 p50 ≈ T_v，感知 TPOT ≈ T_v/k̄。和「真逐步、无投机、间隔 T_v」比，平均值更好，但会出现 T_v 的静音——这是抖动不是吞吐回退。若产品要求「每个字都在约 40 ms 内动一下」，注意一窗内各位置的接受结果是同一次目标前向后同时得到的，不存在「先验证完第 1 个就先发」的捷径；可行的是在网关做节拍放出（pacing）：把这一窗已接受的 k̄ 个字按约 T_v/k̄ 的间隔均匀刷出，用大约一个验证周期的固定延迟换平滑的逐字节奏，回删窗口仍为 0。边界：温度高、k̄ 经常是 1 时，缓冲几乎不增加延迟，回删风险却最大，更应禁草稿上屏；不要把「撤回两个字」归因到草稿 γ 太大——γ 只影响一次最多要删多少，真正的错误是未验证就发送。

**后续追问：** 已接受前缀是「目标分布校正后的接受」还是「贪心比对一致」，两者在温度 0.8 时发送边界有何不同；网关缓冲 80 ms 才能凑齐一窗，语音播报和纯文本聊天谁先不能忍；一次拒绝发生在多字节汉字的中间字节，撤回协议要带字节偏移还是带 token 索引。

**扩展问题：**
- 写出「错误流式：假 TPOT = T_v/γ，回删长度 = γ−k̄」和「整窗提交：感知 TPOT = T_v/k̄，静音 = T_v」两套用户可见时间线。
- 前端若已经把草稿画进输入框，服务端补发 rewind 事件时，怎样避免和用户本地输入抢光标？
- 只缓冲投机 token、普通 decode token 仍逐步推，混合批次里发送路径如何分支？

**推理回答：** 目标是消灭「先看见再撤回」，同时保住投机已经赚到的有效 TPOT。约束是验证从左到右、未接受后缀在数学上不存在。把发送点钉在接受前缀上，用 T_v 与 k̄ 估缓冲抖动，而不是回头改 γ 或关功能。

## SERVE-023. 不另训草稿，用当前已生成后缀 n-gram 去提示和前文里做字符串匹配，把命中处后面的片段交给目标模型验证。代码助手八成流量是根据 diff 改文件、闲聊几乎没有时，一天日志该如何用来选定 n、草稿长度，以及默认关掉哪类请求？

**答：** n-gram 投机（提示查找）用当前已生成后缀在提示和前文里做字符串匹配，把命中处后面的若干 token 当作草稿，再交给目标模型一次验证。没有第二套权重，未命中时额外成本接近一次空查找。它吃的是「输出会大段复述或轻改上下文」的任务；开放闲聊几乎找不到真匹配。用一天日志估命中率、命中后的平均接受长度、未命中时验证是否变贵，再决定 n、γ 和默认开关。

**深入展开：** 流程：取最后 n 个 token 为 s，在 prompt+output 里找 s，取随后 γ 个 token 做草稿，一次前向前缀验证。贪心解码下接受最长一致前缀即可与原输出对齐；若要保持采样分布，仍需按目标/提议分布做接受与拒绝校正，不能只做「看起来像」。n 太小（1–2）假命中多，白跑验证；n 太大（对带唯一标识符的代码取 8–12）命中变稀。可在 n∈{2,3,4,5}、γ∈{4,8,16} 上扫一天 trace，优化 E[接受 token] − α×未命中额外验证（α 由你的内核测出来）。多处命中优先最近一次（局部正在改的那一截），或对 top-2 位置做很浅的树。代码修改、引用原文、改写已给段落命中高；闲聊、全新叙事命中可以低到几个百分点，这时应按任务标签或「是否含大段代码围栏」默认关闭，以免干扰融合内核。查找本身是 CPU 扫描，超长提示上若每次 decode 都全量扫，可能把 TTFT/ITL 的尾巴拉长，长上下文要用滚动窗口或后缀结构。日志字段至少包括：任务类型、是否命中、草稿来源（提示还是已输出）、接受长度、γ、与某段提示的编辑距离。

**后续追问：** 多处命中如何打破平局；温度采样时只做贪心比对会不会改变目标分布；长上下文下朴素扫描会不会变成新的 CPU 瓶颈。

**扩展问题：**
- 设计一张按任务类型拆开的收益表：命中率、命中后平均接受长度、未命中多余前向。
- 提示里反复出现 `return None`，模型其实要写新逻辑，错误命中怎样尽快在验证里杀掉？
- 为什么这种方法几乎不增加显存，却仍可能在超长提示上抬高 TTFT？

**推理回答：** 目标是在高重叠任务上少跑目标 decode。约束是零训练、查找会误命中。用分任务的命中和接受长度决定 n/γ，闲聊默认关，而不是对全部流量开一次「免费加速」。

## SERVE-024. 有人想把若干轻量解码头接到最后隐状态上并行猜后面的 token，再靠候选树一次前向验证，因为 70B 已经把加速卡吃满、运维不同意再驻留一份 7B 草稿。各头接受率随位置怎么掉、部署成本和独立草稿模型怎么比？

**答：** Medusa 这类多头投机复用目标模型在 t 时刻的最后隐状态 h_t，每个头独立预测 t+2、t+3… 的分布，不必再驻留一套完整小模型。主干仍负责真正的下一个 token；随后用树注意力在一次前向里验证整棵候选树，按接受规则留下最长前缀。部署成本主要是几块小矩阵，而不是第二份权重和它的 KV。更远的头看不到前面头实际采出的 token，接受率会随位置掉下去，所以树宜浅、前几层才值得加宽。

**深入展开：** 关键限制是条件独立性：第 k 个头只看见 h_t，不看见已猜的 t+1…t+k−1。前面一旦猜偏，后面的头等于在错误前缀上发言。训练若用真实未来 token 做 teacher forcing，线上却要吃自己的错猜，会出现「训练损失低、第 3–4 头几乎从不被接受」。因此头数常见停在大约 4–5 个（示意档位，按你的接受曲线截断），树在第一层分叉、后面迅速收窄。树注意力用掩码让每个节点只看到自己的路径，一次前向覆盖全部节点；代价是显存随 batch × 节点数线性涨，高峰时一棵灌木就能把赚到的步数吐回去。训练可以冻主干只训头，避免再动目标分布；验证必须仍走原 LM head，头只是提议器。和独立 7B 草稿比：后者 FP16 权重大约十几 GB 还要自己的 KV，但逐步自回归能吃到自己的中间 token，结构化文本上 k̄ 往往更高。显存是硬约束、只需中等加速时选多头；有空余显存或单独的小卡、流量又很可预测时，独立草稿更值。不要把某篇方法报告里的加速倍数当成你这条业务的规格。

**后续追问：** 头与头之间为什么不做成小自回归网络（做成了就滑向特征级草稿）；只训头、冻结主干时接受率的天花板通常卡在哪一步；同样验证预算下「宽 2 深 4」和「宽 4 深 2」谁更值。

**扩展问题：**
- 第 k 个头训练损失已经很低，线上却很少被接受，怎样用「真实未来 vs 自猜前缀」两组对照定位？
- 不改主干权重时，如何回归证明投机路径与纯目标模型贪心输出一致？
- 高并发下树节点数膨胀，你砍宽度还是砍深度，依据哪张直方图？

**推理回答：** 目标是在不能再放一个模型的前提下减少目标前向次数。约束是多头互不看见对方的猜测。用「头参数量 vs 独立草稿显存」和「按位置衰减的接受长度」做取舍，验证仍以原模型为准。

## SERVE-025. 连续批处理想捕获图，但活序列条数和各序列页表长短每步都在变。可变页表怎样从静态 CUDA graph 里拆出去——用设备侧间接块表、按活序列数和页数分档做 padding、再准备一池预捕获图——才能既留下分页带来的并发，又不用每步重录图？

**答：** 图捕获要的是启动拓扑稳定，分页要的是每步块表和活序列数可变，两者不能编进同一份「把页号写死的图」。图里只留「从设备指针读间接块表、再跑注意力 / GEMM」的静态壳，块表内容在每步 launch 前由主机或小核改写；活序列数和最大页数收成几档（例如 8/16/32/64 × 页数桶），每档一份预捕获图，不足的槽位 padding。这样分页照样按真实 token 占槽，图只在档位未命中时才捕获一次，而不是每个 iteration 重录。

**深入展开：** 连续批每步可能 EOS 回收 3 路、新 prefill 插入 2 路，各序列的物理块列表也随 decode 追加一页。若把当前块表地址当常量捕获进图，下一步指针一变图就作废，重捕获常见是数毫秒到数十毫秒，会直接吃掉 decode 步时。拆法分三层。①间接表：设备上放一张固定容量的 `block_table[max_batch][max_pages]`，图捕获的是「读这张表」的内核，而不是读某一帧的具体页号；CPU 或 H2D 只更新脏行。②按档 padding：实际 batch=11 走 16 档图，多出的 5 路 mask 掉；页数按当前批次的 max_pages 上取到 64/128/256 一类桶，短序列多出来的表项标无效。padding 浪费的是少量空序列的调度宽度，换来的是图命中。③graph 池：启动或第一次碰到某档时捕获，池大小是档位数而不是 QPS；同一档内步与步之间只更新表，不改 grid。分页并发仍然来自「用多少块占多少 HBM」——padding 的是索引表和 kernel 维度，不是按 max_model_len 预留连续 KV。边界：档位太稀（只有 64 一档）会让小步长期背着大 grid；档位太密则池膨胀、第一次碰到新档仍会卡一下，要在预热时用假请求把热档录齐。变长页表不要每步 realloc：表按 max_pages 预分配，当前长度写在旁边的 `seq_len[]`。某步需要的 max_pages 超过池里所有图，才允许一次同步捕获或把该请求踢到 eager 路径，不能让全批陪着重录。

**后续追问：** 间接表放主机还是设备，谁在临界路径上；padding 到 64 档后空槽的 mask 是在注意力里还是在采样里，漏一层会出什么错；graph 池在驱动升级后为何必须整池作废重录。

**扩展问题：**
- 画出 batch 从 7→12→9、最长页数从 20→21 时，哪些步走池中图、哪一步会被迫捕获。
- 为什么「把页表钉进图常量内存」看起来少一次读，却和连续批处理根本不兼容？
- eager 路径留给超长鲸请求、热档图留给中位会话时，两套路径的 KV 块分配器能不能共用？

**推理回答：** 目标是同时要分页带来的可变并发和 graph 带来的低 launch 开销。约束是图不能吞下每步都变的块表和 batch。用间接表把可变状态移出图，用档位池把剩余维度离散化，只在未命中档时支付捕获。

## SERVE-026. TTFT 一夜之间回到冷启动水平。客服机器人把每次都变的 request_id 以及实时时钟写进了系统提示最前面时，怎样还原缓存键是怎么拼的，并重排提示？

**答：** 提示缓存命中的是「从序列第 0 个 token 起完全一致的前缀」对应的各层 KV，不是语义相近的句子。把每次都变的 request_id、now() 放在最前面，等于每次换了一把新的前缀键，后面数千 token 的政策与工具 schema 全部重算。把稳定块（系统指令、工具定义、政策全文）顶到最前并保证逐 token 稳定，把时间、请求号、用户问题接到尾部，下一次请求才只 prefill 增量段。

**深入展开：** Prefill 对位置 0…S-1 写出 K、V，形状大约 `[layers, H_kv, S, Dh]`。服务端通常按固定块（例如 16 或 128 token）做哈希：块 i 的键是「块 0…i 的 token 序列」，靠前任意一处改了，其后所有块失效。托管接口常见自动前缀匹配，或要求你标出可缓存断点；计费上命中段输入价往往低于未命中段，但输出仍全价重生成——缓存的是中间结果，不是答案。这和「相似问题直接回旧字符串」的语义缓存不同，后者会把过期政策当正确答案。多轮要把已稳定历史原样追加，不要重排字段、重空格或重序列化工具 JSON。缓存有 TTL 和显存配额，空闲会被逐出；高峰命中率掉也可能是容量不够。数量级只作示意：4k 稳定前缀在 7B–70B 上冷 prefill 可占数十到数百毫秒，命中后 TTFT 往往降到只算用户那一两百 token 的水平。

**后续追问：** 工具 schema 的 JSON 字段被编码器重排，命中率会怎样；同一政策用两种 chat template 包装，缓存能否共享；显存吃紧时你优先逐出冷前缀块还是缩短 TTL。

**扩展问题：**
- 多租户共用同一推理进程，前缀缓存要不要按租户隔离，泄漏面在哪里？
- 系统提示每周五换版，怎样做双版本并存，避免换版瞬间全员冷启动？
- 如何用日志证明一次请求是前缀命中，而不是刚好赶上排队变短？

**推理回答：** 从「KV 按精确前缀索引」出发，把每次变化的字段从键的高位挪到低位。验收看前缀命中率、命中/未命中的 TTFT 分位差，以及提示的字节级指纹是否日稳定。

## SERVE-027. 一份大约八十页的合同被上传进来，任务是圈出其中所有会到期自动续签的条款。把全文一次塞满上下文，和先召回相关段落再细读，两条路在 token 开销与尾部时延上各输在哪里？线上又如何分配流量？

**答：** 80 页量级常见是数万到十万 token，整份塞进窗口会付一次昂贵的长 prefill，注意力和 KV 随长度涨，TTFT 和费用都按「整份」计，还可能超窗口。先按条款切块、用关键词加向量召回「续约 / 自动延期 / 期限」相关段，再只把命中段加原文坐标送给模型精读，费用和首 token 跟召回体积走，漏召回才是主要风险。生产上：单点条款抽取走检索精读；必须对照前后定义节、或用户明确要求「全文通读」的，再开长上下文通道并单独限流计费。

**深入展开：** 示意：中文合同 80 页按版面可能约 4 万–8 万字，视分词大约是数万到十万 token（以你的分词器实测为准）。整塞：prefill 计算和 KV 显存按全长付，并发一高就挤占短请求；同一份合同连问 3 次才值得把稳定全文放进前缀缓存。检索精读：解析 → 按条编号切块 → 混合检索 → 模型只看例如 8–20 段并强制输出页码摘录 → 无坐标的命中作废。漏召回用关键词清单（自动续约、届满、默示延期）和目录规则补洞；扫描件切分失败要升级人工，不能拿邻页凑。费用：检索路径按「召回 token + 生成」计，通常比反复整份通读低一个数量级，但第一次建索引有成本。尾延迟：检索路径的 p99 在切分和重排，整塞路径的 p99 在长 prefill 和排队。长上下文请求要独立配额，避免一份合同堵住一池客服短问。不要为了省钱先做不可逆的摘要再找续约——摘要可能把但书丢掉。

**后续追问：** 续约条款把关键数字放在附件，检索只建了正文索引会怎样漏；同一份合同被 5 个问题连打，何时改走「缓存全文 KV + 多次短问」更划算；窗口标称 128k 但质量在 32k 后滑坡，分流阈值按谁定。

**扩展问题：**
- 用户说「不要漏任何一处」，你怎样用条款编号覆盖率证明检索路径，而不是再塞一次全文？
- 切块跨越「定义 + 续约」两节时，窗口要不要强制带上定义节？
- 如何把长上下文通道的单价和队列优先级标得比检索通道高，让产品不会默认整份硬塞？

**推理回答：** 目标是找全续约条款，约束是费用、尾延迟和漏召回。能定位的抽取用检索加坐标，必须全局对照的才付长上下文。用坐标完整率、漏报抽查和分通道延迟验收。

## SERVE-028. 靠重写来压缩长对话之后，为何前缀缓存的命中率可能反而下降？
**答：** 前缀缓存复用相同 token 前缀的 KV；重写历史或改变靠前的消息，会使后续前缀不再相同。压缩节省输入长度，但可能失去已有缓存收益。
**深入展开：** 比较真实计费 token、prefill 时间和命中率，而非只看压缩后字符数。
**后续追问：** 稳定系统提示与动态摘要应如何布局？可让稳定内容尽量保持不变，把动态部分放在其后，但必须先满足消息角色、安全与模型语义要求。
**扩展问题：**
- 如何设计压缩阈值实验，同时衡量 token 节省、缓存命中和回答质量？
- 仅改变空格、工具定义顺序或序列化方式，为什么也可能影响前缀复用？
**推理回答：** 同时核算长度减少和重算成本，按实际服务缓存语义做实验。

## SERVE-029. 前缀 KV 命中之后，为何逐步吐出的新 token 通常并不会因此更快？
**答：** 命中的前缀 KV 避免重复 prefill；新输出仍须逐步计算。收益主要来自共享长前缀，输出很长或命中很少时总体收益有限。
**深入展开：** 命中率要结合省掉的 token 数与预填充耗时解释。
**后续追问：** 高命中率但端到端延迟没降，应查什么？检查命中的 token 数、排队时间和输出长度；decode 或其他环节可能占主要耗时。
**扩展问题：**
- 两套服务缓存命中率相同但节省的 prefill 时间不同，可能有哪些原因？
- 如何避免把语义相似的提示误当成可直接复用 KV 的相同前缀？
**推理回答：** 分解首 token 与后续生成时间，避免把局部优化误当整体加速。

## SERVE-030. 逻辑序列被 PagedAttention 映到不连续的物理块上之后，是不是所有形式的 KV 浪费都没了？
**答：** 它用非连续物理块映射逻辑序列，减少外部碎片并支持共享；末块未用空间、元数据以及分配粒度仍有开销。
**深入展开：** 块大小影响内部碎片、调度与内核效率，不能只选最小块。
**后续追问：** 大量短请求与少量长请求的最优块大小会相同吗？未必；末块浪费、元数据和内核效率的相对占比会随请求分布变化。
**扩展问题：**
- 如何用有效 token 数、分配块数与块大小分别统计内部浪费和共享收益？
- 共享前缀发生分叉写入时，怎样验证块引用与生命周期管理没有破坏其他请求？
**推理回答：** 分别度量有效 token 占用和预留空间，避免把逻辑容量当物理容量。

## SERVE-031. 投机采样如何让最终 token 服从目标侧分布，而不是草稿看起来过了关？
**答：** 精确投机采样按目标与提议分布计算接受概率，拒绝后从校正残差分布采样；不能仅判断候选文本看起来合理。
**深入展开：** 分布保持依赖正确算法及数值实现，不代表相同随机种子生成逐字相同结果。
**后续追问：** 为什么只接受 argmax 相同的 token 不能替代一般采样校正？argmax 只描述最高概率项，无法保证其余候选的概率质量分配符合目标分布。
**扩展问题：**
- 如何在小词表玩具模型上用频率检验验证接受与拒绝校正实现？
- 比较投机采样与目标模型采样时，为什么逐字输出一致不是必要条件？
**推理回答：** 区分贪心等价和概率分布等价，按目标解码模式验证实现。

## SERVE-032. 你主张用最后一层特征训一层草稿网络、自回归预估下一拍隐状态再复用原 LM head，同事却觉得再挂几个解码头就够。哪些观测能证明，相比各头互不依赖，这样更划得来那几步串行开销？

**答：** 独立多头只从一张 h_t 快照跳着猜未来 token，第一步猜错后面全废。EAGLE 这类特征级方法用一个大约一层的草稿网络，吃目标特征序列和错开一位的已选 token 嵌入，自回归预测下一时刻隐状态，再复用冻结的 LM head 得到词分布。每一步都条件于上一个草稿 token，平均接受长度通常更长，才能摊掉这几步廉价但串行的草稿计算。

**深入展开：** 在特征上预测往往比直接在十万级词表的远处位置上做 softmax 更稳：最后隐状态已经是 LM head 要读的连续摘要，回归 h_{t+1} 比凭空猜 t+4 的离散 token 平滑。错开一位的 token 用来消采样不确定性——同一 h_t 可能走出不同词，不告诉草稿实际选了谁，它只能猜平均分支。草稿逐步走 γ 步，这是多头并行省掉的时间；换来的是更高的 k̄ 和一棵可以按置信度长深的候选树。节点总数仍要设硬预算，否则验证一次比普通 decode 还贵。当 profile 显示拒绝集中发生在第 2–3 个 token、多头后段几乎全是废节点，而草稿单步只占目标步的一小截，特征自回归就值。若 γ 只能取 2、显存紧到连一层草稿 KV 都嫌多，或多头第一头已经很高，继续加头更简单。验证仍必须走原模型，不能把草稿分布直接当输出；分布校正的细节与「只看验证通过」不是同一件事，这里只要求路径上不能跳过目标模型。草稿和主干一起微调时，要盯拒绝率，防止草稿变成「另一个模型」而验证大量打回。

**后续追问：** 草稿为什么可以薄到大约一层；不输入错开 token 时接受曲线会怎样塌；动态树按置信度生长时，总节点预算和最大深度哪条先触顶。

**扩展问题：**
- 同一验证预算下比较「4 个独立头」和「4 步特征自回归」，你看平均接受长度还是看墙钟？
- 草稿网络自己的 KV 要不要缓存，如何和目标 KV 的位置对齐？
- 主干冻结、只训草稿时，特征空间一变（换量化或换微调档）为什么要重训草稿？

**推理回答：** 目标是拉长平均接受长度，而不是再挂几个互不说话的头。约束是多头看不到中间猜测、特征草稿却要逐步走。若拒绝发生在多头后段、且草稿单步很便宜，就付串行成本；否则保持多头。

## SERVE-033. 投机解码一次向前看多长，该依据哪些观测来定？
**答：** 草稿更长可能一次接受更多 token，也会增加草稿、验证及被拒绝后废弃的工作。应根据接受长度分布、目标模型负载和实测延迟调节。
**深入展开：** 高接受率不一定净加速，需计入草稿模型占用与批量变化。
**后续追问：** 吞吐已饱和时是否仍值得启用？不一定；草稿计算与额外验证可能争用资源，应在目标并发下比较净吞吐和延迟。
**扩展问题：**
- 草稿长度增加后接受率下降但每轮接受 token 数增加，应如何判断净收益？
- 怎样按请求类型或接受长度历史动态调整草稿预算，同时避免过度调节？
**推理回答：** 用端到端成本和分位延迟比较，而不单独最大化接受率。

## SERVE-034. 离线选择题分数差不多，可一要求把召回段落里的条款号逐字抄出来，INT4 包就开始瞎编编号。同一套 7B 分别打成 FP16 的服务端构建和 INT4 的端侧包时，半精度浮点（BF16 或 FP16）和整数量化（INT8 或 INT4）破坏的误差类型为何不是同一类，该拿哪类评测来决定哪些层保持更高位宽？

**答：** FP16/BF16 是浮点格式，改的是尾数和指数宽度，矩阵乘有舍入，但很少把罕见标识符的 logit 整段抹平。INT8/INT4 把数值范围装进很短的整数格子，靠 scale（以及常有的 zero-point）还原，离群权重和尖激活会饱和。选择题还能靠语义簇选对字母；要逐字抄条款号、人名、代码时，被裁掉的精细 logit 会让流畅的幻觉压过原文。应用「必须能引用」的集合决定哪些层留在更高精度，而不是看通用准确率是否接近。

**深入展开：** FP16：5 位指数、10 位尾数，精度好、范围窄于 FP32，偶发溢出、多见舍入。BF16：8 位指数（范围接近 FP32）、7 位尾数，训练更爱用它的范围；推理上和 FP16 通常接近，但不是位级相同。INT8 只有 256 档，逐张量 scale 遇到通道差异会伤一层；逐通道或逐组更好。激活长尾（部分 MLP）需要按 token 或按组的动态 scale，否则 clip。INT4 只有 16 档，几乎总是分组（例如组大小 32–128 这一类做法）并给离群值留更高精度。这些是方法类型，不能按位宽承诺「无损失」或固定加速比。引用任务先坏，是因为正确续写是低频 token 序列，注意力/MLP 上的量化噪声会让正确 logit 掉到一个更流畅的近邻下面；选择题的正确项仍在粗语义里。实践中更敏感、常被排除出最低比特的是 embedding、LM head、LayerNorm 的尺度，以及有时最前和最后几块——混合精度配方正是为此。校准必须用领域激活：用干净通识文本校准、去服务法律检索，scale 会偏。生成越长，激活误差越叠；短选择题看不出。权重量化和激活量化要分开关：只压权重时引用任务仍可能过，激活一 clip 就塌。BF16 训练的权重若直接按 FP16 推理，注意少数层是否溢出，这和 INT4 不是同一类事故。

**后续追问：** 权重量化和激活量化谁先搞坏引用；group size 从 128 收到 32，质量和内核速度如何对打；BF16 训练产物用 FP16 推理时你看哪些层的 inf/NaN。

**扩展问题：**
- 设计约 50 条「必须逐字引用」的持出集，说明它比选择题更能暴露 INT4 损伤。
- 哪些层默认不进 INT4，为什么先保护嵌入和输出头而不是任意一层 MLP？
- 业务说「慢一点的准还不如快一点的差一点」时，你用哪条线上指标证明已经不可接受？

**推理回答：** 目标是解释「泛化分还在、复制任务已坏」。约束是整数网格会裁离群值和精细 logit。用格式的表示能力对齐任务类型，再用混合精度和领域校准保护标识符通路。

## SERVE-035. KV cache 量化和权重量化相比：各自压缩的是哪部分字节，误差又分别在哪里显现？
**答：** 权重量化压缩模型参数，KV 量化压缩随请求增长的注意力状态；两者可独立配置，影响的访存与误差来源不同。
**深入展开：** KV 量化需关注尺度、内核支持、长上下文准确率及额外转换开销。
**后续追问：** 显存下降为何不保证延迟下降？量化可能增加转换或尺度处理开销；如果原本瓶颈不在 KV 访存，容量收益也未必转成速度收益。
**扩展问题：**
- 怎样用长上下文与高并发两组实验区分 KV 量化的质量影响和容量收益？
- 权重保持原精度而只量化 KV 时，应怎样建立独立回归基线？
**推理回答：** 先核实当前瓶颈与量化内核，避免把容量收益等同算力收益。

## SERVE-036. 单张 80GB 加速卡塞不进 bf16 的 70B，当场爆显存。量化三刀——权重、KV、激活——顺序该怎么排，每一刀伤哪类质量？

**答：** 先动权重：70B bf16 仅权重就约 140GB，一张 80GB 卡放不下；压到 8 bit 约 70GB，4 bit 约 35GB，才能谈单卡加载。KV 是第二刀：上下文一长，KV 按序列线性涨，先把可服务的 batch 和长度顶满；量化 KV 主要伤长距离抄写、引用和「第 k 个」这类精度。激活量化动的是每层动态张量，省的是峰值而不是常驻体积，数值更脆，通常放在权重量化之后，并用校准看层误差。

**深入展开：** 显存账单大致是权重 + KV + 激活 + 碎片。权重常驻，和 batch 无关；KV ≈ 2 × 层数 × H_kv × Dh × seq × batch × 宽度，70B 级、GQA、8k、batch 8 时可以到数十 GB 量级（示意，随头数变）。激活在长序列 prefill 时出现尖峰，decode 时小得多。8 bit 权重量化（示意：就近取整 + 逐通道 scale）对多数生成任务接近无损；4 bit 要分组 scale，否则离群通道把码本浪费掉。量化改的是同一张量的码本宽度，不是换成更小稠密模型，也不是剪枝。上线必须以业务集对比 bf16 / 8bit / 4bit，数学、代码、专有名词比困惑度先坏。没有对应低比特内核时，量化只省显存、不加速，甚至因反量化更慢。

**后续追问：** 权重已经 4 bit 仍 OOM，你砍最大上下文、上多卡切分，还是再量化 KV；只把 KV 收到 INT8，TTFT 和 TPOT 谁会动；激活里哪些层对量化最敏感，你怎么从校准误差找。

**扩展问题：**
- FP8 权重和 INT4 权重在能否走 Tensor Core 上差在哪？
- 同一套 4 bit 权重，prefill 用高一点的激活精度、decode 用更低，值不值？
- 如何用一小份数字、代码、多语言对抗集，决定能不能砍到 4 bit？

**推理回答：** 按「谁占常驻显存」排序：权重 > 长上下文 KV > 激活尖峰。每刀用对应失败形态验收：放得下、长度和 batch 够、业务指标不塌。

## SERVE-037. 可 mmap、张量允许混精度的 GGUF 单文件是一侧，分片权重外加独立分词器和对话模板是另一侧；这套 7B 要当笔记本本地助手。冷启动时间、多进程只读共享、量化元数据分别绑在哪一层，什么情况下值得压成单文件？

**答：** GGUF 把版本化文件头、键值元数据（结构、词表、合并规则、对话模板、量化类型）、张量目录（名字、形状、dtype、偏移）和对齐后的张量载荷打进一个文件。运行时可以按页映射，用到的层才fault进来，多个进程能共享只读页。分片权重加外置分词器适合训练和集群一次装进显存的路径，但启动要打开一堆文件，词表/模板还容易和权重版本错位。本地、要快起、要混精度量化时转单文件；服务端已经把分片直接灌进 HBM、还要热插组件时，继续分片。

**深入展开：** 布局顺序是魔数与版本 → 元数据 → 张量信息表 → 按对齐（常见按 32 字节一类边界，便于 SIMD 和页故障粒度）存放的数据。对齐是这种格式存在的理由之一，随便序列化一个字典会让 mmap 和向量化加载变扭。自包含的意义：CLI 只指向一个文件就能跑，避免「权重量化档是 A、词表 json 是 B、模板还停留在旧版」这种静默坏输出——分词偏移一个 id，整段回复都会看起来流利但错词。量化元数据写在张量一级，不同层可以是不同整数方案（同一生态里常见的 8-bit / 分组 4-bit 等类型），这是文件格式能力，不是某种方案永远无损的承诺。mmap 下 RSS 可能看起来很大，真正脏页可以很小；首 token 会包含你碰到的那些层的缺页代价，对 CPU 卸载和部分加载是优点。多进程各开一个助手时，同一映射避免 DRAM 乘份数。转换方向一般是：读配置、词表和分片 → 写元数据 → 可选地按张量量化 → 写对齐载荷；已经量化后再倒回去往往有损。集群张量并行要按层切片流式进显存、或要把适配器当独立文件热更新时，单文件反而不如分片。陈述版本号和字段时只当机制说明，不要背诵未核对的规格细节。

**后续追问：** 对话模板为什么必须进文件，而不能假定调用方自己拼提示；映射后覆盖写原文件为什么危险；混精度如何在张量目录里表达，加载器漏读一个 dtype 会怎样。

**扩展问题：**
- 对比「启动时把 7B FP16 整包读进 DRAM」和「mmap + 按层量化」在 16 GB 内存笔记本上的工作集。
- 词表只留在外置文件、权重已进单文件，错配时会出现哪类「读着通顺但全错」的输出？
- 训练检查点为什么仍应留在分片格式，只在发布边缘包时转换一次？

**推理回答：** 目标是本地运行时一次拿齐权重、词表和模板。约束是磁盘随机读、内存和版本对齐。单文件加对齐加 mmap 解决启动和共享；训练与集群互操作仍用分片。用启动时间、唯一脏页和一次错配事故来验收，而不是看文件个数。

## SERVE-038. 数学题和工具 JSON 成批坏掉，闲聊分却几乎不动——权重量到了 INT4。该把敏感层拉回更高精度、扩充校准集，还是把这类请求从 4bit 副本上拿掉？

**答：** 平均闲聊分掩盖的是尾部分布：INT4 对流畅性往往够用，对需要精确累加和严格 schema 的任务，误差会在层间放大。先按切片看数学、代码、长上下文、工具 JSON 是否同时坏；若只是括号和数字，优先混合精度（`lm_head`、首尾层、归一化仍用更高位）和覆盖这些模式的校准；若推理链中间就已经算错，4bit 副本不该接这类路由，应留给 INT8/FP16 或未量化模型。不要在已经失真的 4bit 上靠再多标一点闲聊挽回算术。

**深入展开：** 训练后量化用一小批校准数据估缩放和零点（或等价参数），校准若全是对话，激活分布就覆盖不到长数字和特殊符号，量化噪声会打在这些通道上。经验上（示意，视方法和模型）：`lm_head` 和 embedding 对 token 选择极敏感，很多实现会保持更高精度；注意力输出和 MLP 的离群通道是需要保护的对象。数学失败模式是中间数值被量化噪声推离，后续步骤在错的数上继续写，看起来像「会说话但不会算」。JSON 和工具失败是花括号、转义、枚举值被换成近邻 token。处置树：①先用同一权重的更高精度对照，确认不是提示或解码参数改坏的；②混合精度与更好的校准（把公式、JSON、工具轨迹按比例塞进校准集）；③仍不够就对数学和工具路由走更高位宽副本，闲聊走 INT4 以保吞吐；④若自有训练预算，可做量化感知训练或对关键层短恢复，但上线前仍要看切片，而不是只看困惑度。KV 量化是另一条轴，长上下文记忆丢和权重量化要分开对照。评估禁止只用综合平均分；要报精确匹配、JSON 可解析率、隐藏数字题。若 INT4 省下的显存并没有转化成可卖并发，而修复成本很高，应回退位宽。

**后续追问：** 只把 `lm_head` 回更高精度，JSON 修好了但数学仍差，下一步动校准还是动路由；校准集约 128–512 条时，你怎样避免又变成全是闲聊；激活量化和仅权重量化，哪一个更常先打烂算术。

**扩展问题：**
- 设计一张切片表：闲聊、短抽取、数学、工具 JSON、8k 上下文，每格写最低可接受位宽。
- 量化后 top-1 token 频繁被近邻替换，怎样从 logits 而不是从文本相似度发现？
- 同一张卡上 INT4 闲聊和 INT8 工具模型混部，显存和调度怎么隔离以免互相抢 KV？

**推理回答：** 目标是保住精确任务，约束是 INT4 的误差对流畅和精确不对称。用对照实验区分「校准或层精度不够」和「该任务不该走 4bit」，按切片路由而不是追求全站一个位宽。用可解析率和数字精确匹配验收，不用闲聊平均分宣布量化成功。

## SERVE-039. 7B 聊天模型要靠训练后量化上到 4 bit 生产——不许重训、窗口只有一周。做得到吗？若再压到 2 bit，哪一类能力会先裂？

**答：** 一周且不重训，路径只能是训练后量化（PTQ）：用一小份校准数据估每层或每组的 scale，把已有权重写成 4 bit 码本，再在对话、数学、代码、安全拒答集上对比。4 bit 配分组量化（例如每 64/128 个权重一个 scale）并保护离群通道，不少 7B 级模型可以上线，但必须看业务集而不是只看困惑度。2 bit 有效码本大约 4 个值，误差不再是「差一点」；推理链、算术进位、罕见专有名词会先断。没有量化感知训练（QAT）或更重的补偿，2 bit 不该当生产默认。

**深入展开：** PTQ 不回传梯度，墙钟是校准前向（示意：几百到几千条样本）加一次写权重，适合冻结的开源权重。QAT 在训练里对前向量化、用直通估计器回传，让权重学会待在可量化的格子里，精度更好，但需要数据和 GPU 时间，一周还要冻评测通常排不进。2–4 bit 的共性问题是动态范围：少数大权重若和整层共用一个 scale，其它值被压成零。分组、旋转变换、保护关键通道都是在不重训的前提下挪误差。7B 比 70B 更脆，因为冗余更少。激活若也进 4 bit，比只压权重更伤。低比特还依赖专用 kernel，否则 decode 不加速。经验分层只作示意、不是保证：8 bit 常接近无损；4 bit 加较好的 PTQ 对多数生成可接受；3 bit 开始要个案；2 bit 基本进入「需要 QAT」区。困惑度平稳但业务掉，通常是格式、工具 JSON、多语言等长尾槽位坏了。

**后续追问：** 校准集约 128 条通用文本，对话产品会漏掉什么分布；逐层最小二乘类方法和保护通道类方法，一周内你先跑哪条、怎样并排对比；2 bit 若只压注意力或只压 FFN，哪边先不可用。

**扩展问题：**
- 分组从 128 收到 32，精度和每层额外 scale 存储怎么换算？
- 什么信号说明该停 PTQ、去申请一次 QAT，而不是再调 scale？
- 量化后工具调用的括号开始错、日常闲聊还行，发布门禁缺了哪一类用例？

**推理回答：** 约束是「不重训 + 一周」，所以先用 PTQ 打 4 bit，并用业务集决定能不能发。2 bit 把问题从误差变成码本不够，默认拒绝，除非有 QAT 证据。验收看分层任务，不只看困惑度。

## SERVE-040. 部署 70B 模型：4 张卡把每一层张量切开并行，对比起 4 个完整副本，首 token 延迟谁更低，整个集群的吞吐又是谁更高？

**答：** 张量并行把单层 GEMM 和注意力头切到 4 卡，单请求的计算和显存都按近 4 分，TTFT 和 TPOT 通常下降，前提是卡间 AllReduce 比省下的计算更便宜。4 个完整副本没有层内通信，总吞吐近似 ×4，但每个副本仍要装下整网权重——70B BF16 根本放不进单卡，纯副本方案会先出局。显存不够用张量并行，显存够了要吞吐用副本。

**深入展开：** 以列切 / 行切的 MLP 为例：`Y = SiLU(X W1) W2`，把 W1 按列分到 4 卡，每卡算 1/4 中间通道，SiLU 局部完成；W2 按行分，再对部分和做一次 AllReduce 得到 Y。注意力常按头切，每卡算 1/4 的头，输出再汇合。70B 隐宽大约 8192，TP=4 后每卡 GEMM 的 N 维变成 2048，计算量约 1/4，权重和按头切的 KV 也约 1/4。Decode 每步都要一次或两次 AllReduce，通信量是 `[B, H]` 量级；B=1 时只有几十 KB，但延迟是集合通信的尾延迟，在 PCIe 上可能到数百微秒到毫秒，把省下的计算吃掉。所以张量并行适合机内 2/4/8，很少跨机器做高度数。副本方案每卡独立跑完整前向，零层内通信，调度简单、故障隔离好；但 BF16 140 GB 必须先放得下，或先量化。混合很常见：机器内 TP=2/4 解决容量和单流延迟，机器间复制解决 QPS。度数不是越大越好：TP=8 时通信次数不变但每卡计算更碎，占用率下降，decode 可能更慢。

**后续追问：** 为什么 decode 比 prefill 更怕张量并行通信；GQA 的 KV 头数少于并行度时怎么切；张量并行和流水线同时开时，单请求路径上有几次跨阶段传输。

**扩展问题：**
- 4 卡张量并行里挂掉一张卡，为什么比 4 副本更难做故障转移？
- 同一层的 AllReduce 能否和下层无关计算重叠？decode 时为什么很难？
- 若改用专家并行而不是张量并行，通信从 AllReduce 变成了什么？

**推理回答：** 先看单卡是否装得下 70B：装不下就没有纯副本选项。装得下则比较“用层内通信换单流延迟”和“用零通信换线性吞吐”，在机内高速域用张量并行降延迟，在域外用副本来扩 QPS。

## SERVE-041. 单卡工作集在 70B 压到 INT4 之后仍然装不下。什么时候才必须跨卡切开模型，而不是再压精度或换更小的网？

**答：** 分片解决的是「单设备放不下完整工作集」，不是默认的加速器。先穷尽不切模型的手段：换更小但达标的模型、权重量化、缩小最大上下文或并发以压缩 KV。只有质量或延迟 SLO 不允许再压，且你接受跨卡通信和运维复杂度时，才把权重（必要时连 KV）切到多设备。切早了，小 batch 上的集合通信会先打穿延迟；切晚了，只能 OOM 或拒答。

**深入展开：** 工作集 ≈ 权重量 + KV + 激活 + 运行时。70B bf16 权重大约 140 GB，一张 80 GB 卡放不下；INT4 权重大约 35 GB，卡上还能留几十 GB 给 KV，许多「单卡装不下」其实是高并发长上下文把 KV 抬上去了——这时先限并发或做 KV 量化，不必上分片。真要分片，常见切法是按层切开或按矩阵维切开，也可以按 MoE 专家切开；共同点是每个设备只常驻一部分参数，算到那一块时靠点对点或集合通信把激活或分片拼齐。通信账只作示意：按矩阵切开时每层每步都有一次跨卡同步，decode 逐步都要付；按层切开则阶段间传递激活，气泡会吞掉设备利用率。单请求延迟往往随切分宽度先降（叠了算力）再升（通信和气泡占主导）。这和「同一份完整权重复制到 N 卡」相反：复制不降低单请求显存，只加吞吐。训练里把优化器状态切开是另一条线，不要和服务期权重切分混成一个决策。

**后续追问：** INT4 已经能装下权重，但 32k 上下文 × 64 并发仍 OOM，你切模型还是切 KV 池；跨节点只有约 10–25 GB/s 量级互联时，把 70B 切成 8 路对交互 decode 意味着什么；质量和延迟都不允许再压时，上 2 路切分和直接换 32B 你怎么用评测集拍板。

**扩展问题：**
- 只把 embedding 和 LM head 放第二张卡、中间层仍在一张卡，算不算有效分片，通信会不会反而更差？
- 分片后单卡利用率下降约三成，怎样判断是气泡、同步等待还是实现没重叠通信？
- 何时应该拒绝分片、改成「大模型走离线异步、线上只留能单卡放下的模型」？

**推理回答：** 先写工作集公式，确认墙的是权重还是 KV。能用量化、限流、小模型打掉的墙就不要引入通信。最后用单请求延迟、通信占比和 OOM 率验证「该切」而不是「能切」。

## SERVE-042. 金丝雀和回放门禁要同时盯住可持续吞吐、KV 与工作区显存、TTFT 分位、以及 temperature=0 下同提示的 token 序列，该怎么设？推理引擎小版本升级、发行说明里连分页 KV 块尺寸和调度默认值一并改了时，贪心输出对不上逐字，凭什么区分数值抖动与真回归并决定整包回不回滚？

**答：** 引擎包（内核 + 块大小 + 调度默认）整包金丝雀，回放用冻结提示和冻结并发分布。门禁四条一起看：可持续吞吐 / SLO 内完成率、KV 与工作区显存、TTFT 分位、以及 `temperature=0` 下同提示的 token 序列。贪心不再逐字相同，先不要回滚：先量近并列 token 的 logit 间隙和任务级指标（槽位、拒答、schema）；只有任务指标掉、或显存/TTFT 破线，才整包回滚。单看字符串不等，不够当回归。

**深入展开：** 小版本示意：KV 块从 16 token 改到 64、`max_num_seqs` 从 256 收到 128、切块 prefill 的默认开关翻转。块变大改变页内碎片和内核切块，调度变了改变同批伙伴，两者都会改 GPU 归约顺序；fp16/bf16 加法不满足结合律，注意力累加的最后几 bit 会漂，贪心在 top-2 间隙极小时就会换字。这和换权重不是一类故障，也不是分页块表怎么分配的问题。门禁：①回放昨天高峰的长度分布，比 tokens/s 和「在时延 SLO 内完成的比例」，不要只报峰值吞吐；②显存看已用 KV、预留、OOM 率——块变大常见内部碎片升、并发先掉；③TTFT p50/p95，分开缓存命中与未命中；④输出漂移：冻结 100–300 条提示，新旧引擎各贪心跑，对失败位算 token 一致率。判别：新引擎对同一条提示重复 N 次（示意 N=5），若自己就抖，先记「引擎非确定性」而不是跨版本回归；新旧分歧处若能拿到 logprob，且 `logp1-logp2` 小于约 0.05（示意，按你的精度标定），判近并列数值翻转。任务门：JSON 可解析、关键槽位 F1、拒答一致性——这些稳、只是同义换词，可以接受或钉随机源后放行。数字、工具名、拒答/遵从翻转，不论 logit 多近，都当真回归。回滚粒度是整包引擎，不要只把块大小拨回去却留下新调度。禁止用投机解码当对照（那是另一条加速路径）；也不要用「块表有没有省显存」当这道门的主指标。

**后续追问：** 新引擎在 batch=1 时贪心逐字相同、一上生产批大小就开始漂，你还算不算数值问题；TTFT 变好但显存碎片导致偶发 OOM，你保吞吐还是回滚；回放若不用真实前缀分布，会漏掉哪一种「调度默认值」回归。

**扩展问题：**
- 怎样用「近并列翻转占比」和「槽位 F1」两张表，决定放行、限流观察还是整包回滚？
- 块大小和调度默认值哪一个先做单因素回放，才能知道是碎片还是批形状在伤 TTFT？
- 贪心已漂，线上温度是 0.7，你还要不要把 token 一致率写进门禁，还是只留任务级指标？

**推理回答：** 目标是引擎小版本能回滚、能区分「算子累加顺序变了」和「服务行为坏了」。约束是块大小与调度会同时改数值路径和排队形状，贪心逐字相等从来不是跨内核的合同。所以四条门禁并行，用近并列和任务指标给漂移定性，破线才整包回滚。验收看任务契约和 SLO，不看两条字符串是否完全一样。

## SERVE-043. 权重不再在运行时拼算子，改为先编出发射引擎再接流量；换一款架构不同的 NVIDIA 加速卡就得重编。编译步骤究竟把什么冻在「这张卡、这一代 Tensor Core」上，为何编好的引擎不能当普通权重检查点来拷贝？

**答：** 编译把计算图定到「这张卡、这一代 Tensor Core、这组精度和并行切分」上：融合小算子、挑选调过的注意力与 GEMM 内核、插入量化缩放、规划分页 KV 和飞行中批处理的工作区。引擎里是内核选择和共享内存布局，不是可移植的权重容器，所以换 SM 架构、换精度或改张量并行度都要重建。收益是在对应 NVIDIA GPU 上少一次运行时的内核搜索和多余显存往返；代价是构建时间、硬件绑定，以及新模型结构往往要等编译器支持。

**深入展开：** 典型流程：读入权重 → 选定精度（例如 FP16 / FP8 / INT8 / INT4，以你实际编译器版本为准）和切分 → 构建引擎 → 交给运行时或推理服务器加载。融合的常见对象是 QKV 投影与注意力、残差与归一化、解码循环里的采样周边小核，目的是减少中间张量的写回。内核是按目标 GPU 的算力、共享内存和 Tensor Core 代际搜索出来的，A 代卡上的最优配置搬到 B 代卡可能非法或更慢，因此引擎文件不能当「换卡即用」的 checkpoint。飞行中批处理仍在运行时做：编译负责单步内核，调度负责请求进出。边界：模型结构或最大长度变了要重编；同架构、同版本、同配置的副本可以分发；非 NVIDIA 设备这条路径不适用。不要用某次博客里的加速倍数当合同数字，用你自己的输入输出长度和并发复测。

**后续追问：** 只改最大批大小、不改精度，要不要重编；FP8 在没有对应 Tensor Core 的卡上编译会失败还是静默回退；把引擎构建塞进持续集成时，制品要按 GPU 型号还是按机型标签归档。

**扩展问题：**
- 同一份引擎在两张同代但显存不同的卡上加载，工作区或最大并发会踩到什么限制？
- 算子融合减少了哪些中间写回，却可能让你更难用普通剖析器看到某一层的耗时？
- 新结构的开源模型次日就要上线，编译器还没有对应层，你是等支持、手写插件，还是先用即时引擎顶着？

**推理回答：** 目标是吃满特定 GPU 的低精度算力和融合内核，约束是部署可复现、换硬件可重建。把「可移植权重」和「已调优可执行图」分开，换卡就走重建流水线。用同流量下的 TTFT/TPOT 和构建耗时一起验收，而不是只看引擎文件体积。

## SERVE-044. 谁管拉模型、谁管配方文件、谁管聊天模板、谁管真正的矩阵乘？内网二十人要一条命令切换模型、并以兼容 HTTP 口调调用时，这层本地运行时碰到多大并发就该把位置让给专用服务引擎？

**答：** 拆成四层：后台守护进程管生命周期和兼容 HTTP 口；拉取层按层下载并做本地缓存；配方文件声明基础权重、系统提示、采样参数和聊天模板，保证同一名字对全组员是同一行为；真正的矩阵乘和量化内核交给本地推理库。二十人轮流单会话通常够用；一旦同时十几路长上下文、或要分页 KV 和连续批处理吃满 GPU，就应把「便利封装」换成专用服务引擎，而不是继续加机器复制这份桌面运行时。

**深入展开：** 用户发出「运行某名字」时：守护进程看本地缓存是否已有该标签 → 没有则按层拉取 → 按配方拼出系统提示和模板 → 按机器探测把能放下的层放到 GPU，其余留在 CPU → 空闲一段时间后卸载，避免笔记本常驻占满内存。兼容口调只保证消息数组和流式字段能对上常用客户端，不保证和托管 API 的工具调用、logit bias 行为逐项一致。配方的价值是把「同一个 8B 权重 + 不同系统提示」收成可分发的名字，避免每人本地改一段无法复查的提示。硬件探测失败要显式报「CPU 模式 / 部分卸载」，不能 silently 比昨天慢十倍还当成功。边界：内网若要求审计、租户隔离、配额和 GPU 高利用率，这份运行时缺少生产调度；它适合开发机、演示和隐私敏感的单机试用。模型更新应钉版本摘要，禁止「同名标签漂到另一份量化文件」却没有回归。

**后续追问：** 两人同时 `run` 同一个 13B，守护进程是共享一份权重还是加载两份；配方里写死 temperature=0，客户端又传 0.8，以谁为准；空闲卸载的时间窗怎样既不让早会第一句等冷启动，又不把 16GB 笔记本撑爆。

**扩展问题：**
- 配方只改系统提示、不改权重，缓存键和对外名字怎样避免组员以为模型变了？
- 兼容口调缺少某种工具调用字段时，是在网关补齐还是禁止该客户端直连？
- 用什么并发和 TTFT 阈值触发「从本地运行时迁到集群服务引擎」的决策，而不是凭感觉？

**推理回答：** 目标是低摩擦的本地换模型和统一口调，约束是硬件小、人数少。把便利层和推理核分开，人数或并发越过单机调度能力就换引擎。用同时在线会话数、卸载次数和是否误用同名标签验收。

## SERVE-045. 聊天高峰把 embedding 打到 OOM。同一组 GPU 同时跑对话服务、embedding、夜间评测三个模型时，如何切显存配额，而不是再采购一排加速卡？

**答：** 先把显存拆成「权重常驻区」和「按请求膨胀的 KV/激活区」，给聊天设硬上限（最大并发序列 × 最大上下文），禁止它的 KV 吃进 embedding 权重必须待着的那一段。embedding 和评测不要和聊天共用一块可增长缓存：高峰只保证聊天权重加受配额约束的 KV 常驻，embedding 用独立进程或 MIG 实例拿固定若干 GB，评测错峰加载、用完卸掉。OOM 的根因通常不是「卡太少」，而是没有把会膨胀的 KV 和必须钉死的权重隔离开。

**深入展开：** 一张卡上大约是：CUDA 上下文与分配器碎片（常见大约 1–3 GB 量级，视驱动和分配器）+ 各模型权重 + 激活 + KV。7B 级 bf16 权重大约 14 GB，INT8 大约 7 GB；聊天的 KV 才是高峰变量。示意：若 32 层、GQA 8 头、头维 128、bf16，每 token 每条请求的 K+V 大约是 `2 × 32 × 8 × 128 × 2 B ≈ 128 KB`。100 条并发、每条 4k 上下文就是大约 50 GB，足够把同卡上的 embedding 权重挤掉。对策按侵入性排序：①给每个模型设 `max_num_seqs` / `max_model_len`，KV 池预留且不可互相借用；②热模型常驻、冷模型（夜间评测）用完卸载，加载前先看剩余是否大于「权重 + 一次最小 batch 激活」；③同底座多 LoRA 只留一份基座权重；④必须同卡混部时用 MIG 或独立进程把物理显存切开，比一个进程里靠自觉可靠。调度器要先为将要加载的权重预留，再接纳新聊天序列；反过来就会出现「KV 已经占满 → 加载 embedding → OOM」。监控按模型拆：权重占用、KV 占用、分配失败次数，而不是只看整卡 used。

**后续追问：** 聊天 KV 已经顶到配额时，新请求是排队、截断上下文还是踢掉最老会话，你按什么 SLA 选；同卡跑 embedding batch=64 的激活峰值大概怎么估，会不会比它的权重还大；评测任务凌晨把更大的权重加载进来，怎样保证早高峰前已经卸干净。

**扩展问题：**
- 四个 7B 聊天变体其实是同一底座加不同 LoRA，显存账应该按几个模型算？
- KV 量化能腾出给 embedding 的空间，但为什么不能替代硬配额？
- 多租户时，如何避免 A 客户的长上下文把 B 客户的 embedding 服务打挂？

**推理回答：** 从「会膨胀的是 KV，必须钉住的是权重」出发，先量化聊天高峰的 KV 体积，再决定隔离方式（配额、进程、MIG 或错峰）。验收看 embedding 的 OOM 率归零、聊天分位延迟不坏、各模型权重区不再互相穿越。

## SERVE-046. KV 若用基数树索引，哪些前缀能直接复用树上已有的页？排障 Agent 每个工具步都把工具定义、系统提示以及截至目前的完整轨迹重新喂给模型，到第 12 步时首字延迟已经到秒；如果每步塞进时间戳，或把消息顺序打乱，又会怎样？

**答：** 基数树按 token 序列做前缀索引：从根走到当前请求能重合的那一段，直接复用树上已有的 KV 页，只为分叉之后的新 token 做 prefill。系统提示、工具 schema、少样本和尚未分叉的对话历史通常能命中；一旦插入每步变化的时间戳、请求 ID，或把消息顺序打乱，公共前缀在第一处差异截断，后面整段都要重算。树按最近使用淘汰，显存不够时老前缀会被摘掉，下一步看起来「同一段提示」也会未命中。

**深入展开：** 运行时把正在服务的请求看成树上的路径：新请求从根匹配，命中长度决定少算多少 prefill。Agent 第 1 步到第 11 步若只是在末尾追加观察，路径是同一条枝的延伸，第 12 步应只计算新观察对应的 token。调度可以优先挑「命中深度大」的请求，避免把热前缀挤出树。前端若用分支、并行调用描述多步程序，运行时能预先知道哪些子调用共享同一前缀，比把每次生成当成互不相干的 HTTP 调用更利于复用。结构化输出还可以用压缩状态机一次跳过由 schema 决定的确定性 token，但这与树命中是两件事：树省的是历史 KV，状态机省的是约束解码步数。边界：几乎无共享前缀的一次性长文档、或每步都改系统提示，树会退化成「每请求一枝」，收益接近普通分页缓存。不要把答案本身缓存进树——复用的是中间 KV，输出仍要重新采样。

**后续追问：** 每步在系统提示里写入当前时间，命中率会掉到哪一层；树的淘汰策略按 token 还是按请求计数，长尾 Agent 会不会把客服热前缀挤掉；约束解码跳过的确定性 token 还要不要写入基数树。

**扩展问题：**
- Agent 在第 5 步改了工具参数但历史消息字节完全相同，树会命中到哪一层？
- 两个请求前 3k token 相同、第 3001 个 token 不同，块级哈希和 token 级基数树谁先分叉？
- 怎样用「平均命中前缀长度 / 步数」证明第 12 步变慢是树未命中，而不是模型变大了？

**推理回答：** 目标是让步数变长时 prefill 近似只付增量，约束是 token 必须从左到右完全一致才能复用。先画出轨迹里稳定前缀和每步增量，再把时间戳等易变字段移出前缀。用命中深度和 TTFT 随步数的曲线验收。

## SERVE-047. 四成流量是一次性、几乎不共享前缀的长摘要，六成是共用大约 4k 稳定系统前缀的多步 Agent。面对 TensorRT-LLM、vLLM 与 SGLang，该按哪些负载特征来设计实验，而不是看仓库星数？

**答：** 按「前缀共享程度、输入输出长度分布、并发、硬件绑定、运维约束」五条取数，而不是按星数。Agent 侧应测基数树或自动前缀缓存把 4k 稳定前缀吃下来之后的 TTFT 和 GPU 有效利用率；摘要侧应测超长、互不重复提示下的吞吐和尾延迟，此时前缀复用几乎帮不上忙。TensorRT-LLM 只在你已经锁定 NVIDIA、能接受按卡编译、并要用上对应代际的低精度内核时进入决赛；通用默认和模型覆盖面看 vLLM；程序化多步和前缀密集看 SGLang。最终用本集群、本流量回放说话。

**深入展开：** 构造两套回放：A 套把同一系统提示和工具 schema 放在最前，只在末尾追加轨迹；B 套每条请求换一份几乎不重叠的长文档。记录 TTFT、TPOT、达到延迟目标的完成率、KV 占用、编译或启动耗时。A 套若某引擎的平均命中前缀接近 4k，而另一引擎每步重算 4k，差距会写在首 token 上，不要用「平均 tokens/s」把这件事抹平。B 套要看长 prefill 是否堵住短请求：有的引擎靠切块混合，有的靠编译后的大核，结论不能从 A 套外推。运维账：新结构模型谁先能跑、升级是否要重编引擎、团队会不会排障块表或编译日志、能否进现有编排。硬件账：非 NVIDIA 直接排除编译式路径。三者都在快速迭代，实验结论要写测试日期和版本，过一个季度用同一回放复测。不要引用未经验证的公开榜单数字当容量规划。

**后续追问：** A 套里有 10% 的请求会改系统提示，前缀优势还剩多少；B 套的长摘要如果改成「同一份文档连问 8 个问题」，选型会不会翻盘；编译式引擎在 H 卡上的 FP8 很好看，但你们的回归集对 FP8 敏感，怎样把精度门禁写进对比表。

**扩展问题：**
- 只有一周时间，你最少要采哪些流量特征和硬件约束，才能不做完整三方对比？
- 新模型只有其中一个引擎能加载，你是等另外两个，还是先上再留迁移层？
- 如何避免用「纯合成的短 prompt」把前缀型引擎测成和不做缓存一样？

**推理回答：** 目标是在真实混合流量下同时稳住 Agent 首 token 和摘要吞吐，约束是硬件和运维成本。用两套回放把「吃前缀」和「吃长独有上下文」拆开，再叠加编译绑定。用分场景的 SLO 完成率和复测日期验收，而不是用仓库热度。

## SERVE-048. 怎样用参数量和位宽说明 16GB 笔记本根本塞不进名义上 70B 的开源 checkpoint，并讲普通硬件上的推理引擎如何靠量化与 mmap 把真正能跑的那一档拉起来？

**答：** 先算权重体积：`参数量 × 位宽 / 8`，再留出操作系统、KV 和运行时。70B 在 16 位下约 140GB，4 位下仍约 35GB，2 位也多在 20GB 量级，16GB 机器装不下 70B，应改选 7B/8B 或 13B 这一档。对能装下的模型，把权重量到 4–8 bit、打成单文件，用内存映射按页fault 进来而不是启动时整文件读入，再用 SIMD 多线程和可选的部分层 GPU 卸载，才能在笔记本上给出可交互的逐 token 速度。

**深入展开：** 示意：13B × 4 bit ≈ 6.5GB 权重，加上几 GB 的 KV 和系统，16GB 机器可以对话；70B × 4 bit ≈ 35GB，映射再聪明也会在工作集铺开后开始换页，decode 会卡成不可用。decode 每步几乎都要把用到的权重读一遍，瓶颈是内存带宽，所以降位宽既缩小体积又提高每秒能读完的参数量。单文件格式把分词器、超参数和量化权重绑在一起，避免运行时拼多份原始分片。`mmap` 让进程只为当前计算触及的层付物理页，冷启动不必先等整模进 RAM；代价是第一次走到某层会有缺页，盘慢时首句会顿一下。部分层卸载到 GPU 时，切分点要按「GPU 显存 − 激活 − KV」估算，切太狠则 PCIe 来回搬层得不偿失。并发吞吐不是这类引擎的设计目标：适合单用户、离线或边缘；要几十路并发应换服务引擎。低比特会伤数学和长尾指令遵循，必须用你的任务集回归，不能只看能启动。

**后续追问：** 统一内存的苹果芯片和「内存 + 独立显存」的 x86 笔记本，同一 13B 量化文件的工作集表现差在哪；Q4 文件名里的分组和档位分别影响精度还是体积；CPU 线程数开到超过物理核，decode 会更快还是会抢带宽。

**扩展问题：**
- 8GB 内存要跑 7B，上下文开到 8k 时 KV 会不会反过来把权重量化省下的空间吃光？
- 哪些层值得优先放 GPU，哪些层留在 CPU 对首 token 更友好？
- 如何用「权重字节 + 预估 KV + 2GB 系统余量」一页算式否决 70B，而不是先下载再看它是否换页？

**推理回答：** 约束是物理内存，不是「标称参数量听起来更强」。先用位宽公式判死刑或放行，再谈量化、映射和卸载这些让「放行档」可交互的手段。用能否稳定驻留和任务回归验收，而不是用能否打印出第一个 token。

## SERVE-049. 发热墙大约 3 瓦、可用内存大约 6 GB，上云只有弱网，还要改写短信并总结通知。怎样在上下文窗、模型体积、以及 NPU 覆盖不足时回退 CPU 之间做取舍，从而既不把全精度 7B 硬塞进手机，也不把请求全部打回云端？

**答：** 端侧先是内存和热的问题，其次才是算力。为短信改写和通知总结选任务体量的模型（常见是约 1B–3B，或内核真能跑起来的低比特 7B），上下文只留当前会话需要的窗口，而不是服务端那套超长上下文。量化、蒸馏、缩短 KV（GQA、短窗）是可靠杠杆；NPU 图只有在算子全覆盖时才值得押。长上下文、低置信、多语难例在无线电好时走云；用户拒绝上传或弱网时，本地至少给出抽取式回退。

**深入展开：** 账单是权重 + 激活 + KV + 系统/App。7B FP16 约 14 GB，直接出局；7B 落到约 4-bit 后权重大约 3.5–4.5 GB 量级还要工作区，6 GB 预算会很紧；2B 级 INT8/INT4 才比较容易留下 2k–4k 上下文。KV 在 2k token 上仍可能是数百 MB，应先砍窗口和 KV 头，再纠结少 0.5 bit。计算路径：prefill 的大矩阵优先走厂商 NPU/GPU 委托；decode 是读权重的带宽活，NPU 若启动开销大，batch=1 的逐步生成可能反而在 CPU 上更稳。任一不支持的算子（某种 RoPE 或 GQA 变体）都可能整图回退 CPU，3 瓦和时延一起爆。能量上，每出一个 token 往往要扫过大部分权重，产品指标是 joule/token 和发热节流，不是实验室 tokens/s。提示要短，停止条件要狠，「两条要点」比再追一点量化更省电。混合策略：本地小分类器或规则判断改写/总结留端上（隐私、离线）；邮箱级检索或低置信走云。UI 不能堵在云超时上——超时就展示通知原文加「未能总结」。质量用 50–100 条真实短信/通知看中文乱码、截断、凭空加事实，不要引用未核对的端侧榜分数。热节流降频后，先砍最大输出长度，再切更小模型，避免中途换引擎造成状态错乱。

**后续追问：** 频率掉一半时你降输出长度还是换模型；NPU 缺一种注意力变体时如何优雅回退而不整会话失败；用户关掉上传后，云回退整条路径怎么从配置层掐死。

**扩展问题：**
- 列出 2B 低比特、7B 低比特、云端大模型三条路径在内存、功耗、弱网、隐私上的决策表。
- 上下文从 4k 砍到 1k，通知总结会丢什么，怎样用抽取式预处理补回发件人和时间？
- 端侧几乎不做连续批处理，为什么仍要认真回收 KV，而不是按 max_len 常驻？

**推理回答：** 目标是在内存和热墙内做完高频短任务。约束是原精度 7B 放不下、弱网让云不可靠。按任务选小模型、短窗、能跑的量化，长尾留给云，用端侧小集守住乱码和幻觉。

## SERVE-050. 为何不能让聊天推流和凌晨合同审查共用同一条同步的、长寿命 HTTP 连接？这套集群一边给在线聊天做推流，一边要在黎明前消化一万份合同审查。异步通道还要补上哪些状态？

**答：** 聊天需要在秒级内流式吐 token，连接必须握在调用方手里；一万份合同每份可能数分钟，同步路径会被网关超时、连接数和盲目重试打垮。合同应走「提交 → 任务号 → 队列 → worker → 落库 → 回调或轮询」。异步通道至少要有状态机、幂等键、可见性超时、失败重试与死信、结果过期和取消，否则只是把请求丢进一个没人认领的队列。

**深入展开：** 同步推理把连接和一次生成绑在一起，适合 TTFT、TPOT 被 SLO 卡住、输出必须逐 token 推送的交互；突发到来时只能拒答或扩容，不能先堆积一万个打开的长连接。异步推理接入立刻返回任务号，生成在后台，调用方按任务号查状态。凌晨批处理还能把 GPU 填成更大的 batch，追求吞吐而不是词间流畅。状态机最小集：`queued / running / succeeded / failed / cancelled`；`running` 必须带租约，worker 崩溃后租约到期才能被别人捡起，避免一份合同审查两次或永不执行。重试必须对同一幂等键去重：生成不可随便重放，第二次可能写出不同文本，也占双倍 GPU。结果进对象存储或数据库并设 TTL；回调失败只重试投递，不默认重跑模型。两条路径应分队列甚至分池，避免合同的长 prefill 拖死聊天 SLO。

**后续追问：** 同步聊天中途断线，已占用的 KV 和计费怎么收尾；异步任务已经 running 时用户点取消，如何保证 GPU 上的序列真的被释放；一万份任务在一分钟内打进来，反压打在接入层还是 worker。

**扩展问题：**
- 合同审查要不要流式写部分结果，还是只在 succeeded 时一次交付？
- 同步接口超时 60 秒、模型还在 decode，客户端重试会制造哪些重复副作用？
- 如何用同一套模型副本同时服务同步和异步，而不让批处理占满所有槽位？

**推理回答：** 用延迟数量级和连接持有时间决定交互面：秒级推流走同步，分钟级批量走作业。异步的正确性来自状态机和幂等，而不是多一个消息中间件。验收看聊天超时率、合同完成率、重复执行次数。

## SERVE-051. 客户端取消后，怎样证明引擎停调度并且该请求的 KV 已交还？
**答：** 把客户端取消传到网关和推理引擎，停止调度并释放该请求的 KV 等资源；记录取消到释放的延迟，验证断连与超时路径。
**深入展开：** 取消不会自动撤销已经发生的外部工具副作用，共享缓存也不一定立即驱逐。
**后续追问：** 客户端断流后 GPU 仍忙，如何定位？沿请求 ID 检查网关取消传播、引擎调度和资源释放事件，不能仅凭连接关闭判断计算已停。
**扩展问题：**
- 如何测试取消与正常完成并发发生时，计费、日志和资源回收是否一致？
- 存在共享前缀缓存时，怎样区分释放请求引用与驱逐仍被其他请求使用的缓存块？
**推理回答：** 追踪同一请求跨层生命周期，区分输出停止、计算停止与资源回收。

## SERVE-052. 工具调用的 JSON 还没写完，用户却点了停止，而客服页正在边出字边渲染。哪些增量能马上画到屏幕，哪些必须等完整一帧，取消又如何到达推理引擎？

**答：** 对用户可见的自然语言增量可以立刻上屏；工具名、参数 JSON、将要执行的副作用必须等解析出完整、通过 schema 和权限校验的一帧再处理，半截 JSON 既不上屏成「命令」也不发去执行。取消从浏览器 `AbortSignal` 进网关，再变成对推理会话的 abort，引擎停 decode 并释放 KV；应用还要丢弃未执行的半截工具调用，并给已上屏文本一个「用户中止」状态，而不是当成完整答案去存档。

**深入展开：** 事件流建议拆成类型：`text-delta`、`tool-call-start`、`tool-args-delta`、`tool-call-end`、`error`、`done`。UI 只自动渲染 `text-delta`；工具区可以显示「正在填写参数」而不展示未闭合 JSON，避免半截参数被当成事实。执行器只在 `tool-call-end` 且 JSON.parse 成功、字段通过允许名单后触发。安全：低风险闲聊可逐 token 上屏；退款、医疗、对外发信类应按句或按固定 token 窗先过分类器再冲刷，牺牲一点体感换拦截。中途出错发 `error` 事件，前端冻结已显示文本并标记不完整，禁止把连接断开解释成模型说完。取消路径：客户端关闭读者 → 网关看到断开 → 调引擎 `abort(request_id)` → 确认不再占并发槽；若只关 UI、不传 abort，计费和 KV 会继续。流式不缩短总生成时间，它改的是首字时间和可取消性；总时长仍由输出长度和 TPOT 决定。结束后再跑一次引用/schema 校验，用于存档和工单，不阻塞已显示的低风险文本，但高风险结论可以在校验前显示「生成中」占位。重连：用 `Last-Event-ID` 或会话游标续传，避免整段重算，也避免重放已执行的工具。

**后续追问：** 用户点停止时工具已经执行了转账查询，你回滚什么、保留什么；句级安全窗和 TTFT SLO 冲突时谁让步；前端收到乱序或重复 delta 怎样去重。

**扩展问题：**
- 给出 `text-delta` 与 `tool-args-delta` 的处理伪代码，标明哪一步禁止副作用。
- 取消后如何在指标里区分「用户中止」和「模型自己 stop」，避免误报错误率？
- 把「首个带引用的句子」当体感指标时，流式策略和安全窗怎么改？

**推理回答：** 目标是体感快、可取消、不执行半截动作。约束是工具参数在流式中长期不合法，取消若不透传就会继续计费。文本可增量渲染，工具等完整事件，abort 直达引擎。验收看停止后不再产生 token 账单、也不触发未完成工具。

## SERVE-053. 晚高峰队列先爆、新副本随后空转，扩缩容却仍在 GPU 利用率超过 70% 时加机器。新副本就绪要 40～90 秒才能吃到首个 7B 请求。触发信号和预热池该怎么动，使得按队列与 SLO 扩出，并只在持续低负载后才缩回？

**答：** LLM 副本变 Ready 很慢：装权重、建上下文、预热内核，往往几十秒。按 GPU 利用率扩是滞后且吵的——decode 常受带宽限制，SM% 可以只有四成但队列已经很长。应按排队等待、在途 token/KV 水位和 TTFT SLO 燃烧度扩，并维持已经装好模型的预热池。缩容要有滞回，先排空在途生成，且不得低于预热下限，避免装上就卸、卸了又装。

**深入展开：** 有用信号：到达率 × 分位服务时间 → 所需并发槽；队列深度及其导数；KV 占用（KV 满是硬容量，即使 SM 很低）；若 prefill/decode 分池，两池分开扩。会撒谎的信号：SM 利用率、不看 token 数的裸 QPS、网关 CPU。若 T_ready ≈ 1 分钟、尖峰持续约 3 分钟，必须在 SLO 破之前 T_ready 就启动，所以要有上班时段的预测/定时扩，再加上队列导数的反应项。示意：5 req/s、平均生成 20 s，大约需要 100 个在途槽；每副本 16 槽则约 7 个忙的加若干热备。预热池保持 N_min 个已加载副本，权重放本地盘，必要时跑几次 dummy generate 才标 Ready——「进程起来」不等于「首请求已编译」。交互流量看 TTFT/ITL；摘要、嵌入可以按积压年龄扩，甚至缩到零。缩容必须等流式请求结束（常要数十秒），否则会砍活连接。利用率规则的典型失败就是题面：高峰已排队，副本还没开始装；装完高峰过了，新副本空转被缩回，下一次再交同样的学费。不要用温度或功耗当扩容钩子，热可以是房间问题而不是流量。

**后续追问：** KV 占用 90% 而 SM 只有 35% 该不该扩；缩容时在途流式请求是迁移、排空还是直接切断；预热要跑到第几次 dummy generate 才算 Ready。

**扩展问题：**
- 写出「所需副本 ≈ ceil(到达率 × 服务时间 / 每副本并发) + 预热」的估式，并说明服务时间为什要用分位。
- 定时扩和反应式扩如何叠加，避免早高峰和突发流量叠打。
- 为什么把扩容钩在 GPU 温度或整机功耗上几乎一定误动作？

**推理回答：** 目标是在拉起很慢的前提下保住 TTFT。约束是利用率滞后、容量按 token 和 KV 计。用队列和水位提前扩，用预热池盖住 T_ready，用滞回和排空避免抖动。

## SERVE-054. 新版本提前写入、旧版本只读到切换瞬间，失效回填还要限速扇出——整点政策一翻，大约 40% FAQ 键一起失效，70B prefill 被打满。这套双缓冲预热该怎么落地，才不会把上周政策继续当正确答案，也不会把整点打成一次全量冷启动？

**答：** 整点不是「删光四成键再让流量自己回填」，而是一次带截止的键空间切换。切换秒之前用新政策版本把热点 FAQ 写进新键空间，读路径仍只命中旧键；整点把读指针翻到新空间，旧键立刻对用户不可见。未预热到的那一截允许未命中，但 70B prefill 回填要有扇出上限，多出来的 FAQ 排队而不是同时进引擎。这样旧政策不会在整点后还当正确答案，也不会在 00:00 把预填充队列打成全量冷启动。

**深入展开：** 设 FAQ 命中约占请求四成，整点政策版本从 `v` 升到 `v+1`，若键里带版本，四成键在同一秒变成未命中，70B 要为这些问句重新 prefill（系统提示 + 新政策全文往往是数千 token），连续批的 prefill 预算会被同一时刻的回填吃光，聊天 decode 跟着堵。双缓冲：T−Δ 起后台作业按历史频率把 top 问句用 `v+1` 生成（或只预填前缀 KV）写入新空间；写失败不得回落到把 `v` 的答案抄过去。T 之前读路径显式钉 `v`，即使新空间已经有值也不提前切，避免灰区里两种政策混答。T 时刻只做指针翻转，复杂度与键数量无关。扇出限速：翻转后未命中的回填并发（例如同时最多 N 条 70B prefill）封顶，其余 FAQ 在「必须用 v+1 生成」的队列里等，或短时对非热点 FAQ 走「不缓存、限流后生成」；绝对禁止再返回 `v` 的正文。Δ 和预热覆盖用历史：若四成命中里八成集中在头部键，预热头部就能把切换秒的未命中从 40% 压到约 8%，再靠 N 条回填消化长尾。监控要拆开：新键预热完成率、翻转后旧键被读到的次数（必须是 0）、70B prefill 队列在 T±1 min 的高度、聊天 TPOT。边界：灰度 10% 租户提前用 `v+1` 时，键空间按租户拆，不要全局提前翻指针。预热用的模型和采样参数必须与线上一致，否则新键是「另一个答案」的缓存污染。旧空间的物理删除可以在 T 之后异步做，但读路径不能再看见它。

**后续追问：** 预热覆盖只有 50% 时，扇出上限 N 怎样用 70B 的 prefill tokens/s 和切换后预期未命中 QPS 算出来；指针已翻、一条正在用 `v` 生成到一半的流式请求该写完旧政策还是掐掉重开；新键预热是存整段答案还是只预填政策前缀 KV，对切换秒的 70B 压力差在哪。

**扩展问题：**
- 画出 T−Δ、T、T+1 min 三个时刻读指针、写指针和 70B prefill 队列的状态。
- 为什么「整点把四成键的 TTL 设为 0、让它们自然回填」几乎一定会打满预填充，即使你的键字段版本都是对的？
- 预热作业自己也要 70B，怎样和白天聊天错开卡时，又保证 Δ 内赶得上？

**推理回答：** 目标是整点后只卖新政策，同时 70B 预填充不被四成同时未命中打满。约束是旧答案在 T 之后非法、回填产能有限。用双缓冲把写提前、把读切换收成一次指针翻转，再用回填并发上限消化未预热长尾。

## SERVE-055. 关键词规则会漏检；「取消订单」和「取消订阅」又会被 embedding 近邻打进同一条流水线。同一网关后挂着廉价分类器、昂贵推理模型以及必须转给人工的高风险路径时，路由器如何同时压住误路由和成本？

**答：** 做成「规则先截高风险、分类器选默认通道、低置信或冲突则升级」的混合路由，而不是只靠一段 embedding 相似度。退款、法律、医疗、销户等关键词和账号状态直接进高风险或人工，不交给便宜模型自由发挥。「取消订单」和「取消订阅」要用槽位（对象类型、金额、时效）而不是句子向量决定流水线。路由器自己要打点：预估费用、置信度、是否升级；误路由用用户更正和下游失败回放，允许再跳到更强模型，但不允许从人工通道悄悄降回去。

**深入展开：** 请求先过权限和租户，再抽意图与槽位。规则层处理必须稳定的少数类；其余走小分类器或轻量模型，输出通道和置信度。向量检索只用来找「像不像某类历史工单」，阈值按类校准，开放闲聊宁可不路由到贵模型。代价模型：FAQ 走便宜通道，多步推理走贵模型，高风险走人工或强模型 + 强制引用。误路由成本不对称：把销户送到闲聊模型，比把天气问送到贵模型贵得多，所以风险类召回优先、成本类精度优先。实现可以是短超时的分类调用，失败则按安全默认（升级而不是降级）。要定期用金样和线上抽样算混淆矩阵，重点看「应人工而未人工」。不要把路由提示和业务提示绑死在同一版本，否则改话术会连带改变分流。边界：新意图没有类时进观察桶，不要硬塞最近邻类。

**后续追问：** 分类器置信度 0.51，你升贵模型还是再问一句澄清；向量把两条「取消」打到 0.9 相似，槽位缺失时默认哪条通道；路由模型本身限流了，网关的安全默认是什么。

**扩展问题：**
- 列出至少四个必须进规则层、禁止只靠向量的意图，并说明误路由的业务代价。
- 便宜通道成功率在掉，怎样自动提高升级比例而不把账单打满？
- 如何用「应人工未人工数 / 单次平均费用」成对证明路由在变好，而不是只看便宜通道占比？

**推理回答：** 目标是在费用可控下把高风险请求送对地方，约束是相似问句可能对应完全不同的后端动作。规则守不对称代价，槽位拆开易混意图，分类器处理长尾。用混淆矩阵和费用成对验收。

## SERVE-056. 中文流偶尔冒出 U+FFFD，浏览器又憋到全文结束才渲染，尽管 decode 早已开始。从每个 token 产生到像素上屏，缓冲发生在哪一跳？跨 token 边界的多字节字符应当攒到什么粒度再下发？

**答：** Decode 每步只新产生一个（或一小撮）token，流式的本意是 detokenize 后立刻推增量。浏览器憋到最后，通常是 HTTP 链路上的代理、网关或框架把响应攒成完整 body，而不是模型在等。中文里的 U+FFFD 是 UTF-8 被截在多字节中间：BPE token 不等于一个完整字符，服务端必须缓冲到合法码点（更好是完整字素簇）再写入 SSE/WebSocket 帧。

**深入展开：** 路径：sampler 产出 token id → detokenize 成字节 → 可选安全窗 → 按 `data: {"text":"..."}\n\n` 写 SSE（或二进制 WS 帧）→ 经过网关/负载均衡/反向代理 → 浏览器 EventSource 拼接。Nginx 一类默认 `proxy_buffering on`，会等后端引擎结束或缓冲满；需关闭该缓冲、关掉应用层 gzip 对这条流的攒包，并把读超时放到生成时长量级（数十秒到数分钟），否则代理先断。TTFT 应由「首个可打印增量」衡量，不是整段 `Content-Length`。Detokenize 细节：有的 token 只是半个三字节汉字或英文词片；若按 token 直接 `decode(errors='strict')` 会抛错，`errors='replace'` 就会写入 U+FFFD。正确做法是维护一个 byte buffer，`decode` 到最后一个完整码点，残余字节留到下个 token。不要按「固定 N 个 token」切，N 在汉字上仍可能切开。结束时发明确终止事件（如 `data: [DONE]`），并带 `finish_reason`。取消必须从 TCP/AbortSignal 传到引擎，停止 decode 并丢 KV，否则缓冲层「看起来停了」、GPU 仍在跑。审核若要整句，可延迟一个句末标点再冲刷，这是产品选择，应与「代理误缓冲」区分开。

**后续追问：** 同一接口在直连引擎时流式正常、经公司网关后变一次性，你查哪几个头和代理开关；工具调用的参数 token 流式出来时，不完整 JSON 要不要发给浏览器；SSE 在移动网络被中间盒缓冲，何时改 WebSocket。

**扩展问题：**
- 写一段不超过 15 行的 detokenize 缓冲逻辑：输入是 token 字节片，输出是安全可上屏的 Unicode。
- 如何用「首字节时间」和「首个完整汉字时间」区分代理缓冲和字符缓冲？
- 流式计费以引擎 token 为准还是以发出的字符为准，半截切断怎么入账？

**推理回答：** 目标是让用户看到的延迟贴近 TTFT，且不出现非法 UTF-8。约束是 token 边界 ≠ 字符边界，HTTP 中间层默认攒包。先排除代理缓冲，再在服务端按码点冲刷。验收看首增量时间和抽样无替换符。

## SERVE-057. 默认把流量送到 8B，怎样避免合同审查被静默分流到小模型？网关后同时挂着 8B 与 70B 时，这和副本间负载均衡的差别在哪？

**答：** 路由器选的是「用哪个模型」，负载均衡选的是「同一个模型的哪台副本」。默认规则应是：合同审查、长上下文对账、高风险租户等硬任务钉死 70B（或必须人工的队列），其余用便宜的 8B；再用拒答或低置信触发一次升级，而不是按 GPU 空闲把合同塞进 8B。默默降级是路由事故，不是弹性成功。

**深入展开：** 基础设施层路由发生在鉴权与配额之后、具体推理引擎之前，输入是请求特征（任务类型、长度、租户策略、当前各模型健康与排队、成本预算），输出是模型标识和版本，然后再交给该模型的负载均衡去挑副本。实现可以是规则（路径、标签、输入长度阈值）、小分类器、或级联（8B 先答，低置信或命中拒答模板再打 70B）。必须单独跟踪误路由：本该 70B 却到 8B 的比例、升级额外延迟、以及影子流量上的质量差。高峰降级只能降「允许降级」的类别，并写进响应元数据，不能只留在内部日志。健康检查失败时应切到健康的 70B 副本或明确失败，而不是自动改走 8B——那是换能力，不是换机器。路由键还要带上「此任务是否允许弱模型」，避免和缓存、安全策略打架。成本优化的上限是误路由带来的客服或合规损失。

**后续追问：** 8B 的「我不确定」要怎样标定才配做升级信号；路由分类器自己挂了，失败安全是全走 70B 还是全走 8B；按 token 成本最小化和按投诉最小化两条目标如何同时约束。

**扩展问题：**
- 同一条对话前两轮走 8B、第三轮突然要引用合同原文，路由能否中途升级并带着历史？
- 如何用离线标注集估计「多花的 70B 调用」和「漏掉的错案」之间的交换率？
- 多供应商时路由还要看地域和数据驻留，这时健康度如何降级？

**推理回答：** 先分清「换能力」和「换副本」，再按任务风险画不可降级集合，剩余用级联省钱。验收看误路由率、70B 占比、以及不允许降级类任务的质量，而不是只看平均 GPU 成本。

## SERVE-058. 一张卡 KV 已经顶满，另外两张还空着——三张规格相同的 GPU 却被网关按请求个数轮询，因为有的会话拖着 8k 上下文，有的只是问候一句。怎样按飞行中的 token 量、KV 占用水位、以及前缀缓存亲和来选实例，而不是按连接数均分？

**答：** LLM 服务稀缺的是 GPU 时间乘以 HBM（尤其是 KV），不是请求个数。按 HTTP 轮询会把偶然到一起的长会话堆在一张卡上，短问候去另外两张。应按副本上报的在途 token、空闲 KV 块和排队来选实例，并把多轮会话或相同系统前缀尽量打到已经有前缀缓存的那张卡。亲和必须是软的：目标卡 KV 满或故障时，宁可 miss 一次缓存，也不要堵死。不健康的副本——错误率高、decode 卡死、OOM——要摘掉，不要等 TCP 断。

**深入展开：** 请求代价 ≈ c1×prefill token + c2×decode token，KV ≈ 每 token 字节 × 在途长度。一次 8k 历史的续写，仅 prefill 就可能是 20 token 问候的数十到上百倍；三路轮询均衡的是到达次数，不是工作量。副本应导出 KV 已用/空闲块、当前 batch token 预算、队列等待、以及能否命中某前缀，网关不要猜。会话或冻结系统提示做一致性哈希，让缓存命中留在本地；这是同一模型的实例选择，不是按难度换另一个模型。粘滞过强会制造热钥匙（重度用户），要限制单副本会话数，并在空闲时再平衡。也可以有意把超长上下文和短请求分池，但不要在无专用硬件时把短请求和长请求完全拆开导致两边都难拼 batch。健康：副本可以 TCP 正常却已经 KV 95%，应把「资源耗尽」当成可重试的 503 打到下一张；内核崩溃的 500 则要熔断，不能同样狂重试。决策发生在每一轮对话的首包，而不是这条流式连接建立时永远钉死——多轮变长后要允许再平衡。惊群：所有新会话同时看见「最空的那张」会一起灌满，需要随机打破或 inflight 校准。

**后续追问：** 前缀亲和和目标卡 KV 水位冲突时谁优先；怎样避免「最空副本」被同一时刻的新会话打满；流式长连接下均衡是看连接还是看每一轮用户消息。

**扩展问题：**
- 给出 prefill 为 20 / 800 / 8000 token 的三个请求，对比轮询和「按预估 prefill+KV」的分配差异。
- 会话粘滞提高了前缀命中却造成热钥匙，用什么指标决定哈希环该不该再平衡？
- 副本报 503「KV 满」和报 500「内核崩溃」，网关的重试和摘除为什么必须分开？

**推理回答：** 目标是摊平工作量并复用已有前缀，而不是摊平连接数。约束是请求代价高度偏斜、缓存有局部性。让副本上报水位，网关按容量加软亲和分发，并用不同错误码区分「满」和「坏」。

## SERVE-059. 一次 registry 拉取要 40 s，13B 早高峰前要从 2 扩到 12。节点本地命中、机房二次分发、运行时层与权重层分离的增量层该怎么铺，分段计时又如何证明冷启动瓶颈已经从拉权重挪到把权重装进 GPU，且扩缩触发器仍走原曲线、首 token 仍要落进 2 秒？

**答：** 扩缩触发器可以仍按原曲线在高峰前加到 12，但新副本的关键路径不能再包含 40 s 的 registry 拉取。把权重镜像做成节点本地命中、机房内二次分发、以及「基础运行时层与权重层分离」的增量层，使拉镜像降到秒级或零。用分段计时证明：`registry_fetch` 从约 40 s 掉到接近 0，而 `h2d_weights + first_forward` 成为新的主导且合计能进 2 秒；若拉取仍在关键路径上，缓存就还没做成。

**深入展开：** 13B BF16 权重大约 26 GB。冷启动原来常是：registry 走共享出口拉 26 GB（约 40 s 对得上大约 0.6–1 GB/s 的远端）→ 解层 → 进程起来 → 把张量拷进 HBM → 第一次 prefill。优化按命中距离排：①节点本地：同一机器上已经跑过该摘要的层或独立权重卷，第二次及以后 `fetch=0`，只付磁盘→HBM；本地 NVMe 数 GB/s 时，26 GB 大约数秒，再靠页缓存可降到接近内存拷贝。②机房缓存：第一台仍可能付一次远端，其余 9 台从机房镜像或节点间分发取，避免十条副本同时打满 registry。③增量层：CUDA/运行时基础层预先铺在全机房，副本镜像只含配方和指向本地权重卷的挂载；权重更新若只换若干层，只同步增量而不是再拉整包。不改触发器意味着「2→12 的时刻和判据照旧」，变的是 Ready 定义：必须是权重已在 HBM 且第一次短前向完成，而不是容器 Running。证明用同一套 span：`registry_fetch`、`local_or_dc_cache_hit`（命中率、字节来源）、`weights_h2d`、`first_kernel_or_graph`、`ttft_after_ready`。成功形态是高峰前 12 个副本的 `registry_fetch` p95≈0，`weights_h2d + first_forward` p95 落在约 0.5–1.5 s（示意：26 GB 走高速主机到设备链路可以低于 1 s，再加上一次小 prefill），总首 token 进 2 s。失败形态是命中率很高但 H2D 仍走慢速路径，或每次启动重新捕获整图却没预热——这时该预热装卡，而不是回头改扩缩阈值。边界：权重卷和镜像摘要必须钉同一校验，避免「本地命中了一份旧档」。新机入池第一份副本仍会付冷拉取，扩容规划要先让节点带着缓存入组，或允许第一份不算在 2 秒 SLO 的容量里。

**后续追问：** 12 个副本同时指向机房缓存，缓存本身会不会变成第二个 registry；增量层只更新了 2 GB 适配器，怎样证明你没有又把 26 GB 基座拉了一遍；`Ready` 只做了 H2D、没跑 dummy generate，为什么第一真请求仍可能超过 2 秒。

**扩展问题：**
- 列出从 2 扩到 12 时每个副本的字节来源（远端 / 机房 / 本机页缓存）和对应的 `registry_fetch` 期望值。
- 为什么把权重打进容器层、每次改系统库都会连带重拉 26 GB，而挂本地卷可以切断这条耦合？
- 不改触发器的前提下，如何用「缓存命中率 × H2D 分位」做发布门禁，防止有人关掉机房镜像却仍以为 2→12 是安全的？

**推理回答：** 目标是 2 秒首 token，约束是触发器不能动、远端拉 26 GB 不可能进 2 秒。把拉取移出关键路径，用分段时间证明主导项已变成装卡；装卡仍超标再优化 H2D 和第一次前向，而不是改什么时候扩。

## SERVE-060. 监控里流处理器的占用才 30%，可对话的长尾时延已经由 800 毫秒拉高到 4 秒。量化先别碰，排队等待、prefill、逐步 decode、显存抖动这几段，你会依怎样的顺序逐一拆开排查？

**答：** 先把 4 s 拆成排队等待、prefill、逐步 decode，不要看端到端一个数。SM 只有 30% 说明卡没吃饱，量化或换内核多半不是第一刀——更常见是请求卡在 KV 预留、队头阻塞、CPU 侧分词或调度，或副本不均。只有分段之后确认「计算步本身又慢又闲」才进入内核级剖析；先改量化会同时搅动质量和一个本不该动的变量。

**深入展开：** 建议顺序：①按请求打点入队、开始调度、首 token、后续 token 时间，得到 queue、TTFT、词间间隔。若 4 s 里有 3 s 是 queue，去看队列深度、每租户进行中请求、是否在等 KV 块而不是等 SM。②看 KV 占用、分配失败、前缀块被逐出：显存池满或碎片时调度器会停发新序列，SM 就会空转，这是「低利用率 + 高延迟」的经典组合。③看 batch 大小直方图和 prefill/decode 步时长：batch 长期只有 1–2 且 decode 步其实不慢，则是到达率或网关问题；某一步里出现超长 prefill，则是队头阻塞——那几步 SM 可能打满，其余时间很闲，平均值 30% 会骗人。④最后才用引擎 trace 或系统级采样看内核：prefill 的大矩阵乘有没有吃满，decode 是否卡在显存带宽。常备指标：TTFT 和词间间隔的分位、吞吐、SM 与 HBM、KV 块使用率、batch、队列等待、取消与 OOM。剖析必须能区分 prefill 与 decode，两者瓶颈经常相反。低利用率时优先查调度和内存，不优先查「算力不够」。

**后续追问：** queue 时间很短但 TTFT 仍是 4 s，你下一步剖哪；SM 30% 同时 HBM 带宽已经打满，这还叫不叫「闲」；怎样用一次复盘证明延迟尖峰来自 KV 分配失败而不是模型换大了。

**扩展问题：**
- 只对 GPU 做采样、没有请求级时间戳，为什么几乎定位不了这次 800 ms 到 4 s？
- 安全过滤和工具调用加在 decode 循环外，会把哪项指标污染成「模型变慢」？
- 如何设计一张值班面板，让人半分钟内看出是排队、算力还是显存？

**推理回答：** 低 SM 加高 p99 先当调度或内存问题。用请求级分段排除排队和 KV 等待后，才对计算步做内核级剖析。量化是算力或显存已经饱和时的手段，不是这次的第一假设。

## SERVE-061. 一次发布后模型没换，金丝雀放到 10%：中位时延仍约 800 毫秒，尾延迟却从约 2 秒窜过 4 秒。从排队等待、输出 token 数、首字时延 TTFT 以及逐步时延 TPOT 这四条曲线看，是加速卡真变慢了，还是调度、缓存或同步副作用在拖尾？

**答：** 先不要假定算力退化。把端到端延迟拆成排队等待、TTFT、TPOT×输出 token 数，再按金丝雀与对照、提示长度、租户分面。若只有排队涨，是并发上限或批调度变紧；若 TTFT 涨而输出长度不变，优先查前缀缓存失效、系统提示变长、切块 prefill 或网关里新加的同步审核；若 TPOT 涨，再查 decode 批被长 prefill 打断、KV 分页/抢占或内核回退。p50 不动而 p99 翻倍，说明主体请求仍走原路径，变的是尾部：冷前缀、超长输出、少数副本排队或偶发同步调用。

**深入展开：** 「模型没变」的发布仍可能改推理引擎小版本、最大批大小、`max_num_seqs`、KV 显存占比、chunk 大小、LoRA 模块、提示模板里的日期或工具列表顺序、stop 序列、流式缓冲、sidecar 超时。数据流按 span 对齐：网关接入 → 策略/审核 → 调度入队 → prefill → decode → 输出过滤。例如系统提示从约 1.2k 改到 1.8k 且把时间戳插到最前，前缀哈希全变，原先约 70% 的缓存命中会掉到接近 0；4k 上下文的 prefill 就可能从几十毫秒变成数百毫秒到一秒以上，短请求的 p50 仍像原来，长 RAG 请求的 p99 会翻倍。输出侧若把 `max_tokens` 从 256 调到 1024 或去掉 stop，尾部请求多出 200–400 token，按 TPOT 约 20–40ms（示意，视模型和批大小）就要再加数秒。同步审核若自身 p99 约 300–800ms 且在返回前阻塞，会整体抬尾。对照方法：用同一份流量回放打金丝雀与旧版本，只看这四条曲线以及缓存命中率、抢占次数、批大小分布；再用二分回滚（先回提示、再回调度参数、再回引擎）定位。补上按「提示分桶 × 缓存命中 × 副本」的延迟看板，避免下次只盯平均 QPS。

**后续追问：** p99 只在某个区域或某类 8k+ 提示上翻倍，你还看不看全局 GPU 利用率；如何区分「排队变长」和「单个 decode 变慢」；发布清单里哪些配置必须和权重绑在同一份性能基线里回放。

**扩展问题：**
- 只有流式首包慢、后续 token 间隔正常，故障更可能在哪一段？
- 如何证明新的审计日志 SDK 在事件循环里同步打了远端，而不是模型算力下降？
- 回放流量时如果不用真实前缀分布，为什么会把缓存回归漏掉？

**推理回答：** 目标是解释「权重不变但尾延迟变差」，约束是发布同时动了调度、提示和旁路 I/O。用四段延迟把算力、带宽、队列和同步副作用切开，再用分面和回放排除流量本身变了。验收看金丝雀与对照在同分布下的 TTFT、排队和命中率，而不是看 GPU 平均利用率是否「还很高」。
