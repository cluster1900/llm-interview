# Embedding 与向量检索

## EMB-001. 标题、关键词已经能按字面对上，检索路径为何仍要为每条对象另存数百维实数？这列几何坐标让后面哪一环从字面命中改成找位置？

**答：** Embedding 把一段文本（或其它对象）映射成固定长度的实数向量，让语义或用途相近的对象在几何上靠近。标题和关键词做的是字面命中；这列浮点数做的是改写、同义和跨句表述之后，查询仍能把该对象拉到附近。RAG 里它不替换正文，只把「谁有资格进 LLM 上下文」从布尔词匹配改成向量空间里的近邻查找。

**深入展开：** 数据流是对象 → embedding 模型 → \(\mathbb{R}^d\) → 与查询向量比距离 → 取 top-k id → 回表取原文 → 拼进提示。工程上要一次定清：对象是 query / chunk / 用户还是商品、\(d\) 常见在 256–3072 量级、距离函数是否与训练一致、索引走精确还是近似、对象更新后谁重算向量。数量级：一条 768 维 float32 大约 3KB，一百万条裸向量大约 3GB，还没算图索引的边。边界很硬：embedding 保证的是「像」，不是事实正确；条款号、内部货号、错误码经常不像，必须另留精确匹配通道。它也不是摘要——摘要仍是文本，还要再被模型读；向量让后续步骤用加减乘做相似度，而不是再生成一段话。

**后续追问：** 同一文档是整篇一条向量还是按 chunk 各写一条，漏召回各长什么样；查询和文档是否必须同一套模型、同一套指令前缀；如果只对标题 embed、正文不 embed，会系统性漏掉哪类以细节为锚的问题。

**扩展问题：**
- 推荐里对象是用户/物品，RAG 里换成 query/chunk 之后，更新频率和距离函数分别要改什么？
- 两条工单文本立场相反（同意退款 vs 拒绝退款）却靠得很近，你先查切块噪声还是查模型不会编码否定？
- 不用向量、改让 LLM 对候选逐条打分，成本和延迟在什么库规模会先崩？

**推理回答：** 目标是「语义相近的对象必须能被计算机批量比较」，约束是不能每次让 LLM 读完全库、也不能只靠词表命中覆盖改写。所以把对象编进公共向量空间，检索变成几何近邻。验收看三件事：同义改写能否召回、专有编号会不会丢、以及 top-k 原文是否真的进了生成上下文。

## EMB-002. 生产向量未经 L2 单位化，库侧却按内积打分，篇幅更长的段落分数系统性偏高。改用余弦、改用欧氏，各自消掉哪类偏差？何种条件下三种排法给出同一名次？

**答：** 内积 \(\langle q,d\rangle=\|q\|\|d\|\cos\theta\)，同时吃方向和模长。不少编码器对更长、词更多的段落给出更大的模，于是「写得长」被当成「更相关」。余弦只留方向，消掉这种模长偏好。欧氏距离 \(\|q-d\|^2=\|q\|^2+\|d\|^2-2\langle q,d\rangle\)，在未归一化时既罚模长差也罚方向差。若查询和文档都已 L2 归一化到单位球面，余弦与内积排序完全一致，欧氏排序也一致，因为此时 \(\|q-d\|^2=2-2\langle q,d\rangle\)。

**深入展开：** 训练损失若用的是归一化后的余弦或 InfoNCE，线上必须同一套：先归一化再内积，或直接余弦。若模型故意把信息量编进模长，改用余弦会丢掉这部分信号——该不该归一化看训练约定，不能按爱好选。实现上常在入库时预归一化文档、查询进库前归一化一次，用内积当余弦，避免每次除模。768 维上模长随 token 数缓慢变大是常见现象；某个批次突然大一个数量级，才要查是否混进另一模型。ANN 必须用与打分相同的度量建图或建簇，否则近似邻居和精排分数对不上。欧氏对整体平移敏感，余弦不敏感；后续若还做聚类，两种度量的中心含义不同。

**后续追问：** 只对文档归一化、查询保持原始模长，top-k 会残存什么偏差；用欧氏建图、用余弦打分，召回曲线为什么会和评测脚本打架；模长要不要单独送给 reranker 当「信息量」特征。

**扩展问题：**
- 负内积和 \(1-\cos\) 做「分数 > 0.8」这类阈值过滤时，为什么不能共用同一阈值？
- 向量被截断或按坐标压缩后，三种度量谁的名次先乱？
- 空文本被 encode 成全零向量时，三种度量谁会得到 NaN 或把该条顶到异常名次？

**推理回答：** 把三个公式都展开成模长 × 方向。目标是「按训练时定义的相似度排序」，约束是实现必须与损失一致。先检查是否已在单位球面，再决定三种是不是同一排序；未归一化时按「是否要保留模长」在内积和余弦之间选。用同一 query 对「近重复的短段 vs 注水长段」的名次差验收。

## EMB-003. INT8、乘积量化、标量分箱要对付两千万条、每条宽度 1024 的 float32，常驻占用必须压到约四分之一才能让 RAG 上线。三者分别砍掉哪一层字节，漏召回又从哪类量化误差渗出？

**答：** 只算向量、不含图边和正文：两千万 × 1024 × 4 B ≈ 82 GB；砍到约四分之一，数量级上对应逐维 INT8（约 20 GB）。标量分箱和 INT8 是同一类「每维独立码本」，近邻序大多还在，漏召回主要出在动态范围被截断的尾部维。乘积量化把 1024 维切成多段子空间（例如 64 段 × 8 bit，编码约 1.3 GB），距离改成查表近似，相邻文档更容易被量化噪声打乱序。生产上通常用压缩向量做粗召回，再用更高精度向量或 cross-encoder 精排，砍的是工作集，不是一次把精度扔光。

**深入展开：** 量化把连续坐标映到有限码本，省内存带宽和存储，付距离误差。三条稳定路径：①逐维 INT8 / 标量量化：按训练样本的分位数或对称 `scale` 标定，已 L2 归一化的 embedding 各维动态范围接近，对称量化较稳。查询必须走同一套 scale，度量仍要与训练时一致（余弦或内积）。②二值化：只留符号，内存再降约 8 倍，汉明距离近似余弦；短文本、维内近似对称时才不太崩，领域术语和易混对往往先死，不适合当唯一召回。③乘积量化（PQ）：d 维切成 M 段，每段用小码本（常见 256 中心，即 8 bit）。检索常用非对称距离（ADC）：查询保持 float，库向量用码字，查 M 张表累加。压缩比相对 float32 约为 `4d/M` 字节比（M=64 时每向量 64 B）。漏缝：两个原文空间很近的点落入不同子空间细胞，粗排进不了候选窗；IVF-PQ 再叠「只探少数簇」，是双层近似，nprobe 太小会与量化误差叠加；若查询也被量化（对称距离），误差更大。HNSW 边本身仍占 `N × 约 2M × 4 B` 量级，只向量 INT8、图还按原精度建，内存不会按四分之一掉干净。数据流：抽例如 10^5–10^6 条拟合码本 → 全量编码 → 内存放 code + 主键 → 查询 float 做 ADC → 取 10–20 倍 k 的候选 → 磁盘或旁路里的更高精度向量精排。边界：码本必须用你们自己的向量拟合，换模型后旧码本失效；不要把某次公开实验的「掉 1 个点」当成你们的数，用冻结业务集画「压缩比–recall@k」曲线再选档。

**后续追问：** 查询做 ADC、库向量只有 PQ code 时，HNSW 遍历用的距离和精排距离不一致会怎样歪图；INT8 已达内存目标，为什么还要上 PQ；二值化后「冷却液 / 制冷剂」这类易混对通常先崩在哪一步。

**扩展问题：**
- 在给定 N=2e7、d=1024、HNSW 的 M=16 的假设下，分别估算原向量、INT8 向量、PQ-64B 和图边的 GB，指出只向量量化为什么不够。
- 粗召回 k' = 20k 再精排，k' 太小和太大分别伤害召回还是延迟？你怎么选。
- 换 embedding 模型后，旧 PQ 码本能不能继续用？哪一步必须重拟合？

**推理回答：** 目标是把常驻向量内存压到机器可装下，同时粗排还要把金标送进精排窗。约束是 82 GB 原向量单机难驻留，而 PQ 的距离是查表近似。先用 INT8 对上「约四分之一」这档，更狠的压缩配高精度精排；用自己的冻结集看 recall，而不是假设某种量化无损。

## EMB-004. 入库体积掉到四分之一：有人把 1024 维只留下最前 256 个坐标。检索质量与每次距离运算会先在何处失真？何种前提下更短宽度是训练时就给出的合法工作点，而不是拿砍刀硬切？

**答：** 朴素截断假定信息均匀铺在坐标上，但一般 embedding 的前 256 维并不是独立的低分辨率语义。距离变成残缺内积，近邻关系会乱，召回往往先在细粒度区分（近义条款、易混工单）上掉，而不是所有查询均匀掉一点。存储和距离计算确实约按 \(d\) 线性降：同样 \(n\)，内存、带宽和 Flat 扫描时间都接近四分之一。只有模型在训练时就提供可截断的嵌套维度，并且你按它指定的前 \(k\) 维、截断后仍归一化，「更短」才是受支持的工作点。

**深入展开：** 成本账：\(n=10^6\)、\(d=1024\)、float32 约 4GB 裸向量；\(d=256\) 约 1GB。图的边数不随 \(d\) 线性，但距离仍随 \(d\) 线性，更高维时扫描更吃带宽。随机砍尾通常差于学过的投影（例如训练好的短向量头，或在本域拟合的线性降维），但后者也必须重测。维度过低时，不相关文档挤进相近方向，分数动态范围变窄，阈值难定。维度过高时质量常收益递减：从 768 再升到数千维，存储和延迟的增幅往往大于召回增益，近似索引也要更多探测才能维持召回。截断后必须重新归一化，查询和文档必须同一协议；一边 1024、一边 256 会得到近乎乱序的名次。这和按坐标降比特不是同一条压缩轴。

**后续追问：** 如何用「模型官方短向量」对照「自己砍前 256 维」证明砍刀不可用；\(d\) 减半后 Flat 延迟是否真减半，还是卡在索引常数开销；细粒度条款对和粗主题对，哪一类先受截断伤害。

**扩展问题：**
- 先在本域把向量线性降到 256 维再入库，和直接换一个原生 256 维模型，重建成本和几何含义差在哪？
- 维度提高后 recall@10 不动，只在后段重排后的 nDCG 涨了，问题更像在表示还是在近似索引？
- 查询保留 1024 维、文档截成 256 维，系统会表现出什么「分数挤成一团」的症状？

**推理回答：** 把「成本正比于 \(nd\)」和「几何是否仍是模型定义的度量」分开。只有后者被模型保证时才能用更短向量换成本。用易混对召回和存储账单一起验收，禁止只看容量仪表盘。

## EMB-005. 同一知识块按文档粗算，倒排上「词 ID→权重」的学习稀疏向量和 HNSW 上 768 维实数，两侧大约各占多少字节？词表变宽、中文语料再覆盖英语和法语、每天改写一成文档时，存储或更新哪一侧先顶满？

**答：** 学习稀疏向量是一张几乎全零的词表轴：非零项是「词 ID + 学出来的权重」，靠倒排表按词取 posting。稠密向量是固定 \(d\) 维的实数数组，几乎每维都非零，靠 ANN 图或簇做近邻。按文档计，768 维 float32 裸向量大约 3KB，再加一层 HNSW 邻接通常仍是数 KB 量级；稀疏一侧取决于激活词数，例如平均 80–300 个非零时 posting 大约 0.6–2.4KB，扩张到五六百个词就可能反超稠密。词表膨胀和跨语言先打稀疏的轴和倒排宽度；编码器一换或每天一成文档改写，稠密要重嵌并改图，稀疏要改写多条 posting，两边贵的位置不同。

**深入展开：** 数据流不同。稀疏：编码器（或统计模型）对一段文本吐出 \(\{(t,w_t)\}\) → 词典把 \(t\) 映成全局词 ID → 倒排 `term → [(doc_id, weight)]`；查询同样扩张成一组词，只合并这些 posting，分数是稀疏点积 \(\sum_t w_q(t)\,w_d(t)\)。稠密：编码器吐 \(\mathbb{R}^{768}\) → 写入 HNSW/IVF；查询做一次前向，在图上走边或探簇。存储账（示意，不含正文）：稠密 \(768\times 4=3072\) B，HNSW layer0 按每点约 \(2M\) 个 4B 邻居、\(M=16\) 时大约 128B，加上上层边和主键，常见落在大约 3.2–4KB/文档；一百万条裸向量大约 3GB，图边是小头。稀疏按非零计：每条 posting 大约 `doc_id + weight` 8B，平均 \(L=150\) 则约 1.2KB/文档，外加词表和跳表均摊；学习稀疏常会「扩张」——正文没出现的相关词也被点亮，这是它能做同义匹配的机制，也是 \(L\) 从几十涨到几百的原因。\(L\) 涨则倒排变宽、查询要合并的链表变多，延迟随查询激活词数走，不是随 \(d\) 走。多语言：稀疏坐标绑在分析器和词表上，「退款」和 "refund" 是两根轴，除非扩张模型真的跨语言点亮，否则英法文档几乎不共享 posting；加语言通常要加分析器、扩词表、重刷倒排，IDF 或扩张统计也会漂。稠密若编码器在平行语料上把译文拉近，同一套 \(d\) 和同一张 ANN 就能混存；编码器只覆盖中文则几何先坏，不是索引类型的问题。更新：单条改写，稀疏要从该文档旧的 \(L\) 条链表摘掉、写入新的 \(L\) 条；稠密是重嵌 + ANN 删插（删除常先变墓碑）。每天改 10%、编码器冻结时，两边都能增量；若用了集合级 IDF，稀疏分数会慢漂，学习稀疏在编码器不变时一般不必为了 IDF 全量重建。换编码器：两边都全量重算，倒排重建墙钟通常低于同规模 HNSW 重建。边界：扩张过度会把弱相关词写进大量 posting，索引膨胀且主题漂移；稠密不扩张词表，但同义全靠几何，轴不可解释。不要把学习稀疏叫成「另一种稠密 embedding」——服务接口一个是合并链表，一个是走近邻图。

**后续追问：** 平均激活从 80 提到 400，倒排体积和单查询合并的 posting 长度各涨几倍，查询 P50 会先坏在词数多的问句还是短问句；中英混合一篇文档，稀疏是建两套分析器还是共用 BPE 词表，扩张失败时长什么样；HNSW 墓碑率到大约两成时，稠密侧的有效存储和插入延迟谁先偏离「每文档 4KB」这本账。

**扩展问题：**
- 同一百万文档，画出「平均非零数 \(L\)–倒排 GB」和「\(d\)–ANN GB」两条线，在哪一段稀疏反而更贵？
- 只换扩张模型、不换稠密编码器时，为什么倒排必须全量重刷，HNSW 却可以不动？
- 查询侧扩张出 60 个词、文档侧平均 200 个非零，稀疏点积的时间主要花在求交还是在打分，倒排应按什么排序裁剪？

**推理回答：** 目标是两套表示都能被检索服务吃进去，而不是比较「谁更懂语义」。约束是稀疏按非零和词表计费、稠密按 \(d\) 和图边计费，跨语言等于换轴或换几何，更新等于改 posting 或改图。先把每文档字节和一次更新碰多少数据结构写清楚，再用「加语言 / 换编码器 / 每天 10%」三个负荷看谁先爆。验收看：单文档存储拆账、跨语言切片的召回、以及增量一天后倒排与图的体积和墓碑率。

## EMB-006. 「七天无理由退货」这句话会分别当用户问句和知识段落各走一遍。从切分 token 到写出定长向量，双编码器里哪些环节缺一不可，宽度 d 又在哪一层锁死？

**答：** 文本先被 tokenizer 切成 id，再经 Transformer 得到每个 token 的上下文隐状态，最后用池化（mean、CLS 或 last token 等）压成一条长度为 \(d\) 的向量；\(d\) 由最后投影层宽度决定，与句子有多长无关。双编码器里 query 和 passage 前向分开，互不看对方的 token，所以细粒度词对齐天生弱于交叉编码器。训练目标让相关问答对靠近，写出的是给近邻检索用的位置，不是词袋计数。

**深入展开：** 一条典型前向：子词 id（这句常常只有数个到十几个）→ 位置信息 → \(L\) 层自注意力 → 隐状态形状 \([S, H]\) → 池化到 \([H]\) → 可选线性投影到 \(d\) → 常做 L2 归一化。\(S\) 变长，输出仍是 \(d\)，维度锁在投影，不锁在输入长度。超过最大长度的段落必须先切块或截断，截断会直接丢掉尾部义务条款。归一化之后，内积和余弦排序一致。边界：多一个空格、全角半角、是否加 `"query:"` / `"passage:"` 前缀，都会改 id 序列，向量跟着变；内部缩写被切碎时几何位置不稳定。双编码器省掉的是 query–document 交叉注意力，这是它能建库预计算文档向量的原因，也是它需要 rerank 补细读的原因。

**后续追问：** mean pooling 和 CLS / last-token 在短查询、长段落上各自偏什么；为什么很多检索模型坚持 query 与 document 用不同前缀；截断发生在模型上限（例如 512 或 8k token）时，切块重叠你按什么定。

**扩展问题：**
- 不归一化就入库、检索却按余弦实现，会在哪一步算错或悄悄多一次除法？
- 「退货」和英文 "return policy" 能否靠近，更取决于词表重叠还是对比训练里有没有跨语言对？
- 池化时把 padding token 也平均进去，召回会呈现什么「短句分数发虚」的症状？

**推理回答：** 从「必须输出固定 \(d\)、且 query/doc 可独立编码以便文档预计算」反推流水线只能是 tokenize → 独立 Transformer → 池化/投影。长度只影响中间的 \([S, H]\)。用「改一个空格向量变不变、超长段落尾部丢不丢、query 前缀是否改位置」验收实现有没有按这条数据流走。

## EMB-007. 切片写「周一至周四允许远程」，问句却咬住「周五禁止远程」，余弦居高，真正点名禁令的片段更靠后。编码器怎样把整句收成一条向量？

**答：** 编码器先把句子切成 token，经过多层自注意力得到每个 token 的隐状态，再池化成一个固定维向量（常见约 384–1024 维），检索时用点积或余弦比较。训练多用对比学习：主题相近的一对拉近，不相关的推远。池化之后，否定词、星期和数字只占少数 token，被整句主题平均掉，于是“允许周一到周四”和“禁止周五”在空间里几乎同向。

**深入展开：** 以双编码器为例，查询和文档各走一遍编码器（权重可以对称或不对称）。输入是 token id 加位置信息，输出对 token 做均值池化或取专用标记位，再经线性投影，常常做 L2 归一化；归一化后余弦等于内积，ANN 才能用内积检索。对比损失优化的是整句是否同主题，不是每个逻辑约束是否成立，所以同主题反极性、SKU、工单号、否定范围都会被压扁。这是单向量的容量极限，不是偶发实现错误。短查询更严重，因为可池化的有效 token 更少。工程上用词法检索补“周五”“禁止”这类字面，或在短名单上用 token 级交互、交叉编码器重打分，而不是指望把维度加到 1024 就自动记住否定。

**后续追问：** 查询塔和文档塔权重分开，在短查询上通常赚在哪？不做 L2 归一化改用裸点积，分数分布和索引配置要怎么改？均值池化、CLS 位和末 token 池化，各更常见于哪类编码器？

**扩展问题：**
- 用规则把否定句改写成再嵌入，能修多少“极性翻反”的错排？
- 维度从 384 加到 1024，对否定和数字这类局部特征是否一定更稳？
- 中英混写且词表覆盖不足时，这个向量会表现成近邻乱飘还是全挤在一起？

**推理回答：** 先把“一句话变成一个点”的计算图画清楚：分词、自注意力、池化、可选归一化。再指出对比学习对齐的是主题邻近而非逻辑等价，用这道错排说明局部约束在池化时丢失，从而引出字面检索或二阶段交互，而不是先怀疑标注错了。

## EMB-008. 汽配 RAG 总把 SKU 串错，因为通用向量把冷却液、空调制冷剂挤到一起。要用怎样的正负对和哪种损失，才能让同规格件靠近、易混件分开，且不必把整座编码器重训？

**答：** 这是领域细粒度不够，不是模型不懂中文。构造「用户问法 / 正确配件文档 / 易混配件文档」三元组，用 InfoNCE 或 triplet 把难负例（冷却液 vs 制冷剂、相近 OEM 号）明确推开。冻结编码器主体，只训 LoRA 或一层投影头，通常就够掰开局部邻域，还不容易毁掉「防冻液 ≈ 冷却液」这种该留的同义。训完必须用新模型重算全部向量并建新索引，旧空间不能混搜。

**深入展开：** 正对来自「查询 → 最终采用的配件页 / 手册章节」，以及目录里的「零件号—名称—适用车型」。难负例不要随机抽：用当前模型或 BM25 取 top-20，再按规则或人工标「同功能不同规格」「同一车系不同年款」。假负（其实可互换的件）会把可替代关系拧断，宁可少标。双塔可共享权重；batch 内其它正文档当负例，但汽配目录很窄时这些负例太易，必须额外灌入难负。温度过小，梯度只盯最难的一对、训练不稳；过大，则易混对推不动。参数高效：例如 rank 8–16 的 LoRA 打在注意力投影，或只训最后一层加同维线性头；全参数在几百到几千条领域对上，容易把通用同义方向一并改写。量级：覆盖核心易混对的数百到数千条高质量三元组，往往比十万条弱监督目录更有效。验证必须成对看切片：冷却液查询不得把制冷剂放进 top-k，同时「防冻液」仍要召回冷却液文档；只报平均 recall 会掩盖「平均涨了、串件也涨了」。上线走双索引灰度，看串件率、切片 recall 和一组通用改写回归。数据里的查询侧建议拼上可见上下文（车型、年款），文档侧拼「件号 + 适用车型 + 名称」，减少只靠一个词对撞。

**后续追问：** 难负例全由旧模型挖掘，会不会强化旧模型已经分不开的盲区；query 塔和 doc 塔要不要不对称；没有用户查询、只有零件目录时，用模板或 LLM 生成问法怎样避免问句塌成几种句式。

**扩展问题：**
- 写出 5 条「冷却液」相关正对和 5 条难负，并说明随机负例为什么推不开这两类液体。
- 只训一个 768→768 投影，和给编码器加 LoRA，在串件与通用同义上各伤哪一侧？
- 微调后某条通用改写掉点，你混回通用对做回放，还是降学习率并早停？

**推理回答：** 目标是易混件分开、同义件仍近。约束是通用对比学习没见过这些易混对，且小数据全参数会毁基座。用领域三元组 + 难负 + 小 PEFT，再重建索引灰度。验收看易混切片和同义切片成对过线，而不是平均分。

## EMB-009. 把同一训练批次内其余行的正文档直接当负例，用来训面向检索的 embedding。这种写法省掉了什么？何种情形会把本该靠近的相关文档推开？

**答：** 对比学习把损失写成：正对（查询，相关文档）的相似度，在一堆候选里占比要变大；常见实现是带温度的 InfoNCE。批内负样本把其它行的正文档直接当负例，负例个数大约是 `batch_size − 1`，省掉单独检索和存储难负例的流水线。若同一意图的另一篇制度、同一工单的另一切块碰巧落在同一 batch，它们会变成假负例，梯度会把本该靠近的点推开。

**深入展开：** 设 batch 有 \(B\) 个 \((q_i, d_i^+)\)。对 \(q_i\)，候选常是 \(\{d_1^+,\ldots,d_B^+\}\)（多卡训练还可跨设备收集），分数 \(s(q,d)=q\cdot d/\tau\)。\(\tau\) 小则分布尖锐，模型必须把正例明显抬高；\(\tau\) 大则梯度平，难例学不动。批内负例往往太容易（主题完全不同），所以还要用 BM25 或旧模型捞「像但不对」的难负例。数量级：\(B=128\) 时每条查询有 127 个负例；\(B=16\) 时模型容易靠排除几个毫不相关的文档混过关。正对可以来自问答、标题–正文、点击、同义改写，或用生成模型合成查询；图文对上的 CLIP 类训练是同一损失，只是一侧换成图像塔。边界：假负例一多，模型会学会「只有字面几乎相同才算正」，同义改写召回掉下去。

**后续追问：** 分母只含批内负例和再加硬负例，梯度规模差在哪；为什么增大 batch 往往比单纯把 \(\tau\) 再降一档更稳；没有人工标注时，用标题生成问句和用正文随机窗做正对，各自会引入什么偏差。

**扩展问题：**
- 假负例比例升到大约三成，验证集上同义改写召回和字面命中会朝哪两个方向走？
- 一个查询有多个正文档时，仍用「每行只承认一个正例」的 InfoNCE 会漏掉什么，损失怎么改？
- 训练后期所有向量挤成一团，从相似度矩阵和 \(\tau\) 上你先看哪些信号判断是 collapse？

**推理回答：** 目标是拉近正对、推远负对；约束是负例要又多又难，但不能冤枉真相关。批内负例满足「多且便宜」，所以用它当默认分母；再用「是否可能共指同一答案」过滤假负例，用难负例补区分度。验收看难负例子集上的排序，而不是只看随机负例上的 InfoNCE 是否下降。

## EMB-010. 三选一上线：768 维纯英文、1024 维领域专用、384 维多语言。手头只有 200 对内部工单「问题→应命中段落」，在这份小集上怎样评测决胜？

**答：** 用这 200 对做检索评测，不要用公开榜决胜。把工单问题当查询、应命中段落当金标准，在同一套切块和同一套索引参数下比较 recall@10、MRR、nDCG@10，并记下平均嵌入时延和索引体积。领域模型若没见过你的中文工单、英文模型碰上中文查询，都会在这份小集上直接露馅。200 条不够拿来训练，但固定其他变量后够做三选一。

**深入展开：** 评测协议要锁死切块、k 和近似检索配置；选型阶段甚至可以用精确内积，避免 ANN 误差干扰模型比较。按语言和问题类型分层看指标，不要只报一个平均数：英文模型可能在英文工单上很高，中文工单接近随机。体积粗算：同样一百万块，384 维大约是 1024 维的 3/8，会影响内存和 HNSW 的层数与延迟。1024 维若只能走远程接口，p95 可能比本地 384 维高一个数量级，要单独列进决策表。200 条建议做交叉划分（例如五折）看排名稳不稳。若三者 recall@10 差距落在抽样噪声里，选延迟和部署约束更松的，把剩余差距留给重排。公开榜的语料长度、语言和工单分布不同，只适合列候选，不适合宣布赢家。

**后续追问：** 评测里每个问题只有一段正例，线上却常有三段相关，指标会怎样偏？要不要把同主题的错误工单当难负例加进评测？换模型后面空间不兼容，双索引迁移怎么做才不中断检索？

**扩展问题：**
- 这 200 对有没有覆盖编号查询、否定句和超短查询这几类已知弱点，怎么补采？
- 若还想在工单上继续训领域模型，怎样把评测对隔离出去，避免自己测自己？
- 多语言 384 维在中英混合查询上失败时，先翻译再检索能补多少，多一跳的代价是什么？

**推理回答：** 目标是上线后工单检索的召回和延迟，约束是样本少、不能按公开榜换模型。于是把公开榜降为入围名单，用自家金标准段落当唯一裁判，并锁死切块以免把分块差异算进模型差异。质量接近时用部署约束破平。

## EMB-011. 相关性若只标各系统前二十的并集，哪些文档永远进不了标注池？若后续还要上 reranker，发版该盯 recall@100，抑或盯 nDCG@10？在 400 条查询上领先 1.5 个点，怎样证明并非随机波动？

**答：** 只标各路 top-20 的并集，会系统性漏掉「谁都没召回、但人看其实相关」的文档；新模型若专门挖出这些漏网，它们常被当成未标注负例，nDCG 会被低估。后面还要接 reranker 时，初检门禁应对齐重排窗口，用 recall@100（或你们实际的 50/80）看金标进没进窗，而不是用初检的 nDCG@10——那是在考还没上场的排序。四百条上 1.5 个点先做配对检验或 bootstrap 区间，区间盖住 0 就不够当发版证据。

**深入展开：** 标注是在造度量的支撑集，不是在给模型打广告分。池化偏差：把系统 A/B/C 的 top-k 取并集再人工打 0/1/2，省标注，但并集之外的相关文档永远进不了 qrels。新编码器若改变邻域，召回一批旧系统没见过的真相关，这些文档在旧池子里是「未判定」：若按 0 计，新模型被罚；若直接跳过，recall 的分母又不完整。补法是残差抽样（从库中再抽若干未入池文档来打）、多轮补池（把新系统 top-k 再送去标）、以及明确「未判定」政策并写进脚本。难负例要单独进池：主题相近但答错场景、同手册不同节、过期口径，否则所有还能分清随机文档的模型在 nDCG@10 上都挤在一起。指标跟下游对齐：重排若看 100 个初检，初检的职责是「金标落在这 100 里」，recall@100 是门禁，初检 nDCG@10 可以很差——交叉编码器本来就会重排。若没有重排、生成只吃 6–8 段，才把 nDCG@10 或 recall@8 当门禁。四百条查询的均值标准差通常不小：例如每条 nDCG@10 的波动若在 0.2–0.3 量级，均值差 0.015 完全可能来自十几条查询的起伏。做法：对每条查询算 \(\Delta_i = m_A(i)-m_B(i)\)，做符号检验或 Wilcoxon 符号秩；再对 \(\Delta\) 做配对 bootstrap 看 95% 区间是否离开 0。同时报「\(\Delta_i\neq 0\) 的查询数」和切片（短查询 / 长粘贴 / 中英混），避免 10 条大起大落拖着 390 条平局假装整体赢了。不要编造某次公开比赛的显著性；这套检验只对你们这 400 条 qrels 负责。

**后续追问：** 未判定按 0 计和直接从该查询的度量里剔除，分别会让「更爱挖新文档的模型」往哪边偏；重排窗口从 100 收到 40，初检门禁要不要跟着改，nDCG@10 会不会突然变得有意义；400 条里某个切片只有大约 40 条，1.5 个点的区间会宽到什么程度。

**扩展问题：**
- 写一份标注规程：首轮池化、残差抽样比例、难负例来源、未判定的计分规则，各用一句话规定。
- 下面这段配对 bootstrap 在 \(\Delta\) 严重偏斜时会低估什么，你改用哪一种区间？

```python

delta = metric_a - metric_b  # shape (n,)

```

- 金标不全时，怎样用「新模型多召回的未判定文档」开第二轮标注，避免第一轮池子把创新模型钉死？

**推理回答：** 目标是度量能预测「金标进不进下游窗口」，而不是预测「在旧系统看见过的那一页上谁排序更漂亮」。约束是池子不完整、未判定有两种计法、四百条的均值差很容易是噪声。所以先补残差和难负，按有没有 reranker 选 recall@窗或 nDCG@10，再用配对检验看 1.5 个点站不站得住。验收看 qrels 覆盖、窗口对齐，以及 \(\Delta\) 的区间，而不是只看平均分谁高。

## EMB-012. 公开榜上排第一的是英文长上下文模型，内部制度却是中文、条款号很密、一段常常长过两千字。为何不能凭榜直接上线？用哪些业务硬约束一票否决它？

**答：** 榜单测的是别人的查询分布和语言，不是你的条款编号和内部简称。先用本域「真实问句–应召回段落」小集看 recall@k、MRR、nDCG，再拿硬约束做否决：中文与术语覆盖、有效输入是否真能吃下两千字而不截断尾部条款、全量重嵌的费用与延迟、权重能否内网部署。任何一条硬约束不满足就可以刷掉榜首；质量接近时选更好运维的，而不是分差第三位的那个。

**深入展开：** 把约束写成可拒绝的测试。语言/领域：用条款号、部门简称做探针，系统性排不进编号页就淘汰。长度：模型最大输入小于切块策略时，长段被截尾等于丢义务条款——要么换能吃更长输入的编码器，要么先改切块；更大的输出维度不等于更能读长文。非对称：检索常用双编码器，query 短、文档长，前缀必须与训练一致。成本：全库重嵌的 token 或 GPU 小时、存储 \(d\times 4\) 字节 \(\times n\)、目标 QPS 下的 batch 推理。合规：原文和权重是否出域。不要引用未核验的榜分数值；在自己的大约 200–2000 条标注对上，名次经常和公开表对不上。生成模型很大，也不等于句向量适合检索；把生成模型隐状态随便池化，通常不如专门对比训练过的检索模型。

**后续追问：** 只有约 80 条真实问句时，怎样避免选模型过拟合这 80 条；延迟预算约 50ms 时，本地小模型和远程大模型要看哪张曲线；条款编号失败是换模型，还是先给编号留精确通道。

**扩展问题：**
- 两个模型离线 nDCG 接近，一个 384 维、一个 1024 维，你还要补测什么才敢选小的？
- 一周后库里多了英文合同，当时刷掉英文模型的决定要不要翻案，依据是哪类探针？
- 模型许可禁止用于检索服务，即使本域分数最高，你在评审里用哪条记录否决？

**推理回答：** 目标是「本域问句召回本域段落」，约束是语言、长度、成本、合规。榜单只提供候选名单。用本域探针做否决，用小而真的标注集做排序，用运维约束打破并列。验收看探针集和标注集上的名次是否稳定，而不是看公开表上的第一名。

## EMB-013. 关系库已经托管了正文、ACL 以及版本号。语义检索仍外挂一台只装高维浮点的检索引擎，原因是什么？直接 SQL 扫描 `float[]` 列为什么不够？

**答：** 关系库擅长精确谓词、事务和权威字段（权限、版本、正文）。语义检索要的是高维近邻：离线把空间组织成图或簇，查询只碰一小部分向量。对 `float[]` 全表扫描在万级也许能撑，到十万、百万级代价按 \(n\times d\) 涨，还缺少与过滤协同的近似索引、以及按向量版本重建的运维原语。常见拆法是关系库当真相源，向量引擎只存 `(id, vector, 少量过滤副本)`，用 id 回表取正文。

**深入展开：** 向量引擎的核心接口是 `search(q, k, filter)`，不是优化器碰巧把 `ORDER BY embedding <-> q` 跑快。有些关系库扩展也能建近似索引，判断标准仍是：召回/延迟是否可调、向量更新能否重建、过滤选择性很高时会不会退化成近乎全扫。事务窗口更麻烦：正文先提交、向量后到，会出现「权限已改但仍被旧向量召回」。数量级：100 万 × 768 × 4 字节约 3GB 裸向量，全扫一次就是数 GB 内存带宽；图上的一次查询可能只走几千条边。需要强一致报表和复杂 join 的不要放进向量库；需要毫秒级语义召回的不要指望普通 B-tree。向量库宕了，应能把关系库上的关键词检索当降级，而不是让生成链路空转。

**后续追问：** 权限只存在关系库、向量查询不过滤，泄露面是什么；为什么多数团队不把模型生成的答案写进向量库当权威记录；变更日志保证「关系库提交成功才允许向量可见」时，失败重放如何避免重复 id。

**扩展问题：**
- 向量引擎里复制一份租户或权限字段，和每次回表校验，延迟与一致性怎么选？
- 什么规模、什么过滤复杂度下，关系库里的近似索引就够，不必再运维独立集群？
- 文档删除已在关系库生效，向量侧延迟 10 分钟，你会用墓碑、可见性版本还是查询时回表否决？

**推理回答：** 把负载分成「精确记录管理」和「高维近邻」，匹配两种索引。权威数据和权限留在关系库，是因为事务模型已经在那里；向量侧只优化几何检索。用全表扫描延迟对比近似查询延迟，并用「正文/权限是否仍以关系库为准」验收，而不是看是不是多了一个进程。

## EMB-014. 均摊每条再挂 2KB 标题加摘要、tag 基数上万。向量分之外还要给近七天更新加点、热门 FAQ 小幅抬、官方手册加权。哪些列该做标量索引，哪些只作为命中后回表的 payload？内存和 P95 谁会先崩？

**答：** 权威、新鲜度、热度是排序特征，不是「能不能召回」的几何性质：先用向量取一个较宽的候选窗，再把向量分校准后与有界的加性提升合并。建标量索引的只应是查询会按范围或离散档去读的低基数列（权威档、时间桶、热度桶）；标题、摘要、原始 tag 列表只当回表 payload，给生成或展示用。平均 2KB 正文摘要若常驻在 ANN 进程里，百万级就是大约 2GB 的散乱读取，P95 会先坏在攒 payload 而不是算距离；上万取值的 tag 若按倒排全建，更新放大和内存会先于那几个加分项爆掉。

**深入展开：** 合成可以写成 \(s = z(\mathrm{sim}) + w_a a + w_r r + w_p p\)。\(z(\mathrm{sim})\) 必须按查询做，例如对本查询候选窗 min-max 或 z-score，否则余弦 0.3–0.9 的动态范围会被「官方 +0.5」直接淹没。\(a\) 是 2–4 档权威（官方手册 / 内部 wiki / 闲聊记录），基数低，适合存成整数并建标量索引，便于偶尔「只看官方」这类半过滤半排序。\(r\) 用更新时间做衰减，例如半衰期 30 天的示意指数衰减，线上只需要一个时间桶或一个预计算 float，不必每次扫原始时间戳全文。\(p\) 用 \(\log(1+\mathrm{clicks})\) 或预计算热度分，并设帽，避免头部 FAQ 永久压住新条款。字段分工：索引列 = 查询计划会碰的低基数列；存储列 = 命中之后才读的展示字段（title、2KB 摘要、url、作者）。2KB × \(N\)：\(N=10^6\) 就是约 2GB，若跟向量挤在同一进程、按 top-100 随机跳着读，cache miss 会把 P95 从「扫几千条边」变成「散读 200KB 文本」。摘要应落到旁路对象存储或文档表，ANN 内存只留向量、主键和大约几十字节的排序字段。高基数 tag（上万取值）若为每个取值建倒排，写入一条文档要更新一串 posting，内存按「取值数 × 链表」涨；排序其实只需要一个预计算的 tag 质量分，不需要把原始 tag 字符串当索引键。若产品真的要「按某个 tag 收窄」，只给少数高频 tag 建索引，长尾 tag 回表后筛。边界：热度来自展示位置，不校正点击偏差会让本就排前的文档更前；权威档被业务方随意加「官方」标记，加分就失效，档位要有发布流程。向量分和加分的权重用带标注的窗口调，不要在线上凭感觉拧 \(w\)。

**后续追问：** 候选窗从 50 扩到 200 再加分重排，延迟和「金标本来在 80 名以外」的召回各怎么变；摘要改成磁盘旁路后，top-8 回表的 P95 预算你留多少，冷启动会不会把省下的 ANN 时间吃回去；tag 基数从 200 涨到 2 万，索引体积和单次 upsert 放大你怎么估。

**扩展问题：**
- 列出 payload schema：每个字段标「索引 / 仅存储」、基数、平均字节，并估算 \(N=5\times 10^6\) 时 ANN 进程多出来的 RSS。
- 权威 +0.4、热度 +0.3 时，怎样用一组分差图证明弱相关的官方页压过了强相关的普通页？
- 只把 `updated_at` 当存储字段、每次在 CPU 里算衰减，和预计算 freshness 桶，对写入和查询各贵在哪？

**推理回答：** 目标是「语义近」且「官方/新/有用」的文档排在窗前，同时 ANN 工作集不背 2KB 正文。约束是加分必须和按查询校准的向量分同一量纲，索引列的基数决定内存，payload 大小决定攒结果的尾延迟。所以宽召回后加性融合，只索引低基数排序档，大字段和长尾 tag 回表。验收看带加分的标注窗口、进程 RSS，以及 top-k 回表 P95。

## EMB-015. 一个 RAG 向量库要承载 8000 家租户：其中 200 家大租户各存数十万条向量，其余长尾大都只有两三百条。是为每家单独建集合，还是共享索引、靠分区键隔离？考虑到大户扭曲近邻结果、空壳占内存、配额以及退租清空，你打算怎样切分？

**答：** 按体量切开，不要二选一：过了自己测出来的门槛（例如大约 5–10 万向量）的大户各建独立 collection，长尾按 `tenant_id` 做分区键塞进少数共享索引。独立 collection 没有跨租户边，退租就是丢集合，但八千个空壳的固定开销、文件句柄和 compaction 会先把集群吃满；共享图省空载，可 IVF 质心和 HNSW 边会被大户的密度拽歪，小户自己的点互相连不上。配额在写入路径按租户计数硬拒；退租后共享侧必须删键加合并，才能把墓碑占用的图和内存要回来。

**深入展开：** 物理布局决定图长什么样，不是查询时再补一刀的问题。一租户一 collection：路由层用认证上下文选集合，写入、备份、重建都按集合隔离。两百个大户这么做合理——几十万点够撑起自己的 HNSW，参数可按该户 QPS 调。八千个长尾各建一张图则空载主导：每个集合哪怕只有大约 8–32MB 的头、副本、空码本和文件，8000 份就是大约 64–256GB 的「没有向量的内存」，再加上句柄上限、同时 compaction 的尖峰。两三百条向量上 HNSW 的建图和绕路往往贵过对这几百条做暴力扫描，独立图是亏的。共享索引 + `partition_key=tenant_id`：一份向量、一张图或一套 IVF 列表，磁盘和副本按总量线性涨，运维面小。代价是邻居噪声：抽样训 IVF 时质心被占库 80% 的大户拉走，小户的点掉进形状不对的细胞；HNSW 边按全库几何生长，小户的两三百个点可能挂在大户「制度/合同」高速公路上，彼此缺少短边，表现为「库里有、图上走不到」。这是布局造成的图质量问题。配额：`max_vectors`、日写入条数、存储字节在 API 入口按租户计数器拒绝，共享索引尤其要防一个租户把公共图写爆。退租：独立集合 `DROP` 后异步回收，验收是路由表不再指向它。共享侧是按分区键删除 → 墓碑仍占节点和边 → compaction 或影子重建才能把 RSS 降下来；必须扫一遍断言该 `tenant_id` 剩余 0，否则合规清库只是逻辑删。推荐切法：大户独立；长尾按 `hash(tenant_id)` 进少量共享分片，避免所有小户挤在被某个超大户主导的同一张图里——超大户本就不该进共享池。小户长大越过门槛：按分区键导出 → 灌进新 collection → 切路由 → 共享侧删除并合并。边界：管理员跨租户检索走单独的只读导出，不要把八千张图逻辑上再拼成一张；同一公司多品牌若共享文档，分区键要先定义「租户」是合同主体还是品牌。

**后续追问：** 空载按每集合 16MB 估，8000 个长尾独立集合和 8 个共享分片的「无向量内存」差多少；小户召回变差时，你如何用「只含该户向量的 brute-force 对照」证明是图被大户带偏，而不是向量本身；退租后 RSS 一周没掉，你查墓碑率、段数还是副本是否还挂着旧 collection。

**扩展问题：**
- 给出晋升规则：连续一周向量数、QPS、写入失败率各过哪条线，就把租户从共享池迁走，迁移窗口怎么避免双写漏删？
- 共享分片里一个租户占了该片 40% 向量，要不要再切，还是直接晋升为独立集合？
- 配额按向量数还是按 RSS 字节？HNSW 边和 payload 不计入条数时，怎样防止「条数没超、内存先爆」？

**推理回答：** 目标是大户有稳图、小户付得起、退租能真正释放空间。约束是集合有固定开销、共享图按全局几何长边、删除不合并就还占内存。所以按体量混合布局：头户物理独立，长尾共享并限制单户占比，配额卡写入，退租用「剩余 0 + RSS 回落」验收，而不是只看逻辑删除成功。

## EMB-016. 精确 k 近邻要对全表算距离——规模两千万、维度 768。ANN 为何只碰一小撮仍能给出几乎最近的邻居？图方法、分桶、压缩各自省掉哪一段运算？

**答：** 精确 k 近邻代价约 \(O(nd)\)，两千万 × 768 次乘加对单次在线查询通常不可接受。近似近邻先在离线把空间组织好，让查询沿着更可能近的路径走，只对候选算精确或近似距离。图方法把点连到近邻再贪心爬；分桶方法先聚类，查询只进最近的若干桶；压缩把每次距离从 \(d\) 维浮点换成查表。牺牲的是召回：真正的第 k 近邻可能根本没被碰到。

**深入展开：** 两千万 × 768 × 4 字节大约 60GB 裸向量，全扫既是计算问题也是带宽问题。HNSW 一类多层图：上层边少、步子大，下层边密、局部精修，一次查询常只碰几千到几万条边，`efSearch` 控制候选有多宽。IVF 一类：先 k-means 成 `nlist` 个中心（常见数千到数万），查询只搜 `nprobe` 个簇；数据分布事后漂了，中心过时，该进的桶会错。乘积量化把向量切成 \(m\) 段，每段用码本代替，距离用 \(m\) 次查表累加，常和 IVF 绑在一起。局部敏感哈希让相近点高概率同桶，高维时桶质量往往不如图或簇。评估必须同时报：相对精确结果的 recall@k、延迟、内存、构建时间。过滤掉绝大多数点时，图上的近邻可能全被滤掉，局部性假设破了，召回会比无过滤时更差。

**后续追问：** 数据分布大变后，为什么簇中心要重训，而图结构更怕删除留下的空洞；码本是对文档向量训练的，查询向量要不要同样量化再比；业务上的「差不多最近」用精确 k 近邻重合定义，还是用人工相关性定义，两种结论何时打架。

**扩展问题：**
- 元数据先滤掉 99% 的点，仍走原来的近邻图，为什么召回可能比无过滤更差？
- 同一 IVF 上把 `nprobe` 从 8 加到 64，你少算了哪些距离、多找回的通常是哪类邻居？
- 哈希桶和聚类桶都是先缩小候选，各自最典型的失败模式是什么？

**推理回答：** 从 \(O(nd)\) 不可行推出必须减少「比多少个点」或「每个点算多贵」。三类方法分别砍访问点数、砍桶外点、砍单次距离算术。用与暴力结果的重合率标定「差不多」，用探测点数解释延迟，不要把近似近邻讲成另一种精确算法。

## EMB-017. 词面倒排和向量近邻，知识库两边都要有。同一套检索引擎同时托管，还是词面集群与向量集群分开跑？正文被改写或删掉时，两边如何保持同步？两路并行查询的尾延迟，加上维护双栈的开销，你会怎样据此取舍？

**答：** 绿场、百万级、同一班人值班，优先一个引擎同时持有倒排和向量：一次 upsert、一个版本、删一条两边一起消失。已经有大规模倒排集群、向量是后加的能力，或两种负载要独立扩容，就拆成两套，用文档库变更日志做双投影。拆开会把不一致、并行尾延迟和双倍值班变成日常成本；合并会把建图和倒排合并绑在同一台机器的 CPU/内存上。按「删除可见性 SLA、是否已经有其中一套、资源是否打架」拍板，而不是按哪边召回列表更好看。

**深入展开：** 单引擎：文档进入同一写前日志，分析器写 posting，编码器写向量，提交点共享。查询扇出是进程内两次游标，合并仍要做，但可见性由一个提交序号保证——这是运维原子性，不是某种融合公式更优。备份、映射、副本、权限是一份。代价是资源耦合：HNSW 重建或段合并能把倒排查询的 CPU 和页缓存挤掉；倒排要的是 posting 顺序读，向量要的是图的随机边，硬件画像不同，绑在一起只能按更饿的那边买内存。两套系统：倒排集群和 ANN 集群各自扩。真相源在文档库，变更以单调版本进 outbox，两边独立消费。失败模式是半边成功：正文新、词面旧；或倒排已删、向量还在吐幽灵 chunk。要对账：定期抽 `id` 集合做对称差，查询侧可丢掉版本落后于阈值的一侧。删除 SLA 若是「数秒内两边都不可见」，两套必须有同步屏障或把删除当作交叉检查的硬条件，否则合规清库只清了一半。延迟：并行打两集群，\(t \approx \max(t_{\mathrm{lex}}, t_{\mathrm{vec}}) + t_{\mathrm{merge}}\)，P99 跟更慢那条尾巴走，要分别设超时：一侧迟到是丢掉这一路还是整请求失败，产品要先定。两套缓存、两次 GC、两次冷启动，尾延迟预算必须按「两尾取 max」留，不能按单路 P50 加。运维账：两套容量、两套升级、两套告警；换分析器只重建倒排，换 embedding 只重建向量，这是拆开的好处。决策序：①已有超大规模倒排、向量是新能力 → 两套 + 变更日志。②绿场且总量在百万到低千万、一队人 → 单引擎，直到压测看到建图和检索互相饿死。③删除必须秒级从所有检索面消失 → 单引擎，或双写带屏障，不要「两边最终一致就行」。边界：不要把「一个进程里有两种索引」理解成可以省掉同步设计——单引擎内部段之间仍会短暂不一致，只是窗口通常更短、工具链是一套。

**后续追问：** 向量侧重建要 4 小时、倒排侧只要 20 分钟，单引擎会怎样拖累发布窗口，拆开后又怎样保证重建期间查询不混用新旧向量；outbox 积压 15 分钟时，你对外宣称的「已删除」以哪一侧为准；两路 P99 各 40ms、相关 0.3，合并后的 P99 你按什么上界估。

**扩展问题：**
- 画出双写状态机：只写进倒排 / 只写进向量 / 两边版本对齐 / 两边都缺，查询在每个态怎么降级。
- 单引擎里向量段合并把节点 CPU 打满，你是限速建图、把向量副本拆出去，还是整库拆成两集群？依据哪张争用图？
- 删除审计要求 1 秒内「任何检索面都 0 命中」，两套系统最少要哪些交叉探针？

**推理回答：** 目标是词面和向量看到同一版本文档，并且发布、删除、值班成本可承受。约束是两套索引是同一真相的两个投影，并行延迟取 max，集合级操作（重建、删除）在两套上不会自动对齐。先问删除 SLA 和现有资产，再选单引擎或双集群加日志。验收看双端版本差、删除探针、以及 \(\max\) 尾延迟，而不是看某一路的召回列表有多漂亮。

## EMB-018. 夜间索引重建刚做完，RAG 节点 RSS 已经涨到大约 90GB，远超按裸向量公式估出来的占用。重复 chunk、多余副本、图上的边、裸向量本身各占多少，你怎么拆这笔内存账？哪一刀先砍可以保住召回？

**答：** 先按组件代入 N、d、M、副本数记账，再按「重复文本和未卸旧索引 → 正文常驻 → 图参数 → 量化/降维」往下砍。完全相同的 chunk、夜里留下的旧图、多出来的进程内副本，是零精度损失；HNSW 的 M 过大是用内存换一点召回；量化才动距离，必须用冻结集守门。90GB 里若原向量按 `N × d × 4` 只有一小半，其余多半在邻接表、payload 字符串、分配器和没释放的上一版索引。

**深入展开：** 示意拆账（把数字换成你们的）：原向量 `N × d × 4 B`，节点上若「旧索引未卸 + 新索引」或本机两副本，直接乘 2。HNSW layer0 邻接大约 `N × 2M × 4 B`，M 从 16 升到 64，边内存约乘 4。payload 若把平均 800–1000 字符的 chunk 正文留在进程里，N 到百万时又是数 GB 到十几 GB，有时比 INT8 向量还大。滑动窗口（例如 512 token、重叠 128）让同一段落出现多次；未剥的页眉页脚会复制成一片近邻盆地，N 虚高。运行时还有对象头、页缓存。砍的顺序：①规范化文本哈希去重，剥模板，近重复（向量很近且文本几乎相同）合并到信息量最大的一条——N 下降则向量、边、正文一起降，噪声少了召回常升。②卸旧索引，一节点一副本，水平扩检索副本而不是单机堆两份全量。③正文进对象存储或磁盘，内存只留向量、主键和过滤字段。④再降 M 或改 IVF-PQ/INT8，热文档留高精度精排。⑤最后才换更小 embedding，因为那是换空间，要全量重算。每刀之后跑同一冻结集的 recall@k 和查询 P99。边界：哈希只删「规范化后完全相同」；近重复合并若把同一手册里必要的不同小节当成重复，recall 会掉——合并规则要看文档结构，不能只看余弦。若只向量量化而正文仍全在堆上，RSS 几乎不动，所以必须先拆账。

**后续追问：** overlap 去重时，答案句恰好落在被删的重叠区，你怎么保证还留得住；M 从 32 降到 16，你预期边内存和 recall 谁先明显动；90GB 是多租户均摊还是被一个大租户撑满。

**扩展问题：**
- 给一张记账表：N=4e6、d=1024、M=32、2 份索引、平均 payload 1KB，估算各项 GB 并指出最大头。
- 哪些内存在查询路径上是必需工作集，哪些只是构建残留或缓存？
- 冷数据放到盘上之后，怎样避免一次冷查询把尾延迟打出 SLA？

**推理回答：** 目标是 RSS 回到机器可驻留且召回不掉。约束是内存由向量、图、正文、副本叠加，不是单一量化旋钮。先量再砍零损失项，再动图参数和量化。验收看冻结集 recall 与节点 RSS 同时达标。

## EMB-019. 语料约 80 万条、768 维。在 IVF-PQ、Flat、HNSW 里如何取舍？门禁是 recall@10 至少 0.98、在线 P99 不得超过 20ms。从 0.95 拉到 0.98 该拧哪些参数，何时该承认暴力扫描反而更省？

**答：** 80 万还没到必须上 IVF-PQ 的体量。Flat 召回是 1.0，但一次查询大约是 80 万次 768 维距离，按实现和硬件，延迟可能从十几毫秒到上百毫秒，P99 20ms 往往悬。内存够时 HNSW（原始向量加图边）通常能同时摸到高召回和个位数到十几毫秒，是这个规模的默认项。IVF-PQ 更省内存、适合再大一个数量级，同等 0.98 召回往往要加大 `nprobe`，延迟不一定赢。从 0.95 到 0.98，HNSW 主要加 `efSearch`，IVF 加 `nprobe`；曲线末端会变陡，接近 1.0 时延迟可能翻倍仍不够，这时若 \(n\) 仍是几十万，改回 Flat 或「近似宽召回再加原向量精排」更诚实。

**深入展开：** Flat 无训练、写入即可查，适合当评测真值和小库。HNSW 的 `M`（每点边数）和 `efConstruction` 影响图质量、构建时间和内存，`efSearch` 只影响查询。内存粗算：80 万 × 768 × 4 字节约 2.5GB 向量，`M` 在 16–32 量级时邻接表再加数 GB 量级，整库常落在数 GB 到十 GB 出头，取决于实现，不是某张产品规格表。IVF 的 `nlist` 常从 \(\sqrt{n}\) 量级（例如 1k–4k）起调；PQ 把向量压成短码，内存可再降一截，但距离是近似的，0.98 这种高召回通常要扩大候选再精排。更新也参与选型：高比例增量插入时图可以加点，簇中心会过时；频繁删除会让图留下空洞。不要追求最高召回：用自己的查询画 recall–latency 曲线，选落在 SLA 左侧的最省资源点。

**后续追问：** 如何用 Flat 结果当真值，在自己的集合上测 HNSW 的 recall@10；`M` 加倍和 `efSearch` 加倍，谁先抬内存、谁先抬延迟；过滤掉九成文档后，三种索引谁先达不到 0.98。

**扩展问题：**
- 同样 80 万条，维度改到 3072，Flat 的 P99 大约按什么比例变差，HNSW 是否还该当默认？
- 构建窗口只有 30 分钟，HNSW 建不完时你是降 `efConstruction`，还是先上 IVF？
- 索引侧 recall@10 已经 0.98，人工看起来仍差，你用什么对照实验判断问题在图参数还是在 embedding？

**推理回答：** 约束是 \(n\approx 8\times 10^5\)、recall@10、P99。先估算 Flat 是否已经破延迟预算；破了再看内存是否撑得住 HNSW；内存紧或 \(n\) 再大一个数量级才考虑 IVF-PQ。用自有数据的召回–延迟曲线选工作点，末端收益递减时考虑回到精确搜索，而不是继续加探测。

## EMB-020. 包装破了的现场照交上来，过往同类破损影像和配套处置说明都要能按这张图捞到。图像与文本是否必须进入同一向量空间？两条塔的前向怎样对齐，才不会「按图找图很准、按图找说明却对不上号」？

**答：** 只要还要按照片去排文本说明，图塔和文塔的输出就必须能在同一度量下比较，通常用图文对比学习拉到共享球面。若只需图找图，可以停在纯视觉空间。本题两条都要，就必须对齐，否则图向量和文向量的内积没有训练意义。「图找图准、图找文乱」说明视觉邻域还在，跨模态对齐弱：说明太套话、图侧只编码了背景，或推理时两塔的预处理、归一化不一致。

**深入展开：** 图像经视觉塔（例如 ViT 一类）投影到 \(d\)，文本经文本塔投影到同一 \(d\)，两边常 L2 归一化，用温度缩放的对比损失在成对数据上训练。推理：照片 → 图向量 → 近邻（其它图，或说明文的向量）。不必把像素和文字塞进同一个 Transformer，关键是投影后共空间。失败模式：说明是「按流程处理」这类模板，文本向量挤成一团；照片主体小、背景仓库大，图向量变成「仓库」；旋转、裁剪、分辨率差让同一案件两张图远离。图前向通常比短文本贵一个数量级以上，要按分辨率和 batch 估计算量。音频视频还要时间池化。把图先交给生成模型写成一段话再 embed，是另一条级联，误差叠在生成上，延迟也更高，不能和共空间检索混为一谈。共空间也不等于事实完整：图里有、说明里无的信息，检索补不回来。

**后续追问：** 只有图–图对、没有图–文对时，靠「先出说明再 embed 文本」凑合会丢掉哪类视觉细节；共享空间里要不要给模态加可学偏置；以文搜图和以图搜文召回不对称时，你先查哪一侧的池化或温度。

**扩展问题：**
- 同一商品的「正面完好图」和「破损特写」在视觉空间很远，文本说明却相同，索引该为这个案件存几条向量？
- 用户同时上传照片和一句「漏液」，查询用图、用文还是融合，怎么避免一种模态淹没另一种？
- 对齐是在通用图文对上训的，线上说明却是内部工单腔，你改文本塔输入，还是加一层领域投影？

**推理回答：** 目标是跨模态近邻，约束是两边输出同一 \(d\)、同一归一化、由对比目标对齐。图–图可以走视觉空间，图–文必须共空间。用「图→图」和「图→文」两套探针，把「视觉特征坏了」和「对齐坏了」拆开验收。

## EMB-021. 时延大约 50ms 就要吐出 top-20，底库是十亿条 768 维。单机 HNSW 会先被内存、建图墙钟还是尾延迟打死？分片、量化、冷热分层按什么次序叠加？

**答：** 先撑不住的是内存：十亿 × 768 × 4 B ≈ 3 TB 原向量，图边再加一截（layer0 按每点约 2M 个 4 B 邻接估算，M=16 时大约 0.1 TB 量级），单机 DRAM 放不下；十亿次 HNSW 插入的构建窗口也远超可停机时间。50ms 的 P99 要求每次查询只碰一小片常驻数据，应先按向量切分片（每片工作集可预测），片内再上 IVF/PQ 或量化，热文档留高精度精排，冷数据放压缩编码甚至磁盘。不要先建一张巨型单图再指望把 efSearch 拧小来省延迟。

**深入展开：** 单机 HNSW 的三堵墙不同步：内存墙最先到（原向量 TB 级）；构建墙随后（在线图插入常数大，十亿点是天到周的离线作业，还要预留重建）；尾延迟墙在工作集开始换页或 scatter-gather 的慢分片拖后腿时出现——P50 仍可看，P99 被最慢分片和 GC/缺页决定。顺序：①哈希或随机分片，全局语义检索做 scatter-gather，分片数先让单片原向量或压缩后向量能进内存。例如压成每向量 64 B 的 PQ 后全库约 64 GB 编码，32 片则每片编码约 2 GB，再加上倒排列表或小图，比 3 TB 单图现实。②片内索引选 IVF-PQ 或量化后的图：先用样本训簇中心和码本，再批量灌入；nprobe、efSearch 用自己的「recall–延迟」曲线盯 50ms，而不是追求 100% 召回。③冷热：被查询频繁的文档（可用 QPS 或业务主键）留内存高精度，长尾量化后放 SSD，缺页路径不能占满 50ms 预算，冷查询要么异步补，要么接受走压缩距离。④精排：各片返回例如 5–10 倍 k 的候选，汇合后用更高精度距离或 reranker 截到 20。构建用离线批量，在线只追加到缓冲段，定期合并，避免在十亿图上点插。边界：按租户或类目能路由的查询不要广播全分片；不能路由的必须并行打齐，超时策略是「先返回已到分片」还是「失败」，要产品拍板。不要编造某块 GPU 卡的 QPS，吞吐以你们压测为准。

**后续追问：** 32 分片 scatter-gather 时，1 个慢分片怎样把 P99 从 20ms 拉到 80ms，你熔断它还是重试；热集合占比从 5% 涨到 40% 之后，分层还省不省得下内存；重建一张片要 6 小时，查询如何避开正在换的那片。

**扩展问题：**
- 在「十亿、768 维、目标 50ms、机器内存 256 GB」的假设下，估算至少几片、每片用哪种压缩，才能让工作集常驻。
- 为什么先上量化、后分片，可能把召回和尾延迟一起搞砸？你的顺序依据是什么。
- 增量每天 1% 新向量时，IVF 簇中心多久要重训一次，依据哪张分布图？

**推理回答：** 目标是 50ms 内给出可用的 top-20，而不是单图精确近邻。约束是 3 TB 原向量和十亿级在线插边都不现实。先切到可常驻的分片，再在片内用量化换扫描量，热数据保精度。验收看冻结集 recall@20、P99 和单片 RSS，而不是「索引种类够先进」。

## EMB-022. 纸上如何先估峰值 RSS、段合并、批量吞吐和建图墙钟，判断周末窗口能否把五百万条 768 维灌进 HNSW？在线逐点插边，还是离线建完再切流？日增约 2% 时，何时该停增量、改做全量重建？

**答：** 先拆四笔账：裸向量字节、图边字节、嵌入吞吐决定的墙钟、点插入或批量建图决定的墙钟，峰值 RSS 按最终索引的 2–3 倍留。五百万 × 768 × 4B 大约 14.3GiB 向量，\(M=16\) 时 layer0 边大约 0.6GiB，高峰常到几十 GiB 量级，不是「14GiB 机器就能灌」。周末窗口用离线影子索引建完再切流，比在线一条条插边更可控；每天约 2% 增量可以先点插，等冻结集召回掉、RSS/\(N\) 抬头、插入变慢或经历过大规模删除，再停增量做全量重建。

**深入展开：** 纸上计算（数字当示意，用你们自己的小样本校准斜率）：①`bytes_vec = 5e6 × 768 × 4 ≈ 1.54×10^{10}` ≈ 14.3GiB。②`bytes_graph ≈ N × 2M × 4`，\(M=16\) 得约 0.64GiB，上层边和主键再加一截，稳态索引大约 15–20GiB 加 payload。③嵌入与建图解耦：GPU 出向量，CPU 建图。若单卡大约 500–2000 条/秒，取 800 条/秒则 `5e6/800 ≈ 1.7` 小时只做嵌入。④建图：在线图插入常数大，用 1% 样本测平均插入毫秒数再乘 \(N\)，并留 2× 余量；例如样本上 0.8ms/点，外推大约 1.1 小时，再加合并和校验。⑤峰值内存：构建缓冲、未合并段、有时还有一份原向量副本，`peak ≈ (2～3) × (bytes_vec + bytes_graph)`，按 40–60GiB 这档去要机器，不要按稳态 16GiB 去要。段合并：若每 10 万条刷一段，五百万会留下大约 50 段；HNSW 段合并近似于局部重建，CPU 和 RSS 会再尖峰一次。周末批量应加大 flush 或关掉自动合并，灌完再统一 compact，避免边写边合并把自己打死。在线点插：发布简单，但图质量不如一次离线建，插入延迟随 \(N\) 涨，删除变墓碑，写 QPS 和查询抢同一张图。离线：从真相源扫出全部向量 → 建影子 → 校验冻结集 recall → 原子切路由 → 旧图保留回滚窗；磁盘要按两份索引估。每天 2% ≈ 10 万条，编码器不变就增量；触发全量重建的信号：冻结集 recall@k 连续下滑、RSS 涨幅明显高于 \(N\) 涨幅（碎片和墓碑）、插入 p50 明显变差、一次删掉两成以上、或换了 embedding（必须重建）。边界：窗口不够就先按分片并行建，而不是把单图插入线程加到互相抢内存；不要用别人集群上的「百万/小时」当自己的吞吐。

**后续追问：** 1% 样本是前 5 万条还是随机 5 万条，对插入耗时外推各有什么偏差；灌到一半磁盘只剩一份索引的空间，你停写入、改量化，还是改分片；增量连续 6 周、墓碑大约 15%，重建和不重建的 recall 与 RSS 你怎样在影子上对照。

**扩展问题：**
- 用下面数量级填一张周末计划表：嵌入小时、建图小时、compact 小时、切流和回滚预留，并标出哪一步最先撑破 48 小时。
- 为什么「在线插入 + 后台 compact」在每天 2% 时通常够用，在一次导入 40% 新文档时会先打满写放大？
- 峰值 RSS 若在合并阶段而不是插入阶段破线，你降 M、减并行段数，还是先把 payload 移出建图进程？

**推理回答：** 目标是周末窗口内交出一张可切流、可回滚的图，日常 2% 增长不靠天天全量。约束是墙钟 = 嵌入 + 建图 + 合并，峰值内存高于稳态，点插会积累碎片。先用字节和样本斜率估能不能灌完，默认离线影子切流；增量用召回、RSS/\(N\)、插入延迟当重建扳机。验收看窗口内切流成功、冻结集 recall，以及重建前后 RSS 与 \(N\) 成比例。

## EMB-023. 输出同为 768 维，检索却要在下周从 A 切到 B。为何不能把两类点混进同一张 HNSW？灰度期怎样并行两套空间，才能随时回滚且 A 查询绝不打 B 文档？

**答：** 维度相同只说明数组能放进同一索引结构，不说明几何兼容。A 和 B 的坐标轴是各自训练出来的，A 的查询在 B 的点云里分数会漂，名次变得不可解释——这就是换模型带来的 embedding drift。做法是双索引（或带空间版本的两份向量）：文档用 A、B 各嵌一次；请求按灰度带模型版本，查询只用对应编码器；切流看本域检索指标，随时把路由拨回 A。缓存键、归一化和指令前缀必须跟版本走。

**深入展开：** 变更队列用 B 回填新索引，可按天进行；影子流量让同一查询打 A、B 两套，记录 top-k 重叠、分数直方图和失败样例；再小流量切 B，看采纳或人工相关性，扩大或回滚。不要在同一张近邻图里插两种点：边会把两个空间的「近」织在一起，即使标了来源，查询仍可能穿过异空间的边。维度碰巧相同会让这种错误躲过 schema 检查，所以写入路径要强制 `model_id`。全库重嵌时间由 \(n\times\) 平均 token 决定，常是小时到天，旧索引必须继续服务。即使 B 在公开集更好，A 仍可能更贴你的查询分布；切流依据是本域指标。这和「维度对不上写不进去」不同，也和「已经切完质量崩了再急救」不同：这里要求切之前就能回滚。

**后续追问：** 影子流量里 top-k 重叠很低但人工相关性升高，该切还是该先查标注偏差；只重嵌热数据、冷数据仍留在 A，查询路由怎么避免跨空间比较；回滚时未完成回填的 B 索引要不要立刻删。

**扩展问题：**
- A、B 输出都已单位化，为什么分数直方图的均值仍可能差一截，阈值还能不能共用？
- 双写期间存储翻倍，除了缩短灰度窗口，按文档热度分批切的主要风险是什么？
- 按租户切灰度和按请求百分比切灰度，各自会污染哪些对照指标？

**推理回答：** 目标是换模型且可回滚，约束是「同一度量空间才能比距离」。维度相等不是同一空间的证据，所以物理隔离两套索引，并用版本路由查询。用影子重叠加本域相关性决定切流，而不是看维度数字和模型名字。

## EMB-024. 换了编码器、手册由 FAQ 改成法规条文、查询从五字变成整段粘贴后，生产那道「余弦不到 0.8 就告知生成侧无货」为何会成批拒答或成批放行？「库里没有相关文档」该如何校准？

**答：** 0.8 不是相关性概率，只是某套编码器、某种归一化下的几何值。换模型后各向异性和分数直方图会整体平移，FAQ 短句对的分数会挤在高位、法规长段的真相关可能只有 0.5 左右，短查询会把整片主题都顶到 0.75 以上。固定门槛因此会在一个域上全放行、在另一个域上全拒答。空库决策要按「模型 × 领域 × 查询长度桶」用有无金标的查询校准 top-1 分和分差，编码器一换就重做，不要把弱片段塞给生成模型碰运气。

**深入展开：** 已 L2 归一化时余弦等于内积，它比较的是方向，不是「有用」。各向异性：很多句向量挤在一个窄锥里，随机一对的余弦均值就可以相当高（随模型而变，有的分布中心在 0.4–0.7 这种示意区间）。模型 A 的相关对落在 0.35–0.55，模型 B 落在 0.72–0.90，抄 0.8 会把 A 的真相关杀光、把 B 的弱匹配全放行。领域：客服 FAQ 问句和答案句式接近，弱相关也能到 0.8+；法规段落回答了问题但用词正式、句子长，金标 0.48 并不罕见。查询长度：五个字落在主题质心附近，邻域分数都高、分不开「有/无」；整段粘贴约束多，分数拉开，top-1=0.52 反而可能是真命中。所以「0.8」不能跨模型、跨语料、跨长度复用。校准空结果：准备两类查询——池子里有金标的、以及确认无相关文档的（新功能、外域、故意找不到）。特征用 top-1 分数、top-1 与 top-2 的间隙、查询 token 数。按模型、领域、长度桶估一条门槛，或用逻辑回归把这些特征映成 \(P(\text{有相关})\)，在「有金标却拒答」和「无金标却放行」之间选工作点。换编码器、换池化或换指令前缀后分数整体平移，必须重拟合，禁止沿用旧 0.8。上线：低于工作点就不要把 chunk 喂给 LLM——模型会在低分上下文里照样编；应走「无证据」话术或澄清。辅助信号：分差很小说明一群差不多的近邻，更像主题盆地而不是单条命中。边界：阈值只解决「整窗都不够近」；窗内高分但答错是空间或切块问题，加高 0.8 救不了。不要用点击率反推门槛，没点开不能当不相关。

**后续追问：** 只按 top-1 分数设门槛，和再加上 top-1/top-2 分差，各会误伤哪类「两个都对」的查询；长度桶按字符切还是按 token 切，中英混查询会掉进哪一档；校准集约 150 条时空结果门槛的置信区间有多宽，你敢不敢直接上线。

**扩展问题：**
- 画出同一批查询在模型 A 和模型 B 上的 top-1 余弦直方图，标出 0.8 在两条分布上各处于什么分位。
- 不用绝对门槛、改用「对历史查询分数做分位数归一再设 10% 分位」，跨领域还会在哪里失真？
- 拒答之后若仍把 top-3 低分块悄悄塞进提示「仅供参考」，生成侧通常会怎样无视你的空库决策？

**推理回答：** 目标是「库里没有可用证据」时挡住生成，而不是维持一个全球通用的余弦数字。约束是分数分布随模型、领域、查询长度移动，0.8 没有跨分布含义。所以用带空结果标签的集合按桶校准 top-1 和分差，换模型就重做，拒答时不喂低分块。验收看空结果查询的拒答率和有金标查询的误拒率，而不是看平均余弦有没有靠近 0.8。

## EMB-025. 「发票」——检索框里只有这两个字。向量召回的三条结果分别是税务 FAQ、开票字段说明和报销制度，每条都沾边，却没一条答对。这类短查询，先补全意图，还是先靠关键词倒排缩小范围？

**答：** 先用词面/稀疏倒排按文档类型收束候选，同时用会话上下文或一次澄清补意图；不要让两个字的稠密向量自己消歧。短查询落在「发票」主题的中央，近邻什么类型都有，纯向量 top-k 会均匀地错。有上一轮技能或筛选就先拼进 query 再 embed；没有就 hybrid，并把制度/开票/报销拆开给用户或路由，比把 k 加大更有效。

**深入展开：** 两个汉字的信息量不够固定到单一文档类型，双塔输出的是该词的原型向量，库里所有发票 chunk 都在附近，排序被文档长度、中心性套话绑架，总论性质的制度往往更「像」这个词。HyDE（先让生成模型写一段假想答案再 embed）能把向量推离中心，但会引入幻觉主题且多一跳延迟，只能作为并行一路，不能当第一步。建议次序：①会话里已在报销技能，则扩成「报销发票」再检索。②倒排或字段检索拉标题/类型含「发票」的文档，按类型聚合，避免三类各一条塞进同一上下文让 LLM 编四不像。③受控扩展同义（发票/receipt），不要扩到「税务」这种过宽词。④用户选了意图或上下文已明之后，再用改写或 HyDE 补语义。⑤实体形态（订单号、税号）走精确查找，不要 embed。评估必须单列「极短查询」切片（例如 ≤2 个汉字或 ≤3 个 token）的成功率和答非所问率，全局 nDCG 会把它们平均掉。边界：C 端澄清有转化成本，可用类型先验（日志里两字「发票」有多少比例是报销）先给最可能的一类，并保留切换；B 端客服可以更早弹选项。加大 top-k 到 20 再交给生成模型，通常让选择更难，而不是更准。

**后续追问：** 首次访问没有会话时，怎样用类型先验减少澄清弹窗；HyDE 写成了增值税抵扣、用户要的是电子普票下载，你如何发现并降权这一路；短查询被补成「发票报销」之后，倒排还要不要留着。

**扩展问题：**
- 设计短查询路由：实体正则、BM25、稠密、澄清四路的优先级和超时。
- 如何从日志估计两字「发票」的真实意图分布，用来做类型先验而不是每次均匀召回？
- 为什么 top-k 加到 20 反而伤害生成质量，你用什么多样性或聚类限制上下文？

**推理回答：** 目标是两字查询落到单一可用意图，而不是三篇都沾边。约束是短向量落在主题中心、近邻类型混杂。先用倒排和上下文消歧，向量做补充，澄清当产品手段。验收看短查询切片的成功率和答非所问率，不看全局平均分。

## EMB-026. 夜里重做 RAG 那套索引，当时 90% 的 chunk 正文没改。为免去反复跑嵌入前向，同时挡住次日换模型后将旧向量灌入新库，缓存键得写入哪些字段？

**答：** 键必须绑定「规范化后的文本 + 模型标识 + 向量空间版本」（版本里写清维度、是否归一化、指令前缀），值是那条向量。文本没变且模型没变才允许命中；模型名、修订号或前缀一变，键空间整体失效，必须重新推理。缓存省的是 embedding 前向或接口调用，不是近邻查询。它和「相似问句直接复用答案」不是同一层：这里要求规范化后的输入完全同一。

**深入展开：** 夜间重建对每个 chunk 算 key，命中则写入新索引，未命中才打模型并回填。九成命中时，推理成本大约降到原来的一成，墙钟能不能从数小时降到数十分钟，还取决于索引写入速度。规范化必须稳定：Unicode 正规化、空白、是否去 HTML、切块边界，多一个空格就会 miss。容量：768 维 float32 约 3KB/条，独特 chunk 上千万时是几十 GB 级，通常放磁盘或对象存储，热查询文本才进内存表，并按模型版本整批淘汰，比单条 TTL 更安全。两段文本差一个空格，缓存不应命中——那可能是不同切块；若业务认为应当命中，要在哈希前写明规范化规则，而不是做模糊匹配。换模型当天：旧键可以留着回滚，新索引只允许新键写入。

**后续追问：** 键里要不要包含 tokenizer 版本和最大长度；同一文本作为 query 和作为 passage（不同前缀）能否共用一条缓存；多机同时重建时如何避免缓存未命中惊群、重复打满模型。

**扩展问题：**
- 规范化后来把全角数字改成半角，旧缓存是该批量改键迁移，还是整版作废？
- 缓存命中率已经 90%，重建仍很慢，你怎样判断瓶颈在向量库写入还是在拉原文？
- 用户侧高频相同问句的 embedding 缓存，TTL 为什么通常短于文档 chunk 缓存？

**推理回答：** 目标是「相同输入、相同模型不重复算」，约束是「不同向量空间绝对不能混写」。所以把模型与预处理写进键，命中只表示可复用的同一个几何点。用「换模型后新索引抽样与旧缓存向量是否几乎平行」做反例：它们不应几乎平行，且键必须 miss。

## EMB-027. 有人想把 1024 维的新点 PCA 压到 768，好沿用线上已按 768 维长成的图。何时这是赌近邻没散，何时必须另起索引并回填？

**答：** 维度不同就是另一套坐标，旧 HNSW 的边按 768 维近邻长成，不能把 1024 维点投影后 upsert 进去当「邻居关系仍成立」。PCA 或任何线性压到 768，只有在你们的业务冻结集上证明投影后的排序接近「完整 1024 维新索引」时，才是可回滚的捷径；否则是在赌多出来的维是噪声、且主成分碰巧对齐旧空间。默认做法：新维度新 collection，历史文档用新模型重算，双写、灰度、保留旧图回滚。零填充、截断、硬塞不同 d 的点都会静默损坏距离。

**深入展开：** 索引假定固定 d 和同一度量。1024 插进 768 会报错或被截断，截断等于丢掉模型认为有用的坐标。PCA 优化的是全局重构误差，检索要的是局部序：重构 MSE 好看，recall@10 仍可能掉。模型族、训练目标或指令前缀（如文档侧要加 `passage:`）变了，即使有人再训一个 768 头，也不能和旧向量混在一张图里比。必须双索引的信号：业务切片上投影后的 recall 相对完整新索引掉出你的预算；embed 后的范数或维度统计已经对不上旧库；灰度交叉检索（新 query 打旧库）分数分布塌缩。迁移：影子索引 ← 按热度优先的全量 re-embed ← 查询按模型版本路由 ← 比 top-k Jaccard、切片 nDCG、失败案例 ← 切流 ← 旧索引留窗口。缓存键含 `model_id` 和 `dim`。权宜扇出（旧文档旧索引 + 新文档新索引）只能用 RRF 合排名，分数仍不可比，不能当稳态。拟合 PCA 必须用新模型在你们语料上打出的向量，不能用随机公开句子——主方向会被网页语料带走。

**后续追问：** 同一模型官方带 768 和 1024 两个输出头时，截断 1024 当前 768 用是否仍然在赌；re-embed 要数天时，热查询如何避免新索引还是空的；双索引存储翻倍，你砍哪边副本、保留多久回滚窗。

**扩展问题：**
- 写迁移状态机：未回填 / 热数据完成 / 全量完成 / 切流 / 回滚，每个状态查询打哪张表。
- 怎样同时用新旧 top-10 Jaccard 和业务 nDCG 决定能不能切 100% 流量？
- 若坚持 PCA，主成分用哪批向量拟合，为什么不能用一万条随机公开句子？

**推理回答：** 目标是新模型收益落地且旧检索可回滚。约束是不同 d 与旧图不兼容，PCA 不保证近邻序。默认重算 + 双索引；只有冻结集证明投影保序才走捷径。验收看新索引切片指标和回滚时延，而不是「维度数字对齐了」。

## EMB-028. 公开风格离线集几乎不动，但「引用了错文档」类工单在 embedding 灰度 10% 流量的当天翻倍。半小时内如何区分：旧向量混写入新索引、推理时丢了 L2 归一化，还是域内分布真的发生了 drift？

**答：** 先保证能一键切回旧索引，并核对「查询所用 `model_id` = 被搜索引的 `model_id`」。用同一批线上失败查询做三组对照：旧 query 打旧库、新 query 打新库、新 query 打旧库。交叉检索分数整体塌缩或飙到无意义、维度或 `||v||` 对不上，就是混写或没归一化；新空间内部范数和分数都自洽、只在业务失败查询上金标名次系统性后退，才是真 drift。公开风格集不动，恰恰说明它看不见你们的术语切片，不能拿来给事故续命。

**深入展开：** 三十分钟决策树：①配置。灰度是否 100% 打到新 encoder，有没有旧 replica 被均衡进来；日志里的 `model_version`、`dim`、向量范数。点积检索若丢掉 L2，长度大的文档会占满 top-k，失败面很宽、公开集若碰巧范数均匀就看不出来。②混写。库内 `embed_version` 直方图若双峰，同一张图里近邻无意义，症状是「有的查询还行、有的像随机」。新 query × 旧库的 top-k 与旧对照的 Jaccard 会极低，分数分布相对旧×旧平移。③真 drift。新×新自洽，但失败查询集中在内部专名、易混政策等切片，金标排名后退。这和业务评测盲区是一类问题，此刻先回滚，再离线补切片，不要在线上拧阈值或 nprobe。④其它快速项：距离函数被改成 L2/IP 与训练不一致、文档指令前缀漏加、预处理（去 HTML、拼标题）和建库时不同。工单翻倍而公开集不动，优先当「分布不匹配 + 配置/混写」处理，而不是当模型随机坏掉继续放量。回滚窗口内不要重建那张出事的图，保留现场向量抽样。

**后续追问：** 只有中文专名查询挂、英文 FAQ 正常，更像 drift 还是分词/前缀；混写大约 5% 文档够不够让引用错误率翻倍；回滚后影子索引还要不要继续回填。

**扩展问题：**
- 设计三组对照检索，画出混写、未归一化、真 drift 各自预期的分数直方图和 top-k Jaccard。
- 灰度只有 10% 时，怎样在 30 分钟内凑够失败查询样本，而不是等一天工单？
- 迁移清单上哪三件事必须做成发布门禁，才能避免这类事故再进生产？

**推理回答：** 目标是先恢复引用正确率，再解释原因。约束是三种根因表面都是质量掉，但混写和配置能用交叉检索在半小时内证伪。先锁版本一致性并准备回滚，再用失败查询对照。真 drift 回滚后走双索引加业务评测，不在事故中调阈值。
