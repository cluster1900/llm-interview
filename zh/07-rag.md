## RAG-001. 公开材料早已写进权重，面向内部的问答机器人是否仍要另做检索层？

**答：** 要。参数知识停在训练截止日，看不见未公开的制度、工单和配置，也无法在不重训的情况下替换一条过期规定。检索层把“当前可引用的证据”在推理时拼进提示，使答案可更新、可追溯，并把数字和条款的来源从权重改成上下文。若问题只依赖稳定常识且允许过期，可以不检索；一旦涉及私有事实、必须对得上的数字，或必须指出处，就应检索。

**深入展开：** 一次问答的数据流是：用户问题 → 检索器从企业语料取出 k 段 → 提示构造器按 token 预算裁剪并标注来源 → 生成模型在这些段上作答。参数里的世界知识仍会参与措辞和推理，所以检索并不能消灭幻觉，只是把“事实应从哪里来”换成了当前语料。量级上，改一条制度若走继续训练，往往要准备样本、排队训练和回归，耗时按小时到天计；走检索则只需重切并重嵌入该文档，通常是秒到分钟级。边界条件：语料为空、权限过滤后为空、或检索分数低到不可用时，应拒答或声明证据不足，而不是回退到参数里“好像记得”的版本——那一版可能已经作废。

**后续追问：** 哪些内部问题可以明确标注“无需检索”？检索片段和模型记忆冲突时，提示里怎样强制以片段为准？检索层宕机时，你选择拒答、降级到参数回答，还是只读缓存，依据是什么？

**扩展问题：**
- 同一套制度每周改一次，用检索更新和用继续训练更新，回滚路径差在哪？
- 生成模型被要求“只能使用检索片段中的数字”之后，还需要哪类校验才能拦住口算编造？
- 把检索做成可开关的路由后，你用什么线上指标判断某类问题不该再开检索？

**推理回答：** 先列出内部问答的硬约束：私有、要新鲜、要能指出处。再对照参数知识的三个缺口——截止日、看不见私有语料、不能定点修补一条规则。任一缺口成立就需要检索层；再用“更新一条制度的代价”说明为什么改索引比改权重更合适。最后用“无证据则拒答”守住过期参数被当成现行规定的风险。

## RAG-002. 当季价格仍被说成去年的，尽管回执已经能用本公司口吻。要继续微调，还是补上检索？

**答：** 口吻、栏位、固定话术是稳定行为，适合微调或强模板；会过期的价格、政策、库存是可变事实，必须检索或查业务系统，不能靠权重记住。这类事故应停止把价目表写进监督数据，改成检索或工具出数，微调只保留语气和格式。两条可以叠用，但各管一层，冲突时以检索结果为准。

**深入展开：** 微调改的是风格、术语和任务格式的条件分布，更新周期通常是天到周；价目可能一天一变，写进参数后不可引用、也难精确删除。检索或价格接口改的是每次请求可见的外部状态，并能带上生效日期。反例也很清楚：模型不会填工单 JSON、总爱加表情，再多价目文档也救不了，那才微调或做受限解码。推荐组合是小规模 SFT/偏好对齐锁定格式和拒答话术，知识层走检索；提示写明“数字以检索结果为准，忽略记忆中的价格”。评估拆开：风格遵从率、价格准确率、引用率。不要把“领域微调”当成新鲜度方案——它解决的是怎么说，不是现在是多少。

**后续追问：** 只有两百条历史工单能不能微调出稳定口吻；价格在检索里是对的、模型仍改成整数，算检索失败还是生成失败；何时该直接查交易系统，而不是查 PDF。

**扩展问题：**
- 做一张分流表：事实过期、格式不对、术语不会、安全拒答，分别对应检索、微调、规则还是工具。
- 微调语料里误含旧价格，上线后如何发现并清洗？
- 检索和模型记忆冲突时，怎样在提示和解码约束里让检索胜出？

**推理回答：** 先给错误分类：可变事实还是稳定行为。事实走过期 → 检索或工具；行为不对 → 微调或模板。禁止用监督数据记忆价目。用价格准确率和风格遵从率分别验收。

## RAG-003. 离线建库链路和在线提问链路，各自抽掉哪一环就绝对不能明早接员工手册问答的流量？

**答：** 离线至少要有可重复的采集与解析、按结构分块、写入向量（以及可选的词法）索引，并把块 ID 映射回原文、章节和版本。在线至少要有：鉴权后的检索、按身份过滤、组装带出处的上下文、生成，以及把命中的块 ID 和模型输入输出打进日志。缺解析或索引，线上无证可查；缺过滤或日志，则无法证明没有越权、也无法事后对一条错答追责。

**深入展开：** 离线是批处理写路径：连接器拉入手册文件 → 解析器抽出正文和标题树 → 去掉页眉页脚和重复目录 → 按条款或段落成块 → 嵌入模型按批（例如每批 32–128 条）写成数百到一千维左右的向量 → 写入 ANN 索引，同时把 raw_text、doc_id、section、acl、version 写入元数据表。在线是读路径：鉴权 → 可选的查询规范化 → 检索 top-k（常见先取 20–80）→ 可选重排到最终 4–8 段 → 按生成窗口拼提示 → 调 LLM → 返回答案和引用。上线前的最小闭环不是“接上模型能说话”，而是对几十条真实问题跑通：每条答案能追到块 ID，无权限文档从未进入提示，索引构建时间和查询 p95 落在发布单里的预算内。监控至少看空检索率、最新文档是否可查、引用块是否仍存在。

**后续追问：** 元数据表和向量索引差一个版本时，在线请求会看到什么，怎么修？第一版若砍掉重排和查询改写，哪一步仍绝对不能砍？手册同一条款有两个生效版本，读路径哪一步必须先选定版本？

**扩展问题：**
- 解析失败和嵌入失败分开重试，还是整篇文档重跑，怎样避免索引里留下半成品块？
- 权限过滤放在检索前做预过滤，和检索后做后过滤，对召回和延迟各有什么代价？
- 你准备哪几条金丝雀查询，用来区分“索引在但答案全错”是切块问题还是提示组装问题？

**推理回答：** 按写路径和读路径拆系统：写路径保证证据进得去、能按 ID 回到原文；读路径保证按身份取证、按预算生成、按日志可追。用“权限不泄漏 + 块 ID 可回放”作为放行条件，把重排、改写当成可后加的质量件，而不是上线门禁。

## RAG-004. 退款条款需要精确命中，二十页政策还要能概括。嵌入上限 512 token、生成窗口 8k，切块该取多长？

**答：** 不要共用一个长度。条款检索优先短块，让关键句在 512 的窗口里占足够比例，例如 128–256 token，并把条款号留在元数据里。概括题需要更大的语义单元，可用接近 400–512 token 的节级块，或先用短块命中再回取整节。512 是嵌入硬上限：超长块在建索引时就被截断，等于后半段从未进入向量。

**深入展开：** 块长接近 512 时，一块里若只有一句相关、其余是邻节噪音，向量会被噪音拉偏，精确条款的召回下降。块长落到 64–128 token 时，主语、例外和适用条件常被切开，生成只能看到半句。20 页政策大约是数千到一万 token 量级，8k 生成窗口还要放下系统提示、对话和引用标记，装不下整本，概括题也应检索若干节级块而不是塞全文。操作上先按标题切出节，再在节内用目标长度切；用同一批问题分别试 128/256/512，看条款题的 recall@10 和概括题的要点覆盖率，再锁定长度。重叠是次要修补，常见先加约 10%–20% 盖住跨界句子，但不要用重叠代替选对长度。

**后续追问：** 嵌入截断和生成截断同时出现时，怎样从日志判断是哪一端丢了后半段？短块检索再回取整节，索引里要不要存两套文本？中英文混排按 token 切和按字符切，块长稳定性差在哪？

**扩展问题：**
- 退款例外写在下一节，短块命中主条款后，你用什么回取规则把例外一起带给生成模型？
- 512 token 的块在 8k 窗口里大约能放几段，系统提示和引用标记要预留多少？
- 若换成输入长度到 8k 的嵌入模型，会不会把块直接拉到 2k，理由是什么？

**推理回答：** 先写出两个硬约束：嵌入不能截断丢证据，生成窗口要同时放下多块。再按问题类型拆成“精确匹配要短、综合叙述要宽”，用“短块召回、节级回取”同时满足，而不是找一个万能默认值。最后用分长度的离线召回和要点覆盖做选择。

## RAG-005. 用户带着服务名和变更单号来问，而运维手册里该块原文只有「将超时设为 30 秒然后重启 worker」。词法检索和稠密检索要都能命中，入库阶段该补上什么？

**答：** 块一旦离开全文，服务名和单号这类文档级指代就丢了。写入词法索引和向量索引之前，先为该块生成一段独立可读的短前缀，写明所属服务、章节、环境和关联变更，再把前缀与原文拼接后一起做 BM25 和嵌入。查询里的服务名、单号就能对上前缀的字面和语义，而不必指望操作句自己重复这些实体。

**深入展开：** 生成前缀时把该章或整篇手册放进提示，要求用一两句话说明“这段在文档中的位置和指代对象”，例如“本段出自支付结算服务线上故障手册，对应变更单 CHG-1842，讨论网关超时”。前缀通常只有几十个 token，以免淹没原文操作。同一文档的多个块共享文档前缀，索引阶段可以复用提示缓存，费用主要是每块一次短生成；查询阶段不再为前缀调模型。文档改了，只重做受影响块的前缀并更新两条索引。不要把前缀写成冗长摘要，否则 BM25 会被摘要词带偏；也不要只把服务名放进元数据过滤字段——用户把服务名写在问句里时，过滤字段帮不到词法和向量匹配。文档长过生成窗口时，先按章切开，再在章内写前缀。

**后续追问：** 只拼接文件名和标题、不让模型写前缀，通常还能找回多少这类块？前缀同时进 BM25 和向量，会不会引入章节级停用词、把整章都召回来？手册周更时，怎样避免每次全库重写前缀？

**扩展问题：**
- 怎样构造“去指代”的查询-块对，量化加前缀前后的召回变化？
- 制度、对话日志、代码注释三类里，哪类最值得付这笔索引期生成费用？
- 写前缀的模型和检索嵌入模型不是同一个，值不值得用更强的生成模型，成本怎么摊到每篇文档？

**推理回答：** 从失败个案出发：查询词落在文档级实体上，块正文只有操作和代词。推出必须在索引时把实体写回可搜索文本。再比较元数据过滤、人工标题和模型写前缀：只有进入词法和向量正文的文字才能被两类检索同时用到，并靠短前缀避免摘要反客为主。

## RAG-006. 产品手册大约四十本、每本大约二十页且几乎冻结，提示缓存命中率很高。此时该整本填进窗口还是仍走检索？若每天出一版，结论怎么变？

**答：** 当前产品相关的手册能稳定放进窗口并留出回复余量、内容几乎不变、前缀缓存能摊掉 prefill 时，直填（整本或少数几本）更简单，也更利于跨章节对照。一旦变成每日一版，缓存天天失效，旧页还必须立刻消失，这时检索加版本过滤更合适。需要按用户裁掉无权限章节、或必须引用到具体段落时，同样更该检索。

**深入展开：** 先做容量粗算，而不是看“长窗口”标称值。例如每页大约 500–800 token，20 页 × 40 本就是大约 40 万到 64 万 token，很多模型仍然装不下全部 40 本，只能先按产品路由再直填 1–3 本。直填的好处是少维护切块边界，目录内对照稳，前缀不变时重复请求几乎只付增量。坏处是中间章节利用率差、无关章变成噪声、冷启动 prefill 贵、引用粒度容易停在文档级。检索则按需取证、天然带块级引用，更新只重建脏文档。每日一版后，缓存键必须含手册版本，命中率会掉，直填的成本优势消失；检索侧用版本号过滤即可。决策用自家题比较准确率、P95、单次费用和权限误放行，而不是比较窗口广告长度。注意：这是线上怎么切流量，不是“如何公平评测两条路”的实验设计题。

**后续追问：** 只塞进 1 本手册时，章内还要不要再检索；缓存前缀里若拼进用户名会怎样破坏命中；跨手册对照题，直填 3 本和检索 top-20 谁更稳。

**扩展问题：**
- 单本从 20 页涨到 200 页、窗口标称 128K，你如何重新做容量和位置扫描？
- 全文摘要、逐条对照、单点查条款，分别更偏向直填还是检索？
- 先按权限裁剪再直填，和带访问控制的检索，安全验收有何不同？

**推理回答：** 先确认 token 是否真能装下并留输出，再看更新频率是否允许缓存。装得下且稳就直填；更新快、要权限或段级引用就检索。用自家负载在两条路上跑，不预设哪边永远便宜。

## RAG-007. 长上下文已经能上线，整篇直填与 RAG 要用什么尺度公平对照？
**答：** 在同一任务集上比较答案正确性、证据覆盖、权限隔离、延迟与总成本；按文档长度、更新频率和多跳需求分层。不能仅比较模型单次调用费。
**深入展开：** RAG 有漏检风险，全文输入有噪声和长上下文退化风险，可采用检索后扩展上下文。
**后续追问：** 什么任务适合两条路径动态路由？可按文档长度、证据分散程度、更新频率和质量门槛选择，但路由规则本身也需要评测。
**扩展问题：**
- 如果全文方案答对而 RAG 答错，怎样区分漏检、分块破坏与生成错误？
- 如何把索引维护、文档更新和权限过滤成本纳入两种方案的总成本比较？
**推理回答：** 用真实工作负载找成本质量边界，不预设全文或 RAG 必然更优。

## RAG-008. 答复里的超时秒数被用户判为错误。排查链路时先后次序如何排，每一级该盯什么迹象？

**答：** 先分清是证据没进库、进库了没被召回、召回了没进提示，还是提示里已经是对的秒数、模型仍写错。对应地：解析和分块看原文数字是否完整留在块里；检索看金标准块是否进入 top-k；重排和组装看它是否在截断后仍留在模型输入中；生成看输入已正确时输出是否偏离。前几层没排除之前，不要先换更大的生成模型。

**深入展开：** 准备一条诊断用例：问题、应命中的 chunk_id、应出现的数字（例如手册写 30 秒）。解析失败的信号是原文在表格或两栏排版里，块中只剩残句或数字丢失。分块失败是“30”和“秒”被切开，或例外条件落到下一块。检索失败是金标准块排名落在 k 之外，诊断时至少看 k=20/50/100 三档。重排或组装失败是块在初检里很靠前，拼提示时因 token 预算被丢掉。生成失败是模型输入里已有“超时 30 秒”，答案写成 3 或 300。每一层打结构化日志：chunk_ids、分数、截断位置、模型输入哈希，才能把一次错数归到单层。定位应先回放这一条 trace，而不是先重跑全库嵌入。

**后续追问：** 召回指标已经达标但数字仍错，生成侧你还对哪些字段做断言？表格被解析成乱序纯文本时，回归集最少要补哪类文档？同一数字在两个块里不一致，哪一层不该悄悄选一个？

**扩展问题：**
- 怎样用只重放检索、不调用生成模型的离线 replay，把定位成本和生成费用分开？
- 解析器和分块器的单元测试各自至少要覆盖哪些版面：纯条款、有表、有页眉页脚？
- 线上只采样 1% 的完整 trace，偶发截断被漏掉的风险你怎么估计？

**推理回答：** 目标是找出“正确秒数在哪一层离开了原文”。把流水线当成单向数据流，用金标准块 ID 和目标数字做分层断言：源头完整性 → 召回覆盖 → 提示留存 → 生成一致。哪一层断言失败就停在哪一层改，避免把切块或截断问题当成提示词问题。

## RAG-009. 嵌套条款的合同、成对短问答的 FAQ、几乎无标题的会议纪要，分别该配固定长度切分、语义边界切分还是按标题递归切分？

**答：** FAQ 按问答对切开，或用固定长度，因为检索单元已经是一对问答，不必再找主题边界。合同按标题和条款号递归切：先章、再条、再句，直到落入长度上限，避免把“但书”和例外切到下一块。会议纪要没有稳定层级，用句边界上的固定长度，或在相邻句嵌入相似度明显下降处切开；不要假装它有目录。

**深入展开：** 固定长度是滑窗，按 N 个 token 切、可选重叠。块大小均匀，索引体积和批嵌入时间都好比；代价是表格行、编号列表和“第 7.2 条之例外”容易拦腰截断。递归切依赖解析器给出的标题树：节点文本不超过上限就成块，否则按子标题或段落再切。合同和制度的收益主要来自“块边界对齐阅读单位”。语义切对相邻句子算嵌入，相似度低于在自家语料上标定的阈值就分段；纪要里话题跳变时有用，但嵌入调用次数大约随句数增长，建索引成本明显高于固定切。可以混合：能识别的标题先递归吃掉，剩余无结构正文再固定切。验收不要只看平均块长，要抽样看：例外是否和主条款同块、FAQ 的问和答有没有被拆开。

**后续追问：** 解析器把条款标题认错时，递归切会怎样恶化，回退策略是什么？语义切阈值偏高或偏低，块长分布会变成什么样？同一份约 100 页的合同，三种切法的块数和建索引时间大概差多少？

**扩展问题：**
- 合同是扫描件、只有版面没有真实标题树，你还坚持递归切吗？
- 语义切用的嵌入模型和线上检索用的必须是同一个吗？
- 切完后块长方差很大，对批量嵌入和 ANN 建索引各有什么影响？

**推理回答：** 先看文档有没有可靠的结构信号。有标题树就递归，让块对齐条款；已经是问答对就按对切，避免过度设计；无结构就在固定切和语义切之间用成本和话题完整性做取舍。用“例外条款有没有被切开”这类结构断言验收，而不是抽象比较三种算法的名声。

## RAG-010. 生成总缺同节里的定义与例外，尽管条款召回已经够准。把块直接做大为什么不是办法，而要把召回粒度与送入模型的上下文粒度拆开？

**答：** 检索要的是可区分的短向量，生成要的是完整论域。条款、例外和术语定义常常隔着两三段，一块大到能装下整节时，向量会被并列条款平均掉，命中反而变差。正确拆法是：子块（大约 100–250 token）只负责召回，命中后再映射到父块（一节或一页，大约 800–1500 token）送给模型。加大分块是在同一个粒度上同时牺牲可检索性和可读性；父子分离是让两个目标各用各的窗口。

**深入展开：** 入库时按标题切开父块，父块内再切子块，子块向量进 ANN，元数据带 `parent_id` 和字符偏移。查询：ANN 取子块 top-k → 去重父块 → 按原文顺序拼给模型，必要时只扩同一父块的相邻一句，而不是整章。政策、手册、合同最受益，因为“本条所称 X”和“但下列情形除外”经常不和命中句在同一窗口。边界：父块若涨到整章（数千 token），噪声和“中间丢失”会回来；许多子块映射到同一父块时，top-8 子块可能只展开成 2 个父块，表面召回很高、证据覆盖很窄。父块还不能跨权限或跨版本拼接。不要把这套和“重叠滑动窗口”混用到同一层——重叠解决的是切断，父子解决的是粒度为两用。

**后续追问：** 父块按小节还是按页切，遇到没有标题的纪要怎么办？子块 top-8 塌缩成 2 个父块时，你补检索还是强制每个父块只留最高分子块？父子块权限不一致时以谁为准？

**扩展问题：**
- 子块 128 token、父块 2k token，重排应该打子块分数还是展开后的父块分数？
- 若父块包含与问题无关的并列条款，怎样在展开后裁掉而不切掉例外句？
- 如何用“子块命中但父块未覆盖定义句”的比例证明父子方案比单纯加大 chunk 更值？

**推理回答：** 目标拆成可检索的区分度和可生成的完整论域，二者对窗口长度的要求相反。比较“单一大块 embedding”和“小子块召回 + 父块投喂”在条款命中与例外覆盖上的表现，并检查父块膨胀后的噪声。用子块 recall@k 和父块是否含定义/例外验收。

## RAG-011. 「过期令牌应当如何刷新」是一类查询，「RFC-214」里的 4.2 节是另一类。纯向量通道和纯关键词通道各会漏掉哪一种，两路候选名单该如何合成？

**答：** 编号、章节号、错误码适合词法检索（如 BM25）：这些稀有字面不在块里就几乎召不回。换一种说法的操作问题适合稠密检索：词法对不上 refresh、rotate、renew 这类同义表达。两路各取 top-n，用只看名次、不看原始分的融合（例如 Reciprocal Rank Fusion）合成一路，再截断给重排或生成。只调一路的分数阈值，往往顾此失彼。

**深入展开：** BM25 靠词频和逆文档频率，对 RFC-214、4.2、ECONNRESET 这类稀有 token 很敏感，对同义改写和轻度错字弱。稠密检索能把“令牌过期怎么刷新”对到讲 rotate expired credentials 的段落，却也可能把另一个也带 214 的工单、或把第 4 节概述当成近邻。RRF 对每个文档累加 Σ 1/(κ + rank_i)，κ 取几十量级（实现里常见约 60）以减弱极端第一名。两路分数量纲不同：余弦大约在 -1 到 1，BM25 可以到几十，直接加权相加前必须各自归一化。每路先取 20–50、融合后再留 20–80 进下一层，对多数企业文档够用。用户把编号写在句子中间、抽取过滤器失败时，融合仍能靠词法一路保住该文档。

**后续追问：** κ 过大或过小时，稀有编号的最终名次会往哪偏？中文分词把“令牌过期”切错，BM25 一路会不会整路失效？两路召回高度重叠时，融合还有没有收益？

**扩展问题：**
- 稀疏侧从 BM25 换成由模型估计词权重的稀疏向量，能补上哪些字面漏洞？
- 怎样用“含编号查询 / 纯改写查询”两套切片，证明融合两边都赚到了，而不是只看一个总分？
- 融合放在权限过滤前还是后，空结果率和泄漏风险各是什么？

**推理回答：** 先用两类真实查询暴露单路盲区：标识要字面，操作要语义。推出必须保留两路召回。再选名次融合避开分数不可比的问题，并用分片子指标证明两路都在工作，而不是只优化一个加权总分。

## RAG-012. SKU 开始串到别的产品线时（已从十二条扩到八十条），相关度过滤该做成 ANN 前置过滤还是召回后再裁？权限字段能否沿用？

**答：** 产品线、语言、地区、时间这类相关度过滤，可以预过滤，也可以多取再切，取决于过滤有多“窄”、以及索引是否支持带条件的近邻搜索。权限和租户字段不能走“先检索再扔掉”：敏感块一旦进入提示就算泄露。SKU 混入是范围没写进查询，先保证入库 metadata 准确，查询时强制带上当前产品范围。

**深入展开：** 预过滤在 ANN 检索时带 payload 条件，只在子集里找近邻。条件很窄（例如 `sku_id = 当前型号`，子集只有几千块）时又快又干净。若实现其实是“先全局搜再 bitset 过滤”，而过滤又极严，候选会被滤光，recall 骤降——这时应多取（要 20 条就先取一两百）或按产品建分区索引。后过滤实现简单，但会把算力花在无关 SKU 上，条件一严还可能凑不满 k 条。字段要结构化、枚举稳定；不要把自由文本规格拿来做等值过滤。时间用范围条件。权限必须走独立链路：chunk 带允许列表，查询注入用户身份，索引层强制命中，缓存按用户隔离。评测用带错误 SKU 的干扰集，看答案是否引用了范围外文档，以及过滤后 recall@k 是否塌。

**后续追问：** 用户没说产品名、会话状态里才有当前 SKU 时，过滤从哪注入；预过滤得到 0 条要不要放宽再查；同一文档属于多条产品线，metadata 用多值还是拆成多条 chunk。

**扩展问题：**
- 什么情况下按产品线分片索引，比全局索引加过滤更合适？
- 过滤条件和向量分数如何一起用，避免“范围对但语义差”的块排在前面？
- 怎样用越权测试证明权限过滤没有走“检索后再切”的捷径？

**推理回答：** 先分清过滤目的。相关性可以在预过滤和后过滤之间折中；授权必须在检索前强制生效。SKU 变多后选择变窄，优先分区或带条件的 ANN，并用范围外引用率验收。

## RAG-013. 一百万条商品描述均长约 200 token，单向量又常把品牌、尺码、「儿童不宜」糊成同一主题。查询还同时咬住这三条。后期交互按 token 计分时，描述分怎么算，库里大约要存几条向量？

**答：** 后期交互不把整段描述压成一个点，而是查询和文档都为每个 token 保留一个向量。打分时对查询的每个 token，在文档所有 token 里取最大相似度（MaxSim），再把这些最大值相加。这样品牌、尺码、“儿童 / 不”可以分别对齐到描述的不同位置。存储上，100 万条 × 200 token 就是约 2×10^8 个 token 向量，比“每条商品一个向量”大约多两个数量级。

**深入展开：** 编码阶段查询和文档仍分开走，所以文档 token 向量可以离线算好，交互推迟到打分。若 q_i、d_j 已做归一化，则 s(q,d) = Σ_i max_j (q_i · d_j)。某个查询约束在描述里找不到近邻时，该项贡献接近 0，总分会被压下去；单向量却可能只因品牌很近就排前。空间按示例粗算：token 向量 128 维、float16 时每 token 256 字节，2×10^8 个约 51GB 只算向量载荷，不含倒排或聚簇结构；每文档一个 768 维 float16 向量大约只需 1.5GB 量级。实际系统会用残差压缩和聚簇剪枝把体积打下来，但仍远高于单向量方案。查询只需编码一次，然后在预计算索引上做剪枝 MaxSim，既可当第一段检索，也可当对几十到几百候选的重排。极短描述 token 很少，区分度下降；查询很长时求和项变多，要事先约定是否按查询长度归一化。

**后续追问：** MaxSim 对更长的描述是否天然偏心，要不要除以查询 token 数？token 向量不归一化、改用 L2 距离，检索结构怎么改？和“单向量召回 + 交叉编码器重排”比，什么流量才值得付这笔存储？

**扩展问题：**
- 平均 200 token 里有大量功能词，索引阶段丢掉这些 token 向量会伤到哪类查询？
- “不适合儿童”被切成多个子词后，怎样避免 MaxSim 只对齐到“儿童”而忽略否定？
- 只改一条商品描述时，token 级索引的局部更新比单向量索引难在哪里？

**推理回答：** 从单向量无法同时保存三个硬约束出发，引出按 token 保留、到打分再交互。用 MaxSim 说明多约束如何分别对齐，再用 100 万 × 200 的乘法把存储代价算成可讨论的数量级，让精度和空间可以权衡。

## RAG-014. 原句是「不要含税的报价」，改写却扩成「报价流程」，召回全变成制度操作指南。如何约束查询改写，使否定词与实体不被丢掉？

**答：** 改写是为了补检索用语（同义词、子问题、假想段落），不是把用户意图升格成一个主题。必须保住否定、实体、数字和约束，并且始终保留原始问句作为一路查询。“不要含税”应扩成“未税报价 / 税前单价”这类同义检索式，而不是“报价流程”。上线要有改写门：实体是否还在、极性是否被翻转。

**深入展开：** 常见变换用途不同。多查询：原句加两三条同义检索式再融合，最稳。分解：把多跳问拆成可独立检索的子问。后退一步问更抽象的原理，对“不要含税”这类带约束的题很危险，因为正好抽掉修饰。HyDE 先写一段假想答案再做 embedding，对缺关键词的概念题有用，但对必须字面命中的税、型号、否定偏弱，应与关键词路并行。漂移的根因是生成式改写没有接地，把“不要 X”写成“X 的流程”。约束做法：先抽槽位（产品、是否含税、币种）再做结构化改写；改写后做实体和否定覆盖检查，失败则只用原句；融合时原句的关键词检索必须在。评估看改写前后的 context recall，以及“约束被丢”的专项集，不要看改写句子好不好读。改写通常是一次小模型调用，可与意图分类并行。

**后续追问：** HyDE 的假想答案写错数字，会不会把向量拉进错误簇；多查询融合如何避免 top-k 被同一文档占满；要不要把对话里提到的型号写进改写。

**扩展问题：**
- 定一条规则：出现否定词时禁止后退式改写，只允许同义词扩展。
- 如何自动检测改写后极性翻转，例如含税变成不含税？
- 分解出的子查询有一路失败时，还要把部分证据交给生成吗？

**推理回答：** 改写的目标是提高可检索性且不改变约束。先锁住必须保留的槽位，再允许同义扩展。原句始终留一路。用约束丢失率验收改写器，而不是用流畅度。

## RAG-015. 一线研发搜「熔断阈值」却命中电气保险丝材料，产品内部代号在向量里也被冲淡。该改术语表、查询扩展还是嵌入空间？又如何防止把常用词钉死在一种用法上？

**答：** 先保留原始术语做混合检索：词法通道保住“熔断”“阈值”和产品代号的精确 token，向量通道提供同义表达。查询扩展只许走受控词表（一份术语对一种工作区语境），禁止让改写模型把“熔断”泛化成“断开/保险/保护”。词表不够再考虑把术语定义写成独立块，或在领域句对上继续训练编码器。不要做全局同义替换——把“熔断”永远绑到微服务保护，运维问电气安全时会系统性失召。

**深入展开：** 失败分两类：多义词（熔断/保险丝/交易熔断）和罕见代号（预训练里几乎没见过的内部名）。混合检索对第二类立刻有效，因为 BM25 不依赖语义邻域。第一类要靠语境：词表带限定（“服务治理/交易/电气”），或在查询前用分类器选工作区，再启用对应同义集。向量侧的稳妥补法是把“术语 + 定义 + 禁用义”做成短文档参与检索，而不是改 tokenizer。若仍不够，才用领域对比学习微调 embedding，并必须看通用查询回归。边界：自动同义扩展会把代号译成普通名词；拼写纠错会改掉合法的内部缩写。评测集要切四片：缩写、别名、历史名、不含术语的通用问法。

**后续追问：** 工作区分类错了，把交易熔断词表加到工程查询上，你如何回退到“只保留原词”？领域微调后通用 FAQ 的召回掉多少算不可上线？词表由谁维护，过期别名删不删？

**扩展问题：**
- 同一代号在两个产品线含义相反，不靠用户选产品，检索如何避免串线？
- 只加定义块、不改编码器，对“只出现代号、从未解释”的查询够不够？
- 怎样用术语片召回和通用片召回的双指标防止词表把日常用语绑死？

**推理回答：** 约束是原词不能丢、义项不能全局唯一化。按失败类型排序手段：词法保 token，受控扩展加语境，最后才动向量空间。用术语/通用双切片召回证明没有把通用词绑死。

## RAG-016. 生成总把排名第十二的段落当作证据，尽管一阶段 Recall@50 已达标。代价更高的打分器该插到哪一环、候选截到多少？

**答：** 插在初检之后、拼提示之前：用交叉编码器或同等的查询-段落点对模型，对这约 50 段重新打分，把能支撑答案的 4–8 段顶到提示里更靠前、或模型更不易忽略的位置。候选数等于已经覆盖金标准的初检 k，再往上加收益很快变小，延迟却近似线性增加。若重排后该段仍进不了最终 m 段，再查组装截断或生成，而不是先换更大的生成模型。

**深入展开：** 初检（双编码器、BM25 或两者融合）优化的是召回，分数和“这段能否直接回答”不对齐，所以有用段经常沉在十名以外。重排吃短名单，计算大约随 k 线性增长：k=50、每条前向若在 10–20ms 量级，这一步就可能到 0.5–1s，需要批处理或把 k 降到刚覆盖金标准的位置。生成窗口若只能再放下约 2k token 证据，4–8 个中等块已经顶满，把 50 段全塞进去既贵又稀释。因此这一层的目标是 precision@m（m 为最终进提示的段数），不是继续刷 Recall@50。日志里同时留初检名次和重排名次，才能确认“第 12 名升到第 2 名”这类位移。重排后答案仍不用该段，说明瓶颈已离开检索。

**后续追问：** k 从 20 加到 100，通常是重排延迟先爆，还是端到端正确率先饱和？重排器和嵌入模型若在相似语料上训练，会不会一起踩同一类近义错段？只对分数接近的中间段重排、两头不动，靠不靠谱？

**扩展问题：**
- 怎样用金标准段的名次位移证明这一层值钱，而不是只看用户是否点赞？
- 提示里按重排分数排和按原文阅读顺序排，对引用完整性各有什么影响？
- 重排器把 50 个分数挤成一团时，你认为是模型失效，还是查询本身缺少区分信息？

**推理回答：** 约束是召回已经够、进提示的名额不够。因此加一层只对短名单负责精度的点对打分，并把 k 钉在初检刚覆盖金标准的最小处。用名次位移和 precision@m 验收，避免把生成窗口重新当成检索器来用。

## RAG-017. 64 条候选的时延预算大约只剩 80 毫秒。三选一：交叉编码器、逐 token 的后期交互打分、大模型一次看完整张名单。你押哪条，另外两条为何排除？

**答：** 在 80ms 处理 64 段的预算下，优先文档侧已经预计算好的后期交互打分；若有 GPU 且模型够小，批处理交叉编码器也可以挤进预算。不要把 64 段整表送给大模型做列表重排：这一步要付长上下文编码和生成时间，还常有位置偏差，80ms 里几乎排不完。选后期交互是因为它把昂贵编码留在索引期，在线只做查询编码和 64 次 MaxSim。

**深入展开：** 交叉编码器把查询和每个候选拼成一段做全自注意力，点对交互最充分，精度通常最高，但文档侧不能离线预计算，耗时大致随 k 线性增长；中等模型在 GPU 上批量跑 64 条有可能落在数十毫秒，CPU 上通常超预算。后期交互的文档 token 向量已在索引里，80ms 主要花在查询编码和短名单 MaxSim，精度一般略低于同规模的好交叉编码器。LLM 重排有逐点打分、成对比较和列表排序：列表排序最擅长“找出和该条款矛盾的段”这类指令，但 64 段可达数万 token 输入，一次调用常要数百毫秒到数秒，且靠前位置更容易被选中。常见折中是级联：先用后期交互或小交叉编码器在预算内把 64 收成 8，只有复杂指令题再放宽预算用 LLM。验收看重排后 nDCG@8 和端到端正确率，同时盯 p95；顶段变了但答案不变，说明瓶颈不在重排。

**后续追问：** 64 这个数字是初检 k 还是拍脑袋，你怎么用金标准覆盖率往下砍？没有 GPU 时，80ms 预算对交叉编码器还成立吗？LLM 只重排前 8 段，会不会把已经排对的结果打乱？

**扩展问题：**
- 列表重排因上下文装不下 64 段而改成滑动窗口，各窗口名次怎么合并？
- 交叉编码器若在业务数据上微调，难负例从初检前 100 里挖，还是随机挖？
- 短编号查询和长对比查询上，三个重排器的相对名次会不会对调？

**推理回答：** 先把约束写成“80ms 内给 64 段一个新名次”，再按“文档表示能否预计算、是否要自回归生成”淘汰方案。LLM 因时延和位置偏差出局；交叉编码器取决于硬件和模型体积；后期交互最贴这笔预算。保留级联，避免所有查询都绑死在一种重排器上。

## RAG-018. 各段都挂着 [3] 且点进去跳到别的页时，入库、生成、事后校验怎样把引用锁在真正撑住该断言的原文跨度上？

**答：** 引用必须是“断言 → 原文跨度”的可验证链接，而不是模型随手点的块号。入库时每个 chunk 带稳定 id、文档版本、页码和字符偏移；生成时先摘句再作答，块号只能引用本轮提示里出现过的 id；后处理对每条断言做蕴含检查，对不上就删掉该句或改为拒答。

**深入展开：** 常见坏法是模型只学会“答案后面要有脚注”，于是循环贴 [1][2][3]；或提示里的编号和块错位；或引用了相关文档但不是支撑该数字的那一句。三层钉法：入库保存不可变的 `chunk_id` 以及 `doc_id、version、page、start、end、text`，提示里用 `[#c17]` 加短摘录，少用 1、2、3 这种易换位序号。生成做成两步，先输出断言、引句、chunk_id，再润色成给用户的句子；或在解码时把引用符号限制在允许集合。后校验对每个断言在对应 chunk 内做包含或蕴含判断，数字和否定尽量字面对齐——18% 不应挂到只写“约两成”的段，除非评价标准明确接受口径改写。用户点击必须用偏移打开原文并高亮，而不是只打开文档首页。评估看点开即能支持的比例、关键断言的覆盖率、以及指向提示外 id 的悬空引用率。合规场景里，错引往往比不引更糟。

**后续追问：** 一条结论由两段拼起来时如何表示多引用；用户只能看到文档级链接时怎样降级；模型输出了提示里不存在的 chunk_id 怎么办。

**扩展问题：**
- 写一个最小结构，描述断言和原文跨度的对应，并标明哪一步做校验。
- 如何区分“引用了正确文档的错误段落”和“引用了错误文档”？
- 流式输出时后校验尚未结束，对用户先显示什么？

**推理回答：** 目标是可追溯、可自动打回。约束是模型不会天生对齐块号。把可引用的 id 收成提示内闭集，再用蕴含检查切断悬空引用。用“点击还原到支撑该断言的原句”定义引用正确。

## RAG-019. 在对照实验里，仅有的支撑段从提示第 1 槽换到第 6 槽后准确率明显下滑。这是召回坏了，还是生成没读中间段？

**答：** 检索集合没变、只改拼接顺序就掉点，应先判为位置偏差，而不是漏检。许多 decoder-only 模型在长提示里更吃开头和紧贴问题的尾部，夹在中间的相关段更容易被跳过，这一现象常称为 “lost in the middle”。加长窗口本身不会抹平这种 U 形；要减噪声、重排，并把高分证据放到两端，同时用引用约束强迫模型点名用过的句子。

**深入展开：** 一次 RAG 请求的可见范围通常是「系统提示 + 按序拼接的检索块 + 用户问题」。注意力对超长序列并不均匀：靠前的块有首因优势，紧贴问题的块有近因优势；若取 10 块、每块大约 300–500 token，第 5–7 块会落在离两端各 1–2K token 的“中间带”。这与召回失败正交：context recall 可以很高，模型答题时却没利用那一段。可用位置扫描定位：同一 top-k，把黄金块分别插到下标 0、k/2、k−1，若准确率呈 U 形，就是位置问题。缓解顺序是：交叉编码器把真正有用的 3–5 块顶到最前或最贴近问题；丢掉低分噪声，把总上下文从例如 4K 压到 1.5K；生成改为“先摘句再作答”，或对答案做蕴含核对。窗口从 8K 升到 32K 只是把中间带拉长，U 形往往还在。

**后续追问：** 黄金块放在末尾也掉点，是截断、表格 token 膨胀，还是尾部被系统提示挤掉；位置扫描和重排一起做时如何归因；流式解码是否更依赖先读到的块。

**扩展问题：**
- 设计一个只打乱块顺序、不改块集合的回归集，怎样避免评测本身让模型学会“看编号不看内容”？
- 把同一句证据复制到开头和中间各一份，准确率回升能证明什么、不能证明什么？
- 若必须保留约 20 块做多跳，如何分段阅读，而不是一次全部堆进中间带？

**推理回答：** 目标是区分“证据不在提示里”和“证据在但没用上”。约束是块集合固定、只改顺序。出现 U 形就按位置偏好处理：缩短有效上下文、把关键块移到两端、用引用让中间证据变得不可跳过。

## RAG-020. 召回段落压短之后，怎样防止证据含义走样？
**答：** 保留原文位置、实体、数值、否定和条件，区分抽取压缩与生成摘要；评估压缩前后答案及引用是否一致，必要时回读原文。
**深入展开：** 压缩后的文本不能成为新的权威来源，引用应落到原始版本。
**后续追问：** 怎样构造数值或否定被误删的回归样本？使用含单位、范围、例外和否定条件的最小对照文本，检查压缩后结论是否改变。
**扩展问题：**
- 压缩文本中的一条结论依赖多个原文片段时，应怎样保存来源映射？
- 压缩前后答案一致但都错误，为什么仍需要原文级事实校验？
**推理回答：** 用可回溯证据换取 token 节省，而不是以不可验证摘要替代事实。

## RAG-021. 引用已经附在写完的答案上。生成后校验怎样补：原子断言如何切开、如何用 NLI 或 LLM 评审对所引块做蕴含判定、时延与费用如何估；失败时再生成、丢掉该句还是拒答？

**答：** 把已写成的答案拆成一条谓词、一个槽位的原子断言，每条对上它自己引用的那一块（没有分条引用就对全部引用块），用字面核对打数字/日期/ID，用蕴含模型或短裁判调用打定性句，得到蕴含、矛盾、中立。这一步加在用户看到“终稿”之前。矛盾或绝对必要的槽位中立就拒答或删掉该句；只允许再生成一次且仍失败则停。时延按“断言数 × 单次核对”估：小蕴含模型可批处理到几十毫秒级，用大模型逐条裁判会再吃掉一整段生成时间。

**深入展开：** 拆断言不要按句号一切：一句里的“30 天且运费自理”是两条。可用短提示让模型输出 `{slot, value, cite_id, text}` 列表，数字和专名再跑一遍正则补漏。裁判输入必须锁死为前提=引用块正文、假设=断言文本，禁止带上对话或参数记忆。混合策略更稳：金额、日期、工单号、百分比先做规范化后的子串/数值相等（含单位），相等记蕴含、对不上记中立或矛盾；剩余定性句才走蕴含分类（例如百兆到十亿参数量级的 NLI）或一次很短的裁判补全。量级上，原答案若大约 2 秒、拆断言一次短调用大约 100–300ms，4–6 条断言批给 NLI 常常几十毫秒；若每条再开一次生成式裁判且串行，例如各 300ms，就要再加约 1.5 秒，很容易把 P95 打穿。能并行就并行；P95 只剩大约 400ms 时，只核高风险槽位，或放过本请求、抽样离线核。失败策略按槽位风险分支：价格、权限、剂量、合规数字矛盾 → 整题拒答或转人工，不要默默删掉让人以为其余部分已审过；一句修饰性定语中立 → 删该句或改成“材料未写明”；多条中立且问题本来就要这个数 → 拒答。重写只准一轮：把失败断言和允许引用块贴回提示，写明“不得写出块中没有的数”，出来再核一遍，第二次仍坏就停，避免核对–重写死循环。已经流式吐给用户的，删句/拒答必须发一条更正或撤回，不能只在日志里改。

**后续追问：** 裁判模型和答题模型同权重时，怎样防止它把“主题相关”判成蕴含；一条结论要两块合起来才成立，你是允许前提拼接，还是强制生成时拆成两条各带一块；流式已经露出错误数字后，撤回和补丁消息哪一种对客服场景更安全。

**扩展问题：**
- 只对数字/日期做字面核对、对定性句不做蕴含，漏掉的不忠实通常长什么样，这类漏检能占断言的多大比例？
- 把核对从同步门禁改成异步抽检，省下的 P95 和漏过终稿的风险怎么用同一周的日志对账？
- 矛盾时重写一次、删句、整题拒答三条路径，各自在金额类问题上的误伤和漏放怎么比？

**推理回答：** 目标是终稿里每条可核断言都被其引用块支撑。约束是生成已经花掉大部分预算，核对不能再复制一条同样贵的生成链路，失败时也不能让模型再自由编一轮。于是先拆原子断言，数字走字面、其余走短蕴含，并按槽位风险在重写一次、删句、拒答之间做硬分支，用“断言数 × 单次核对时延”验收能不能塞进剩余 P95。

## RAG-022. 要报的那个数在文档 B 的预算里，但得先从文档 A 取出项目代号。只跑一轮 top-k 为何常常两边都落空，检索应按怎样的日程执行？

**答：** 用户问句里往往没有那个代号，B 的检索词要等 A 被读到才能形成。对原句做一次 top-k，A 可能进来，B 却因词面和语义都对不上原句而进不了名单。应当先检索并抽出中间实体，再用实体重写第二次查询，分跳组装证据。把 k 从 10 加到 50，解决不了“第二跳的查询词还不存在”。

**深入展开：** 单跳检索匹配的是用户原句。第二跳证据常常是代号表、预算行，和原句的字面重叠很低。可行日程：先把问题拆成有序子问（“正式代号是什么”，再“该代号的预算行”）；或迭代 retrieve(q0) → 抽取 entity → retrieve(entity + 原需求) → 证据够用或步数用尽就停。每跳 k 可以更小，例如 5–10，因为查询已经变具体。不要指望“多塞一些文档让模型自己连”：B 若从未被检索，就不在上下文里。评估要按跳标注：A 是否找到、实体是否抽对、B 是否找到、最终数字是否被 B 支持；只看端到端对错会把抽取错误和检索错误混在一起。两跳仍缺证据时，应拒答或请用户确认代号，而不是用参数记忆补一个整齐的预算数字。

**后续追问：** 中间实体抽错时，怎样避免第二跳很自信地对准另一个项目的预算？两跳的时延预算怎么拆，第一跳超时是取消还是带着不完整实体继续？需要三跳以上时，还保持线性日程，还是对实体关系做有界遍历？

**扩展问题：**
- 怎样构造“必须先 A 后 B”的评测题，避免模型靠参数知识跳过第二跳检索？
- 第二跳是改写自然语言查询，还是直接用代号做等值过滤，哪种更不容易漂到同名项目？
- 多文档进提示时，怎样强制分别引用 A 和 B，而不是合成一句没有出处的结论？

**推理回答：** 先画出证据依赖：B 的可检索键来自 A 的输出，不是来自用户原句。由此否定加大 k 和一次塞更多文档。再设计最少两步的检索日程，用跳级指标把实体抽取从检索里拆开。证据链不完整就拒答，防止第二跳在错误代号上给出精确但张冠李戴的数字。

## RAG-023. 带完整目录的 280 页监管手册，该让模型顺着标题树往下走，还是先切块建向量库？

**答：** 目录可信、文档是少数长篇、问题依赖“在哪一章”时，按树导航（少向量或无向量）往往更准：模型读标题和摘要，推理该打开哪一枝，最后才读原文。海量短篇、结构乱、或要几十毫秒级召回时，向量索引仍是默认。常见折中是先用关键词或向量缩到一本/一章，再在章内走树。

**深入展开：** 树检索的离线产物是层级节点：标题、短摘要、子节点指针，叶子指向原文段落。在线从根开始，模型看当前层目录，选出 1–3 个孩子，直到叶子。判断依据是对标题的推理——“赔偿上限”更可能在「理赔」而不是「释义」——而不是余弦相近，因此能躲开措辞像、章节不对的近邻。代价是每层一次模型调用；例如 4 层、每层数百毫秒，再加上朗读叶子，延迟常到秒级，不适合超高 QPS。树的质量就是上限：没有目录时可用标题规则或轻量模型分层，但父节点选错会整枝剪掉正确答案，必须留回头预算。和“先摘要再向量选节点”的树不同，这里可以纯靠模型点选，不维护 embedding 或向量库。混合用法：向量先找回几本候选手册，本内禁用向量、改走目录。评估应看“是否经过了必须章节”，而不只看最终对错。

**后续追问：** 某一层选错枝，回头重试几次才停止；摘要还是旧的、原文已修订时树还能不能用；导航路径日志怎样当成可解释证据交给审核。

**扩展问题：**
- 手册被拆成 200 个独立页面且没有统一目录时，你还坚持无向量吗？
- 如何用“必须经过的章节”做评测，而不是只看最终答案？
- 把每一层的单选改成对少数候选打分，怎样折延迟？

**推理回答：** 约束是结构清不清晰、本数、延迟预算。结构清、本数少、人会按目录找 → 树导航；本数大、结构弱、要吞吐 → 向量。先问人会怎么翻这本书，再决定索引形态。

## RAG-024. 必须查制度的流量占一半，闲聊占一半。由模型自行打出「现在检索」标记，是否比逢问必检更稳？

**答：** 稳不稳定取决于检索门是否可检验，而不取决于“听起来更智能”。Self-RAG 一类做法是让模型在生成轨迹里显式打出检索和评价标记：先判断这一步要不要查库，拿到段落后再判断是否相关、续写是否被支持。寒暄和纯常识可以跳过检索；制度、数字、时效题必须查。若没有这些标记的监督数据或规则兜底，模型会漏掉高风险问题，还不如默认检索，再在生成侧忽略无用段落。

**深入展开：** 控制流不是一次检索打天下。模型先发出检索控制符（或走一个小分类头），为真才查询；随后对每段打相关/无关，过滤垃圾；每写完一个片段再打“是否被证据支持”，不支持就改写或再检索。这和工具循环式的 Agent 检索不同：决策嵌在同一条生成轨迹的特殊标记里，通常要在带标记的数据上训练，或至少用非常硬的指令约束。工程上更常见的折中是轻量门控：问题是否含政策名、日期、工单号、金额等，比让基座模型自由发挥更可控。漏检代价不对称——报错价格比多一次检索贵得多——所以高风险意图默认检索，只对明显闲聊短路。评估要拆开：门控的精确率/召回率、“该检索却没检索”的事故率，以及触发之后的 context recall。延迟节省只有在门控真的少打了检索、且事故率可接受时才算数。

**后续追问：** 分类器把“看起来像闲聊、其实在问赔偿上限”放行怎么办；未微调模型只靠提示打特殊标记稳不稳；检索无益时强制续写和拒答哪个更安全。

**扩展问题：**
- 列出至少三类必须强制检索、不允许模型跳过的问题模板。
- 如何用离线日志估计少一次检索省下的延迟，以及一次漏检的业务损失？
- 多步生成中途发现证据不足，是再检索、回退改写查询，还是直接拒答？

**推理回答：** 目标是该查的必查、不该查的别浪费。约束是漏检代价远高于多一次检索。先圈定高风险问题并强制检索，其余才交给模型或分类器的检索门。没有触发指标就不要上条件检索的形式。

## RAG-025. 排障助手允许自行改写问句并再次召回；上线后轮次均值来到 3.4，同一批段落还被反复打中。怎样设定停跳规则、跳数硬顶和循环识别，好把额外一轮的延迟和成本都算进预算？

**答：** 每一跳开始前先问“还够不够付这一跳”，付不起或信息不再增加就停，不要等模型自己说够了。硬上限按交互 SLA 反推，例如预留最终生成约 1.5 秒后，每跳大约再 0.7–1.2 秒则线上最多 2 跳、绝对不超过 3。循环用规范化查询指纹、查询向量近重复、以及新 top-k 的 chunk_id 是否已被看过三道门，而不是字符串完全相等。平均 3.4 跳说明停跳条件几乎没在工作，先把空转掐掉，再谈要不要加 hop。

**深入展开：** 一跳的账单通常不是一次 ANN：改写 150–250ms、检索 50–100ms、若重排再 300–600ms、再加一次“证据是否够答”的短判断 150–300ms，合计大约 0.7–1.2 秒，并再付一次短生成的 token。3.4 的均值意味着大约 2.4 次额外跳，端到端会从单跳大约 2 秒抬到 4–5 秒量级，费用也接近按跳相加。停跳谓词在发下一跳之前求值：跳数 ≥ `H_max`；剩余时延 `<` 本跳预估费用（预估用最近窗口的 p50，再留一点余量）；新查询与历史任一跳近重复；新 chunk_id 集合是已见表的子集，或新增唯一块少于 1；本跳检索为空或最高分低于地板；或者够用判断为真——够用看问题类型的槽位是否已被当前证据填上（错误码、服务名、最近变更），而不是模型自报自信。循环检测三层：NFKC/小写/去空白后的查询哈希；查询嵌入与历史的余弦高于例如 0.92；`new_ids ⊆ seen_ids`。只做精确字符串去重会漏掉“熔断阈值 支付”和“支付网关 熔断怎么配”这种空转。`H_max` 不要写成研究代理的 6–8：交互助手要把最终生成时间从 SLA 里扣掉再整除单跳费用。证据够用应在跳数用尽之前触发，否则系统会永远跑满上限。边界：第一跳完全空不能算够用，应改写一次再停；槽位未齐但预算已尽，输出“已查到的部分 + 还缺的槽”，禁止再开一跳去赌。

**后续追问：** 近重复阈值从 0.92 降到 0.85，会误伤哪些合法的第二跳改写（例如补上服务名）；够用判断和答题模型同权重时，怎样避免它提前喊停或永远说不够；重排很贵时，第二跳是否允许跳过重排，只用词法补实体。

**扩展问题：**
- 写出停跳函数的条件顺序：预算、跳数、查询近重复、chunk 集合无增量、槽位够用，谁必须最先判断？
- 如何用一周轨迹估计“再加一跳的平均新增唯一块数”，并找出新增掉到接近 0 的那一跳当作默认 `H_max`？
- 同一会话里用户追问“那生产环境呢”，算新问题重置跳数，还是继承已见表继续跳，两种各会重复付什么？

**推理回答：** 目标是多跳只在还能换来新证据且仍能按时生成时发生。约束是每跳的墙钟和 token 接近一次短 RAG，空转的重复块没有价值。于是用预算和硬上限做硬停，用查询近重复加 chunk 集合增量抓循环，用槽位是否填满做软停，并用平均跳数和每跳新增唯一块验收，而不是看模型是否还想再搜一次。

## RAG-026. 单次检索再生成总漏条款，要把去年与今年的承包商休假制度对比并列出差异。何种情况下才应允许模型自行决定下一轮检索？

**答：** 当单次 top-k 装不下两个年份，或第二份政策的检索词要等第一份读完才知道时，就把“是否再检索、用什么查询、查哪个源”交给一个有预算的循环。模型读完今年条款后，应能发出针对去年版本或具体条款号的第二次检索，再综合。若问题其实是单文档 FAQ，不要开这个循环，以免把延迟和费用白白加倍。

**深入展开：** 固定流水线是 retrieve(q, k) → generate。这里把检索器当成工具：模型每步输出动作（检索 / 停止），系统执行后把观察写回。本例最少两跳——先定位今年承包商休假所在节，抽出要比对的条款名，再按条款名加年份去检索去年文本。必须加硬限制：最大步数（例如 3–6）、最大检索次数、总 token 和时延预算、工具白名单，并记录每步查询和命中 ID。典型失控是同一查询改写空转，或把已读块再取一遍，用查询去重和已读 chunk 集合拦截。它解决的是多步工具调度，而不是“这一题要不要检索一次”的单次门控。两到三轮会把一次检索加一次生成的延迟，变成数次模型调用，因此只对对比、跨版本、跨系统这类题开启。

**后续追问：** 怎样自动把请求分成固定单跳和循环检索两类？步数用尽仍缺一年政策时，是拒答、只答已知年份，还是降级扫更多文档？如何防止模型捏造一个不存在的去年条款号再去检索？

**扩展问题：**
- 对比题怎样算成功：条款级对齐完整，还是最终列表看起来像样即可？
- 检索工具要不要直接暴露“按版本过滤”参数，而不是让模型把年份写进查询字符串？
- 循环检索的 trace 怎样压缩给人看，才能解释为什么多花了两次调用？

**推理回答：** 先判断失败是不是“一个查询词覆盖不了两份证据”。若是，再加大 k 也变不出第二年的检索词。于是把检索做成带停止条件的工具循环，并用步数和白名单锁住成本和乱跑。简单题保持单跳，避免把循环检索设成默认路径。

## RAG-027. 向量 top-k 往往只打中一跳，问句却是「隔级汇报给 CFO 且经办过供应商 X 合同的是谁」。什么条件下值得把知识建成图？

**答：** 当正确答案依赖“实体—关系—实体”的显式路径，而不是某段文字碰巧和问句语义相近时，图比扁平向量合适。汇报线、供应商—合同—负责人、零件—替代料这类问题，单次相似度检索会停在只提到 CFO 或只提到 X 的段落，缺中间节点。若问题只是“合同模板怎么填”，建图是额外成本和抽取噪声，向量加查询分解就够。

**深入展开：** 离线一般从文档抽出带原文跨度的三元组，做实体消歧后落入知识图；也可以对社区或子图做摘要，当作另一路检索单元。在线先把问句链到种子实体（CFO、供应商 X），再按边类型走 1–3 跳，把路径上的原句——而不是节点名本身——交给生成模型。迭代向量检索也能做多跳（先查 X 的合同，再拿负责人去查组织说明），但第二次能否对齐取决于措辞；图是把关系提前物化，查询变成有类型的遍历。主成本在抽取和消歧：两个“李伟”、一条“临时抄送”被当成汇报边，后面的遍历会系统性地错，而且错得看起来很完整。文档更新必须补边、删边，不能只重嵌向量。上图的经验门槛：评测集里大量题目必须组合至少两个不相邻文档，且实体类型稳定。否则先用查询分解加迭代检索，把图留到关系密度真的高的时候。

**后续追问：** 实体消歧失败时，图遍历为什么比向量错得更自信；社区摘要和原始三元组谁当生成证据；引用应该指向节点，还是指向抽边所用的原句。

**扩展问题：**
- 给汇报线和合同两套异构来源，schema 怎样设计才不会把“抄送”写成汇报边？
- 图抽取准确率低到什么程度就该停用遍历、改回迭代检索？
- 如何评测“路径对但贴上的原文片段错”这种部分正确？

**推理回答：** 先看问题是不是类型化的关系组合。单跳文本相似度能覆盖就别建图。必须沿边走时，把关系物化，并坚持用原句做证据。验收看路径命中率，不看表面相似度。

## RAG-028. 要的是按事业部分组的季度毛利率。让模型生成只读 SQL，还是把每一行压成向量去碰数字？分流看什么信号？

**答：** 涉及过滤、分组、排序或聚合的单元格问题，走受控的 text-to-SQL 或固定查询模板，不要把整表拍扁成行向量再靠相似度碰数字。向量检索适合找到“哪张表、哪段文字在解释毛利率口径”；真正的数值必须来自查询结果，或来自仍带表头和单位的结构化片段。分流信号很简单：问句含比较、时间范围、分组就进查询引擎；问“毛利率怎么定义”才进文档 RAG。

**深入展开：** 按行 embedding 的典型失败是：行文本变成“华东 2024Q3 毛利率 18%”，问“哪个事业部最低”时，近邻检索不会做 min，top-k 往往只返回措辞相近的几行。SQL 路径应是：schema 链接（表、列、枚举）→ 生成只读 SELECT → 沙箱执行 → 把结果表（例如上限 50 行）和口径说明一起交给模型。硬约束包括只读账号、列级权限、禁止多语句、超时、结果集封顶。若数字还在文档表里、没有库，应保留表头、单位、行列坐标，序列化成 Markdown 或 CSV 片段，检索键用“表标题 + 表头”，而不是无表头的单元格。生成阶段禁止模型口算改写结果里没有的合计。评测看执行结果是否正确、数值是否被改写，而不是看句子像不像。

**后续追问：** schema 很大、存在同名列时如何避免选错；SQL 对了但口径文档过期听谁的；合并单元格导致解析失败时如何降级。

**扩展问题：**
- 写一套只允许白名单视图的工具约束，说明怎样拒绝多语句和跨租户 JOIN。
- 同一问题既要口径解释又要当期数字，两路结果在提示里如何拼接、冲突时以谁为准？
- 怎样检测模型把 18% 改口成“约两成”这种口径幻觉？

**推理回答：** 数字题的约束是可执行、可复现。相似度检索不携带比较和聚合语义。先做意图分类：定义走文档，计算走查询引擎，再用结果表锁住生成，避免模型心算。

## RAG-029. 从左右分栏的年报 PDF 里抽文本，页眉掺进了正文，跨页报表被截成两段，数值和所在行错了位。版面分析、表格结构重建、保留坐标各自修的是哪种错？扫描版要不要另走一条管道？

**答：** 双栏被抽成“一行读穿两栏”，是阅读顺序问题，要靠版面分析恢复左栏再右栏，而不是更好的 embedding。跨页表表头在上一页、行在下一页，要靠表格结构重建并按表头拼接，不能当两个互不相关的块。页眉页脚每页重复，应按坐标聚类后剔除，否则会污染分块和词法权重。坐标保留让引用能回到页和单元格，也让页眉剔除可复现。扫描件先走 OCR 和置信度，低置信页隔离；原生 PDF 走文本对象和字体，两套错误不同，应分管道。

**深入展开：** 失败链路在解析，不在向量。朴素文本抽取按 PDF 绘制顺序或 x 坐标横扫，双栏会变成半句拼半句；表会变成“营收 12.3 成本 9.1”这种错位词袋，模型再忠实也只能忠实于错表。布局模型输出段落/标题/表/页眉的框和顺序；表结构输出单元格网格、跨行跨列、表头层级，再序列化成带表头的 Markdown 或行记录。坐标用于：（1）识别 y 方向周期性出现的页眉页脚；（2）跨页对齐同一表的列 x 范围；（3）答案引用页码和框。扫描件没有可靠文本对象，OCR 会把“.”和“,”、千分位搞错，必须带字级置信度，低置信数字禁止直接当事实。边界：多栏中的跨栏大表、旋转扫描件、脚注和表共享数字，都要抽样人工核对，不能只看抽取文本和原文的整体相似度——整体像、单元格已经错。

**后续追问：** 阅读顺序错但表结构对，你会先修哪一个？跨页表没有重复表头时，凭什么判断两页是同一张表？OCR 置信度 0.8 的金额，产品上是展示并标注不确定，还是拒答？

**扩展问题：**
- 只用整页 OCR 再切块，和“先版面再 OCR 区域”，对双栏错序的修复率差在哪里？
- 表格转行记录之后，合计行和注释行如何避免被当成普通数据行检索出来？
- 如何用单元格级核对（抽 20 张财报页）而不是全文重叠率，决定解析器能否进入索引？

**推理回答：** 目标是数字与行、列、页对齐，约束是 PDF 绘制顺序不等于阅读顺序。按错误种类选工具：顺序靠布局，行列靠表结构，页眉和引用靠坐标，扫描件靠独立 OCR 管道。用单元格正确率和错栏率验收，而不是用全文相似度。

## RAG-030. 运维文档里要紧操作写在屏幕快照和参数表中，只建文字索引因此会答错。把图像改写成说明、把图像编成视觉向量、把表格按单元格落成记录，各漏什么、如何混用？

**答：** 图转说明或 OCR，能进现有文本 ANN，但界面截图里未写入说明的状态（红框、按钮位置）和 OCR 错字会丢；生成端若看不到像素，也抄不出图上的准确参数。图做视觉向量，能按“像哪张图”召回，但没有可读文字时，文本问题对不上，引用也很难落到单元格。表拆成“表头 + 一行一条”记录，适合“某服务超时是多少”，但会拆坏合并单元格、脚注和合计行。生产上通常三路并存：图存字节与框、表存 Markdown 加行记录，检索取并集，答案必须能指到页和区域。

**深入展开：** 入库按模态分叉。截图：OCR 文本块 + 可选 caption + `page, bbox`；若生成用多模态模型，检索命中后把原图一起放进上下文，否则只能放 OCR。表：先结构化，再（1）整表 Markdown 保关系，（2）每行一个块，字段名在每行重复，避免“8 / 16 / 32”脱离列名。检索可用文本向量、图像向量或两者都查再按文档聚合。边界：把表拍平成一段词袋会让行列错位，数字对上错误服务；只建视觉索引则“超时设为多少”这种纯文本问法会失召。引用要带页码和坐标，用户才能在 PDF 里核对。不要和“把整本手册塞进长上下文”混为一谈——图和表的结构丢失发生在解析，不发生在窗口长度。

**后续追问：** 没有多模态生成模型时，你敢不敢只靠 OCR 答参数题，错字率多高就改拒答？行级块和整表块同时召回时如何去重？图像向量和文本向量不在同一空间，要不要各搜再融合？

**扩展问题：**
- 一张图里既有架构又有参数表，你切成两个对象还是一个多模态块？
- 单元格记录如何编码合并表头（两级列名），避免“生产 / 超时”对到“预发 / 超时”？
- 怎样用“参数题必须命中行记录或图像区域”的专项集，证明扩展不是只加了能搜的噪音 caption？

**推理回答：** 目标是步骤和参数能被定位到图或行，而不是手册里有段模糊描述。比较三种编码丢掉的结构，选择并集加引用，而不是单一拍平。用参数类问题的行/区域命中率和错位率验收。

## RAG-031. 旧文件今天仍排在第一，尽管退货政策 PDF 昨天刚换掉。墓碑删除、按时间降权、增量 upsert，哪一层应先修？

**答：** 先修删除传播：旧 chunk 必须从主索引消失，或与新版本做原子替换，不能只插入新向量。Upsert 只保证“新的进来”；旧 id 还在时，旧文本和新问句仍然很像，相似度会继续打赢。按时间降权只能当双版本短暂共存的保险丝，不能代替删除。

**深入展开：** 写路径应是变更检测（内容哈希、源系统更新时间、文件 etag）→ 对受影响文档“先写新 chunk、再按旧 id 批量删”，或切换别名 → 等搜索副本都可见后再切读流量。墓碑要同时打进向量索引和关键词倒排，否则会出现“向量没了、倒排还在”的半新半旧。chunk 元数据至少保留 source_id、content_hash、生效时间、被谁替代。查询侧对政策类意图加生效窗口过滤，过期文档分数乘零。和“保留历史快照、按某日回放”的版本管理不同，这里要的是在线主索引与源系统收敛。SLA 应拆开：索引可见延迟（常见到分钟级）以及“旧版仍可被搜到”的最长窗口。监控看源已更新但索引哈希未变的文档数、删除滞后，以及答案引用的版本日期。热查询缓存的键必须含索引版本，否则删除成功用户仍看到旧答。

**后续追问：** 同一地址内容变了但抓取侧哈希缓存没失效怎么办；多副本如何避免读到一半旧一半新；缓存 TTL 怎样和索引可见 SLA 对齐。

**扩展问题：**
- 设计一次更新：10 个旧 chunk 换成 12 个新 chunk，如何保证中间状态对查询不可见？
- 若要求“变更后十分钟内不得引用旧条款”，用哪些指标证明？
- 文档只改了一段，全量重嵌和局部重切各有什么风险？

**推理回答：** 目标是源系统的当前版本成为唯一可检索版本。约束是过期不会让相似度自动下降。所以先保证删除/替换的原子性和双索引一致，再用时间过滤兜住传播窗口，最后才谈降权。

## RAG-032. 鉴权头一周前已换，答案却仍引用旧版 API 文档。怎样用新鲜度指标拆开三类原因：源已改但索引未跟上、旧哈希还在线、两版都进提示却偏爱更长旧段？

**答：** 三类在日志里的痕迹不同。同步滞后：源的修改时间新于索引时间，库里仍是旧哈希，根本没有新块。旧块未删：新旧哈希同时可检索，往往旧块更长、分数更高。生成偏好：两版都进了上下文，模型引用了更完整的旧段落。指标用“源时间–索引时间”分布看滞后，用“同文档多哈希仍在线”看幽灵块，用“双版本入选时引用了哪一版”看生成偏好。对症分别是加快同步、墓碑旧哈希、排序和提示偏向带最近日期的来源；价格和鉴权这类字段必要时绕过静态库查实时系统。

**深入展开：** 每个块存 `source_mtime`、`indexed_at`、`content_hash`、`rev`。滞后：`now - indexed_at` 超过 SLA（例如高变 API 文档 24 小时）就告警，这类问题加机器没用，要修连接器和变更通知。幽灵块：同一 `doc_id` 下旧 hash 没有墓碑，检索像“更新过”其实 top-1 仍是旧文；删除传播要覆盖所有分片和缓存。生成偏好：即使重排把新块排第一，长旧文仍可能赢走注意力，应对新块加权、截短无日期旧文、要求回答带来源日期。边界：源时钟不准会让新鲜度排序反转；有的页面“昨天改了导航、鉴权段没改”，mtime 新不等于事实新，应用段级哈希。这和版本合规不同：这里要的是线上默认看见当前事实，而不是回放历史。

**后续追问：** SLA 按文档类型分档还是全局一个小时？实时系统查询失败时，你用带日期的旧块并警告，还是直接失败？缓存按查询文本键住时，怎样在源更新后主动失效？

**扩展问题：**
- 只监控平均索引延迟，为什么仍会漏掉“删不掉的旧块”？
- 新块短、旧块长，重排模型没有时间特征时，你会在特征里加什么？
- 如何用三列指标（滞后、幽灵率、双版本引用比）做周报，证明过期答案在下降？

**推理回答：** 目标是默认答案对应当前源文本。用块级时间和哈希把失败分成接入、删除和生成三层，各改各的，而不是笼统“再同步一次”。用三类指标和带日期的引用验收。

## RAG-033. 白天每小时都在改政策，但复盘时每条问答仍要能回放当时引用过的文档版本。索引快照与块级版本号怎样搭配，才不必每次修订都整库重做嵌入？

**答：** 把“可复现”做成答案上的版本戳，把“常改”做成只重嵌脏块。每条问答记下 `snapshot_id` 以及引用块的 `(doc_id, rev, content_hash)`；复盘时用同一快照或按时间点过滤 `effective_from/to` 重放检索。小时级修订只对哈希变化的块写增量段，未改块沿用旧向量；每日再冻一条只读快照供审计回滚。全库重嵌只在模型更换或哈希算法变更时做。这样合规要的是引用集合可重建，不是每小时一份全量向量副本。

**深入展开：** 块是不可变版本：改一个段落就新哈希、新向量，旧版本标过期时间而不是原地覆盖——原地覆盖会让昨天的问答无法解释。增量段类似 LSM：热更新写新段，查询先读热段再读日快照，合并时同 `chunk_id` 以更新的 rev 为准，删除用墓碑。若每小时只有约 1% 文档变化，重嵌量大约是全量的百分之一。点查历史：给定时间 t，只可见 `effective_from ≤ t < effective_to` 的块。边界：快照太多会爆存储，通常热段保留数小时到一天、日快照保留合规期；权限和正文要同版本变更，否则会复现出“当时不该可见”的块。这和“答案过期”不是同一件事：这里即使最新答案正确，也必须能回到任意已记录的问答现场。

**后续追问：** 复现时 embedding 模型已经换了，你重放旧向量还是用新模型重嵌当时文本？跨快照的增量段损坏，如何仍给出审计视图？引用里只存 doc_id 不存 hash，会缺哪一类纠纷证据？

**扩展问题：**
- 同一文档一小时内改三次，查询应看到最后一次还是该小时结束时的冻结？
- 如何估算“热段 + 30 日快照”相对“每小时全量拷贝索引”的存储倍数？
- 问答日志被抽走 hash 字段后，怎样证明无法再做合规复现？

**推理回答：** 约束是时间点可重放和变更窗口短。把块做成带哈希的不可变版本，把索引做成热增量加冷快照，只对脏哈希编码。用复现命中同一组 hash、以及每小时重嵌比例验收。

## RAG-034. 报销封顶被模型报成 4000，其实是把 wiki 的 3000 和一年前邮件的 5000 平均了。权威序、时间戳、把冲突显式标出各适用何种情形，何时必须拒答？

**答：** 4000 在任何来源里都不存在，是把冲突平均成假事实，必须禁止。权威序适合来源等级清晰且高权威未过期的时候：已发布制度高于未备案邮件。时间戳适合同一权威层级的修订链，新文本覆盖旧文本，但仍应点出旧值。显式标冲突适合等级或时间无法单独裁定时，把 3000 和 5000 连同日期、文种并列。涉及钱、安全、合规且没有唯一的现行有效依据时，应拒答或转人工，而不是挑一个听起来更顺的数。

**深入展开：** 检索之后先做槽位对齐：从各块抽出“报销上限”这个字段及数字、日期、文种、状态（试行/废止）。若多个值，进入裁定：废止标记直接丢掉；制度类且在有效期则压过闲聊邮件；同为制度则比生效日期；仍并列则输出冲突结构，而不是自然语言里揉成一句。生成层要看到冲突标记，提示里写明禁止对数值取平均、取中位数或“综合来看”。边界：新邮件声称“已批准调到 5000”但制度页未改，这不是检索错误，是治理问题，系统应标“制度未更新，存在未落地修订”，而不是悄悄采用邮件。检测可用规则（同一字段数字不一致）加聚类，不必先上大模型仲裁。评估看冲突检出率和“无中生有的中间值”为零。

**后续追问：** 权威表由谁维护，业务方自己改 wiki 优先级怎么办？用户明确说“按去年邮件执行”时，还要不要并列制度？冲突检测放在重排后、生成前，漏检和误报哪个更贵？

**扩展问题：**
- 三个来源给出 3000/5000/3000，多数票能当裁定吗，什么时候不能？
- 如何在引用里同时展示被否决的来源，避免用户以为系统没检索到邮件？
- 怎样用“必须输出冲突结构”的用例防止模型再把两个数合成一个？

**推理回答：** 目标是字段值可追溯到单一有效依据或被明确标成冲突。由“禁止发明中间值”推出先抽槽再裁定，钱与合规场景默认升级拒答。用冲突检出率和中间值出现次数验收。

## RAG-035. 某客户合同只允许其对接人检索。权限谓词应插在 ANN 路径的哪一环？为何不能先全库召回再吩咐模型保密？

**答：** 全局召回一旦把合同块读进服务内存、提示或日志，泄密已经发生，后面的“不要输出”只是生成约束，不是访问控制。权限必须变成检索谓词：先按租户/客户把图或分片收窄，再在子图上做 ANN，使禁止块根本不会被取回。后过滤可以当最后一道保险，但不能当唯一闸门——选择度低时既慢，又只要有一条代码路径忘了过滤（缓存、调试接口、预取）就会漏。缓存键要带主体 id，权限回收要在约定 SLA 内让旧块不可检索。

**深入展开：** 块上存 ACL：客户 id、角色、组展开后的主体列表或主题位图。查询带调用者身份，预过滤用分片或倒排位图限制可访问 id，再搜 HNSW/IVF；payload 读取仍要二次校验，防止 id 被篡改。不要依赖模型“认出敏感再闭嘴”：提示注入、引用展示、思维链日志都会把原文带出去。权限变更：组员离开后，相关块的可见集合要更新，用户级缓存整组失效；删除/降密比新增更要强一致。边界：父块展开若拼进无权限的邻节，等于旁路；跨客户的“类似合同”语义检索必须在预过滤之后，否则会命中别人的合同再丢弃，既慢又在日志里留下别人的 id。验收必须有越权套件：用户 A 对用户 B 文档的 recall 应为 0，且响应里不能出现 B 的文档 id。

**后续追问：** 组嵌套五层时，你在查询时展开还是入库时物化成员？权限从“能看”改成“不能看”的 SLA 是秒还是小时，审计怎么证明？搜索和生成分属不同服务时，哪一层是权限的最后责任人？

**扩展问题：**
- 共享磁盘上的向量文件若被直接打开，还要不要在存储层加密或按租户分盘？
- 调试回放生产查询时，如何避免运维人员借回放看到无权合同？
- 预过滤导致某客户分片过小、ANN 召回不稳，怎样在不放开隔离的前提下补召回？

**推理回答：** 安全约束高于召回：不可见文档的任何原文和 id 都不能进入提示或日志。由此推出预过滤/分片是主路径，提示保密只是多余的软约束。用越权 recall=0、缓存隔离和回收 SLA 验收。

## RAG-036. 生成占 2.0s、交叉编码器重排占 900ms、改写占 200ms、ANN 占 80ms，整段问答 P95 为 3.2 秒。你会动哪一段，并用怎样的对照避免质量下滑？

**答：** 先动占比最大、且能并行或能减输入的段：生成 2.0s 用流式改善等待、缩上下文减 prefill；重排 900ms 用“候选从 50 收到 20、换更小的重排器、或只对前段重排”做对照。ANN 80ms 不是这条链路的主因，不要先换向量库。任何降延迟的改动都要在同一评测集上看 context precision@k 和 faithfulness，而不是只看秒数。

**深入展开：** 端到端大约是串行段之和再加排队。改写和多路检索通常可并行；重排和生成更影响质量。交叉编码器对几十段各数百 token 做逐对打分，候选 50 时很容易到秒级；收到 20 或换成蒸馏模型，常常能少一大截。生成 prefill 随输入 token 涨：检索上下文从例如 3K 减到 1.2K，往往比换 ANN 算法更省。热门问句可缓存“规范化问题 + 索引版本 → 重排后的块”，把改写到重排整段打到数毫秒，索引一更新必须失效。不要为了 P95 直接丢掉重排：先做有/无重排的质量差，只有 top-5 已经够好才降级。流式只改体感，总时长仍在。计时必须带追踪号看分位数。这和大库上 ANN 本身很慢不是同一道题：这里瓶颈在重排和生成。

**后续追问：** 重排候选从 50 收到 20 后，漏掉的是哪类题；提示缓存命中时生成还剩多少时间；多路检索并行会不会把下游候选加倍、把重排时间吃回来。

**扩展问题：**
- 画出这条链路的关键路径，标出哪些段能并行、哪些必须等重排结束。
- 若 faithfulness 在评测集上几乎不允许下跌，延迟预算应怎样在重排和生成之间切？
- 何时该用小模型改写、大模型生成，而不是两端都用大模型？

**推理回答：** 按耗时排序，先处理重排和生成。用同一套题做质量和延迟的对照实验。ANN 已不是瓶颈就不要动索引。缩上下文和带版本的结果缓存是便宜杠杆，丢掉重排是贵杠杆。

## RAG-037. 嵌入模型与重排器都没改，百万级向量库上 P99 检索却从大约 80ms 爬到大约 900ms。买加速硬件之前，过滤时机、ANN 参数、缓存应按什么次序排查？

**答：** 模型和重排没变，说明贵在查询向量之后、重排之前：ANN 访问、过滤候选和取回正文。先看过滤是在图搜索前还是后——后过滤且选择度只有几个百分点时，为凑满 k 会把候选扩大十几倍，P99 从几十毫秒爬到近秒是典型现象。再查 HNSW 的 `efSearch`、IVF 的 `nprobe` 是否被上调、图是否因未优化的插入变乱、索引是否被换出内存。最后才是查询向量缓存和 `(查询哈希, 过滤条件)` 的结果缓存。换 GPU 救不了“先搜全集再丢 95% 结果”。

**深入展开：** 拆延迟：查询 embedding（未改模型则应仍大约 10ms 量级）→ ANN → 元数据过滤 → 拉 payload → 重排（题目说没动，可先当对照）。后过滤的代价近似 `k_effective ≈ k / 选择度`：选择度 5% 要大约 20 倍过检，图遍历和随机读都会冲高 P99。预过滤或按租户/时间切分子图，让每次搜索落在百万级而不是全库。插入高峰若边插边查且没有后台 optimize，HNSW 层间链接变差，延迟和召回会一起坏。缓存键必须含过滤条件，否则会把 A 租户的 id 列表供给 B。边界：热查询缓存能把 P50 压回去，但长尾新查询仍走 ANN，所以 P99 要靠分片和过滤时机，不能只靠缓存。硬件应在“索引已常驻、过滤已前置、参数未误调”之后再考虑。

**后续追问：** 你怎么从一条慢查询日志判断时间花在图遍历还是 payload 拉取？选择度随用户权限波动时，`efSearch` 该动态调还是该预分区？磁盘型索引的 page cache 冷启动会不会单独造成 900ms？

**扩展问题：**
- 过滤条件从“租户 = X”变成“租户 = X 且标签 ∈ {20 个值}”，后过滤的过检倍数怎么估？
- 查询 embedding 缓存命中但文档刚更新，你会为新鲜度牺牲多少命中率？
- 如何用分阶段耗时和“过滤后剩余候选 / k”证明慢因是过滤时机而不是 ANN 实现？

**推理回答：** 目标是把 P99 拉回百毫秒内且召回不塌。先按未改动的段排除模型和重排，再用选择度公式估计后过滤过检，最后才动硬件。用分段延迟、候选放大倍数和分片大小验证。

## RAG-038. 先不要堆机器。面对五百万份内部文档，如何用数量级估算选定分片、存放规模和按变更重建，再去做检索索引？

**答：** 先把文档数换成向量数和常驻字节数，再决定“单分片能放进内存的图”和“一次变更要重算多少 embedding”。五百万文档按每篇约 8 个块估算是约四千万向量；768 维 float32 裸向量大约 115 GiB，HNSW 邻接再加五到十成，整库常驻往往要 180–230 GiB。这个量级已经不该做单图硬塞，而应按租户或命名空间切成百万级分片，并用内容哈希只重嵌脏文档。加机器只覆盖内存，盖不住全量重嵌的时间和误删残留。

**深入展开：** 数据流是：解析 → 分块 → 内容哈希 → embedding → 写入分片 ANN，查询只路由到权限命中的分片。示意计算：`n_vec = 5e6 * 8`，`bytes = n_vec * 768 * 4 ≈ 1.2e11`。IVF 粗量化可把编码压到每向量几十字节，但召回依赖 `nlist`（常见取 `√N` 量级，四千万大约几千到一两万个簇）和 `nprobe`；HNSW 延迟稳、内存贵。增量不要全库重跑：未改哈希的块跳过；删除写墓碑并在 SLA 内从所有副本摘掉，否则百万库里的“幽灵块”会长期占 top-k。边界：按时间一刀切分片会让跨年政策查询漏分片；按租户切则单租户若自己就有千万块，仍要二次切。全量重嵌四千万块，若嵌入吞吐大约 1k 块/秒，要十小时量级，所以“先买更大机器再全量重建”会把变更窗口拉到不可接受。

**后续追问：** 单分片目标向量数你按内存、QPS 还是召回方差来定？墓碑还没传播完时，查询该失败、降级还是读到旧块？PQ 压缩后，百万库的召回掉几个点你能接受，用哪套固定题来看？

**扩展问题：**
- 若 5% 文档每小时改一次、其余几乎不动，脏集重嵌和夜间全量重建的 CPU/GPU 预算差多少？
- 分片键从租户改成“租户 + 文档类型”后，跨类型的多跳问题要打几个分片？
- 如何用“索引字节 / 向量数”和“删除后仍被召回的块比例”判断扩容方案有没有把账算错？

**推理回答：** 约束是内存驻留、变更窗口和删除可见性，目标是召回不随规模塌缩。先把文档数映射成向量数和 GiB，判断单图是否放得下；再比较“哈希增量 + 分片路由”和“垂直加内存后全量重建”的时间。用分片级 recall@k、索引延迟和幽灵块比例验收，而不是看机器是否买够。

## RAG-039. 政策在 wiki、纪要与 PDF 里各有一份，召回名单全是同一条结论。三种去重分别会错杀哪类证据：按文档 ID、按相邻窗口、按语义去重？

**答：** 文档 ID 去重会删掉同一文件里两段都相关的内容（定义段和例外段），对跨源副本没用。相邻窗口去重只吃掉重叠切开的近重复，吃不到 wiki 与 PDF 的意译。语义去重（例如余弦高于约 0.9 留一条）能压跨源副本，但可能丢掉“措辞很像、数字相反”的少数派来源。应分层：入库用规范化文本和哈希合并真副本；查询先做同文档区间合并；最后语义聚类时，若关键槽位（金额、日期、是否）不一致则强制都留着。

**深入展开：** 三份来源常见差异：wiki 短而新、纪要口语、PDF 带版式噪声，embedding 仍可能挤在一起，于是 top-k 表面很满、信息熵很低。入库阶段用 URL 规范、标题+正文 simhash、附件派生关系，把副本链到一条权威 id，检索默认只出权威，需要审计时再展开别名。查询阶段 MMR 提高向量多样性，但不检查槽位冲突，不能替代聚类后的数值对比。边界：两份文件一个写“试行”、一个写“废止”，语义很近，去重若只留高分会系统性删掉废止声明。评估用“唯一论断数 / k”和“冲突槽位是否被同时保留”，不要用去重条数当 KPI——条数下降可以是误删。

**后续追问：** 权威副本选 wiki 还是已签署 PDF？语义阈值如何按文档类型分开，避免把短标题误判成重复？去重放在重排前还是后，对交叉编码器分数意味着什么？

**扩展问题：**
- 同一结论的三份来源日期跨两年，去重后你留哪一份，排序分和新鲜度谁优先？
- 近重复检测用字符 n-gram 还是向量，扫描件 OCR 噪声会把哪一种打崩？
- 如何构造“同意见多副本 + 一条反例”的评测集，防止语义去重静默丢掉反例？

**推理回答：** 目标是 top-k 覆盖不同证据，而不是覆盖不同文件名。按误伤类型选择去重键：身份、几何、语义，并在语义层加入槽位冲突保护。用唯一论断数和反例保留率验收。

## RAG-040. 同一段落的滑动窗占了 top-8 里的五条，块重叠大约 20% 时就会这样。入库时把重叠降下去，对比召回后按偏移做区间合并，两种做法各会丢掉什么？

**答：** 20% 重叠是为了不切断句子，但相邻块共享大约一百 token 时，向量会非常接近，ANN 会用近重复塞满 top-k。入库把重叠降到约 5–10%，或改成按标题切、只重叠一句，能从源头减少克隆，代价是指代和跨句定义更容易被切开。召回后按 `(文档, 偏移)` 做区间合并（例如 IoU 超过约 0.3 就合成一条再展开一次），不改入库、立刻腾出槽位，代价是分数抖动时可能丢掉唯一完整的那一窗。两者不是替代：先保证切分不断关键句，再在查询侧合并几何重叠。

**深入展开：** 512 token 块、重叠 102 token，相邻余弦常常高到 0.85 以上，top-8 里 5 条同源并不奇怪。区间合并要存 `start/end`，按文档分组，保留最高分窗口或取并集一次展开，避免“五条变一条后又丢上下文”。MMR 按向量多样性挑，几何上仍重叠的两窗若用词略不同可能都留下，所以 MMR 去的是语义近亲，不是滑动窗口。边界：表格一行被切到两块时，降重叠会让表头和数字分离；此时应按结构切，而不是继续加大重叠。评估看 context precision 和“top-k 唯一父段数”，不要只看 recall@k——克隆会把召回表面做高。

**后续追问：** 合并后要不要把并集再送去 embedding 打分？标题切分的文档没有标题时，你用句子边界还是 token 窗口？重叠从 20% 降到 5% 后，哪类问题的召回最先掉？

**扩展问题：**
- 同一段三个滑动窗口分数为 0.84/0.83/0.82，合并规则怎样避免总是留下缺主语的中间窗？
- 入库重叠和查询合并同时做，怎样防止“切太碎 + 合并太狠”把例外句丢掉？
- 如何用“top-8 中同源窗口占比”做上线门禁，而不是等用户抱怨答案啰嗦？

**推理回答：** 约束是 top-k 槽位有限，目标是同一论断只占一格且不断句。比较“少重叠的切分”和“带偏移的区间合并”各自误伤的查询，再叠加而不是二选一。用唯一父段数和切开句导致的漏检验收。

## RAG-041. 被点踩的回答约 200 个，是客服在七天内收集的。先用低成本探针标成六种故障，再按占比决定优先修抓取、切分还是生成侧校验？

**答：** 把这 200 条当成失败分布样本，而不是 200 次单条排雷。主因只分六类且互斥：库中无文档、切块切断、排序未进顶、过期版本、生成忽略上下文、问句理解偏了。用索引成员、块内字面、提示里的 chunk 集合、版本哈希、金句是否已在模型输入、改写是否丢掉约束这六条探针自动打标，人只看分不出的残差。哪一类过大约两成——或条数少但全是金额/权限——就先投那一层，不要六路并行改。

**深入展开：** 200 条这个量级能分清十五到二十个百分点的占比差，分不清两个百分点的细差，所以目的是排下一个迭代，不是给六层各开一个项目。每条必须能回放到当时的索引版本和完整模型输入，否则“现在库里有”会把当时的缺文档或过期版本标错。探针按最早坏的一层级联，命中就停：（1）用户或复核给出的应命中文档、政策名、SKU、错误码，在当时索引快照里点查不到 → 库中无文档；（2）文档在，金句或数字在 chunk 表里被切断，或只出现在原始解析、没有任何一块完整包含 → 切块切断；（3）金块存在，但日志里最终进提示的 chunk_id 集合没有它（初检 top-50 有、重排后无也算）→ 排序未进顶；（4）命中块的 content_hash 或生效日对不上源系统当时的当前版，或带废止标记 → 过期版本；（5）金句已经出现在模型输入文本里，答案的数字、极性或对象仍与它不一致 → 生成忽略上下文；（6）改写丢掉否定、对象或时间窗，召回的是另一个自洽但答非所问的主题 → 问句理解偏了。前五条是点查、正则扫块、集合运算、哈希比对和提示内子串，单条毫秒到几十毫秒；第六条和残差（例如大约三四十条）再人工一两分钟。一条票只标一个主因——“只修这一层就应对”——次因另记，避免一张票在六类里各加一。投资看加权计数：若大约八十条是库中无文档，先补连接器和覆盖率，不要先换嵌入；若生成忽略上下文占头，加引用约束或断言核对，不要重切全库。修完一类必须用同一 200 条再加随后一周的新点踩重打标签，分布会移动。200 条不够做六路并行对照，只够锁一个主迭代。

**后续追问：** 没有用户贴出正确文档时，怎样用实体词典近似“库中无文档”，又避免把冷门但库里其实有的问题误标成缺文档；一条又切坏又生成胡写，主标切块还是生成，回归怎样避免只修一层就整条变绿；点踩里混进“事实对但语气差”，你如何从 200 里剔掉以免扭曲占比。

**扩展问题：**
- 六类探针各最少要哪些日志字段（索引版本、chunk_id 列表、prompt 文本、源哈希、改写前后查询），缺哪一个会把两类标串？
- 过期版本只有十几条但全是金额，库中无文档有六十条且都是边缘产品，下一个迭代仍按计数还是按风险加权？
- 怎样用“假定修该层后重放这 200 条有多少转正”来验证分类，而不是凭感觉说切块最重要？

**推理回答：** 目标是把下一个迭代投到真正的众数（或最高风险）失败上。约束是 200 条付不起逐条读完整流水线，更付不起六层同时拧旋钮。于是用可机跑的层探针做成互斥主因，用占比加风险加权排序，先修一类再重测分布是否真的移动。

## RAG-042. 上下文召回仍然高、端到端准确率持平，忠实度却在跌。应当先排查检索，还是先排查生成？

**答：** Context recall 高说明答题所需要点大体已进入提示；faithfulness 下跌说明答案里出现了当前上下文撑不住的断言。这是生成不忠，不是漏检。应先冻结检索，检查提示约束、噪声块和输出校验。只有 context precision 同时塌掉、或黄金文档根本不在 top-k 时，才回头改召回。

**深入展开：** 四个指标分别盯四段链路。context recall：标注里回答问题所必需的要点，有多少出现在本次检索上下文中。context precision：检索到的块里有多少真正有用，以及有用块是否排在前面。faithfulness：把答案拆成原子断言，每条是否被给定上下文蕴含。answer relevance：答案是否在回用户的问题，而不是正确但跑题。它们可以独立坏：正确段落来了，但又塞进多段相似旧政策，模型折中出一个上下文里没有的数字——recall 仍高、precision 偏低、faithfulness 掉。用模型当评判时必须锁死上下文边界：只能看本轮检索结果，不能用参数知识补全。构造样本时同时带问题、检索列表、答案、必要要点和故意放入的干扰块。线上点赞不能代替断言级检查：用户觉得“像那么回事”时，忠实度可能已经坏了。抽检时每条答案拆 3–8 个断言，比只打一个对错更能定位。

**后续追问：** 用模型当评判时如何防止它编造“这段能支持”；context precision 该用二元相关还是带位次折扣；拒答样本要不要单独统计 faithfulness。

**扩展问题：**
- 画出这四个指标分别单独下跌时，你改 pipeline 的哪一层。
- 怎样构造“检索对、答案错”和“检索错、答案碰巧对”两类对抗集？
- 引用准确率和 faithfulness 不一致时，哪一个应该挡住发布？

**推理回答：** 先把指标映射到链路：recall/precision 属检索，faithfulness/relevance 属生成。当前信号是 recall 高且 faithfulness 低，生成在说证据没有的话。先加“只能依据上下文、否则拒答”和断言级校验，再决定要不要动 retriever。
