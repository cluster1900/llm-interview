## OPS-001. 周六日赶出来的样机，周一要吃进生产流量的 10%。生命周期里哪些关卡你坚持不能绕过，每一道得提交何种凭证？

**答：** 拒绝省略的至少是：问题与拒答边界写清、离线评测集（含安全、幻觉、格式）对照基线、成本与延迟预算、先小流量对照而不是直接 10%、回滚开关、以及监控能回放单次请求。周末 demo 只证明「能生成」，不证明「在真实分布上可治理」。10% 已经是生产事件，不是内部预览。

**深入展开：** 每个阶段都要留产物，而不是口头「感觉不错」。问题定义交出成功指标、禁止事项、人工接管条件。评测从日志或标注抽一套冻结集，覆盖主路径、长尾、越权和应拒答；模型或提示一变就跑，分数和失败用例入库。原型只用来暴露集成风险。离线过线后再做风险审查：证件号、提示注入、工具副作用。试点应从影子流量或约 0.5%–1% 开始，看对照差异（投诉、人工接管、格式失败、单请求成本），不是绝对分数。放到 10% 前必须已有一键切回旧提示、旧模型、旧检索的开关。上线后闭环才开始：漂移、提示版本、安全拦截、成本异常都要能告警。常见失败是用内部同事的问题当评测集——分布比线上窄得多。

**后续追问：** 离线集全绿但金丝雀投诉上升，你停放量还是先查分布偏移；没有标注团队时，最小可接受的评测集长什么样；成本预算按 QPS 估还是按 token 分位估。

**扩展问题：**
- 哪些闸门可以并行（评测集建设与网关限流），哪些必须串行？
- 提示每周改三次时，生命周期里哪一步会变成日常，而不再是「上线一次」？
- 如何用回放日志证明 10% 流量和周末 demo 不是同一分布？

**推理回答：** 目标是可撤回地试真实用户，约束是质量、安全和成本。把生命周期写成必须交证据的闸门，10% 只能出现在对照和回滚都就绪之后。验收看冻结集回归、金丝雀对照、一键回滚演练通过。

## OPS-002. 病区手持机进了电梯就断网，此时仍须能改病案摘要；开鉴别诊断则要调用云端最新的大模型。哪些请求留在本机、哪些走云上，网络回来之后如何合并才不把病案写脏？

**答：** 端侧吃已经在本机的病历片段：离线摘要、语音转写、敏感字段打码和医生正在改的草稿；云端吃需要最新医学知识和工具的鉴别诊断、指南检索和跨患者统计。断网时诊断入口降级为「仅本地草稿 + 待发送队列」，恢复后按记录版本向量合并，医生本地未提交的修改优先于过期的云端回写，禁止静默覆盖。选型看隐私、离线硬约束和模型能力，而不是笼统「端侧更安全、云端更强」一句话。

**深入展开：** 平板内存和电池决定端侧只能驻留小模型或强量化模型，上下文也短，适合改写已有段落，不适合当权威诊断。云端模型可热更新、可接检查检验接口，但电梯里 RTT 无限大，必须在产品层把这两类意图拆开，而不是同一个按钮「能点就送云」。数据流：本地先写带版本号的病历草稿 → 有网再把医生确认过的片段加密上传 → 云端诊断结果以建议块写回，不直接改主诉原文。冲突：同一段落本地 v3、云端基于 v1 的建议返回，应提示差异并让医生点选，而不是 last-write-wins。合规：默认识别出的患者标识留在设备，上传集合要最小且可审计。端侧模型通过 MDM 发版本，云端可以日更；两边的提示和安全策略要分开版本号，避免「云端已拒答、端侧还在乱写用药」。电池和发热要把端侧推理限制在插电或短突发，长报告等恢复网络再走云。

**后续追问：** 端侧摘要把剂量抄错，云端诊断是否还允许引用这段摘要当事实；无网超过 N 小时的队列，过期后是丢弃、重算还是只保留医生原文；同一账号换了一台平板，未同步草稿怎样避免变成第二份正本。

**扩展问题：**
- 哪些字段永远不准出设备，哪些字段在医生点「请求诊断」后才准上传？
- 端侧小模型只会「通顺改写」，怎样在 UI 上防止它被当成鉴别诊断结果？
- 恢复网络后用什么日志证明没有用旧云端结果覆盖更新的本地病历？

**推理回答：** 约束是无网可用和写脏病历的代价高于漏一次自动诊断。按「数据是否已在本地 / 是否必须最新权重」切分意图，同步用版本而不是时间戳覆盖。用冲突提示率和未授权上传次数验收。

## OPS-003. 7B 档会话每天约 200 万次，夜里几乎空转。买按 token 计费的托管接口，对比预留自有 GPU：自建要从多高有效利用率起才更省，哪些成本科目经常被忘掉？

**答：** 自建便宜的条件是「按峰值配好的卡，在全天里的有效利用率」足够高，而不是日请求次数看起来大。日间高峰要按峰值配卡，夜间空转把日均利用率打下去；只有（高峰容量 × GPU 单价 + 人力 + 备援）低于同期按 token 的账单，且你能吃下运维和合规成本时，自建才赢。两百万次若挤在大约八小时，真实卡时往往只有「按日均估」的一小半被用满，盈亏拐点会比直觉更靠后。

**深入展开：** 示意账（数字只供面试推演，不是某家报价）：假设每次 800 输入 + 200 输出 = 1000 token，日均约 2×10⁹ token。托管按每百万 token 零点几到数美元量级计，月账单会落在数千到数万美元这个数量级。自建侧：7B 级 INT8/INT4 单卡能扛的并发取决于 KV 和延迟 SLO，不能把「权重放得下」当成「一张卡吃完全天两百万次」。漏计项通常比 GPU 目录价更大：①为 p99 峰值而不是日均配卡；②至少双副本做发布和故障；③夜间和周末空闲；④KV 迫使你多买的是显存不是算力；⑤值班、镜像、评测回归、安全补丁；⑥数据必须留在自建环境——这是否决项，不是折扣。稳健形态常是混合：稳定基线自建，溢出走托管。决策输出应是一条「日均利用率 / 峰值比」的盈亏平衡线，加上「数据不能出境则无条件自建」的硬约束。

**后续追问：** 峰值是日均的四倍时，盈亏平衡利用率怎么改；自建省下的钱够不够覆盖一个值班工程师；输出 token 明显比输入贵的计价下，你更该砍提示长度还是转向自建。

**扩展问题：**
- 把闲时容量租给内部批处理（摘要、评测），如何计入自建的有效利用率？
- 模型三个月一换，自建的沉没成本和托管的「即换即走」分别怎么进账？
- 哪些 SLA（地域、数据驻留、审计）会让单纯的成本比较直接失效？

**推理回答：** 把日请求换成峰值 QPS 和全天利用率，再把人力、备援、空闲加进自建总拥有成本，和按 token 的可变成本比。拐点用利用率表示，而不是用「请求很多所以该自建」。

## OPS-004. 产品是提示裹一层的托管大模型，你接手的却是特征仓库加按周重训那套 MLOps。哪些子系统仍然值得留，还缺哪些控制面？

**答：** 还能干活的是：环境与配置的 CI、服务鉴权与限流、模型/工件注册表的「版本+回滚」习惯、以及业务指标监控。几乎帮不上忙的是特征仓库、每周重训、以及把离线 accuracy 当唯一门禁——权重不在你这边训，输入是提示+检索+工具，输出非确定。缺的控制面是：提示/检索/工具 schema 的版本，token 级成本，基于轨迹的评估（不是单点标签），安全护栏，以及供应商模型静默变版本时的回归。

**深入展开：** 传统 MLOps 假设「数据→特征→训练→checkpoint→服务」，漂移靠重训修正。LLM 应用假设「冻结或外购的生成模型 + 运行时装配」，漂移更多来自提示改写、知识库更新、解码参数、供应商切权重。要版本化的工件从「一个权重文件」变成「模型 ID + 提示 + RAG 索引版本 + 工具契约 + 解码配置」一组。CI 不能只跑单元测试：需要冻结评测集、格式/引用校验、安全用例。监控从特征倾斜扩到 TTFT/TPOT、token、拒答、工具失败、人工反馈。训练集群利用率不再是主 KPI；单次请求能否回放才是。两者仍共享权限、密钥、灰度、回滚、审计。不要为了「栈里有训练」而每周空转一个用不上的分类头。

**后续追问：** 特征仓库还能不能给 RAG 的元数据过滤用，还是该退役；供应商无公告改模型时，注册表里的「模型版本」怎么定义；人工评估和自动评测各卡在发布流程的哪一闸。

**扩展问题：**
- 若后来要对开源模型做监督微调，哪些 MLOps 部件会重新变得关键？
- 提示和索引版本不一致上线，故障看起来像什么，谁该拦住？
- 怎样用同一套实验框架比较「换提示」和「换模型」，避免两套仪表盘？

**推理回答：** 列出旧栈「我们训权重」的假设在新产品里是否成立；成立的留下版本/灰度/监控，不成立的换成提示-检索-评估-护栏。验收看一次失败请求能否按版本五元组回放。

## OPS-005. 客户合约中，销售写上了「首 token 3 秒内到达、整段回复 15 秒内结束」。哪些量必须变成可测的服务质量度量；业务对错的哪些含义，绝不能跟可用性挤在同一条款？

**答：** 合同要拆成：按输出长度分桶的端到端时延、首 token 时延、超时与 5xx/429 定义的可用性、以及「完成且满足时延」的有效吞吐。3 秒应对齐 TTFT，15 秒必须写明最大输出长度或按 token 计的时间，否则长答会合法超标。事实是否正确、检索是否召回、用户是否满意，不能写进同一条可用性：它们依赖离线集和抽样审核，实时探测无法判定，混在一起会逼着系统拒答保「正确」或把幻觉算作成功。

**深入展开：** 建议的可测集合：可用性（在约定超时内返回最终状态，安全拦截要单独计数，不要和引擎故障混成一个错误率）；TTFT 的 p50/p95/p99；按输出长度分桶的整段时延或每输出 token 时间；schema/工具失败率；token 与费用。质量另立 SLO：任务成功率、引用可回源率、人工升级率，用金样和周抽样，而不是用拨测脚本。RAG 再加检索命中和新鲜度，但那是功能 SLO。边界：流式接口若把「第一个空格」算首 token，合同会被钻空子，应定义「第一个可见内容 token」；用户中途取消算不算失败要写清，否则取消潮会污染可用性。成本不要写进客户可用性条款，但内部要有「单次成功任务费用」以免靠堆并发假装稳。不要把 GPU tokens/s 写进对客合同，那是容量指标，不是用户可感知 SLA。

**后续追问：** 输出从 200 token 变到 800 token，15 秒条款怎样改成按桶或按 TPOT；安全策略拦下一句攻击，对客户是成功、失败还是单独类别；只报平均时延、不报 p99 和分桶，续约时会怎样被反咬。

**扩展问题：**
- 同一合同里客服短答和报告长答共用 15 秒，怎样改成分级 SLA 才不会让短答去背长答的锅？
- 「可用」是否包含备用模型降级成功？降级时质量 SLO 怎么改阈值？
- 如何用拨测证明 TTFT 条款，同时用周抽样证明质量条款，两套数不会互相污染？

**推理回答：** 目标是合同可判定、纠纷可取证，约束是生成长度和质量无法在同一探测里核实。把用户可感知的时延和可达性做成实时指标，把对错做成独立质量 SLO。用分桶延迟、明确的错误分类和抽样协议验收。

## OPS-006. 首字时延、可点击回链和前端事件协议要一起设计。制度问答要流式出字并挂 [n] 出处：生成是等检索加重排全部冻结后再开始，还是先吐字、编号事后补？中途证据被撤权或掉出终榜时，已显示的 [3] 如何处置？

**答：** 带可点击出处的句子，证据集合必须在第一句带编号的主张出现之前冻结；冻结前可以流状态条或无编号导语，不能发出稍后会变成链接的 `[3]`。边检索边生成时，模型只许输出不透明槽位，等权限复检和终榜稳定后再用绑定事件回填序号，而不是先把临时数字焊在句子上。半路发现第 3 号块被撤权或挤出终榜，已上屏的 `[3]` 必须走撤回事件，变成不可打开的「来源失效」，禁止继续指向正文。首字延迟要拆成「第一颗可见字」和「第一句可回链主张」两份合同，前端用绑定/撤回事件改脚注，不指望模型事后改口覆盖旧 token。

**深入展开：** 两条可落地的装配。栅栏式：检索与重排跑完 → 按调用者复检每个块的注入权 → 冻结 `evidence = [{slot, chunk_id, version, locator}]` → 再开始生成。编号取自这份闭集，点击用 locator（页、字符偏移、内容哈希）打开绑定时刻的快照，而不是打开「现在的最新文件」。用户会多等整段检索墙钟才看到字，但屏幕上不会出现假脚注。占位式：粗召回之后先流「正在核对来源」或一段不带编号的导语；若产品坚持边写边标，decode 只吐 `⟦s3⟧` 这类槽位，此时槽位没有 URL、不能点。终榜和复检完成后发 `cite-bind`，前端再把槽位画成 `[3]`；若该块没能进入终榜或注入权已没，发 `cite-retract`，槽位变成灰色失效标记，依赖它的那句加「依据已更新」，必要时截断后续生成。半路失效按原因分支：权限回收后 locator 立即作废，点击不得打开条款；主张里的数字只靠这一块支撑时，追加更正条，不能留一条还能打开全文的脚注。重排把块挤出终榜且尚未绑定，则保持未绑定；已经绑定并可能被点过，按回收同样撤回，并写审计。协议最小集是 `status`、`text-delta`、`cite-bind`、`cite-retract`、`evidence-final`、`done`：服务端只认 `slot` 与 `chunk_id`，屏幕上的 `[n]` 是前端绘制序号。乱序到达时后到事件按 `slot` 幂等合并，终态必须等于 `evidence-final`。不要用模型再生成一句「刚才的 [3] 作废」当主路径——已画在画布上的字，客户端不一定替换。延迟合同分开写：要「马上出字」就对齐状态条或无引用导语的首包；要「带出处的第一句」就必须对齐第一次成功 `cite-bind` 之后的那一句。评估：冻结前发出的可点击引用次数为 0；撤权演练里已上屏脚注的可打开率为 0；bind/retract 乱序重放后终态与终榜一致。

**后续追问：** 导语已经写了「根据第三份附件」，随后 bind 失败，你改导语、整段作废，还是留下无链接的句子；移动端把脚注画成芯片，retract 时芯片消失还是变成「已失效」；同一槽位先后绑到两个 `chunk_id`，前端以谁为准。

**扩展问题：**
- 写出最少事件类型和顺序约束：哪一类可以早于证据冻结，哪一类绝对不能出站？
- 用户在撤回之前已经点开并复制了原文，审计记什么，界面要不要补一条事后声明？
- 怎样把「首可见字」和「首条可回链主张」做成两条独立指标，避免用前者冒充后者？

**推理回答：** 目标是体感快，同时脚注可回链、可作废。约束是终榜和注入权在复检完成前不稳定，而浏览器很难代替服务端收回已画的字。于是把「出字」和「编号生效」拆开，用绑定和撤回事件表达引用生命周期。验收看冻结前零可点击引用、撤权后零可打开脚注，以及两条延迟是否分开上报。

## OPS-007. 证件号夹在 prompt 里，输入会冲到 8k token，吞吐按 200 QPS。自托管引擎、混合路线、托管 API：各自强迫你亲自维护哪些模块？

**答：** 托管 API：你养网关（鉴权、配额、重试、超时）、提示与输出过滤、证件号脱敏或合同内处理条款、降级与多供应商路由；不养 GPU 和推理内核，但把延迟、限流和数据出境交给对方。自建：你还要养权重分发、推理引擎（连续批处理、KV、量化）、GPU 容量和故障替换；证件号可以不出域，但 8k 尖峰要你自己用前缀缓存和切块扛。混合：日常走自建、溢出或更大模型走托管，必须统一请求 ID、统一计费和统一安全策略，否则排障会裂成两套真相。

**深入展开：** 200 QPS 不是 200 个 HTTP 连接就结束。若平均约 2k 进 / 200 出，token 速率大约 200×2200 = 4.4×10⁵ token/s 量级，70B 级自建要按 decode 带宽和 KV 显存估卡，而不是按 Web QPS。8k 尖峰让 prefill 队列和 KV 同时胀：要设最大并发序列，按优先级丢弃或降到短上下文模型。证件号：自建可在隔离网络内、盘上加密、日志脱敏；托管则要确认不用于再训练、区域存放和删除接口——工程上仍应出站前最小化（能哈希就不传明文）。批处理能抬吞吐但伤 TTFT，交互流量要单独队列。这里先定数据面和容量面谁拥有，而不是先卷某个引擎实现。观测必须从网关贯穿到引擎或供应商响应头（token、缓存命中、限流）。

**后续追问：** 溢出到托管时证件号怎么降级——拒答、打码，还是只走已签约区域；8k 尖峰是排队、OOM 还是 TTFT 爆，你用哪三个容量旋钮；200 QPS 里约 5% 是 8k，卡数按均值估会怎样翻车。

**扩展问题：**
- 自建集群单卡故障，进行中的流式请求如何让客户端续上？
- 托管突然返回限流，本地队列是削峰、降模型还是读缓存答案？
- 混合路由按数据敏感度还是按长度/延迟，冲突时谁优先？

**推理回答：** 从约束（证件号出境、200 QPS、8k 突发）反推控制面所有权。数据不能出境就偏向自建或混合里的本地路径；算力不想养就托管，但必须补齐网关与降级。用分位延迟、限流次数和出域审计验收，而不是用「接口通了」。

## OPS-008. 周五要开服一套问答助手，高峰按同时 200 条在途请求来估，单次输入大约 2k token、输出大约 400 token。如何从「单卡可并行容纳多少 decode 槽位」倒推到卡数、队列与限额，而不是只抛平均 QPS？

**答：** 容量不能用平均 QPS 乘平均延迟交差。先用 Little 定律把 200 路在途换成到达率：若端到端 p95 目标约 8 秒，可持续到达率大约是 25 请求/秒，再按峰值与均值比留余量。真正卡住的是 decode 槽位和 KV 显存——prefill 吃算力，decode 吃显存带宽，一张卡同时能挂的序列数由「权重吃掉后还剩多少显存 / 每 token 的 KV」决定。供应商的 RPM/TPM、检索 QPS，以及故障时少一池 GPU，都要单独进预算，不能假定模型服务永远按压测均值吐 token。

**深入展开：** 把一笔请求拆成两段：prefill 大致按输入长度吃 FLOPs，约 2000 token 的提示在大模型上可能就要数百毫秒到数秒，取决于并行度和是否命中前缀缓存；decode 每步都要读整段 KV，400 token 按每卡每秒数十到一百出头的生成速度（示意，视模型大小、量化、批大小而定）就要数秒。KV 可以自己算：例如 70B 级、GQA、约 80 层、每层 8 个 KV 头、head_dim=128、FP16，每 token 的 K+V 大约是 2×80×8×128×2 ≈ 320KB，一条 2.4k 上下文大约 0.75GB。权重占满后若只剩约 40GB 给 KV，单卡组大概只能同时挂约 50 路；200 路并发就需要约 4 组，再加 30–50% 峰值余量和一张卡掉线仍能顶的冗余。排队必须有界：队列长度 ≈ 到达率 × 可接受等待，超过就拒或降到小模型，而不是让 p99 无限涨。压测要按真实输入/输出长度分布打，只打 128+128 的短请求会严重低估 KV 和 decode 时间。成本按「token 单价 × 日 token」和「GPU 小时」对账，长上下文的少数请求常常吃掉大半预算。

**后续追问：** 前缀缓存命中率从 0 提到约 60% 时，你减的是卡数还是只减 prefill 池？用户开始写长回复、输出从 400 涨到约 1500 token，哪一项先爆？检索集群的 QPS 和向量维数要不要和 GPU 一起估？

**扩展问题：**
- 同一集群混部 7B 和 70B，槽位和队列怎么隔离，避免短请求被长 prefill 堵住？
- 如何用「在途请求 × 平均 KV」实时判断该扩卡还是该截断上下文？
- 供应商 TPM 先于 GPU 打满时，本地排队和切小模型谁先触发？

**推理回答：** 目标是 p95 延迟和峰值不丢请求，约束是 decode 槽位、KV 显存和配额。从并发反推到达率，再从每 token KV 反推单卡并发上限，两者取紧的那个决定卡数；用有界队列和真实长度分布的压测验收，而不是看平均 QPS 是否「看起来够」。

## OPS-009. 凌晨 3 点，售后对话机器人也得能把人喊醒。值得为之配寻呼的实时信号有哪四类，哪些所谓 LLM 指标只配挂在看板上充数？

**答：** 值得 paging 的是：可用性（5xx、超时、供应商限流比例）、延迟 SLO 违约（TTFT / 词间延迟的 p99，按短/长请求分层）、安全与合规拦截异常（拦截率骤降比骤升更危险）、以及业务闭环断裂（工具失败率、格式或工单创建失败、人工接管飙升）。装饰性的是：平均 tokens/s、没有对照的平均「满意度」、单独一张 GPU 利用率图、以及没有版本维度的质量分数——它们不回答「用户现在能不能办完事」。

**深入展开：** 监控要能在约五分钟内指向层：网关、检索、模型、工具。请求量用来判断是流量尖峰还是依赖挂了；token 与成本做成小时预算告警，避免早上才发现烧穿。模型、提示、索引版本必须打在每一条时序上，否则「质量变差」无法归因。检索命中率和空检索要单独看，否则会把检索故障误判成模型编造。用户点踩是滞后指标，只适合次日复盘，不该当唯一夜间页。日志必须脱敏。paging 要有抑制和对照：拦截率从约 2% 跌到 0.1% 可能是分类器挂了，应比升到 3% 更紧急。容量类（KV 占用、队列深度）给值班做预判，只有威胁 SLO 时才升级为页。

**后续追问：** 供应商延迟整体多了约 300ms，你页谁、阈值看绝对值还是对照昨天同时段；工具成功率掉但模型调用仍是成功状态码，告警为什么必须拆开；成本告警按金额还是按 token 分位，怎样避免被一条超长提示刷爆。

**扩展问题：**
- 短闲聊和 8k RAG 共用一个 p99，会掩盖哪类事故？
- 怎样用人工接管率做夜间页，又不被倒班人手变化误触发？
- 质量离线分每天跑一次，怎样避免把它误做成实时 paging？

**推理回答：** 从「夜间必须有人修」反推：能办完事、不泄不漏、不烧预算。把信号分成页、工单、次日，去掉无法行动的均值。用分层 SLO 和版本维度验证告警有解释力。

## OPS-010. 有人来报：回复点到了子虚乌有的条款。可查的记录只剩最后正文，状态码还是 HTTP 200。要把问题拆到检索、prompt 拼接、生成环节或工具调用，单次 trace 至少该记下哪些字段，又有哪一类严禁以明文持久化？

**答：** HTTP 200 只说明网关没崩，不能说明引用从哪来。一条最小 trace 要有：`trace_id`/`span_id`、租户与用户假名、提示版本、模型版本与解码参数、检索查询和文档 id、分数、索引版本、注入块 id 列表、工具名与状态、输入输出 token、TTFT/TPOT、结束原因、护栏裁决，以及输出侧的引用 id。条款正文、证件号、完整提示原文默认不落明文；需要复盘时进受控、有 TTL 的对象库。有了文档 id 和注入列表，才能区分「检索就召回了错条款」「拼提示时张冠李戴」还是「模型编造了未注入的编号」。

**深入展开：** 跨服务用同一 `traceparent`：网关 span → 编排 span → 检索 span → 模型客户端 span → 每个工具 span。检索 span 记规范化查询、top-k 的 doc_id、chunk_id、分数、过滤器（权限、时效），不记全文。提示组装 span 记模板版本和按顺序列出的 `chunk_id`，这是「模型当时看见了什么」的证据，比事后重跑更可信。模型 span 记 provider 请求 id、token 账、`finish_reason`、是否命中前缀缓存。若答案里出现 `条款 14.3` 而注入列表没有该 id，判生成幻觉；若注入了错误的 14.3，判检索或权限过滤；若 id 对但模型改写了数字，判不忠生成。采样：错误和用户投诉 100% 留全字段，成功请求可降采样，但版本和 doc_id 建议常留，否则稀有幻觉无法回溯。访问控制：能读 trace 不等于能读原文；原文查看单独授权并审计。时钟对齐用服务端时间。不要只存最终字符串——那会逼人用猜测当根因。

**后续追问：** 检索返回了正确 chunk_id，但组装时被长度截断丢掉，trace 怎样表现；用户允许复盘却要求 7 天后删除原文，id 字段还留不留；多跳工具里第二跳改写了第一跳的数字，span 怎么串。

**扩展问题：**
- 写一份 span 字段表：检索 / 组装 / 生成 / 工具各必填哪些，哪些必须脱敏。
- 如何用「答案引用 id ⊆ 注入 id」这条规则自动打幻觉标签？
- 日志系统按请求体大小计费时，你先砍哪类字段，不能砍哪类？

**推理回答：** 目标是把「错引用」归因到链路中的一层。约束是 200 和终态文本没有因果信息，且原文受隐私限制。留下版本、id、分数和裁决，原文进受控仓。验收看能否在不猜测的情况下指出是检索、组装还是生成。

## OPS-011. 界面给用户只丢下一句「生成失败」字样。一线值班无法分辨超时发生在切分、向量召回还是模型本身。要把失败点在五分钟左右钉住，同一 request id 该串起哪些分步字段，并保证日志不写入原始提示词？

**答：** 每个用户请求一个稳定 request id，在切块、embedding、检索、生成、工具、输出过滤上各开 span，字段至少包括：步骤名、下游依赖、耗时、状态码或错误类、输入输出 token、检索命中数、模型与提示版本、缓存是否命中。正文只存哈希、截断后的脱敏摘要或对象存储指针，禁止把完整提示和检索原文写进可广泛查询的日志。值班靠瀑布图看哪一段超时或非零错误，而不是检索一句「生成失败」。

**深入展开：** 黑洞来自只在最外层捕获打一条错误。补齐后的数据流：网关打 request id → 各服务注入同一 trace → 检索 span 记索引版本、`top_k`、命中数、过滤是否为空、内部 p99 → 模型 span 记模型 id、提示版本、TTFT、TPOT、出入 token、缓存命中、结束原因、排队毫秒 → 工具 span 记名称、超时、重试。错误要分类：超时、限流、空检索、schema 失败、安全拦截、依赖 5xx；前端可以仍显示同一句用户文案，对内必须是不同 code。五分钟定位：打开 trace，看最后一个成功 span 和下一个失败 span；若检索命中为 0 且过滤过严，不是模型；若排队时间占满预算，不是提示词。量级上，每请求数 KB 的结构化字段可以留，每请求数十 KB 的原文不能进热日志；抽样（例如错误全量、成功 1%）把原文放到带访问控制的桶，保留期按合规。成本字段（每步 token 或金额）一并打上，方便区分「贵且慢」和「失败」。高基数标签（原始问句）不要当指标维度。和通用应用追踪的差别是必须能回答「哪一版提示、是否缓存、检索是否空」。

**后续追问：** 生成 span 成功但用户仍抱怨空回答，你还缺哪类「质量 span」；多租户下 request id 能不能跨租户查询；embedding 批处理把 32 条打成一次，怎样把失败映射回单条 request id。

**扩展问题：**
- 列出最小字段表：哪些是排障必须、哪些只在错误抽样时出现？
- 如何检测「全链路成功码但引用 id 对不上检索 id」这种逻辑失败？
- 提示里有身份证号时，哈希和掩码各保什么、丢掉什么？

**推理回答：** 目标是五分钟内指向失败步骤，约束是不能把提示原文变成新的泄漏面。用统一 request id 和步骤级结构化 span 代替最外层一句错误，原文只留哈希和受控抽样。用故障注入（检索空、模型超时、过滤拦截）检查能否从 trace 一眼区分。

## OPS-012. 从午后起，托管 API 的引文忠实程度一小时一小时地变差，厂商未发布任何版本说明。把冻结金样拿去做影子回放，再对上对方回传的模型指纹，如何把「权重被静默替换」和「检索或提示刚发版」区分开？

**答：** 把「线上流量」和「冻结金样」拆成两条曲线：金样钉死提示哈希、注入 chunk_id、索引版本和解码参数，按小时走影子回放，只判引用号是否落在注入块里。同时把对方回传的模型别名、snapshot / system fingerprint（若该接口提供）以及贪心金样的输出哈希画成时间序列。你们自己的 prompt_version、index_version 在午后若是空窗，而金样忠实度与 fingerprint 同步跳变，就可以指认对方静默换模；金样稳住、只有线上掉，再去查检索或提示发版。

**深入展开：** 金样从线上抽一批必须带引用的问句（示意：80–200 条，覆盖政策、价格、例外条款），把当时的模板、chunk_id 列表、索引版本、`temperature=0`、stop 打成不可变快照；正文按合规进带 TTL 的对象库，回放时禁止重新检索。影子走独立配额和独立 `model` 别名调用，不占用户并发。厂商指纹分两层：①接口若回 `system_fingerprint` 或 snapshot id（以你对接的 API 版本为准，有的别名会在无公告时换快照），按小时做「值是否变化」；②接口不回或只回稳定别名时，用行为指纹——同一金样贪心下前 32 个 token id 的哈希，或首位 token 的 logprob（若开放）。三张图对齐：金样引用可回源率、fingerprint/行为哈希、内部发布日历。判定树：fingerprint 在时刻 H 跳变且金样同小时下跌、日历为空 → 静默换模；fingerprint 稳定、钉死 chunk 的金样稳住，但把回放改成「现查现拼」就掉 → 检索或索引；金样在你们刚切 prompt 的时刻掉 → 提示发版。数量级只作示意：可回源率从约 0.91 滑到 0.74 且与 fingerprint 同跳，比「GPU 利用率没变」更有归因力。边界：对方只改隐式系统提示或安全过滤、fingerprint 不动，行为指纹仍会跳，所以接口指纹是充分线索不是唯一线索；语义缓存若未纳入金样键，会把旧答案当成「模型没变」。影子结果只写评测库，不回写用户会话。

**后续追问：** 厂商连 snapshot 字段都不给，你准备用多大的贪心前缀才能把行为指纹的假阳性压住；金样钉的是上周的 chunk，知识库今天合法换了条款，忠实度下跌该不该报警；同一别名在两个区域 fingerprint 不一致，你按区域切片还是先当对方在做金丝雀。

**扩展问题：**
- 影子回放要不要带上当时的工具结果？不带的话，你怎样避免把工具契约变更误判成换模？
- 行为指纹只哈希前 32 个 token，对方只改了长答案后半段的引用风格，你会漏掉什么？
- 怎样用「fingerprint 跳变时刻 ±1 小时」自动拉出内部发版空窗，写成给厂商的事故时间线？

**推理回答：** 目标是在无公告时指认权重/快照换了，而不是再列一遍请求轨迹字段。约束是线上忠实度同时会被检索、提示和缓存打动。所以用钉死输入的金样去掉检索/提示变量，用 fingerprint 与内部日历做对照。验收看三条曲线能否在同一小时对齐，而不是看 GPU 看板。

## OPS-013. 若把提示视为可发布工件：质量在周二变差，三个人各自咬定「只改了一句话」。代码仓、线上请求、评测报告分别必须钉住哪些版本，才能把这次事故定位清楚？

**答：** 仓库保存不可变模板：文本、变量 schema、默认模型别名和生成参数，用内容哈希当版本号，变更走评审，禁止在 wiki 或生产控制台就地改字。运行时每条请求写下模板版本、渲染后哈希（脱敏）、模型版本和解码参数。评测报告必须钉住同一组版本再出分，否则「赢了 5 个点」无法复现。对得上这三处指纹，才能知道周二是哪一句话、哪一次发布进的生产。

**深入展开：** 模板与渲染要分开：版本钉的是带占位符的模板，运行时注入检索块和用户文本；调试需要时再存渲染后的哈希或脱敏全文，避免把 PII 当版本的一部分。发布通道与代码相同：分支 → 评测 → 金丝雀 → 全量，回滚就是流量指针改回上一哈希，而不是再改一句「改回去」。多人同时编辑时，没有不可变 ID 就会出现「线上跑的是甲的句子、评测跑的是乙的句子」。配套绑定：某提示版本声明兼容的模型别名和索引版本，不兼容组合在网关直接拒绝。热修复可以走紧急通道，但必须事后补评审和评测，并保留那次哈希。不要把「最新」当标签用在生产；`prod` 是指向某个哈希的指针。日志保留策略要让事故窗口内的版本字段可查，否则定位链在过期后断开。变量改名属于模板变更，要升版本，不能只改代码侧的 dict key。

**后续追问：** 模板没变、few-shot 库里换了一条例子，算不算新版本；渲染后全文因 PII 不能落盘，事故复盘看什么；提示按租户覆盖时，全局版本和租户补丁哪个优先、日志怎么记。

**扩展问题：**
- 写一条请求日志的最小版本字段集，并说明少记一项时周二的事故会卡在哪。
- 如何防止评测任务默默拉取 `latest` 提示，导致历史分数不可比？
- 提示回滚了，但模型侧的 chat template 没回滚，用户会看到什么？

**推理回答：** 目标是让「改了一句话」变成可指认、可回放、可撤销的发布。约束是提示不在传统制品里，却决定条件分布。三处同钉哈希，生产禁止无名热改。验收看能否在五分钟内指出周二的版本指纹并切回。

## OPS-014. 内部只拿 5% 租户试新 RAG 策略，开关却只绑定「换上新模型」；prompt、索引版次与工具授权并未同步翻转，对照因而作废。AI 发布用的 flag 必须罩住哪些维度，紧急切断又该一并扳倒哪几根？

**答：** 一条 AI flag 必须指向一整束可兼容配置：模型别名、提示版本、索引/embedding 版本、工具白名单、解码参数和护栏策略，外加分流键（租户、用户哈希、百分比）。只切模型、对照臂仍吃新提示或新索引，两边差的就不是「新 RAG」，实验作废。紧急关闭要一次切回上一束，而不是只把模型布尔量拨回去、留下新工具权限。

**深入展开：** 求值发生在编排器组好模型请求之前：读租户/用户身份 → 算粘滞哈希 → 命中则取出 bundle_id → 用 bundle 里的版本去拉提示、路由模型和选索引。粘滞保证同一用户在实验期内不来回跳，否则多轮对话和 A/B 同时失效。百分比放在租户允许名单之内：先「内部租户」，再在其中抽 5%，避免外部流量误入。工具权限是安全轴：新策略若多了一门能发邮件的工具，kill switch 必须同时摘掉这门工具，否则关「新模型」仍可能外发。Flag 配置本身要版本化、可审计（谁在何时对哪租户打开），并设过期，避免永久脏旗。不要在提示文本里写 `if flag` 让模型自己解释开关。默认失败策略：flag 服务不可用时走最后一次成功的安全束（通常是旧生产束），而不是放行新束。观测：每条请求打上 `flag_id` 和 `bundle_id`，这样才能解释「5%」实际命中了谁。与发布系统的关系：flag 切的是已通过评测门的束，不是把未评测的提示直接挂到 5% 上。

**后续追问：** 用户同时命中「新模型」和「旧索引」两个独立 flag，兼容性谁仲裁；kill switch 在网关还是编排器，漏一层会怎样；百分比从 5% 调到 50% 时要不要重新哈希导致人群洗牌。

**扩展问题：**
- 列出 bundle 里至少六个字段，并说明只改其中两个时对照臂污染了什么。
- 紧急关闭后仍有进行中的流式请求，flag 对它们是否追溯生效？
- 如何用「对照臂的 bundle_id 分布」证明实验没有被单轴 flag 污染？

**推理回答：** 目标是让 5% 流量完整进入新 RAG 联合行为，其余保持旧束。约束是模型、提示、索引、工具单独开关会交叉污染。flag 指向不可变 bundle，kill switch 整束回退。验收看两臂的 bundle_id 是否各自纯净。

## OPS-015. 离线 80 条样例上，新版提示大约多出 12 分，产品要求放到 100% 流量。生成抖动很大。在线试验如何分层、固定哪些因素、何种证据才能判胜？

**答：** 80 条离线分差不能发版。线上按用户或会话随机分流，按意图、租户、语言和时段分层，并锁死模型版本、索引版本、工具集和解码参数，只暴露提示这一条差异。主指标用业务结果（一次解决、转化），并行看人工或抽样裁判的质量、成本、延迟和安全事件；安全或延迟击穿 SLO 则自动停实验。样本量按输出方差加宽，覆盖至少一个周周期，禁止看两小时领先就切全量。

**深入展开：** LLM 同一提示重复抽样也会抖，温度 >0 时更明显；离线 80 条还常和训练或演示同分布，12 个点里有抽样噪声和过拟合。分流单位必须是用户或会话：按请求抛硬币会让同一人看到两种口径，既污染体验也让配对失效。分层保证「退款咨询」「闲聊」不会碰巧堆在同一臂。锁定清单：权重、tokenizer、chat template、检索语料版本、重排模型、工具名单、`temperature`/`max_tokens`。记录每次请求的提示版本哈希，便于事后剔除误入对照的流量。统计上不要用未校正的多次偷看；预先算所需样本量，或用顺序检验并扣多重比较。主指标若是稀有事件（投诉、幻觉工单），要提前算「实验期内期望命中数」，太少就加长时间或改成配对人工评审。裁判模型必须冻结提示和模型，并抽检人工校准，不能让「新提示自己评新提示」。结束条件同时满足：主指标置信区间不再跨零、护栏未破、无严重安全切片恶化。失败则回到旧提示版本号，而不是再改一句话继续烧流量。

**后续追问：** 同一用户跨设备换了匿名 id，怎样避免两臂串扰；离线赢、线上平，是流量分布变了还是裁判标准变了；业务指标涨但引用忠实度跌，你听哪一个。

**扩展问题：**
- 设计一张实验卡：分流键、分层因子、锁定变量、主指标、护栏、最短时长、停实验规则。
- 为什么「连续三天新臂更好」仍然可能是假阳性？
- 多轮对话中途切换提示版本，会话级指标该怎么算？

**推理回答：** 目标是证明新提示在真实流量上净收益为正。约束是高方差、小离线集和多变量耦合。用户级分流、锁死其余版本、用业务加护栏成对看、样本盖过方差。没达到预注册条件就不宣布获胜。

## OPS-016. 金丝雀放新权值刚满两小时，拒答比例翻了一番。磁盘里仍有旧检查点，可配对提示、量化设定以及 tokenizer 已跟到新版。回退要一并拉回哪些东西，才算重新可服务？

**答：** 只把权重文件指回旧 checkpoint 不够。一次可工作回滚要恢复整包：权重、tokenizer / 词表、chat template、量化位宽与 kernel、默认生成参数，以及声明兼容的提示版本；RAG 场景还要 embedding 模型和索引读指针。灰度开始前就应有「上一包完好」的热副本或可在数分钟内拉起的镜像，流量指针整包切换。缺任一件，表面上「模型回旧了」，输入编码或指令模板仍按新包走，拒答或乱码会留下。

**深入展开：** 版本清单是一份不可变清单，例如 `model_id=acc_7b_2026w12`，列出文件摘要、tokenizer JSON 哈希、`quant=awq-4bit`、`rope`/`max_seq`、配套 `prompt_id` 和 `embedder_id`。发布时新包在独立副本池加载，旧包继续服务；灰度只切路由权重。回滚 = 路由 100% 回旧池，而不是在已加载新 tokenizer 的进程里热换一份旧 safetensors。不匹配的典型故障：新词表把旧提示里的特殊符切碎；chat template 从「系统在前」改成另一种角色标记，旧提示等于没生效；4-bit kernel 加载 8-bit 权重直接起不来。索引若已用新 embedding 重打并切了读指针，模型回旧、向量空间仍是新的，检索会系统性跑偏——要么双读指针都能回退，要么 embedding 变更与生成模型解耦发布。会话中途换包会让未完成的工具参数或语气断裂，回滚窗口内宜按会话粘滞到旧包，或接受进行中的对话结束再切。验收：回滚后拒答率、格式合规、p95 回到灰度前基线，且清单哈希与灰度前一致。不要指望「再部署一次新包但改回提示」当回滚，那是另一次发布。

**后续追问：** 旧包装在冷对象存储里，回滚要 40 分钟拉盘，SLO 怎样定才算合格；只回模型、提示仍是新版，你如何用日志证明这就是拒答翻倍的原因；多机张量并行时，一包切换的原子性怎么保证。

**扩展问题：**
- 列出版本清单里至少六个必须一起回滚的字段，并各写一种单独回滚时的故障。
- embedding 已全量切到新空间，生成模型要回旧，你选双索引回退还是先停 RAG？
- 怎样用「回滚完成时间」和「回滚后主指标」证明演练过，而不是只在事故里第一次试？

**推理回答：** 目标是恢复灰度前的输入编码、指令模板和权重联合行为。约束是这些文件被当成独立改动在前进。以整包清单为发布和回滚单位，旧包保持热备。验收看清单一致加基线指标恢复，而不是看磁盘上是否还有旧权重。

## OPS-017. 自建推理还不能丢掉会话：embedding 的索引必须重建，权值由 8-bit 换成新版 4-bit。双轨、影子观测、翻转读侧指针按何次序排期，哪一环出错必须马上撤回？

**答：** 先在新副本池加载 4-bit 包并做影子，再金丝雀切生成流量，索引单独做「双写或离线重建 → 校验 → 原子切读指针」，旧 8-bit 池和旧索引一直可回退。影子阶段只比质量、延迟和安全，不改用户可见输出；影子失败不准进金丝雀。金丝雀破线则路由回旧池。读指针切完若召回或延迟恶化，指针立刻打回旧索引，生成模型不必绑死一起回滚，除非两者被声明为一包。

**深入展开：** 顺序：①新 GPU 池加载 4-bit 权重、匹配的 tokenizer 与 kernel，就绪探针通过；②影子：把真实请求复制到新池，比较格式合规、关键槽位、拒答、TTFT/TPOT，差异入日志，用户仍只看旧池；③生成金丝雀 1%→10%→50%，会话可粘滞到同一包，避免一轮用 8-bit、下一轮用 4-bit 造成工具 JSON 风格断裂；④索引：用同一语料和新 embedding（若 embedding 没变则只需量化侧）离线建新库，抽样对旧库做近邻重叠和业务探针；⑤读指针一次切换，写路径若需要可双写缓冲；⑥旧池在观察窗口后退役。量化变更常见风险是数学/长尾能力悄悄掉点，影子必须含这些切片，不能只看困惑度。embedding 维度或模型一变，旧向量不可复用，禁止在服务中的库上原地重嵌。边界：GPU 不够双跑时，可先扩再切，或在低峰只双跑影子的一小部分流量，但全量切换前仍要有可回退镜像。不要把「重打索引」和「换生成权重」塞进同一次不可逆发布。回滚演练要量「切回旧池 + 旧指针」的墙钟时间。

**后续追问：** 影子里新模型更短、更常拒答，你算变好还是变差；会话粘滞导致金丝雀实际流量偏了某类长对话，怎样校正；索引切指针是瞬间的，重建却要三小时，这三小时写进来的新文档怎么办。

**扩展问题：**
- 画出一张发布状态机：每态可前进的条件和必须回退的条件。
- embedding 没变、只换生成量化时，哪些步骤可以跳过？
- 如何用影子差异率证明 4-bit 可切，而不是等用户投诉？

**推理回答：** 目标是会话不中断且随时能回到旧联合行为。约束是量化误差和索引空间可能同时变。新池先影子后金丝雀，索引用只读指针切换，旧资源保持热。失败就退指针或退路由，不做原地不可逆改写。

## OPS-018. 业务侧单元测试全部通过，有人仅动系统提示词和召回权重就推上线。相对常规 CI，AI 发布管线还得加哪些闸门，少一扇会放出哪类事故？

**答：** 传统 CI 证明的是确定性代码路径；提示、模型、索引和策略不在 `pytest` 里，绿测也能放出质量回归。流水线要把这些当成一等工件：变更绑定不可变版本，合并前跑冻结评测集（格式/槽位、回归金样、红队）、索引兼容检查，合并后走金丝雀并看质量护栏而不只看 5xx。缺评测门，提示里一个否定词就能让拒答塌掉；缺金丝雀，全量用户先替你当测试集。

**深入展开：** 工件清单：应用镜像、提示模板及哈希、模型清单（权重、tokenizer、量化、生成默认值）、索引/embedding 版本、工具 schema、护栏规则。门禁建议：①静态：提示占位符与代码参数一致、JSON schema 可解析、密钥未进仓库；②离线 eval：与线上先验分层的金样，温度固定，断言级忠实和格式合规；③非确定性：跨供应商即使温度 0 也不保证逐 token 相同，测试应是「合规率 ≥ 阈值」或快照加裁判，而不是字符串全等；④检索：embedding 维度或相似度度量一变，旧索引必须拒绝加载；⑤发布：先影子或 1% 流量，盯拒答率、格式失败、p95、单请求成本，破线自动回滚到上一组版本指纹；⑥评测本身也有账单和泄漏风险，评测集禁止含未脱敏 PII，并与训练集隔离。提示改动走同样的评审和标签，不允许在生产配置中心「热改一句话」却不打版本。边界：纯 CSS 改动不必跑全量红队；任何能改变模型输入分布的改动（提示、默认 `max_tokens`、检索 k）都必须跑评测门。

**后续追问：** 评测集只有 60 条且全是演示问题，绿了有什么意义；金丝雀看的是点赞率，幻觉在涨你怎样不被它骗过；提示和代码必须同 PR 还是允许提示单独发布。

**扩展问题：**
- 列出至少五道 AI 特有门禁，并各举一个「这道门被跳过时」的故障。
- 温度无法固定为 0 的创意任务，CI 怎样做回归才不会天天红？
- 索引重建要数小时，CI 里你跑全量重嵌还是跑兼容探针？

**推理回答：** 目标是把会改变模型行为的东西都放进可测、可回滚的发布。约束是这些东西不是确定性函数。补工件版本、离线评测、兼容检查和带质量护栏的金丝雀。验收看「只改提示」能否被拦住或被安全灰度，而不是看单测是否全绿。

## OPS-019. 主厂商合约 30 天后结束。备援的 tokenizer 与工具 JSON 合不上。怎样迁走流量且写请求不丢，并保证故障后一分钟内能切回？

**答：** 在网关把业务消息、工具 schema、错误码、流式事件收成自己的协议，供应商差异留在适配器里，调用方不直接绑某一家的 URL 和字段名。先用离线评测加影子流量量出工具调用格式、拒答率和超长提示截断差，再按 1%→10%→50% 切流，功能开关必须能在一分钟内把路由拨回主路。Tokenizer 和上下文上限不同，意味着同一段文本的计费和能否塞进窗口都要按目标模型重算，不能沿用旧 token 计数做截断。

**深入展开：** 切换失败几乎总是协议而不是「模型笨一点」：函数名大小写、JSON 是否允许多余字段、并行工具调用、`finish_reason`、流式 delta 的分片方式。适配器要做消息角色映射、工具声明转换、输出 JSON 修复或语法约束，并把对方的限流和内容过滤错误翻译成本地错误码。分词差一个数量级少见，但 10–30% 很常见；旧模型约 7.2k token 的提示在新分词下可能到 8.5k，直接超窗。做法是按目标 tokenizer 在网关截断，并在影子流量里统计「旧过、新溢出」的比例。质量上看工具选择是否仍对、槽位是否仍能解析、安全拒答是否变松；影子对比看可解析性和关键槽，不是逐字相等。数据面双写 prompt 版本和模型路由配置，灰度按租户或请求哈希，出问题拨开关而不是重新发版。成本与配额要按两家同时预留，迁移窗口避免只留 5% 余量。不要在同一天改提示词又切供应商，否则分不清是谁的回归。回滚演练要在工作时间做过一次真切流，确认连接池、密钥和区域都热着。

**后续追问：** 影子流量发现约 3% 的工具参数类型不一致，你是改适配器、改提示，还是挡住这类请求不切；两家安全过滤一个更严，用户会看到什么，产品是否接受；上下文 128k 迁到 32k，长对话压缩放在哪一层。

**扩展问题：**
- 流式 SSE 字段不同，前端已经按第一家的事件名解析，网关要不要统一成内部事件再往外吐？
- 如何用「目标 tokenizer 下的溢出率」做切流门禁，而不是只看平均分？
- 密钥轮换和供应商切换撞在同一变更窗口，故障时你先回滚哪一个？

**推理回答：** 目标是连续服务，约束是两家接口和分词不一致。先用适配器隔离协议，用评测和影子暴露工具与截断差，再用可瞬间回拨的路由迁流。验收是溢出率、工具可解析率和一分钟回滚演练，而不是合同日期到了再全量切。

## OPS-020. 有人拿最贵的模型做翻译，月底结账才发现——六个产品组都是各用各的密钥直连供应商。把调用收进统一网关后，配额、审计、鉴权、别名路由分别归哪一层？网关绝不能长成什么？

**答：** 网关做模型 I/O 的控制面：服务身份鉴权、把应用侧的模型别名映射到具体供应商和型号、按租户/应用执行次数-token-金额配额、统一脱敏日志与成本标签、以及失败转移。业务提示编排、检索和工具循环留在各应用或编排服务里，网关不要长成第二个智能体运行时。没有这层，密钥分散、单价不可见、翻译这种低价值流量也会打到最贵别名上。

**深入展开：** 请求进入：mTLS 或工作负载身份 → 应用 id / 租户 id → 别名解析（如 `translate-small` → 指定小模型，`reasoner` → 大模型）→ 配额与预算准入 → 可选脱敏 → 发出，带上组织侧密钥，应用拿不到供应商原钥。别名是关键：团队禁止在代码里写死供应商型号名，换供应商或降级只改映射。配额在别名和租户两级，翻译别名给低单价和低输出上限，推理别名才给高预算。审计字段：谁、哪个别名、实际模型、token、金额、是否缓存命中，日级汇总到各团队，而不是等财务账单。限流、重试、熔断、对供应商 429 的退避也集中在此，避免六个 SDK 各写一套。缓存若做，只做允许的前缀或幂等 GET 式补全，并带权限。网关反模式：在网关里堆业务 few-shot、按租户写死长提示、直接跑多步工具——那会让发布和评测无法按应用切开，网关变更变成全公司风险。网关可以提供「策略插件」（PII、主题拦截），但插件要版本化且默认拒绝不明流量。观测：每个应用一条成本曲线，翻译打到 `reasoner` 应在分钟级告警，而不是月底。

**后续追问：** 某个应用必须用未收录的临时模型做评测，网关开后门还是开带过期时间的别名；网关自身限流比供应商更严时，客户端看到的错误码怎样设计才可重试；多区域就近出口时，配额账本放哪以免超发。

**扩展问题：**
- 画网关内分层：鉴权 / 别名 / 准入 / 策略 / 出口，并标明密钥存在哪一层。
- 怎样阻止应用绕过网关、用偷带的供应商密钥直连？
- 网关延迟预算只有数毫秒到数十毫秒，哪些功能必须外移？

**推理回答：** 目标是集中身份、预算和审计，同时保持应用能独立发布。约束是分散密钥会让贵模型被误用。网关管别名和配额，不管智能体业务逻辑。验收看日级分账能否在分钟级发现「翻译走了最贵模型」。

## OPS-021. 搞调研的内部 agent 三天内把当月 token 额度烧光。网关只限制 QPS，根本没挡住。限额要在租户、模型、工具和预估花费上如何叠起来？

**答：** 每秒请求数限制的是调用次数，智能体循环是“请求不多、上下文很长、工具很多、自调用很多”，所以必须按预估 token 和预估金额做准入。分层是：租户日/月预算硬顶 → 应用或工作空间配额 → 按模型单价分档（越贵越严）→ 单请求 token 上限和最大步数 → 搜索、浏览、代码执行等工具的独立配额。超限则拒绝、改走小模型或排队，不允许默默透支。强制点在网关和编排器，不在模型“自己省着花”。

**深入展开：** 预估输入约为提示加历史加工具回灌，输出按本次允许的最大生成长度计最坏情况，工具按次或按返回字节计价。下发前做准入：预估超过剩余预算就拒绝或改便宜路由。编排器再加步数封顶（例如数十步量级）和每步输入上限，防止轨迹回灌按步数膨胀。租户令牌桶允许日内突发，但不能预支下月；单个失控循环不能抽干共享加速器。短时消耗相对基线高出若干倍时告警并熔断该凭证。账单按租户、模型、工具、任务类型拆开，才能看出是长上下文还是工具在烧。流式输出超长要中途切断；重试必须幂等且计入同一预算，避免故障把账单放大。对内“免费额度”也要有硬顶，否则内部账号会变成无主账户。不要等到财务月底对账——那时预算已经用完。

**后续追问：** 按最大生成长度预估会不会过度拒绝，你怎样用事后真实用量校正；派生出的子智能体预算如何从父任务继承；用户对话和后台批处理是否共用一个桶。

**扩展问题：**
- 只限每秒请求数、不限 token 时，构造一种完全合法的请求模式把日预算打光。
- 降级到小模型后步数反而增加，总成本可能更高，熔断条件怎么写？
- 如何用“预估与实际用量比”和“单凭证消耗占比”证明限流打在了循环调用上？

**推理回答：** 目标是失控循环不能透支组织预算；约束是请求次数和费用不成正比。按金额和 token 做准入，再按步数和工具加一层。用分项账单和熔断次数验收。

## OPS-022. 退还的额度如何投放，才不会让等在门口的长摘要再次饿死短问答？流已经解码约 200 token 时租户每分钟美元桶见顶：未耗尽的输出预留，你是中止并退回，还是把当前请求跑完？

**答：** 已经开口的请求优先写完，但只允许在「剩余预留不大」时写完：例如已产出 200、`max_tokens` 还剩一小截，就耗完预留，不要中途撕掉用户屏幕上的半段。若剩余预留仍按上限（示意：还挂着 1.5k–2k 输出）且金额桶已硬顶，则切断、`finish_reason=budget`，并只退回未写出的那一段预留。退回绝不能灌进一个无差别的分钟池：短问答走低水位即可准入，长摘要必须等金额回到高水位，或进独立的加权公平队列，避免切断瞬间十几条长摘要同时通过准入。

**深入展开：** 调用前已经按「实测输入 + `max_tokens`」做了悲观预扣，所以桶打满通常不是这 200 个 token 本身，而是许多路在飞的长预留把分钟额度锁死。示意：输出按当时合同约 $15 / 1M token，200 token 只值几美分的零头，真正占坑的是每路还挂着的数千预留。写完的条件写成数字：剩余预留 / 原预留 < 约 0.2，或剩余预估墙钟小于短问答的目标排队（例如 < 2s），就让本路结束，用户看到的是完整句而不是半截。切断的条件是剩余预留仍大，继续写会把下一分钟的桶也借穿。退回账：`refund = reserved_out - decoded_out`，入账要带 `class=short|long`。准入用双水位而不是「桶>0 就放行」：

```python
def admit(job, remain_frac, lo=0.08, hi=0.30):
    return remain_frac > (lo if job.cls == "short" else hi)
```

长摘要在退回后仍须重新走高水位，不能因为「刚腾出 1.8k 预留」就立刻入座。队列按加权公平：示意短:长 = 7:3 的并发槽，短问答的 `max_tokens` 上限单独封顶（例如 256）。滞回：一次切断风暴后的数秒内冻结长作业准入，防止抖动。观测要分开「在飞预留」「实扣 token」「切断率」「短问答排队」，只看分钟消耗会被退回毛刺骗过。边界：法律/医疗结论不宜在句中切断，应在切断后补一句「已达本分钟额度」而不是静默截断；工具参数 JSON 未闭合时切断必须丢弃、不得执行。这里处理的是途中预留与公平，不是调用前第一次怎么分层限流。

**后续追问：** 预留按 `max_tokens=2048` 但模型通常 80 token 就停，你按历史 p80 收紧预留，还是继续悲观预扣、靠退回来回血；切断时客户端已经渲染了 200 个 token，你回滚屏幕还是保留半段并标不完整；多区域网关各记各的分钟桶，退回在本区入账会不会让另一区继续超发。

**扩展问题：**
- 金额桶按自然分钟对齐，:59 切断并退回的额度，下一分钟的长摘要能不能立刻用？
- 同一租户里内部智能体和面向用户的短问答如何拆成两个子桶，退回时禁止互相抽干？
- 怎样用「短问答 p95 排队」而不是「分钟消耗是否回零」证明退回策略没有再次饿死交互路径？

**推理回答：** 约束是预扣按上限、实扣按已写 token，退回会在同一秒放出大块额度。目标是不撕已开口的短尾请求，同时不把腾出的预留给长摘要抢光。所以用剩余预留比例决定写完还是切断，用双水位和分队列发放退回。验收看短问答排队，不看桶是否瞬间回满。

## OPS-023. 早高峰 TPM 先触顶，RPM 仍闲着半数，调用方已在吃 429。改走小模型、入队合并、就地准入或直接打回，凭什么迹象决定优先丢掉哪类调用？

**答：** TPM 先满说明瓶颈是 token 吞吐量而不是请求个数，原样重试只会把窗口打得更满。先在网关按预估 token 做准入：延迟或拒绝「输入已经很长、可异步的批量」，保住短交互和付费路径的剩余额度。能合并的相同前缀或相同 FAQ 合成一次调用；实时路径在额度危急时切到更小模型或压缩上下文。对用户返回明确的忙碌或降级状态，而不是让客户端无抖动地连打。

**深入展开：** 供应商限额通常是 RPM、TPM、并发请求三条独立水位，429 体里常带重试等待。TPM 满而 RPM 松，典型画像是 RAG 长提示、多轮把历史全塞进去，或一夜批量总结在早高峰和在线流量抢额度。例如额度 2M token/分钟，均请求 6k 输入 + 400 输出，理论上限大约 300 次/分钟；到达 20 次/秒就已经是约 4 倍超卖。本地令牌桶应按「预估输入 + `max_tokens`」扣减，超了进有界队列，队列长度 ≈ 目标等待 × 可持续 TPM / 平均 token；等不及的走 429 或降级，不要做成无限缓冲。合并只对幂等读有效：同一租户同一问题在 2–5 秒窗口可以共用一次生成。退避必须带抖动并尊重 `Retry-After`，全局限流器要比客户端各自重试更早触发，否则会形成重试风暴。非交互任务（日报、回填 embedding、离线评测）应在高峰前就迁到错峰队列。切小模型前要确认该任务切片在小模型上可接受；否则宁可少接请求，也不要批量产出错误 JSON。监控剩余 TPM、本地队列深度、429 率、降级率、重试倍率。预留例如 10–20% 额度给 P0，避免营销活动吃光客服和支付说明。

**后续追问：** 只有某条产品线的长文档请求在吞 TPM，全局限流和按路由限额谁先动；客户端已经做了指数退避，网关还要不要再排队；切小模型后 TPM 降了但 RPM 顶满，策略怎样改。

**扩展问题：**
- 怎样用「预估 token」做预扣，避免实际分词与网关估计差一倍导致误杀短请求？
- 高峰里工具调用循环把同一用户打出十几次生成，怎样在会话层熔断？
- 备用供应商此刻 RPM 充足但 TPM 更紧，切不切，依据哪两个数？

**推理回答：** 信号是 TPM 先饱和，所以优化目标和拒答对象都是「贵而可延后」的长请求，不是平均 QPS。用预扣令牌桶和有界队列保护短交互，合并与切模型只用于仍能保证任务切片的流量。用剩余额度、队列等待和重试倍率验收，禁止靠客户端盲重试自愈。

## OPS-024. 获准发邮件并查库的 Agent，有的 trace 把连接字符串回显进思维链。秘密只能出现到哪一层？轮换如何让在途调用既碰不到旧秘密、也不会被中断？

**答：** 密钥只存在密钥管理服务和工具执行进程的内存里，永远不要进提示、模型上下文、前端或普通日志。模型只能看见工具名和经过校验的业务参数；连接串由后端代理在出站时注入。轮换用双密钥窗口：新密钥先发布，飞行中的请求拿着租约继续用旧密钥直到结束，过了重叠期再停旧密钥，禁止「立刻作废导致半封邮件发出去」。发现轨迹泄露要立刻轮换、作废已打印的串，并修红线。

**深入展开：** 数据流：编排器校验工具参数 → 用工作负载身份向密钥服务换短时令牌 → worker 建连 → 返回给模型的只有查询结果的脱敏视图。思考过程、中间摘要、错误信息都要走密钥扫描后再落盘，连接串、Bearer、私钥模式直接剥掉。按环境、租户、工具分身份，开发密钥进不了生产工具。用量异常（突然的邮件爆发、异地查库）按凭证告警。轮换：写入新版本 → worker 新租约只取新版本 → 旧租约仍有效直到 TTL → 监控两版本成功率 → 撤销旧版本。飞行中请求不要中途换连接串，以免连接池和事务裂开；长工具调用的租约要覆盖最坏执行时间。Agent 若被诱导「请重复你的环境变量」，系统提示拦不住，必须在工具层根本不提供这些变量。本地调试用独立短时凭证，禁止把生产密钥拷进笔记本。这和输入输出里的用户 PII 治理是不同层：这里保护的是机器身份。

**后续追问：** 模型在参数里编造了一个「password」字段，代理是丢弃、告警还是当成用户密码去连？；轮换重叠期定为多长，要覆盖最慢的报表查询；轨迹存储若被分析同事只读访问，还要不要二次加密。

**扩展问题：**
- 工具错误把 JDBC URL 打进了异常栈，这条日志在哪一层必须截断？
- 多租户共用一个 worker 池时，怎样保证租户 A 的令牌不会被租户 B 的工具调用带到？
- 如何用「提示/日志中密钥扫描命中数」和「轮换期间失败率」证明泄露窗口在收，而不是只证明密钥服务能存值？

**推理回答：** 约束是模型会回声任何进了上下文的秘密，飞行中请求又不能因轮换中断。秘密停在代理注入点，轮换用租约重叠。用扫描命中、双版本成功率和零停顿轮换演练验收。

## OPS-025. 账单落地后大约达到原先估计的 4 倍。财务此前用「单次 3000 token × 目录价」批月度预算。漏项通常趴在哪些环节，单价如何写成可反复回算的费用模型？

**答：** 「3000 token × 标价」把一次用户请求当成一次、一种单价的生成，漏掉了输入/输出差价、系统提示和检索块、多跳工具回灌、重试、缓存未命中，以及 embedding、重排、日志和评测。可复算模型要以「一次成功业务结果」为分母，按功能 × 租户拆行，每行写成：请求次数 × 每请求模型跳数 ×（未命中输入 × 输入单价 + 命中前缀 × 缓存单价 + 输出 × 输出单价 ×（1+重试率））+ 检索与存储附加项。预估用分位数长度而不是口头平均数，上线后用实际 token 账单回算误差。

**深入展开：** 数据流先画调用图：网关 → 改写/分类 → 检索/重排 → 主模型 → 工具 → 可能的二次生成。用户口中的「3000 token」常常只是可见问句；系统提示、工具定义、对话历史和 RAG 块经常把输入撑到数千。示意量级（数字仅作演算，须换成当时价目）：输入 4.5k、输出 400、输出单价约为输入的 3–5 倍时，单跳费用已被输出主导；智能体 3–5 跳、格式失败重试 15%–30%，账单再乘同一系数。附加项：查询 embedding 每次一次；重排若对 top-50 打分，费用按条或按 GPU 时间；提示和轨迹日志按 GB 计，高流量下存储可能接近小模型本身；离线评测集每发一版都要烧一遍。自托管不要用 token 标价，而用 GPU 小时 × 占用率，空载也计费。必须分开平均长度和 p95：按均值定价会在长尾文档摘要上穿预算。缓存命中只减未命中那一段 prefill，不能假设「有缓存就按 0 算」。租户和功能分账才能发现「内部智能体循环」而不是「用户 QPS」在烧钱。

**后续追问：** 失败请求已经打到模型但业务侧记为失败，成本算进单价还是单独列损耗；预估输出长度用 max_tokens 还是历史 p80，过松或过紧分别会怎样；多租户共享一个项目密钥时，没有分账标签你怎样回溯这四倍差额。

**扩展问题：**
- 给一条「用户问句 200 token、系统+工具 1.5k、检索 2k、历史 800、输出 400、30% 格式重试、平均 3 跳」的假设，写出单次成功工单的 token 账单公式。
- 何时该从「按 token 买 API」改成「按 GPU 小时自托管」来做预算，决策里至少要有哪三个量？
- 怎样用「预估/实收比」和「每成功工单成本」周报证明模型在收敛，而不是只看总账单下降？

**推理回答：** 目标是签得住、事后对得上的预算；约束是一次用户请求不等于一次计费调用，且输出和重试单价更高。先按跳数和 token 类型拆账，用分位数而不是口头整数，再把检索、日志、评测和空载算进去。验收看能否用真实账单回算到同一张表，而不是看「乘过官价」。

## OPS-026. 三个核心评测切片通过率不许下滑，同时下季模型账单要再砍约 40%。裁短上下文、prompt 缓存、语义级缓存、任务分流，你会按什么次序动手，怎样证明生产环境没有悄悄掉质量？

**答：** 先按任务、模型、输入/输出、缓存命中和重试拆账单，优先砍「付了钱但不影响判决」的输入，而不是先换更便宜的模型。顺序通常是：丢掉检索和对话里用不上的块 → 把稳定系统提示和工具定义放到可前缀缓存的位置 → 对高重复 FAQ 做带租户和版本的语义缓存 → 最后才按复杂度把简单抽取/分类路由到小模型。每一次改动都要在那三个切片上做前后对照，并用线上影子流量看分歧，禁止只盯总价下降。

**深入展开：** 成本要落到请求：例如日均 200 万次调用，均输入 3k、输出 250 token，输出单价往往是输入的数倍（以当时合同为准），但输入总量大，长上下文和重试才是大头。检索若每次塞 20 段×400 token，而引用只用得上 3–4 段，先按重排或分数截到 K=6 就能少掉大约一半输入，质量用「应引用未引用 / 乱引用」衡量，而不是看摘要好不好读。前缀缓存要求从开头逐 token 相同：系统提示约 1.5k 且命中率从 0 到 60%，账单按供应商对缓存输入的折扣计（例如按合同可能是未命中价的一个零头），对生成分布几乎无影响。语义缓存只适合答案稳定、允许短 TTL 的问法，键必须带模型版本、提示版本、索引版本，源文档一更新就要失效。路由按规则或分类器切：字段抽取、意图、短 FAQ 走小模型或分类器；多步推理、代码、合规话术留在大模型。验证闭环：离线三个切片 + 线上 canary 的分歧抽样 + 单请求成本。回滚开关按路由和缓存分开，避免「为了省 40% 一次切走全部大模型」。重试和空转工具调用也要进账单，一次超时再打两遍等于把贵请求乘三。

**后续追问：** 三个切片里哪一个对输入截断最敏感，你怎么决定 K；语义缓存命中但知识库已删条款，算不算「没降质」；小模型路由的误分率到多少就必须强制回大模型。

**扩展问题：**
- 如何用「每成功任务的美元」而不是「每千 token 单价」判断优化是否真省钱？
- 输出 `max_tokens` 从 1024 收到 256，对哪类任务是免费的，对哪类是在截答案？
- 同一条系统提示被两个产品线共用，缓存命中变高但权限提示被稀释，你怎样拆前缀？

**推理回答：** 约束是切片质量不能掉，目标是账单而不是模型体积。先去掉对判决无贡献的 token，再复用已计算的前缀和稳定答案，最后才把简单任务换廉价模型。每一步用同一套切片和线上分歧率验收，避免用总价一个数掩盖某类任务崩了。

## OPS-027. 拆开费用，输出侧 token 约占 70%，输入侧前缀 cache 已能打中。给 max_tokens 设上限、单纯意图改走小模型、缩短召回块，这三招试验次序怎样排，才避免先把准确率砍掉？

**答：** 输出已经占七成时，先动生成长度，再动路由，最后才动检索块。`max_tokens` 和停止符对准真实需要的字段长度，往往立刻砍掉空话和重复结尾，且不改变已写出的内容分布。简单意图（分类、抽槽、模板填空）再切到小模型或固定模板，用离线集卡住格式和关键槽位。压缩检索主要减的是输入和 TTFT，对这条账单是次要杠杆，而且误删证据会直接伤忠实度，应放在长度和路由都有质量门禁之后。

**深入展开：** 先冻结一张拆账：输入未命中 / 输入缓存命中 / 输出 / 额外跳数 / embedding。输出主导说明模型在写长：缺停止符、让它「尽量详细」、或把推理痕迹留给用户。可执行顺序：①把 `max_tokens` 从「以防万一的 2k」收到任务所需的上界（例如工单摘要 256–512），并加结构化停止；②提示里要求短条目或 JSON 字段，而不是散文；③意图路由：能规则化的不进大模型，能小模型稳定抽槽的不进主模型；④仍贵再看语义缓存，只覆盖答案不随限定词抖动的 FAQ，键必须绑模型、提示、索引和权限版本；⑤检索块从例如 12 段收到 4–6 段高分证据，用引用忠实度而不是长度验收。不要一上来量化或换更弱的主模型——那是另一条质量曲线，和「输出太长」不是同一病。每刀只开一个开关，用同一冻结集看：槽位 F1 / 引用蕴含 / 拒答率 / 平均输出 token。平均输出从例如 600 降到 220 而槽位不掉，这刀就留下；掉了就回滚再试下一刀。边界：法律或医疗结论不能为了省输出改成无依据短句；工具参数 JSON 截太短会废掉整跳，上限要按 schema 留余量。

**后续追问：** 截断后模型把关键免责声明挤出长度预算，你加字段优先级还是允许超长；小模型抽槽稳、一解释政策就编造，路由规则写在分类器还是提示里；检索从 12 段减到 4 段后忠实度上升但漏答增加，你补关键词通道还是加回块数。

**扩展问题：**
- 若拆账其实是「跳数」而不是「单跳输出」占七成，顺序还一样吗？
- 如何用「每成功答案的输出 token」而不是「每请求费用」判断截断是在去水分还是在砍内容？
- 前缀缓存已经很高时，再压缩系统提示值不值得，会破坏哪些命中？

**推理回答：** 目标是降输出账单且不丢已证明的正确槽位。约束是三条杠杆打的不是同一段费用、对忠实度的伤害也不同。按「费用贡献 / 质量风险」排序：先限长，再分流，最后动证据集。用成对指标验收，禁止只看账单。

## OPS-028. 刚把语义缓存投进线上，用户只动一处修饰语，系统仍吐出七天前那份答复。要把哪些版本维度钉进缓存键？失效规则如何拦住「意思相近但授权集合或事实已过期」的误命中？

**答：** 语义近不等于可复用。精确缓存用规范化后的请求指纹；语义缓存只对答案不随限定词抖动的意图开放，例如稳定的产品说明。缓存键必须绑定模型版本、提示与策略版本、检索语料版本、租户与权限集、工具结果版本或时间桶，少绑一维就会串。时间、金额、对象、否定词变化应直接未命中；语料或权限变更要主动失效或缩短存活期。错误复用的代价高于多打一次模型。

**深入展开：** 请求先进入权限上下文和意图分类，再决定走精确键、语义键还是不缓存；回填前再次核对语料版本和访问控制。精确键是规范化文本加上述版本维度的哈希。语义键是向量近邻加同一组版本维度加距离阈值，阈值按意图校准，开放问答宁严勿宽。把时间、数量、实体、否定抽成槽位，槽位不一致即使向量很近也禁止命中，例如“不含坚果”和“含坚果”。文档更新发布语料版本，按文档标识反查缓存；用户权限变更使该用户键失效；模型或提示发布则切换命名空间。存活期按易变程度：库存和价格用秒到分钟或不缓存，政策文档用小时级并依赖版本号。个性化回答、实时工具结果、跨权限内容禁止语义缓存。命中后仍做输出侧政策检查，避免把旧的有害回答冻住。日志记录命中类型、版本是否对齐、用户是否立刻改问，把“改问后仍命中旧答”当成事故切片。

**后续追问：** 两个问题向量很近但一个带否定，你调严阈值还是靠槽位拦截；缓存了带引用的答案后源文档被删，你删缓存还是让引用失效；多租户共用向量索引做语义缓存，怎样避免跨租户命中。

**扩展问题：**
- 列出至少六个必须进入缓存键的版本字段，并说明少绑一个时会发生哪类事故。
- 语义缓存命中率上升、投诉也上升，怎样证明是错误复用而不是模型变差？
- 前缀键值缓存和最终答案缓存同时存在时，提示版本变更要先清哪一层？

**推理回答：** 约束是错误复用会静默给过错答案。把语义相似降级为召回候选，把版本维度和槽位一致性做成命中条件。用改问事故率和版本对齐率验收，而不是用命中率。

## OPS-029. 有块加速器在推理资源池里死掉，所有按 token 解码的长对话一并垮掉。为把续写迁到别处而非推倒重来，请求、运行时缓存、会话记录该如何切开？

**答：** 把会话记录放在推理进程之外：对话历史、已提交的工具结果、用户已经看见的流式文本进会话存储；模型运行时的键值缓存只当作可丢的加速器。单卡死亡后，编排器把未完成请求标成可恢复，带着“已发送前缀”到健康副本续跑或重算，而不是让客户端连接重置后再问一遍。多副本、健康检查、熔断、过载排队仍然需要，但还要把冷启动、显存碎片、单卡死亡和检索索引不可用分成不同故障域。

**深入展开：** 逐 token 生成绑在该卡的运行时缓存上，卡死缓存就没了。若已经向用户流出约两千个 token，从头再生成可能换一种说法，界面和审计都会裂开。短的只读请求可以直接到其他副本重试；长生成要保存已输出文本，续写时把它们当作必须遵守的前缀，或至少在界面上接在用户已读内容后面再补。能命中公共前缀缓存的副本优先承接。大模型加载权重往往要数十秒，需要预热池，不能等第一张卡加载完再接流量。过载时拒绝新会话、保护已经在生成的请求。检索索引和模型分属不同故障域：索引不可用应降到关键词或拒答，不要让加速器探活把这件事报成“模型死了”。写操作的半执行仍用补偿状态机处理——高可用层负责请求能迁，不负责猜测写结果。用请求标识把日志和追踪串起来，才能在掉卡时找出哪些流式连接要重连。

**后续追问：** 运行时缓存不落盘时，迁移后的首个 token 会不会比原来多付一次预填充；会话粘滞到已死的那张卡，负载均衡怎样摘掉；索引和模型同时抖动，熔断先切哪一侧。

**扩展问题：**
- 预热池占用约两成加速器，对成本和故障切换时间各意味着什么？
- 流式中途重连后，客户端已渲染的半句和服务器续写不一致，以谁为准？
- 如何用“掉卡后会话续写成功率 / 重复生成率”证明你迁的是状态，而不是只在重试？

**推理回答：** 目标是单卡死亡不丢掉已对用户可见的语义；约束是运行时缓存与卡绑定。外置会话记录，把运行时缓存当加速层，用前缀约束续写。用续写成功率和重复生成率验收。

## OPS-030. 检索页把重排与作答塞进同一段 800ms 额度，重排一超时页面就被掏空。怎样写下时限、隔舱和「不做重排仍展示检索」的降级契约，避免最弱 AI 部件单独裁定平台在不在线？

**答：** 页面可用性必须定义成「用户能看到可用的检索结果」，而不是「所有 AI 组件都成功」。给重排单独的短超时和独立并发/配额舱壁，超时或熔断时把初检索结果直接渲染，生成再单独计时；生成失败则展示片段列表，而不是整页失败。组件之间禁止共用一个无界等待和同一线程池，否则重排的尾延迟会吃光生成预算，再把网关线程卡死。

**深入展开：** 预算切分示例：接入加检索 150–200ms，重排 100–150ms（硬超时），生成 400–450ms，余量给网络。重排超时不是错误页，而是 `rerank=skipped` 的正常分支。舱壁：重排、生成、embedding 各有并发上限和熔断（例如连续错误率超阈值 30–60 秒打开），避免重排失败把连接池打光。降级菜单按用户可见性排序：①无重排，保留相关性尚可的 top-k；②无生成，展示标题、摘要和链接；③无向量检索，回退关键词；④无任何搜索，才是平台事故。合同写清哪些字段可空、前端骨架如何占位、是否展示「回答暂不可用」。搜索主路径的 SLO 应按降级后的可用页来算，AI 增强路径另算成功率，否则重排一抖会被算成整站故障。隔离还要包括模型池：不要让重排模型和对话大模型抢同一批 decode 槽。验证：故障注入重排超时，断言接口仍成功且有结果数组；注入生成失败，断言列表仍在。日志打降级原因，便于事后看有多少页靠降级活着。

**后续追问：** 重排超时率到约 20% 时你是扩重排还是永久跳过低价值查询；生成流式已出前两句后重排才返回，还有没有意义；舱壁按线程池还是按 GPU 槽，哪一种先防白屏。

**扩展问题：**
- 写一份降级合同：每个 AI 依赖失败时的用户可见结果、状态码和是否计可用性失败。
- 如何防止降级分支自己依赖另一个更慢的模型，形成假降级？
- 用故障注入证明：重排全部失败时，搜索页 p99 仍低于未降级时的空白等待。

**推理回答：** 目标是平台核心搜索在 AI 增强失败时仍可用，约束是共享预算和共享池会把局部故障放大。用分步超时、舱壁和写明的降级产物切断耦合。用「重排全挂仍返回可用结果」做验收，而不是要求所有模型同时健康。

## OPS-031. 主路模型那一区接连 12 分钟回 5xx。手册里才有备用厂商，真实工具调用从未跑过。探活与预热得覆盖厂商间哪些差异，故障切换才能自动发生？

**答：** 纸面备用在故障当天不可用，通常是因为工具 schema、鉴权、区域配额和提示缓存都没被真实流量打过。活容灾要求：持续用合成探针走完整的「带工具的一次生成」，并始终把一小股生产影子或金丝雀打到备用；自动切流看错误率和关键路径成功率，不是端口探活。切过去之后还要能接受质量略降和缓存全冷，关键业务必须另有非 LLM 兜底（规则、检索原文、人工）。

**深入展开：** 12 分钟区域故障足够让只依赖一家的同步对话全死。备用路径的差异清单：①API 协议与工具 JSON；②内容过滤松紧；③上下文上限和 tokenizer；④该区域的 RPM/TPM 是否真的开通且不是很小的试用额；⑤密钥和网络出方向是否在故障域之外。健康检查至少每分钟跑：短生成、一次工具往返、一次长提示截断边界；连续失败则打开熔断。预热：保留例如 1–5% 流量或异步影子，避免故障时连接池、TLS、模型冷启动和空缓存叠在一起。切流策略：主路错误率或 5xx 过阈值（例如连续 1–2 分钟）→ 新请求切备用，在途请求快速失败并让客户端重试到网关；不要把已经半流式的响应硬接另一家。质量上备用模型要有近期评测基线，切流后看工具可解析率、拒答率、延迟；若备用明显不会某类工具，这类路由应直接降级到非 LLM，而不是换一家继续 500。多区域、多供应商、本地缓存和规则引擎是不同层的冗余，缺一层就仍是单点。演练必须定期真切，而不是只改配置不走流量。

**后续追问：** 探针只打了对话没打 tools，切流后第一分钟会看到什么；1% 金丝雀备用质量差，你是提高金丝雀还是接受故障时质量阶梯；主路恢复后如何避免立刻切回造成振荡。

**扩展问题：**
- 两家同时依赖同一云区域的出口地址，这还算不算消除了供应商单点？
- 备用没有前缀缓存折扣时，12 分钟故障的账单和 TTFT 要怎么预告？
- 怎样用「工具调用成功率」而不是 HTTP 成功码做切流条件？

**推理回答：** 目标是主路区域故障时关键任务仍有出口，约束是备用在协议、配额和缓存上都不热。把健康检查做成带工具的真调用，用持续小流量保持热路径，关键功能准备非 LLM 兜底。用定期切流演练和工具成功率验收，而不是看文档里写了第二家名字。

## OPS-032. 大模型栖身的那一区停摆长达两小时。查余额、写解释、改订单这几件事，支付咨询助手还该做吗？列一张按风险分层的降级表：哪些操作必须停掉，哪些还能用模板或检索顶着？

**答：** 按动作风险画矩阵，而不是按“还能不能打到某个模型”。查余额、查物流走原有只读接口加模板或短时缓存，可以保留；改订单、退款、改绑卡必须停止自动执行，只收工单或转人工；开放闲聊和创意解释应明示“智能回复暂停”，改成检索片段或静态问答。用户看到的是能力收缩后的清楚状态，不是报错堆栈或无限转圈。能力较弱的小模型可以顶常见问题，不能顶资金写路径。

**深入展开：** 档位可以这样切：全功能；主模型不可用时备用模型只做检索式问答；生成模型都不可用时只保留只读接口、模板和缓存；连检索也不可用时只留表单和人工排队。切换由健康信号驱动，界面标明“部分功能暂停”。进入主模型不可用档就要摘掉模型对写操作的决策，因为较弱模型在压力下更容易乱填参数。余额类缓存要么极短要么不用。能答的先答，不能做的动作给出预计恢复或人工入口，避免假装正在处理。定期把生成集群标成不健康，检查支付主路径是否仍可查询、写路径是否仍被拦住。不要在恢复后自动重放用户已确认的退款，以免重复执行；恢复时从最低档逐级加回，先开只读再开写。降级窗口内自动资金动作次数应接近零，同时盯重复提交和人工接起量。

**后续追问：** 备用小模型仍能生成“看起来像退款确认”的句子，确认按钮还放不放；缓存的政策答疑已经过期一天，最低生成档还展示吗；人工队列已满时，是拒收新单还是只登记回呼。

**扩展问题：**
- 把功能乘以档位画成表，每一格标明是模板、检索、人工还是关闭。
- 恢复瞬间流量回涌，怎样避免排队请求同时打写接口？
- 如何把“降级窗口内自动资金动作次数”写成必须为零的验收项？

**推理回答：** 目标是中断期不产生不可逆资金错误，同时保留可安全提供的查询。按可逆性和责任划分必须停、可用模板、可用检索。用零自动写和明确的用户状态验收，而不是用接口还在返回成功。

## OPS-033. 主路厂商连着吐 429，备用侧工具参数名对不齐。怎样在切流时拦住未完成的工具调用，免得订单落入脏数据？

**答：** 把“换模型”和“继续执行写操作”拆开。限流或不可用时，只读查询和纯生成可以切到备用；已经进入写路径的请求走补偿或人工，不把不兼容字段“猜”成另一套参数。编排器维护显式状态机：模型输出的是意图，执行前由适配层把字段校到当前供应商的工具描述，校验失败就停。退路是降能力，不是换一张看起来能跑的接口继续写库。

**深入展开：** 切换顺序一般是：同一供应商其他区域 → 不同供应商的同档能力 → 小模型、缓存或模板 → 人工队列。触发看错误码、延迟和健康检查，而不是单次超时。对内维持一份规范工具描述，各供应商适配器负责自己的函数名和字段，禁止把甲的 JSON 原样交给乙的执行器。下单、改地址、退款等写操作必须带幂等键，先落入“待确认”，执行成功再提交；切换中断则补偿或标“待人工”。遇到 429 应带抖动退避，并按预算决定降级；全流量瞬间压到备用会把备用也打满。只读退路可以用稳定问答缓存，不能用过期余额。定期演练适配和补偿，不要等供应商事故才发现字段对不上。备用模型缺少某类工具时，应关闭该路径并提示，而不是跳过校验。对照“模型声称已调用”和执行层审计，不一致就告警。

**后续追问：** 备用模型延迟高一倍，你切全部流量还是按比例；用户已经看到“正在退款”，切换失败后界面说什么；两家供应商对并行工具调用的语义不同，适配层怎样收成一种内部表示。

**扩展问题：**
- 主供应商恢复后，进行中的备用会话立刻切回，还是等本轮结束？
- 只读切换和写路径切换的健康探针能否共用？
- 如何用“切换窗口内写操作补偿次数 / 脏订单数”证明字段不兼容时你停对了？

**推理回答：** 约束是部分执行的写操作比多等几秒更贵。按错误类型选择切换目标，用规范描述和补偿把不兼容挡在执行前。用补偿次数和演练结果验收，而不是用备用接口是否返回成功。

## OPS-034. 值班脚本见内容安全拒答就当故障并自动重放原文到策略更松的备用；主模型给的并不是 429。按失败类别给 fallback 链分叉，怎样既不绕开安全、又保住真限流逃生，并让审计点名走过哪一枝？

**答：** 先把失败分成运输类和策略类，禁止用「不是一次正常 completion」当唯一开关。429 / 503 / 超时：尊重 `Retry-After` 后重试主模型，再切备用，但备用必须套同一套输入输出安全策略，不得因为是逃生路径就摘掉过滤。内容安全拒绝（例如 `finish_reason=content_filter`，或带政策码的 4xx）：这是策略办结，原样返回拒答，禁止把同一输入重放到更松的模型。审计每跳写下 `failure_class`、`hop`、`policy_bundle_id`、是否重放了原文，安全类之后若仍出现 hop，直接当事故。

**深入展开：** 值班脚本的典型漏洞是 `if not ok: fallback(backup)`——安全拒绝经常是 HTTP 200 加过滤结束原因，或 400 带稳定错误码，两者都不是限流。分支表要写进编排器而不是 wiki：①运输类（429、网关超时、连接重置）→ 抖动退避 → 主模型有限次 → 备用；②策略类（内容过滤、拒答模板、本地输入分类器命中）→ 终止，用户看到主路径的拒答文案和原因码；③schema / 工具参数坏 → 只允许对同一模型做带错误路径的有限修复，不准 hop 到「更会配合」的弱安全模型；④供应商 5xx → 可切备用，但请求仍先过你自己的输入政策，响应再过输出政策。更松的备用模型往往缺同一套安全分类器或系统拒答，原样重放等于把主模型已经拦住的注入句送到弱护栏上。数据流：主调用 span 记下厂商错误码和安全类别 → 路由器只读枚举，不读「有没有文本」→ 备用 span 必须引用同一 `policy_bundle_id`。观测：`fallback_after_safety` 计数应为 0；运输类 fallback 率、备用安全拦截率单独看。演练要分别打 429 夹具和安全拒绝夹具，禁止只用拔网线验收。这里不讨论备用模型字段少了怎么补齐工单，只讨论「该不该 hop」。

**后续追问：** 主模型返回 200，正文却是「我不能帮助你」，没有 content_filter 标记，你靠分类器、拒答模板还是当运输失败；备用模型的安全策略比主模型更严，运输类 fallback 之后用户只看到第二次拒答，产品怎么解释；本地输入分类器停机时，运输类逃生还允不允许自动 hop。

**扩展问题：**
- 画出 429、content_filter、schema 失败、5xx 四条枝，每条写是否重放原文、是否换模型、审计必填哪几个字段。
- 怎样防止「人工值班按钮」一键 replay 绕过策略类禁止 hop 的硬门？
- 如何用「安全类之后的 hop 次数」而不是「备用调用次数」做值班脚本的回归验收？

**推理回答：** 目标是限流可逃生、安全拒绝不可绕。约束是两种失败在 HTTP 层长得很像，而备用模型通常更松。所以按失败类型枚举分支，安全类终止且禁止重放，运输类 hop 时绑定同一政策束。验收看审计能指认枝，且安全后 hop 为零。

## OPS-035. 少量 32k 输入的出报告作业出现在日志里。傍晚高峰 p99 从约 2s 飙过 10s，而 p50 基本持平。如何证明属于队首堵住而非权重变慢，队列又该按什么轴切开？

**答：** 先按输入长度和请求类型拆延迟：若短对话单独重放时 TTFT/TPOT 仍接近 2 秒，而与 32k 报告混跑时排队时间涨、计算时间不涨，就是长请求堵住了批或 GPU，不是权重坏了。把报告生成和短对话切到不同队列与并发上限，长请求限流、短请求保留槽位；必要时对长 prefill 切块或放到另一池，避免一个报告占用整段调度量子。用「排队时间 vs 纯计算时间」和分位数字段证明，而不是先换模型。

**深入展开：** 数据流：网关入队 → 调度选批 → prefill/decode → 回包。32k prefill 可以独占加速器数百毫秒到数秒，同批或同卡上的短请求只能等，于是 p99 被少数长尾拉起、p50 仍由大量短请求决定——这正是队头阻塞的签名。对照实验：把长请求从高峰流量里滤掉再看 p99；或在预发用同样短请求打满，再注入 1% 的 32k 报告。若短请求的每 token 时间稳定、排队直方图出现长台阶，定位在调度。治理：按输入长度或 SLA 类分队列（交互 / 批量报告）；每类独立并发和令牌桶；批量类用离线通道或独立副本。缓存和备用供应商解决的是重复问和供应商抖动，不解决「本地一条长 prefill 挡住一排短请求」。扩容可以减排队，但不切队列的话长请求仍会在新副本上重演队头阻塞。观测字段至少包括：输入长度、排队、prefill、decode、是否抢占。这和「刚发版后 p99 翻倍」的排查不同：这里假设配置没变，是流量组成在高峰变了。

**后续追问：** 切队列后报告的 TTFT 变差是否可接受，合同有没有批量类 SLA；1% 的 32k 请求在连续批处理里是否足够把短请求 p99 打到十几秒，怎么用排队论或回放估计；供应商侧抖动和本地队头阻塞在 trace 上如何一眼分开。

**扩展问题：**
- 只有 p99 涨、p50 和短请求 TPOT 不变，为什么更像排队而不是「模型变慢」？
- 长短请求分队列后，怎样避免空闲的短请求槽位在报告积压时被浪费，或反过来？
- 如何用「短请求排队时间」告警，而不是等端到端 p99 已经炸了再查？

**推理回答：** 目标是高峰下短交互仍然稳，约束是长报告合法存在且更吃 prefill。用对照重放把排队和计算拆开，用分队列和独立并发消除队头阻塞。用分类型的排队时间和 p99 验收，而不是先怀疑权重。

## OPS-036. 升至 5000 rps 后检索率先超时、GPU 队列接着被灌满。100 rps 压测下同步聊天路径本还能稳住。扩副本、打开连续批、把非交互步骤挪出同步链，三者该怎么取舍？

**答：** 50 倍流量会依次打满不同资源，不能只给应用层加副本。先看饱和信号：向量库 QPS 和连接、embedding 队列、GPU KV 占用和调度队列、下游工具线程池。检索先超时说明同步链在模型之前已经破了，应先给检索做缓存、分片和隔离，而不是先买 GPU。GPU 随后排队，说明交互 decode 槽位不够：短请求靠连续批处理和更多副本摊，长总结、重嵌和评测必须离开同步对话池。能异步的（写回会话摘要、埋点 embedding）从用户等待路径拿掉，同步路径只留检索加生成的关键段。

**深入展开：** 100 rps 时单副本或单检索实例往往还有空闲，问题被平均延迟掩盖。5000 rps、均输入 1.5k、输出 150 token，光输出就是每秒约 75 万 token，这不是多开几个 Web 进程能吃下的；即便 7B 级高吞吐引擎，也要按单副本可持续 QPS（例如示意数十到一两百，取决于长度和批）反推副本数，再加 KV：例如每 token 约 100–300KB 量级（视层数、GQA、精度），长尾 8k 上下文会先把显存打满。检索侧 5000 QPS 的 top-k 常常先于 GPU 死掉——连接池、锁或内存带宽。判断树：①检索 p99 涨、GPU 利用率仍低 → 扩分片、热缓存、把 embedding 与检索分池；②GPU 计算利用率低但 KV 或队列满 → 加副本或减并发上下文，而不是再加大批；③GPU 算力打满、短请求被长 prefill 堵住 → 连续批处理、切块 prefill 或把 prefill/decode 分池；④大量请求其实是「生成后再写摘要」→ 把写摘要改成队列。压测必须用真实长度分布和缓存命中，用 128+128 打到 5000 rps 没有意义。限流和背压要在网关按路由设，防止检索一慢把线程打满、反过来把生成也拖死。

**后续追问：** 检索超时是尾部 1% 的大库租户还是所有租户；连续批处理把吞吐拉起来后 p99 TPOT 恶化，你加副本还是调最大批；异步拆出去后用户刷新页面看不到摘要，产品能接受的可见延迟是多少。

**扩展问题：**
- 怎样用「在途 KV 总量」决定该扩 GPU 还是该截断历史？
- embedding 写入和在线检索共用集群时，5000 rps 读会被批量写打成什么样？
- 只把网关扩到 5000 rps、模型池仍按 100 rps 配，故障会先表现成哪类错误？

**推理回答：** 目标是 5000 rps 下同步对话仍有界延迟，约束是检索、KV 和 GPU 批各有上限。按谁先饱和决定扩谁，把非交互工作移出用户等待。用真实长度压测和分池利用率验收，而不是看 100 rps 时「看起来还能再加」。

## OPS-037. 检查器超时发生时，生成已花掉约 2 秒。流水线依次是改写、生成、引用核对。重试、跳过核对并打上「未核实」，还是整笔作废？状态机要留下哪些痕迹，才不把失败产物递给下一步？

**答：** 按步骤的「失败是否让结果不可信」选策略：改写失败可以回退到用户原句继续检索；生成失败才值得有限次重试或换模型；校验失败通常不应丢掉已经花掉的约 2 秒生成，而是返回正文并打上未核实，或只对无引用的句子再跑一次短校验。状态机要记录每步输入摘要、输出是否通过 schema、错误类型和是否允许下游消费，禁止把超时空串或半截 JSON 当合法上下文往下传。

**深入展开：** 编排不是一条快乐路径脚本。每步声明超时（改写约 300–500ms、生成约 2–8s、校验约 400–800ms，按 SLO 切）、重试次数（只对网络和 429，不对 4xx schema）、fallback、幂等键。数据流：`rewrite.ok ? rewritten : original_query` → retrieve → generate → `verify.ok ? cited : {text, verified=false}`。校验超时若整单失败，用户付出了生成成本却看到错误，体验和账单都差；若静默跳过校验，引用幻觉会进生产。折中是：校验可降级、不可伪造成功。状态里至少有 `step`、`status`、`attempt`、`input_digest`、`output_ref`，下游准入写成显式谓词，例如 generate 不得在 retrieve.failed 时运行（除非产品允许无检索回答）。重试生成必须用同一幂等键，避免双写副作用（例如发信工具）。部分成功：已有检索结果和草稿时可以先流式出正文，校验异步补徽章。依赖图要能跳过非关键节点，而不是线性全部失败。度量：分步成功率、因校验降级的比例、重复生成次数、因脏输入导致的级联错误。

**后续追问：** 校验模型连续 5 分钟约 30% 超时，你是自动跳过、切备用校验模型，还是提高整单失败率以保护品牌；改写模型把查询扩写成约 2k token，检索被拖死，这算改写成功还是编排要加输出预算；生成已流式到一半校验才失败，前端怎么展示。

**扩展问题：**
- 如何用状态机测试：强制某步超时，断言下游收不到空输出？
- 校验与生成共用同一供应商限额时，重试校验为什么可能让生成更糟？
- 多步里哪一步必须「失败即失败」，哪一步允许部分结果，写进合同的依据是什么？

**推理回答：** 目标是单步故障不毁掉整单已付成本，也不把无效输出当成事实。按步骤关键性选择重试、降级或失败，用显式状态和输入摘要切断级联。用分步故障注入和「脏输入零消费」验收编排，而不是只看流水线快乐路径。

## OPS-038. EU 用户会话与索引不能离境，US-East 索引整库重建耗时数小时。跨区切流，你保过期本地索引还是把推理送出国境？同步滞后对外如何承诺？

**答：** 数据驻留优先于跨区那份“更新”的副本。欧盟用户的原始对话、向量、权限表和审计日志留在区内，推理默认打区内端点。美东即使有更新索引，也不能为了新鲜度把查询和文档向量送出去。切流只在区内故障时切到区内备用，或切到合同明确允许的对等区。索引滞后要写成对外承诺，例如政策文档分钟级、附件小时级；落后时宁可声明“可能不是最新”或对时效问题拒答，也不跨境补齐。

**深入展开：** 每个区域打成完整单元：网关、会话库、对象存储、向量与关键词索引、密钥、日志。身份和访问控制在区内裁决，组成员缓存也不得拿到区外。控制面可以同步文档标识、版本和权限摘要，正文和向量按驻留规则复制；不允许的复制路径在配置里关掉，不靠提示约束。重建要数小时的索引应走变更日志加按文档重算向量，全量重建只当灾备。区内推理容量不足时，先降级到小模型、缓存或排队，再评估是否存在合法的区外推理——把个人数据当作模型输入等于传输。密钥按区隔离，避免一把主密钥解开所有区域。监控同样受驻留约束，不能把提示原文打到区外分析系统。员工出差导致地址在区外时，仍按账户的驻留策略路由，而不是按网络地址。集成测试应能抓到欧盟租户的向量请求出现在美东，并把这种情况判失败。

**后续追问：** 区内加速器售罄且法务未批准跨境，产品能承诺的最低能力是什么；同一公司的美东空间和欧盟空间要共享目录但不共享正文，元数据怎么切；跨区版本乱序时，删除墓碑怎样保证先于向量到达。

**扩展问题：**
- 索引增量延迟从约 1 分钟变成约 6 小时，哪些查询必须改成“未知”而不是继续用旧块？
- 区域故障时只读副本在区外、写入仍在区内，会话追加会碰到什么冲突？
- 如何把“跨区载荷里的对话或向量字节数”做成合规回归项？

**推理回答：** 约束是驻留和传输是否合法，目标是区内可服务且索引滞后可解释。先固定数据平面不出区，再谈增量和降级。用跨区流量零目标和滞后承诺验收。

## OPS-039. KV 全冷、新副本还在装权重。活动刚起势的三分钟，聊天到达率跳到日常约 20×。预热、优先级、削峰队列各自拦住过载的哪一截？如何避免这次尖峰变成所有人排队超时？

**答：** 尖峰的本质是到达率突然超过已热容量，而 GPU 权重加载往往要数十秒到数分钟，自动扩容赶不上这三分钟。预热负责活动开始前就把副本和前缀缓存热好；优先级负责把热容量留给交互和付费；有界队列只吸收数秒级抖动，超了就拒或降级，绝不能把 20 倍流量全堆进队列把每个人拖到超时。冷 KV 的新副本即便起来了，TTFT 也会差一截，所以扩容完成不等于容量可用。

**深入展开：** 设日常 80 rps、活动 1600 rps、持续 180 秒，多出来的大约 27 万次请求。若平均处理 2 秒，要在 3 分钟内消化需要约 3200 个并发槽；现有池若只按日常 2–3 倍冗余配，必然丢请求。队列若允许排 60 秒，队头体验已经崩了，队尾还在进。因此：①变更日历驱动的预热——提前加载权重、跑若干合成前缀把系统提示推进缓存、把连接和内核热好；②准入按优先级分桶，P0（结账说明、登录辅助）保留例如 30% 热槽，营销试用先降到小模型或静态 FAQ；③队列上限按「可接受等待 × 热槽吞吐」设，超过返回 429 或「请稍后」，并给重试等待。降级菜单：缩 `max_tokens`、关重排、关多步工具、切小模型。活动页那几条固定提示要预热，避免尖峰时刻全是冷 prefill。容量规划用历史峰值的分位而不是日均值；告警看队列深度和热副本数，而不是 CPU。扩容探针必须是「已能在目标 TTFT 下完成一次真实生成」，不能只探测端口。

**后续追问：** 预热了权重但没预热约 2k 的系统提示，尖峰第一分钟 TTFT 会怎样；优先级如果只看 API key 不看会话是否已在生成中，会不会把半成品打断；尖峰结束后如何把扩出去的 GPU 收回又不在长尾请求上杀实例。

**扩展问题：**
- 如何用「热槽位数 × 目标等待」算出队列硬上限，而不是拍一个很大的整数？
- 同一活动落地页导致约 80% 请求前缀相同，预热缓存和语义缓存谁更该先做？
- 自动扩容冷却时间约 10 分钟，三分钟尖峰为什么几乎总是要靠预热而不是弹性扩容？

**推理回答：** 约束是冷启动时间和有限热槽，目标是高峰期关键路径仍可用。预热把容量提前变成热的，优先级决定热槽给谁，有界队列防止把尖峰转化成全员超时。用热副本上的真实 TTFT 和拒绝/降级率验收，而不是看「机器已经在启动」。

## OPS-040. 10% 金丝雀上还挂着旧提示与旧模型；订单 JSON 契约一周添一个必填项。如何靠默认值、未知字段与版本协商做成向前兼容的校验，以免把解析失败浪涌看成模型回退？

**答：** 校验器跟「本周最新 schema」解绑，改跟请求自己的契约走。提示包和模型臂要声明 `schema_version`，网关按版本选校验器：旧金丝雀继续用旧必填集，新字段在重叠窗口由应用侧给安全缺省，而不是逼旧模型现在就吐出来。未知字段忽略或进扩展袋，不整单失败。解析失败率必须按 `(prompt_ver, model_ver, schema_ver, 臂)` 切片；只有旧臂在新必填上失败，是契约重叠，不是模型回退。

**深入展开：** 周更示意：v12 新增必填 `fulfillment_window`。10% 金丝雀仍跑 prompt_v11 + 旧模型，它从未在指令里见过该字段，若写库统一改用 v12 校验，失败率会在发 schema 的那一分钟跳起来，看起来像质量回归。正确的协商：请求信封是 `{schema_version, payload}`，`schema_version` 由正在服务的提示包写入，不由模型自由发挥；未声明时按「出现过的必填键」推断，禁止默认 `latest`。兼容规则分向：写库端对旧版本要向后兼容——v11 载荷在重叠期（示意：1–2 周）可落库，`fulfillment_window` 用业务缺省（例如 `standard`），缺省必须是运维可接受的值，不能让模型瞎编窗口。读库端要正向兼容——新加的未知键不推翻整单，放进 `_extra` 或丢掉。新臂产出的 v12 不得被旧校验器误杀。指标：`parse_fail{arm,schema,prompt,model}`；再加 `default_filled` 计数。对照：两臂在各自声明版本上的失败率平稳、只有「错用 latest 校验」的对照实验失败飙升，即可排除模型回退。重叠期结束、旧臂流量到 0，再把缺省通道关掉，那时缺字段才是真错误。不要用一次全局「收紧必填」当发布；schema、提示、模型要能独立回滚。这里管的是版本共存，不是缺引号怎么拦半截对象。

**后续追问：** 新字段没有安全缺省（例如必须用户选配送日），重叠期你是挡旧臂下单、升人审，还是把该字段改回可选；模型在 v11 载荷里多写了 v12 的键，未知字段策略是收下还是剥掉；金丝雀 10% 里混着新提示旧模型，`schema_version` 听提示包还是听模型自报。

**扩展问题：**
- 怎样用一张「臂 × schema_ver」失败率表，五分钟内否定「模型回退」这条假说？
- 缺省写入的字段如何在订单上打标，避免事后把系统填的窗口当成用户承诺？
- schema 回滚到 v11 时，已经按 v12 写入的订单读路径怎样继续认识多余字段？

**推理回答：** 目标是周更契约时金丝雀仍可解析，且失败率能归因到臂而不是模型变笨。约束是旧提示旧模型不可能预知新必填。所以校验跟请求声明的版本走，重叠期用缺省和忽略未知键，指标按版本切片。验收看旧臂在旧契约上稳定，而不是看全局 parse_fail 一个数。
